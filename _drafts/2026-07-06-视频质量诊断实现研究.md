### 1.5 传统算法原理

> **CV** 是 **Computer Vision（计算机视觉）** 的缩写。传统CV算法指不依赖深度学习神经网络、基于经典图像处理技术的算法方法，如边缘检测、直方图统计、帧间差分、频域分析等。与之相对的是基于CNN、ViT等深度学习模型的方法。

以下是基于传统计算机视觉技术推断的各指标检测原理。注意 `libdhivs_sdk_vqa.so` 是闭源的，确切实现不可见，但下面描述的是该领域通用的 CV 算法方法。

#### 1.5.1 iqa6 — 13 项指标

1. **清晰度检测 (CLARITY / 模糊检测)**

   原理：基于拉普拉斯算子（Laplacian）的边缘能量分析。

   对图像做拉普拉斯卷积，计算响应值的方差。方差越大表示边缘越锐利，图像越清晰；方差越小表示边缘越弱，图像越模糊。

   Laplacian 核：

   ```text
   [[ 0, -1,  0],
    [-1,  4, -1],
    [ 0, -1,  0]]
   ```

   清晰度分数 = `Var(Laplacian(image))`，分数低于阈值则触发模糊告警。

   也可以用 Sobel 梯度幅值的均值或频域高频能量占比来评估。

2. **高亮度检测 (HIGHBRIGHT)**

   原理：统计图像 luminance 通道（Y）中高于阈值的像素占比。

   将 RGB 转 YUV，统计 Y 分量 > T_high（如 230/255）的像素比例。如果过亮像素占比超过阈值，判定为过曝。可进一步分析过曝区域的空间分布（全屏过曝 vs 局部光源）。

3. **低亮度检测 (LOWBRIGHT)**

   原理：统计 Y 通道中低于阈值的像素占比。

   统计 Y < T_low（如 30/255）的像素比例，结合均值亮度判断。如果整体均值过低且暗像素集中，判定为低亮/欠曝。低亮与黑屏的区别在于：低亮仍有图像内容可见，黑屏几乎是全黑。

4. **冻结检测 (FROZEN)**

   原理：帧间差异性分析。

   连续帧之间计算结构相似性（SSIM）或归一化互相关（NCC），或计算帧差图的均值和标准差。如果连续多帧的相似度接近 1（或帧差接近 0），判定画面冻结。需要消除 PTZ 转动、场景切换等导致的低相似度误报。

   `frame_diff = ||frame_n - frame_{n-1}||²`，如果 `frame_diff < ε` 持续 K 帧 → 冻结告警

5. **雪花检测 (SNOWFLAKE)**

   原理：时域脉冲噪声分析。

   雪花在视频上表现为随机闪烁的亮/暗点（椒盐噪声）。方法：

   - 帧差图中检测大量孤立的、高幅值的像素点
   - 时域上这些点在连续帧间随机出现，无空间一致性
   - 统计噪点密度，超过阈值判定为雪花干扰

   与普通传感器噪声的区别：雪花噪声更密集、幅度更大、时域不连续。

6. **码流异常检测 (BITSTREAM)**

   原理：块效应和马赛克检测。

   码流异常时会出现明显的宏块边界（blocking artifacts）。检测方法：

   - 在 8x8 或 16x16 块边界处计算像素梯度
   - 如果块内平坦但块边界处有跳变，说明存在块效应
   - 如果出现大面积的马赛克方块，通过局部方差聚类检测

7. **黑屏检测 (BLACKSCREEN)**

   原理：全局亮度统计。

   计算整帧 Y 通道的均值 `mean(Y)` 和标准差 `std(Y)`。如果均值极低（如 < 10）且标准差也很小（如 < 5），说明画面几乎全黑，判定为黑屏。与低亮度的区别在于：黑屏无任何图像细节（标准差极低）。

8. **遮挡检测 (COVERED)**

   原理：背景图差分 + 纹理分析。

   需要预设背景图。当前帧与背景图做绝对差（SAD），得到差异区域。如果差异区域在空间上呈现大面积、连续的覆盖（而非局部运动目标），且该区域的纹理复杂度下降，判定为遮挡。遮挡物（如手指、贴纸）覆盖镜头时，图像会变得模糊、平滑，边缘能量显著下降。

   `diff_map = |frame - bg|`，`cover_region = diff_map > T_diff`，如果 cover_region 面积 > 阈值 且 `texture(cover_region) < 阈值` → 遮挡告警

9. **场景变化检测 (CHANGED)**

   原理：全局图像对比。

   与背景图做全局直方图比较或全图结构相似度比较。如果 SSIM 低于阈值，或直方图巴氏距离大于阈值，判定场景发生变化。与遮挡的区别：场景变化通常伴随整体色彩、亮度的系统性偏移，而非局部覆盖。

10. **镜头脏污检测 (CAMERADIRTY)**

    原理：固定位置模糊区域检测。

    脏污（灰尘、水滴）在图像固定位置造成局部模糊/暗斑。方法：

    - 分析图像局部区域的清晰度（拉普拉斯方差）空间分布
    - 查找持续固定的低清晰度区域
    - 与背景图对比，固定位置有稳定差异且边缘模糊

    与树叶遮挡的区别：脏污区域更小、边缘更模糊（无树叶纹理）、位置长期固定。

11. **镜头膜未撕检测 (LENSFILM)**

    原理：全局雾化效果检测。

    保护膜未撕时，图像整体偏灰、对比度降低、高频细节丢失。方法：

    - 计算图像的对比度（RMS 对比度或 Michelson 对比度）
    - 分析频域：高频分量显著减少，低频占主导
    - 可以结合边缘强度分布（EBP, Edge Blur Parameter）来量化

12. **固定遮挡检测 (COVEREDFIXED)**

    原理：长期固定位置的遮挡分析。

    与普通遮挡的区别在于"固定"属性：同一位置的遮挡持续超过 N 帧/分钟才告警。检测方法：

    - 逐帧计算遮挡区域 mask
    - 跟踪 mask 的时空稳定性
    - 如果遮挡区域在长时间内（如 5 分钟）位置、形状不变 → 固定遮挡

13. **紫边检测 (PURPLEEDGE)**

    原理：高对比度边缘处的色差分析。

    紫边（Purple Fringe）是高反差边缘处透镜色散导致的紫色/洋红色伪影。检测方法：

    - 在高梯度区域（边缘）分析色度分量（UV 平面）
    - 检测边缘附近的紫色调区域（U 和 V 的特定比值）
    - 结合边缘方向和色度过饱和区域定位紫边

#### 1.5.2 iqa10 — 4 项指标

这 4 项指标都需要帧间时序分析，所以单独放在 iqa10 节点。

1. **抖动检测 (JITTER)**

   原理：全局运动估计。

   连续帧之间使用相位相关法（Phase Correlation）或光流法估计全局运动矢量。如果帧间运动呈现高频、小幅、随机的振荡模式（而非平滑的摇镜或 PTZ 运动），判定为画面抖动。

   ```text
   // 估计帧间全局运动矢量 (dx, dy)
   (dx, dy) = estimate_global_motion(frame_n, frame_{n-1})
   
   // 分析时序运动模式
   if variance(dx, dy) 高 && 均值接近 0 → 高频振动 → 抖动告警
   ```

   常用的消除 PTZ 误判的方法：PTZ 运动时运动矢量呈现单向、平滑趋势，抖动则呈现零均值、高频振荡。

2. **噪声检测 (NOISE)**

   原理：时域高斯/散粒噪声分析。

   利用帧差法分离噪声：`noise_frame = frame_n - frame_{n-1}`（假设场景静止），`noise_level = std(noise_frame)`。

   在静止场景下，帧差主要反映传感器噪声。分析噪声的分布特征（高斯分布拟合）来判断噪声等级。也可以考虑局部方差法：找图像中的平坦区域，计算该区域的方差作为噪声估计。

3. **条纹检测 (STRIPE)**

   原理：频域周期性条纹分析。

   图像受到电磁干扰时会出现水平或垂直的滚动条纹，在频域表现为特定频率的峰值。方法：

   - 对图像做 FFT，在频谱中检测异常的水平/垂直线性峰值
   - 对行/列均值曲线做傅里叶分析，查找周期性波动
   - 对角度积分投影分析特定方向的条纹模式

   水平条纹：对每行均值做 1D-FFT；垂直条纹：对每列均值做 1D-FFT。检测到异常频点且幅值超过阈值 → 条纹告警。

4. **丢失检测 (LOSS)**

   原理：信号丢失检测。

   检查视频数据是否完全丢失（全绿/全蓝全屏、最后一帧定格、或完全无信号）。方法：

   - 检测纯色帧（全绿、全蓝，整帧方差为 0）
   - 检测持续无帧更新（与冻结类似，但可能出现纯色或雪花屏）
   - 检测视频黑场（black burst）信号特征

#### 1.5.3 算法处理流程

```text
输入帧 (352x288 缩放)
  │
  ├── 单帧分析 (iqa6)
  │  ├── 亮度直方图 → HIGHBRIGHT / LOWBRIGHT / BLACKSCREEN
  │  ├── 拉普拉斯方差 → CLARITY
  │  ├── 背景图差分 → COVERED / CHANGED / CAMERADIRTY
  │  ├── 频谱分析 → BITSTREAM / PURPLEEDGE
  │  └── 纹理分析 → LENSFILM / COVEREDFIXED / SNOWFLAKE
  │
  ├── 帧间分析 (iqa10)
  │  ├── 帧差法 → FROZEN / NOISE / LOSS
  │  ├── 全局运动估计 → JITTER
  │  └── 频域分析 → STRIPE
  │
  └── 结果整合 (OCR_FUNC7 → integration_result_article8)
```

这种架构的意图很清晰：单帧判定的放入 iqa6 一次处理完，需要多帧缓存和时序分析的放入 iqa10 独立处理，并行执行提高吞吐。

### 1.6 nnx 推理模型

从配置和文件结构来看，这个 VQA 算法使用的是 dhnnx + kitert 两层推理引擎架构。

#### 1.6.1 整体推理链路

```text
输入帧
  │
  ├── 图像预处理（缩放、归一化、格式转换）
  │
  ├── dhnnx 层（模型加载 + 前处理 + 后处理）
  │   ├── 解析 .nnx 模型文件（格式版本 1.2.0）
  │   ├── 加载模型权重和算子图
  │   ├── 执行前处理（mean/std 归一化等）
  │   ├── 调用 kitert 执行 NPU 推理
  │   └── 后处理（结果解析、阈值判定）
  │
  ├── kitert 层（NPU 推理调度）
  │   ├── 接收 dhnnx 下发的推理请求
  │   ├── 将输入数据拷贝到设备侧（Host → Device）
  │   ├── NPU 执行模型推理（Ascend 310/310P）
  │   ├── 结果拷贝回主机侧（Device → Host）
  │   └── 返回推理结果给 dhnnx
  │
  └── KNN 分类
     └── 模型输出特征向量 → KNN 分类器 → 最终判定
```

**NN 推理的核心** 是 CNN 特征提取 + KNN 分类 的两阶段架构。下面从模型结构、推理管线、硬件调度三个层面说明。

#### 1.6.2 CNN+KNN 两阶段架构概览

以 `color_arm_knn.nnx` 为例：

```text
┌──────────────────────────────────────┐
│ 1. CNN Backbone（特征提取器）         │
│                                      │
│  输入: 图像（如 224x224x3 RGB）      │
│   ↓                                  │
│  Conv2D → BN → ReLU → Pooling       │
│   ↓                                  │
│  Conv2D → BN → ReLU → Pooling       │
│   ↓                                  │
│  ... (若干卷积块)                    │
│   ↓                                  │
│  Global Avg Pooling                  │
│   ↓                                  │
│  FC Layer (全连接) → L2 Normalize    │
│   ↓                                  │
│  输出: 128维特征向量                  │
├──────────────────────────────────────┤
│ 2. KNN 分类器（内嵌在 nnx 后处理中）  │
│                                      │
│  输入: 128维特征向量                  │
│   ↓                                  │
│  计算与 N 个聚类中心的欧氏距离        │
│   ↓                                  │
│  K=5 最近邻投票                      │
│   ↓                                  │
│  输出: 类别 + 置信度分数              │
└──────────────────────────────────────┘
```

CNN 部分负责将图像映射到一个判别性特征空间，KNN 部分在这个特征空间中做分类。KNN 之所以是"后处理"而不是网络层，是因为它实际上是在训练阶段对大量 CNN 输出特征聚类得到的中心点集，推理时只需要计算距离，不需要反向传播。

#### 1.6.3 CNN 特征提取原理

CNN（卷积神经网络）的核心思想是**层次化特征学习**——低层学习局部纹理/边缘，高层学习全局语义/概念。

**卷积运算原理**：

```text
卷积核 (3×3 示例) 在输入图像上滑动，每次与局部区域做加权求和：

输入局部区域 (3×3)          卷积核权重 (3×3)           输出像素
┌────┬────┬────┐            ┌────┬────┬────┐
│ a₁ │ a₂ │ a₃ │            │ w₁ │ w₂ │ w₃ │         a₁×w₁ + a₂×w₂ + a₃×w₃
├────┼────┼────┤     ×      ├────┼────┼────┤      =    + a₄×w₄ + a₅×w₅ + a₆×w₆
│ a₄ │ a₅ │ a₆ │            │ w₄ │ w₅ │ w₆ │         + a₇×w₇ + a₈×w₈ + a₉×w₉
├────┼────┼────┤            ├────┼────┼────┤
│ a₇ │ a₈ │ a₉ │            │ w₇ │ w₈ │ w₉ │
└────┴────┴────┘            └────┴────┴────┘

卷积核从左到右、从上到下逐位置滑动，每个位置产出一个像素值，
所有输出像素组成一张"特征图" (feature map)。
```

**为什么卷积而不是全连接？**

全连接层每个输出像素与所有输入像素关联，参数量爆炸（224×224×3 输入 → 224×224 输出 = 150M 参数）。卷积核共享权重、局部连接，一个 3×3×3 卷积核只有 27 个参数，不管输入多大——这是 CNN 的核心效率来源。

**层次化特征学习**：

```text
Layer 1 (浅层): 学习低级特征
├── 边缘检测：水平/垂直/对角线边缘
├── 颜色梯度：局部色彩变化方向
└── 纹理基元：细颗粒/粗颗粒纹理
    示例卷积核效果:
    水平边缘核: [[-1,-1,-1],[0,0,0],[1,1,1]]
    垂直边缘核: [[-1,0,1],[-1,0,1],[-1,0,1]]

Layer 2-3 (中层): 组合低级特征为中级模式
├── 边缘组合 → 角点、交叉点、简单形状
├── 纹理组合 → 周期性条纹、斑块、颗粒感
└── 色彩组合 → 色偏方向、亮度分布模式

Layer 4+ (深层): 组合中级模式为高级语义
├── 形状组合 → "遮挡物轮廓"、"异常区域形状"
├── 模式组合 → "蜘蛛网纹理"、"树叶纹理"、"脏污模糊"
└── 全局组合 → "整体偏色"、"画面冻结"的语义特征
```

**VQA 中的 CNN 架构分析**：

各子模型的 nnx 文件体量从 36KB 到 65MB 差异巨大，说明架构深度不同：

```text
轻量级模型 (36KB ~ 53KB: 黑白/偏色检测)
├── 架构: 3-4 层浅 CNN + GAP + FC
├── 参数量: ~18K (blackwhite) ~ ~26K (color)
├── 推理计算量: 极小，单帧 < 1ms
├── 为什么这么小就能工作？
│   └─ 黑白检测只需判断"色度通道是否接近零"
│   └─ 偏色检测只需判断"色度通道的偏移方向"
│   └─ 这些是低级特征，浅层 CNN 就能提取
└─ 输出: 128 维特征向量 → KNN 分类

中型模型 (65MB: 变更/抖动检测)
├── 架构: MobileNet 或 ResNet-18 变体 + 自定义头部
├── 参数量: ~30M
├── 推理计算量: 中等，单帧 ~5-8ms
├── 为什么需要这么深？
│   └─ 变更检测需要语义级比对（不是像素差分）
│   └─ 抖动检测需要理解全局运动模式
│   └─ 这些需要高层语义特征，浅层 CNN 无法提取
└─ 输出: 256 维特征向量 → KNN 分类

目标检测模型 (20MB: od_trunk 遮挡检测)
├── 架构: YOLOv5s 或自研轻量检测器变体
├── 参数量: ~10M (仅检测头，不含骨干)
├── 推理计算量: 输出 bounding box + 分类 + 置信度
├── 为什么不是纯分类而是检测？
│   └─ 遮挡物需要定位（bounding box）和分类（遮挡类型）
│   └─ 纯分类只能回答"有没有遮挡"，检测还能回答"在哪里"
└─ 输出: 检测框列表 + 各框的 128 维特征 → KNN 细分类
```

**CNN 特征向量的数学含义**：

```text
CNN 最终输出一个 128 维特征向量 f = [f₁, f₂, ..., f₁₂₈]

这个向量是图像在"判别性特征空间"中的坐标：
├── f₁: 可能编码了"水平边缘密度"
├── f₂: 可能编码了"红色通道偏移量"
├── f₃: 可能编码了"局部纹理粗糙度"
├── ...
├── f₁₂₈: 可能编码了"全局语义概念匹配度"
└── 单个维度的含义不可解释，但向量整体有几何意义

L2 归一化后: ||f||₂ = 1
└── 将特征向量投影到单位超球面
└── 使余弦相似度 = 内积（计算更高效）
└── 消除图像亮度/对比度对特征长度的干扰
    （亮图和暗图的同一场景应映射到相同方向）
```

#### 1.6.4 KNN 分类原理

KNN（K-Nearest Neighbors，K最近邻）是最古老的分类算法之一，核心思想是**在特征空间中找最近的邻居来投票**。

**算法步骤**：

```text
给定: 训练集聚类中心 C = {c₁, c₂, ..., cₙ}（每个中心附带类别标签）
输入: 待分类的特征向量 f（128 维，已 L2 归一化）
参数: K = 3 或 5（投票邻居数）

Step 1: 计算距离
  对每个聚类中心 cᵢ，计算与 f 的距离：
  dᵢ = ||f - cᵢ||₂ = √(Σ(fⱼ - cᵢⱼ)²)  (欧氏距离)
  或 dᵢ = 1 - f·cᵢ  (余弦距离，L2归一化后等价)

Step 2: 排序取 Top-K
  按距离从小到大排序，取前 K 个最近的聚类中心：
  nearest = sorted(C, key=distance)[:K]

Step 3: 投票分类
  每个最近邻 centerᵢ 投票给自己的类别 labelᵢ：
  ├── 简单投票: count(label) → 取最多的类别
  ├── 加权投票: weightᵢ = 1/dᵢ → Σ weightᵢ per label → 取最高分的类别
  └─ 加权投票更优：距离近的邻居更可信，应给更大权重

Step 4: 置信度计算
  ├── 简单置信度: count(winning_label) / K
  │   └─ 如 K=5, 3 个邻居投"异常" → 置信度 60%
  ├── 加权置信度: Σ(weightᵢ for winning_label) / Σ(all weightᵢ)
  │   └─ 距离近的邻居权重大，置信度更精确
  └─ 映射到 0~100 分数: score = confidence × 100
```

**以偏色检测为例的 KNN 分类过程**：

```text
训练好的聚类中心（在 128 维"偏色特征空间"中）：

  c₁ = "正常色彩"     类别=正常   位置=(0.02, 0.01, 0.98, ...)  ← 正常图像特征的平均
  c₂ = "轻微偏红"     类别=告警   位置=(0.45, 0.03, 0.72, ...)  ← 轻微偏红图像特征的平均
  c₃ = "严重偏红"     类别=异常   位置=(0.82, 0.01, 0.15, ...)  ← 严重偏红图像特征的平均
  c₄ = "轻微偏绿"     类别=告警   位置=(0.03, 0.48, 0.75, ...)  ← 轻微偏绿图像特征的平均
  c₅ = "严重偏绿"     类别=异常   位置=(0.01, 0.85, 0.12, ...)  ← 严重偏绿图像特征的平均
  c₆ = "轻微偏蓝"     类别=告警   位置=(0.01, 0.02, 0.45, ...)  ← 轻微偏蓝图像特征的平均
  c₇ = "严重偏蓝"     类别=异常   位置=(0.01, 0.01, 0.82, ...)  ← 严重偏蓝图像特征的平均

  注: 上面是示意性坐标，实际128维空间中每个维度由CNN学习得到，
  无法直接解释为"红色偏移量"，但几何含义一致。

输入图像 CNN 特征: f = (0.40, 0.04, 0.70, ...)

Step 1: 计算距离 (余弦距离)
  d(f, c₁) = 1 - f·c₁ = 0.15  ← 距正常较近
  d(f, c₂) = 1 - f·c₂ = 0.08  ← 距轻微偏红最近！
  d(f, c₃) = 1 - f·c₃ = 0.55  ← 距严重偏红很远
  d(f, c₄) = 1 - f·c₄ = 0.42  ← 距偏绿较远
  d(f, c₅) = 1 - f·c₅ = 0.71
  d(f, c₆) = 1 - f·c₆ = 0.35
  d(f, c₇) = 1 - f·c₇ = 0.62

Step 2: Top-3 最近邻 (K=3)
  nearest = [c₂(0.08), c₁(0.15), c₆(0.35)]

Step 3: 加权投票
  c₂(轻微偏红, 告警): weight = 1/0.08 = 12.5
  c₁(正常色彩, 正常): weight = 1/0.15 = 6.67
  c₆(轻微偏蓝, 告警): weight = 1/0.35 = 2.86

  告警类总分: 12.5 + 2.86 = 15.36
  正常类总分: 6.67

  → 告警类胜出 (15.36 > 6.67)

Step 4: 置信度
  告警置信度 = 15.36 / (15.36 + 6.67) = 69.7%
  → 映射为分数 70 分
  → 与阈值比较: 若 threshold = 60 → 触发偏色告警

  注: 即使最近邻 c₂ 是告警，c₁ 是正常，加权投票仍倾向告警
  └─ 因为距离近 (0.08) 的权重远大于距离远 (0.15) 的权重
```

**KNN 聚类中心的生成过程**：

```text
训练阶段 (在实验室/数据标注平台完成，不在 VQRS 运行时):

Step 1: 数据收集
  ├── 正常图像: 5000 张 → CNN 提取 → 5000 个 128 维特征
  ├── 偏红图像: 3000 张 → CNN 提取 → 3000 个 128 维特征
  ├── 偏绿图像: 2000 张 → CNN 提取 → 2000 个 128 维特征
  └─ ... 各类别数千张标注图像

Step 2: K-Means 聚类
  ├── 对每个类别内部做聚类，找出该类别的典型特征中心
  │   ├── 正常类: 聚类出 3-5 个子中心（白天/夜间/室内等子场景）
  │   ├── 偏红类: 聚类出 2-3 个子中心（轻微偏红/严重偏红）
  │   └─ 总计产生 20-50 个聚类中心
  │
  └── K-Means 算法:
      1. 随机初始化 K 个中心点
      2. 将每个特征分配到最近的中心
      3. 重新计算每个中心的均值（移到类内平均位置）
      4. 重复 2-3 直到中心不再移动（收敛）
      └─ 收敛后的中心就是 KNN 推理时使用的分类参考点

Step 3: 中心点打包到 nnx 文件
  └─ 聚类中心以 float32 数组存储，嵌入 .nnx 后处理配置中
  └─ 推理时直接加载，不需要重新训练
  └─ 每个中心约 128 × 4 字节 = 512 字节
  └─ 50 个中心 = 25,600 字节 ≈ 25KB（对模型体积贡献微乎其微）
```

**为什么 CNN+KNN 而不是 CNN+FC（全连接分类头）？**

```text
方案A: CNN + FC 分类头（传统深度学习分类）
├── 训练: CNN骨干 + FC层一起训练，FC层权重隐式编码分类边界
├── 新增类别: 需要重新训练整个网络（CNN + FC）
├── 部署: 每次更新需要替换整个 .nnx 文件
├── 优势: 推理只需一次前向传播，端到端优化
└─ 劣势: 更新成本高，无法增量扩展

方案B: CNN + KNN 分类器（VQRS 采用的方案）
├── 训练: CNN骨干单独训练（特征提取任务），KNN中心事后聚类
├── 新增类别: 只需收集新类别数据 → CNN提取特征 → 新增聚类中心
│   └─ CNN骨干不需要重新训练！
│   └─ 只更新 KNN 中心点集（几十KB）
├── 部署: 更新只替换 KNN 配置，不替换 CNN 模型
├── 优势: 增量扩展、解耦更新、低部署成本
└─ 劣势: 推理需要两步（CNN前向传播 + KNN距离计算）

VQRS 选择方案B 的根本原因:
├── 1. 监控场景异常类型不断演变
│   └─ 新的遮挡物类型（新型遮挡物出现）
│   └─ 新的异常模式（新型干扰源）
│   └─ CNN+FC 需要每次重训，CNN+KNN 只需新增中心
│
├── 2. KNN 中心的语义可解释性
│   └─ 每个中心明确代表一个已知类别
│   └─ FC 层的权重无法直接解释
│   └─ 运维人员可以理解"中心c₃代表严重偏红"
│
├── 3. KNN 不需要 GPU/NPU 计算
│   └─ 欧氏距离/余弦距离是 CPU 纯数学运算
│   └─ 在 dhnnx 后处理阶段执行，不占用 NPU 算力
│   └─ CNN 占用 NPU，KNN 占用 CPU → 并行不冲突
│
└── 4. 少样本场景下的鲁棒性
    └─ 某些异常类型（如蜘蛛网）样本极少
    └─ FC 层需要大量样本才能收敛
    └─ KNN 即使只有 5-10 个样本也能建立中心
```

#### 1.6.5 图像预处理

```text
原始帧 (YUV420, 如 1920x1080)
  │
  ├── 1. 缩放 (Resize)
  │   // 算法: bilinear / bicubic 插值
  │   // 目标: NN 输入尺寸（各模型可能不同，统一由 dhnnx 处理）
  │
  ├── 2. 颜色空间转换
  │   YUV420 → RGB (或 BGR，取决于训练时约定)
  │   // 转换矩阵标准 BT.601 / BT.709
  │
  ├── 3. 归一化 (Normalize)
  │   pixel = pixel / 255.0      // [0,255] → [0,1]
  │   pixel = (pixel - mean) / std   // 减均值除标准差
  │   // mean/std 在模型训练时统计得到
  │
  └── 4. 排布转换 (Layout)
      HWC (原始排布) → CHW (NN 输入排布)
      // 因为卷积层在 CHW 上计算效率更高
```

#### 1.6.6 dhnnx 推理管线（以 iqa2 color 为例）

dhnnx 是自研的 NN 模型加载框架，作用类似于 ONNX Runtime 或 TensorRT。它不负责实际的 NPU 计算，而是负责模型加载和推理编排。

**阶段1：模型加载**

- 解析 `color_arm_knn.nnx`
  - 读取文件头（格式版本 1.2.0）
  - 反序列化网络结构 protobuf
  - 加载权重数据到 Host 内存
- 构建推理 Session
  - 创建输入/输出 tensor 占位
  - 记录输入尺寸、数据类型、mean/std 参数
  - 通过 nnx_netprotocol 与 kitert 握手

**阶段2：预处理**（前述的图像处理）

- 缩放、颜色转换、归一化、CHW 排布
- 数据写入 Host 侧 tensor buffer

**阶段3：调用 kitert 推理**

- 向 kitert 提交推理请求
- kitert 调度到 Ascend NPU
- 等待推理完成（同步模式）
- 从 Host 侧 tensor buffer 读取输出

**阶段4：后处理**

- 提取特征向量
- KNN 分类（计算距离 + 投票）
- threshold 阈值比较
- 输出最终诊断结果（分数 + 状态）

#### 1.6.7 kitert 推理引擎

kitert 是华为 Ascend NPU 的推理运行时，相当于 TensorRT for NVIDIA。从 `version_desc.json` 看它是 NPU 的 `forward_runtime`。

```text
kitert (Ascend NPU Runtime) V1.20.0
│
├── 硬件后端：Ascend 310 / 310P NPU
│   ├── AI SDK 版本 1.21.0
│   └── nck (NPU Kernel) 版本 V1.3.0.874965
│
├── 推理流程
│   ├── 1. aclrtMallocHost → 分配主机（Host）内存
│   ├── 2. aclrtMalloc → 分配设备（Device）内存
│   ├── 3. 数据拷贝 Host → Device
│   ├── 4. NPU 执行模型计算图
│   ├── 5. 结果拷贝 Device → Host
│   └── 6. aclrtFree / aclrtFreeHost → 释放内存
│
├── 调度模式
│   ├── 同步模式：ProcessImageMulti 同步等待结果
│   ├── dhnnx 通过 nnx_netprotocol 协议向 kitert 下发任务
│   └── kitert 返回推理结果给 dhnnx
```

推理是 batch 模式执行的。`alg_conf.json` 中每个模型的 `batch_size: 1`，即一次处理 1 帧数据。NPU 上的计算是同步或异步取决于调用方式——同步模式直接等结果，异步模式通过回调获取。

#### 1.6.8 nnx 模型格式

`.nnx` 是大华自定义的加密模型文件格式，相当于把模型结构、权重和配置文件打包在一起。

```text
.nnx 文件内部结构（基于格式推断）：
┌──────────────────────┐
│ 文件头                │
│  ├── magic number    │  ← 标识 nnx 格式
│  ├── format version  │  ← 1.2.0
│  └── model metadata  │  ← 输入尺寸、数据类型等
├──────────────────────┤
│ 模型结构描述          │  ← 网络层拓扑（CNN 结构）
├──────────────────────┤
│ 权重数据              │  ← 序列化的 float32 权重
├──────────────────────┤
│ 配置文件（内嵌或关联） │  ← jinn_vqa_iqa*_default.conf
└──────────────────────┘
```

#### 1.6.9 nnx 子模型

所有 6 个带 `.nnx` 的子模型架构一致：

```text
模型组成
├── CNN Backbone（特征提取器）
│   ├── MobileNet / ResNet 变体
│   └── 输出 128-256 维特征向量
│
└── KNN 分类器
    ├── 训练阶段：在特征空间建立聚类中心
    └── 推理阶段：计算特征到各中心的距离
```

| 模型文件                    | 学习的特征空间          |
| --------------------------- | ----------------------- |
| `color_arm_knn.nnx`         | "色偏"特征空间          |
| `blackwhite_arm_knn.nnx`    | "黑白/灰度"特征空间     |
| `lowcontrast_arm_knn.nnx`   | "对比度"特征空间        |
| `iqa_treeblock_arm_knn.nnx` | "树/叶纹理遮挡"特征空间 |
| `ptz_arm_knn.nnx`           | "PTZ 运动轨迹"特征空间  |
| `cobweb_oc_arm_knn.nnx`     | "蛛网状遮挡"特征空间    |

所以模型文件名中的 `knn` 表示：CNN 提取特征 + KNN 做最终分类，两者组合成一个完整的推理流水线。CNN 部分通过 NN 推理（NPU 加速）输出特征，KNN 分类器在后处理步骤执行。

> **oc 分类**：在 dhnnx 推理引擎中，`op_category: "oc"` 表示 **Object Classification（目标分类）** 算子。小模型诊断的 6 个 nnx 子模型本质上都是独立的分类任务——每个模型负责一类异常的二分类或多分类判定（如偏色/正常、黑白/彩色）。这与大模型诊断中 CLIP+权重矩阵的"特征提取+线性解码"范式不同，小模型采用的是"CNN特征提取+KNN聚类分类"的经典模式。

#### 1.6.10 模型推理详述：以偏色检测为例

工程名是 `jinn_vqa_iqa_color`，模型文件 `color_arm_knn.nnx`。完整的推理链：

```text
输入帧 (1920x1080 YUV)
  │
  ├── 1. 预处理
  │   ├── 缩放到 NN 输入尺寸（如 224x224）
  │   ├── YUV → RGB/BGR 转换
  │   ├── 归一化：除以 255，减 mean 除 std
  │   └── HWC → CHW 排布转换
  │
  ├── 2. dhnnx 加载模型
  │   ├── 从 color_arm_knn.nnx 解析网络图
  │   ├── 设置输入 tensor
  │   └── 调用 kitert 执行推理
  │
  ├── 3. kitert (Ascend NPU)
  │   ├── 数据搬运 Host → Device
  │   ├── NPU 计算特征图 → 全连接层 → 输出特征向量
  │   └── 特征向量 Device → Host
  │
  ├── 4. 后处理
  │   ├── dhnnx 对特征向量做 L2 归一化（通常）
  │   └── 输出 N 维特征向量（如 128 维）
  │
  └── 5. KNN 分类
     ├── 特征向量与训练好的 KNN 分类器匹配
     ├── 计算与各聚类中心的距离
     ├── K=3 或 K=5 投票
     └── 输出偏色分数 → 是否告警
```

与小模型诊断的关键区别：

1. **CLIP 骨干是新增的核心环节**：小模型诊断没有视觉大模型特征提取，各子模型独立做 CNN+KNN 分类；大模型诊断引入 CLIP ViT-L/14@336 提取 3072 维通用视觉特征，再通过权重矩阵映射出 31 个质量指标。
2. **流水线更深**：小模型是 8 路并行 → 汇总 → 输出（3 层）；大模型是 7 路并行 → CLIP → 矩阵 → 融合 → 输出（5 层），OCR_OX23 和 OCR_OX24 构成串行的第二级处理。
3. **OCR_FUNC25 必须同步等待**：使用 `input_stream_sync_policy: "sync_set"`，需要 7 路 VQA 输出 + 矩阵输出全部齐备后才能融合计算。

### 2.5 关键推断

1. **bigvqa.so 使用 VDS 接口而非 VQA 旧接口**：
   `CAlgorithmBigVqa` 通过 `DHIVS_VDS_*` 符号（Init/UnInit/GetCap/SetCfgFile/CreateHandle）加载算法库，而非经典 VQA 的 `DHIVS_VQA_*` 符号。这说明 bigvqa 内部封装了完整的 VDS 流水线框架，对外暴露通用视觉检测接口。

2. **VQRS 负责 ACL 内存搬运**：
   `CAlgorithmBigVqa::HandleAlgorithmAnalyse()` 中，VQRS 应用层执行 I420→NV12 格式转换后，通过 ACL API 分配主机侧和设备侧内存，将图像数据从 Host 拷贝到 Device，然后设置 `dhivs_pic_v2_t` 的双地址（buffer_addr1=虚拟地址, buffer_addr2=物理地址），通过 `ProcessImageMulti` 送入算法。

3. **14 个 VQA 指标使能映射**：
   `HandleSetVqaFuncEnable()` 将 VQRS 的 14 个诊断开关映射到 SDK 的 `DHIVS_OBJ_VQA_INDICATOR_TYPE_*` 枚举，通过 `UpdateAlgorithmInfo` 下发。

4. **背景图三级共用**：
   遮挡(COVERED)、变更(CHANGED)、脏镜头(CAMERADIRTY) 三个指标共用同一张背景图，通过 `dhivs_vqa_func_changed_t.bg_img` 分别下发到算法。

5. **与大模型共享启用条件**：
   bigvqa、vqatsa(文搜图特征提取)、qbic(特征比对)、ts_inference(文搜图推理) 四个算法包共享 `ENABLE_BIGVQA` 启用条件，仅在 OpenEuler/aarch64 + sun002 NPU 平台上有意义。

6. **Weight_Matrix 是单层线性映射**：
   187KB 的模型体积精确吻合 3072×31×2(FP16) = 190KB，证实这是一个无隐藏层的线性映射：`Score[i] = sigmoid(W_i · CLIP_feature + b_i)`。OCMULTIATTR 的 attr_num=200 表明权重矩阵实际存储了 (200, 3072) 的完整权重，当前只激活前 31 行，预留了 169 行扩展空间。

### 2.6 大模型诊断原理

以下是基于配置文件、模型体积和架构线索推断的各环节实现原理。注意 `libdhivs_sdk_vqavlm.so` 是闭源的，确切实现不可见。

#### 2.6.1 传统算法节点 (iqa28) — 5 项指标

与小模型诊断的 iqa6/iqa10 原理一致，此处复用相同的传统 CV 方法：

- **冻结检测 (FROZEN)**：帧间 SSIM 或帧差均值接近零，持续 K 帧判定冻结
- **低亮度 (LOWBRIGHT)**：Y 分量均值低于阈值
- **高亮度 (HIGHBRIGHT)**：Y 分量均值高于阈值
- **低对比度 (LOWCONTRANST)**：Y 分量直方图动态范围低于阈值
- **清晰度 (CLARITY)**：拉普拉斯方差低于阈值判定模糊

图像缩放到 352×288（`img_td_size`）降低计算量，传统算法不需要高分辨率。

#### 2.6.2 CLIP 视觉骨干 (OCR_OX23) — 特征提取

**预处理**：

```text
输入帧 (NV12, YUV420SP)
  │
  ├── DVPP 硬件加速 (acl_dvpp)
  │   ├── NV12 → RGB 转换
  │   ├── 缩放到 336×336 (CLIP 标准输入分辨率)
  │   └── 归一化: pixel/255 → (pixel - mean) / std
  │
  └── 排布转换: HWC → CHW
```

DVPP（Digital Vision Pre-Processing）是 Ascend NPU 的专用图像预处理硬件，格式转换和缩放不占用 AI 核算力。VQRS 侧已完成 I420→NV12 转换和 ACL 内存搬运，算法内部再做 NV12→RGB+缩放。

**推理**：

```text
CLIP ViT-L/14@336
  │
  ├── Patch Embedding: 336/14 = 24×24 = 576 patches + 1 CLS token
  │   patch_dim = 14×14×3 = 588 → linear proj to hidden_dim
  │
  ├── 24 层 Transformer Encoder
  │   hidden_dim = 1024 (4层拼接: 1024×4 → 投影 → 3072)
  │   MLP_dim = 4096
  │   num_heads = 12
  │
  └── 输出: 3072 维特征向量
      ├── 取最后4层隐藏状态拼接 (1024×4 = 4096)
      ├── 投影头压缩到 3072 维
      └── L2 归一化 → 写入 REID 记忆队列
```

3072 维而非标准 CLIP 的 768 维输出，实现方式是**取最后 4 层隐藏状态拼接+投影**，保留更丰富的空间和语义信息供权重矩阵映射。581MB 的模型体积也与 ViT-L 的参数量吻合（~304M 参数 × 2 字节/参数 ≈ 608MB FP16）。

**REID 记忆队列**：

```text
每帧推理后:
  ├── 将 3072 维特征追加到队列尾部 (滑动窗口, 长度与 async_depth=25 一致)
  ├── 计算当前帧与前一帧特征的余弦相似度 sim
  ├── drastic_score = 1 - sim
  │   若 drastic_score > threshold → 标记 is_drastic=true
  └── custom_attr_label: 205 → 计算 CLIP 特征与 205 个语义原型的相似度分布
```

205 个语义类别是预定义的质量相关语义概念（如"模糊的画面"、"正常监控场景"、"遮挡物"、"偏色"等），CLIP 预训练的视觉-语言对齐使其天然理解这些概念，微调后特征的区分度更高。

#### 2.6.3 权重矩阵映射 (OCR_OX24) — 指标分数生成

```text
输入: OCR_OX23 输出的 3072 维特征向量 (FEATINPUT模式)
  │
  ├── 线性映射 (单层, 无隐藏层)
  │   Y = sigmoid(W × X + b)
  │   W: (31, 3072) FP16 权重 → nnx文件187KB精确吻合
  │   b: (31,) 偏置
  │
  ├── 输出: 31 个质量指标分数
  │   ├── biz[0]: IQA类型 → indicator_map[31个ID]的分数
  │   └─ biz[1]: SERVICETYPE(66) → 当前画面的场景分类
  │
  └── OCMULTIATTR队列
      max_obj_num=20, attr_num=200 (当前激活31, 预留169行)
```

**为什么单层线性映射就能工作？** CLIP 微调后的 3072 维特征已经隐含编码了所有质量相关信息，权重矩阵只需做维度选择和归一化——将"偏色相关"的维度选出来映射到偏色指标分数，将"模糊相关"的维度选出来映射到清晰度分数。本质上是把 CLIP 特征空间中已有的质量语义"解码"回具体的指标数值。

**SERVICETYPE(66)**：输出一个场景类型分类（室内/室外/道路/夜间等），用于辅助 OCR_FUNC25 的平滑策略选择——不同场景类型的指标基线和平滑参数可能不同。

#### 2.6.4 遮挡检测 (iqa36) — 目标检测骨干

```text
输入: 原始分辨率图像 (不缩放, 遮挡区域可能很小)
  │
  ├── od_trunk 推理 (Object Detection trunk)
  │   ├── 轻量级检测器 (YOLOv5s变体或自研轻量检测器)
  │   └─ 输出: 遮挡区域 bounding box + 遮挡类型分类
  │
  └─ MemQueueVQAIQA: 缓存多帧遮挡区域, 用于时序一致性验证
```

"od_trunk" 名称直接暗示 Object Detection trunk。遮挡检测需要定位遮挡物的位置和形状，比单纯的二分类更复杂，所以模型 19.8MB 远大于黑白/偏色的几十 KB。

#### 2.6.5 黑白检测 (iqa31) — 轻量分类

```text
输入: 缩放后的图像
  │
  ├── 轻量二分类 CNN (3-5层, 几万参数)
  │   └─ 输出: 2类概率 [彩色, 黑白]
  │
  └─ 判断: 色度通道饱和度是否接近零
```

36KB 的模型极小，说明是裁剪版的小 CNN。黑白检测的本质是判断画面色彩饱和度是否接近零——一个简单的色度统计加分类器即可。

#### 2.6.6 偏色检测 (iqa32) — 轻量分类

```text
输入: 缩放后的图像
  │
  ├── 轻量分类 CNN (稍大于黑白检测)
  │   └─ 输出: 偏色方向 + 强度 (偏红/偏绿/偏蓝/正常)
  │
  └─ 判断: 色度通道的偏移方向和幅度
```

52KB 模型比黑白稍大，因为偏色检测需要判断色度偏移方向（4 类 vs 2 类），决策边界更复杂。

#### 2.6.7 画面变更检测 (iqa33) — 语义级差异检测

```text
输入: 当前帧 + 背景参考帧 (由VQRS通过bg_img下发)
  │
  ├── Siamese-style 变更检测网络 (~30M参数)
  │   ├── 双分支特征提取 → 差异特征融合
  │   └─ 输出: 变更区域掩码 + 变更置信度
  │
  └─ MemQueueVQAIQA: 缓存背景帧特征摘要, 消除光照变化干扰
```

62.5MB 的模型量级对应 ~30M 参数的中型网络。画面变更检测需要语义级比对——简单的像素差分会受光照变化干扰，需要理解"这是不同场景"而非"这是同一场景的不同光照"。

背景图通过 VQRS 的 `HandleAlgorithmAnalyseRules()` 以 `dhivs_vqa_func_changed_t.bg_img` 下发。

#### 2.6.8 抖动+云台检测 (iqa34) — BiGeoNet 双任务

```text
输入: 连续帧序列 (MemQueueVQAIQA缓存)
  │
  ├── BiGeoNet (Bi-directional Geometry Network)
  │   ├── 学习帧间密集几何变换场
  │   └─ 多任务输出头:
  │       ├── Head_1: 抖动指标 → 帧间位移的统计特征 (均值/方差/峰值)
  │       └─ Head_2: 云台方向 → PTZ分类 [不变/左/右/上/下/zoom-in/zoom-out]
  │
  └─ 判断逻辑:
      抖动: 运动矢量呈零均值高频振荡 (随机小幅)
      PTZ: 运动矢量呈单向平滑趋势 (定向大幅)
```

BiGeoNet 的核心思想是预测帧间密集几何变换场，通过分析变换场的统计特征区分自然抖动和人为 PTZ 控制。两个 func_param（JITTER + PTZCONTROL）共用同一模型，说明 BiGeoNet 内部有多任务输出头。

#### 2.6.9 功能聚合 (OCR_FUNC25) — 加权融合 + 时序平滑

```text
输入 (7路同步汇聚):
  ├── jinn_vqa_iqa_28.vqa_out  → 传统5指标分数
  ├── jinn_vqa_iqa_36.vqa_out  → 遮挡分数
  ├── jinn_vqa_iqa_31.vqa_out  → 黑白分数
  ├── jinn_vqa_iqa_32.vqa_out  → 偏色分数
  ├── jinn_vqa_iqa_33.vqa_out  → 变更分数
  ├── jinn_vqa_iqa_34.vqa_out  → 抖动+云台分数
  └─ OCR_OX_24.oc_out          → 31个Matrix指标分数
  │
  ├── 场景切换保护 (is_drastic=1)
  │   CLIP特征余弦距离 > threshold → 清空EMA状态, 跳过平滑
  │   防止跨场景的评分平滑污染
  │
  ├── 时序平滑 (smooth_type=2, EMA)
  │   score_smooth[i] = α × score_current[i] + (1-α) × score_prev[i]
  │   α 经验取值 0.3-0.5 (噪声大的指标用较小α)
  │
  └── 指标冲突解决策略:
      ├── 传统指标(257-273): 传统算法为主, Matrix值辅助验证
      ├── 深度模型指标(515-521): 深度模型为主
      ├── 高级语义指标(1025-1037): 仅Matrix输出, 直接使用
      └─ 时序指标(1281-1283): CLIP特征一致性直接计算
```

`is_drastic=1` 的关键含义：当 CLIP 的 REID 队列检测到相邻帧的 3072 维特征差异超过阈值时，判定为场景切换（如摄像头切换），此时重置 EMA 平滑状态，防止跨场景的评分被错误平滑。

`control=[4]` 表示每 4 帧执行一次推理——VQA 不需要逐帧分析，4 帧间隔足以捕捉质量变化趋势，同时降低 NPU 算力消耗。

#### 2.6.10 算法处理流程

```text
一帧NV12图像进入系统
  │
  ├── DVPP预处理 (缩放/格式转换)
  │   ├── CLIP骨干: 缩放到336×336, NV12→RGB
  │   ├── 小模型: 缩放到各自输入尺寸
  │   └─ 传统算法: 缩放到352×288
  │
  ├── [并行7路, NPU时分复用]
  │   ├── 传统VQA(CPU): 5个统计指标
  │   ├── 遮挡检测(NPU): 原始分辨率 → od_trunk → 遮挡分数
  │   ├── 黑白检测(NPU): 缩放 → blackwhite → 黑白概率
  │   ├── 偏色检测(NPU): 缩放 → color → 偏色分数
  │   ├── 变更检测(NPU): 当前帧+背景图 → changed → 变更分数
  │   ├── 抖动检测(NPU): 多帧序列 → BiGeoNet → 抖动+云台分数
  │   └── CLIP骨干(NPU): 336×336 → ViT-L → 3072维特征
  │        └── 权重矩阵(NPU): 3072×31 线性映射 → 31 个指标分数
  │        └── CLIP特征余弦距离 → 场景切换标记
  │
  ├── 功能聚合(CPU): 7路加权融合 + EMA平滑 + 场景切换保护
  │
  └── 结果输出: 封装为 dhivs_detect_result_t → 回调VQRS应用层
```

### 2.7 指标映射深度分析

#### 2.7.1 indicator_map 精确映射

OCR_OX24（权重矩阵）输出的 31 个指标 ID 与 SDK 枚举值的精确映射如下。这是大模型诊断 Pipeline 的核心数据结构——决定了哪些诊断项由 CLIP+Matrix 路径产出。

**基础质量类 (0x0100)** — 传统指标由 iqa28/31/32/33/34 直接覆盖，Matrix 辅助验证其余：

| indicator_map ID | 十六进制 | SDK 枚举  | 含义       | 主要产出算子               |
| ---------------- | -------- | --------- | ---------- | -------------------------- |
| 257              | 0x0101   | CLARITY   | 清晰度     | iqa28(传统)+Matrix辅助     |

#### 2.7.3 融合层深度机制

OCR_FUNC25 的 `SUBFUNC_IQAV2` 配置揭示了融合层的精确机制：

```text
SUBFUNC_IQAV2 核心参数:
├── is_drastic = 1 (场景切换保护开关)
├── smooth_type = 2 (EMA 平滑类型)
├── indicators = [31 个指标 ID] (与 Matrix indicator_map 完全一致)
│
├── 融合策略 (按指标 ID 来源):
│
│   Case A: 指标同时有 VQA 子算子输出 + Matrix 输出
│   ├── CLARITY: iqa28 统计分数 (权重α) + Matrix CLIP分数 (权重β)
│   ├── COVERED: iqa36 od_trunk 检测分数 + Matrix 遮挡分类分数
│   ├── NOISE: iqa28 统计分数 + Matrix 语义分数
│   ├── SNOWFLAKE: iqa28 统计分数 + Matrix 语义分数
│   └─ 融合公式: final_score = α × vqa_score + β × matrix_score
│      α > β (VQA 子算子更可靠) 或 α < β (CLIP 更泛化) 取决于指标
│
│   Case B: 指标仅有 VQA 子算子输出，Matrix 不覆盖
│   ├── HIGHBRIGHT/LOWBRIGHT/LOWCONTRANST: iqa28 直接输出
│   ├── BLACKWHITE: iqa31 独立 nnx 输出
│   ├── COLORCAST: iqa32 独立 nnx 输出
│   ├── JITTER/PTZCONTROL: iqa34 BiGeoNet 输出
│   ├── FROZEN: iqa28 帧间差分输出
│   ├── CHANGED: iqa33 Siamese 网络输出
│   └─ 融合公式: final_score = vqa_score (直接使用，不融合)
│
│   Case C: 指标仅有 Matrix 输出，VQA 子算子不覆盖
│   ├── 纯色屏(PURECOLOR), 蜘蛛网(SPIDER), 保护膜(LENSFILM)
│   ├── 紫边(PURPLEEDGE), 逆光(BACKLIGHT), 朝天(SKYWARD)
│   ├── 14 类细分遮挡 (0x0400 系列)
│   ├── 3 类天气 (FOG/RAIN/SNOW)
│   └─ 融合公式: final_score = matrix_score (仅 CLIP 路径)
│
├── 场景切换保护 (is_drastic=1):
│   ├── 当 CLIP REID 队列检测到帧间特征余弦距离 > threshold
│   │   → is_drastic 标记为 true
│   ├── 触发时: 清空所有指标的 EMA 平滑状态
│   │   → 防止场景 A 的评分被场景 B 的评分错误平滑
│   │   → 下一个非 drastic 帧重新开始 EMA 积累
│   └─ 场景切换阈值: cosine_distance > 0.7 (70%差异)
│      或 drastic_score > 0.3 (即余弦相似度 < 0.7)
│
├── EMA 平滑 (smooth_type=2):
│   ├── score_smooth[i] = α × score_current[i] + (1-α) × score_prev[i]
│   ├── α: 按指标噪声特性自适应
│   │   ├── 统计指标(亮度/对比度): α 较大 (0.4-0.6)，统计值本身较稳定
│   │   ├── 深度学习指标(遮挡/变更): α 中等 (0.3-0.5)，模型输出有波动
│   │   └─ Matrix语义指标(天气/紫边): α 较小 (0.2-0.3)，CLIP特征变化较快
│   └─ 至少 2 帧才开始平滑 (integration_result_article18 frame_size=2)
│
└── 指标冲突解决:
    ├── 同一指标多源覆盖: 加权融合而非简单替换
    ├── 不同指标交叉告警:
    │   ├── 视频丢失(LOSS) → 跳过其他所有指标 (VQRS 应用层逻辑)
    │   ├── 场景变化(CHANGED) → is_drastic=true → 重置EMA
    │   └─ 高亮度(HIGHBRIGHT) → 替代频闪(STROBOSCOPIC) 判定
    └─ 无冲突指标: 独立阈值判定，不互影响
```

#### 2.7.4 CLIP 骨干的特征空间分析

CLIP ViT-L/14@336 的 3072 维特征向量是大模型诊断的核心数据结构。从配置中可以推断其内部编码方式：

```text
OCR_OX23 配置解读:
├── feature_size = 3072
│   └─ 不是标准 CLIP 的 768 或 1024 维
│   └─ 实现方式: 取 ViT-L 最后 4 层隐藏状态拼接 + 投影
│      ├── Layer 21: 1024 维 (自注意力输出)
│      ├── Layer 22: 1024 维
│      ├── Layer 23: 1024 维
│      ├── Layer 24: 1024 维 (最终层)
│      ├── Concat → 4096 维
│      └─ 投影头 → 3072 维 (减少冗余,保留关键质量语义)
│
├── custom_attr_label = 205
│   └─ CLIP 特征与 205 个预定义语义原型的相似度分布
│   └─ 这些语义原型覆盖了 VQA 场景中所有可能的质量异常概念:
│      ├── 正常场景类: "正常监控画面"、"白天室外"、"夜间室内"...
│      ├── 亮度类: "过曝画面"、"欠曝画面"、"全黑画面"...
│      ├── 色彩类: "偏红画面"、"偏绿画面"、"黑白画面"...
│      ├── 清晰度类: "模糊画面"、"清晰画面"、"镜头模糊"...
│      ├── 遮挡类: "树叶遮挡"、"人为遮挡"、"脏镜头"...
│      ├── 天气类: "雾天画面"、"雨天画面"、"雪天画面"...
│      └─ ... 共 205 个语义概念
│
├── REID 记忆队列 (mem_que.type = REID)
│   ├── 滑动窗口存储历史帧的 3072 维特征
│   ├── 队列长度: 与 async_depth=25 一致，存储 25 帧特征
│   │   └─ 25帧 × 3072维 × 2字节(FP16) = 153,600 字节 ≈ 150KB
│   ├── 每帧计算: cosine_similarity(feat[n], feat[n-1])
│   │   └─ 相似度高 → 场景稳定 → 启用 EMA 平滑
│   │   └─ 相似度低 → is_drastic=true → 场景切换 → 重置EMA
│   └─ feature_version = 0 → 特征版本标识，用于底库匹配兼容性校验
│
└── dataloader_type = COMMON
    └─ 通用图像数据加载器，执行预处理（缩放+归一化+格式转换）
    └─ 与 iqa28 的 DataloaderTD 不同，COMMON 支持 NPU 上的 DVPP 加速预处理
```

#### 2.7.5 权重矩阵的指标解码机制

```text
OCR_OX24 配置解读:
├── dataloader_type = FEATINPUT
│   └─ 输入不是图像而是特征向量 → 直接接收 OCR_OX23 的 3072 维输出
│   └─ 无需图像预处理，纯向量运算
│
├── mem_que.type = OCMULTIATTR
│   ├── max_obj_num = 20 → 每帧最多输出 20 个检测目标
│   │   └─ VQA 场景通常只有 1 个"整帧"目标（无局部检测框）
│   │   └─ max_obj_num=20 是为多摄像头帧混合场景预留
│   ├── attr_num = 200 → 200 个属性槽
│   │   └─ 当前激活 31 个（indicator_map 长度）
│   │   └─ 预留 169 个 → 新增指标只需增加 indicator_map 条目
│   │   └─ 权重矩阵物理存储: (200, 3072) FP16 = 200×3072×2 = 1,228,800 字节
│   │   └─ 但 nnx 文件只有 190KB → 实际只存储了当前激活的 31 行
│   │      或使用了稀疏存储/量化压缩
│
├── biz[0]: IQA 类型
│   ├── indicator_map = [31 个指标 ID]
│   └─ 每个 ID 对应权重矩阵的一行: W[i] × X + b[i] → score[i]
│   └─ 指标 ID 不连续排列（按类别分段而非顺序递增）
│   │   └─ 权重矩阵内部按 indicator_map 的顺序排列
│   │      行 0 → indicator_map[0] = 264 (NOISE)
│   │      行 1 → indicator_map[1] = 265 (STRIPE)
│   │      ...
│   │      行 30 → indicator_map[30] = 1028 (TRUNKCOVERED)
│
├── biz[1]: SERVICETYPE
│   └─ service_type = 66 → 场景分类输出
│   └─ 输出当前帧属于哪类场景（室内/室外/道路/夜间等）
│   └─ 作用: 为 OCR_FUNC25 的 smooth_type 和 is_drastic 提供场景上下文
│   └─ 不同场景类型的指标基线不同:
│   │   ├── 室外白天: 亮度/对比度基线较高
│   │   ├── 夜间: 低亮度基线较低
│   │   └─ 道路: 遮挡类指标更敏感
│
└── 187KB 模型体积 vs 理论体积:
    ├── 理论: 31 行 × 3072 列 × 2 字节(FP16) = 190,464 字节 ≈ 186KB
    ├── 实际: 190,682 字节 ≈ 187KB
    └─ 差值 4KB → 偏置向量 b (31 × 4 字节 FP32 = 124 字节) + nnx 元信息
    └─ 精确吻合单层线性映射: Score = sigmoid(W × Feature + b)
```

#### 2.7.6 自定义告警与文搜图闭环

`DealCustomAlarmTextSearch` 函数揭示了 BigVQA 和 TSA 子系统的深层交互：

```text
触发条件:
  stVideoProfile.vecCustomAlarmList.size() > 0
  └─ 用户在诊断方案中配置了自定义告警列表
  └─ 每个自定义告警包含: strAlarmName(告警名称/搜索文本), nAlarmThreshold(阈值)

执行流程:
  1. ExtractAndDispatchImageFeature:
     └─ BigVqa 诊断完成后，用同一帧图像调用 TsFeature Pipeline
     └─ 提取 6144 维 GME 特征 (dhivs_scene_feature_info_t)
     └─ 同时将特征异步入库到 TextSearchManager (特征库 dbId=1)

  2. DealCustomAlarmTextSearch:
     ┌─ 获取 TSInference 算法句柄 (ALG_TYPE_TS_INFERENCE)
     ├─ 获取 QBIC 算法句柄 (ALG_TYPE_QBIC)
     ├─ 创建临时特征底库 (dbId = routID + 9000000)
     │   └─ 临时底库避免与永久特征库(dbId=1)冲突
     ├─ 插入当前帧图像特征到临时底库
     │   └─ InsertFeature(dbId, imageId=routID, feature, featureSize)
     │
     ├─ 逐个处理自定义告警:
     │   ├── stVideoRoutingInfo.strPrompt = customAlarm.strAlarmName
     │   │   └─ 如 "路口交通事故"、"人群聚集"
     │   ├── HandleAlgorithmAnalyseRules:
     │   │   └─ 注册 QBIC 临时底库句柄 + 相似度阈值
     │   ├── HandleAlgorithmAnalyse (TsInference Pipeline 2):
     │   │   └─ 文本 → GME-Qwen2-VL-2B 编码 → 6144维
     │   │   └─ general_fm76 QBIC 比对 → TopK 结果
     │   │   └─ 比对结果中 score = vecMatchItems[0].nSimilarity
     │   └─ 告警判定: score >= nAlarmThreshold → 触发告警
     │
     └─ 销毁临时底库 (DestroyFeatureDb)

  3. 告警结果纳入诊断消息:
     └─ DealVideoQualityAnalyzeResult 增加自定义告警项
     └─ strItemType = customAlarm.strAlarmName (用户自定义名称)
     └─ 与标准 28+ 诊断项并列上报到 RabbitMQ
```

这个闭环的核心价值：传统 VQA 只能检测预定义的异常类型（模糊/遮挡/偏色等），自定义告警利用 GME-Qwen2-VL-2B 的开放语义理解能力，用户可以自定义任何异常描述（如"路面有大坑"、"消防通道被堵塞"），系统自动判断当前画面是否匹配——这是 CLIP/VLM 大模型在 VQA 场景中最具创新性的应用。

| 紫边(PURPLEEDGE)      |             |                |                |                |                |                |      ✓       |       Matrix独占        |
| 保护膜(LENSFILM)      |             |                |                |                |                |                |      ✓       |       Matrix独占        |
| 逆光(BACKLIGHT)       |             |                |                |                |                |                |      ✓       |       Matrix独占        |
| 镜头脏污(CAMERADIRTY) |             |                |                |                |                |       ✓        |      ✓       |        双源加权         |
| 视频剧变(DRASTIC)     |             |                |                |                |                |                |              |  CLIP REID is_drastic   |
| 朝天(SKYWARD)         |             |                |                |                |                |                |      ✓       |       Matrix独占        |
| 14类细分遮挡          |             |                |                |                |                |    ✓(通用)     |  ✓(细分类)   | od_trunk通用+Matrix细分 |
| 3类天气               |             |                |                |                |                |                |      ✓       |       Matrix独占        |
| 自定义告警            |             |                |                |                |                |                | GME(6144维)  |       文搜图比对        |

**矩阵总结**：

- **传统独占指标**（6个）：高亮度、低亮度、低对比度、冻结、黑屏、清晰度传统路径——像素统计无法被 CLIP 替代
- **nnx独占指标**（4个）：黑白、偏色、抖动+云台——专用轻量网络在这些指标上比 CLIP 更精确
- **Matrix独占指标**（8个）：纯色屏、蜘蛛网、固定遮挡、紫边、保护膜、逆光、朝天、3类天气——CLIP 语义理解的优势区域
- **双源加权**（6个）：噪声、条纹、视频丢失、遮挡、雪花、码流、镜头脏污——传统+CLIP 交叉验证提高准确率
- **CLIP REID独占**（1个）：视频剧变——仅靠帧间特征距离判定，无传统算法对应

### 2.8 dhnnx 推理引擎

dhnnx 是大华自研的 NN 推理引擎框架，是 BigVQA 和 TSA 算法库的底层推理调度核心。它承担模型加载、Pipeline 编排、NPU 调度、结果聚合四层职责，作用类似于 ONNX Runtime + TensorRT，但专门为 Ascend NPU 和自研 DHPIPE 架构深度定制。

#### 2.8.1 VDS 接口层架构

BigVQA 和 TSA 使用 VDS（Video Data Struct）接口而非传统 VQA 接口。VDS 是大华算法 SDK 的统一视觉检测接口层，通过 `dhivs_vds.h` 暴露给应用层。

```text
VQRS 应用层                          VDS 接口层                   dhnnx 推理引擎
─────────────────                ──────────────────           ──────────────────

DHIVS_VDS_GetCap()      →       查询能力集                     ← 返回 scene/func 支持列表
  ├── scene_mask                       ├── DHIVS_VDS_SCENE_DEFAULT (BigVQA诊断)
  ├── batch_size                       ├── DHIVS_VDS_SCENE_FEATURE (特征提取)
  └── input_pic_type                   └── DHIVS_VDS_SCENE_CUSTOM_1 (推理比对)

DHIVS_VDS_CreateHandle() →         创建 VDS 句柄                 ← 加载 graph.proto
  ├── scene_mask 决定使用哪条 Pipeline                           ← 解析算子拓扑
  ├── pcfg_file = graph.proto 路径                               ← 分配 NPU 共享缓冲区
  └── func_mask 决定启用哪些功能                                  ← 创建算子实例

common_interface.UpdateAlgorithmInfo() (动态配置)
  ├── type=INIT → 初始化算法信息 (buffer_frames)
  ├── type=SET_VQA_FUNC_ENABLE → 使能诊断项
  ├── type=SET_VQA_FUNC_PARAM → 设置背景图
  ├── type=QBIC_ALGHANDLE → 注册QBIC句柄
  ├── type=OBJ_COMPARE_CFG_INFO → 比对过滤配置
  ├── type=ACTIVE_DB → 活跃底库选择
  └── ... 100+ 种配置类型 (0x2000~0x20C4)

ProcessImageMulti() (核心推理入口)
  ├── 同步模式: 传入 pResult 指针，等推理完成再返回
  ├── 异步模式: pResult=NULL，通过 RegProcessDoneCallBack 回调
  │   ├── GetResults/GetResultsV2 → 取得推理结果
  │   └── ReleaseResults → 释放结果内存
  └── 内部流程:
      ├── VDS 将 dhivs_pic_v2_t 转交给 dhnnx
      ├── dhnnx 按 graph.proto 编排执行各算子
      ├── 各算子结果汇聚到 dhivs_detect_result_t
      └── 结果返回给 VDS → 返回给 VQRS 应用层

DestroyHandle() → 销毁句柄，释放 NPU 资源
```

**Scene mask 的 Pipeline 选择机制**：

```text
scene_mask 是一个位标志 (bitmask)，决定使用 graph.proto 中的哪条 Pipeline:

  BigVQA (方法一: 统一句柄):
  ├── 通过 DHIVS_VDS_CreateHandle 创建句柄时指定默认 scene
  ├── graph.proto 解析后选择对应 scene 的算子拓扑
  └── 整条 Pipeline 7路并行+融合 → 输出 28+ 诊断项

  TSA (方法二: 两个句柄共用同一 SDK):
  ├── DHIVS_VDS_SCENE_FEATURE (0x1000): image → 6144维嵌入
  │   └─ 对应 graph.proto 第一条 Pipeline (OX78 → result79)
  │
  ├── DHIVS_VDS_SCENE_CUSTOM_1 (0x100000): text → 嵌入 → QBIC比对
  │   └─ 对应 graph.proto 第二条 Pipeline (OX75 → fm76 → FUNC80 → result62)
  │
  └── 两种 scene 共享同一 .so 和 graph.proto，
      只是创建句柄时指定不同场景标志位，
      dhnnx 内部根据 scene_mask 选择相应的子图执行

  关键: scene_mask 的值决定了 graph.proto 中的 business_op_type 匹配
  ├── integration_result_feature ← scene=FEATURE
  └─ integration_result_custom_1 ← scene=CUSTOM_1
```

#### 2.8.2 graph.proto 流水线编排机制

graph.proto 是 dhnnx 推理引擎的流水线描述文件（JSON 格式），定义算子拓扑、数据流连接和调度参数。

**graph 结构顶层**：

```text
graph.proto 顶层结构:
{
  "graph": [
    {
      "graph_name": "integration_result_article",  // BigVQA 单条 Pipeline
      "async_depth": 25,           // 异步流水线深度（最多25帧在流水线中）
      "max_camera_count": 10,      // 最多10路摄像头共享
      "business_op_info": { ... }, // 业务算子信息（入口算子）
      "node": [ ... ],             // 算子节点列表（10个节点）
      "input_stream": [ ... ],     // 输入数据流名
      "output_stream": [ ... ]     // 输出数据流名
    },
    ...  // TSA 有两张 graph
  ],
  "model": [ ... ]                 // 模型文件目录索引
}
```

**Node 算子节点的调度参数**：

```text
每个 node 描述一个算子:

{
  "calculator": "CustomizeOp",        // 计算器类型（固定为 CustomizeOp）
  "name": "OCR_OX23",                  // 算子名（节点ID）
  "input_stream": [ ... ],             // 输入数据流名列表
  "output_stream": [ ... ],            // 输出数据流名列表

  "operator_options": {
    "api_name": "dhpipe::Get_OCR_OC_OperatorTable",
    // API 名称: dhnnx 通过此符号 dlopen 加载算子实现
    // dhpipe::Get_*_OperatorTable → 返回算子的函数表
    "type": "DHPIPE_VQA_ALG_TYPE_VQA_Backbone",
    // 算子类型: 对应 model_info.json 中的 model_dir，
    // dhnnx 用此类型名查找对应的模型文件
    "op_category": "oc",
    // 算子类别: oc / vqa / func_ocr / integration_op_*
    // 决定调度优先级和资源分配策略
    "op_conf_file": "OCR_OX23_default.conf",
    "op_conf_path": "../model/DHPIPE_VQA_ALG_TYPE_VQA_Backbone",
    // 算子配置文件路径：
    // 每个算子独立的配置文件，包含模型参数、特征向量维度等
    "input_name": [ "integration_io_article.frame" ],
    // 输入端口名，与 input_stream 一一对应
    "output_name": [ "OCR_OX_23.oc_out" ],
    // 输出端口名，与 output_stream 一一对应
    "instance_cnt": 1,
    // 算子实例数 = 1（每个算子只有一个实例在流水线中）
    "support_multicam": false
    // 是否支持多摄像头帧混合
    // CLIP骨干 support_multicam=false → 一次只处理一帧
    // result聚合算子 support_multicam=true → 可处理多路结果
  }
}
```

**数据流连接与调度**：

```text
BigVQA Pipeline 的数据流拓扑:

输入帧
  ↓ (integration_io_article16 分发到7条流)
  ├── iqa28_tra: 传统算法(FROZEN/BRIGHT/CONTRAST/CLARITY)
  ├── iqa36_cov: od_trunk 遮挡检测  ← 原始分辨率
  ├── iqa31_bw: blackwhite nnx     ← 缩放到模型输入尺寸
  ├── iqa32_color: color nnx       ← 缩放到模型输入尺寸
  ├── iqa33_chg: changed nnx       ← 需要背景图
  ├── iqa34_jpt: BiGeoNet          ← 需要帧序列缓存
  └── OX23: CLIP Backbone          ← 336×336, 610MB

  7 路并行 → 但 NPU 是时分复用，实际串行执行

  OX23 输出 → OX24 (权重矩阵) → 31 个指标分数

  ┌────────────────────────────────────────────┐
  │ OCR_FUNC25 同步汇聚点                       │
  │ input_stream_sync_policy = "sync_set"      │
  │ 必须等待所有 7 路输入齐全才能执行融合        │
  │ 7路输入: iqa28/f36/f31/f32/f33/f34 + OX24  │
  └────────────────────────────────────────────┘
      ↓
  integration_result_article18 (frame_size=2)
      ↓
  dhivs_detect_result_t (含 custom_result + detect_result)
```

**Sync set 同步机制**：

```text
graph.proto 中 OCR_FUNC25 的同步策略:
"input_stream_handler": {
  "input_stream_sync_policy": "sync_set"
}

sync_set 的含义:
  ├── 当 7 路输入中有任意一路到达新数据 → 暂存在同步缓冲区
  ├── 等待所有 7 路的新数据都到达 → 匹配一套"完整数据帧集"
  ├── 将完整的 7 路数据同时喂给 OCR_FUNC25
  └─ 如果没有 sync_set:
     └─ OCR_FUNC25 每收到一路数据就执行一次 → 会输出 7 次不完整结果

  匹配规则:
  ├── 每路数据携带 frame_index 或 timestamp
  ├── sync_set 按 frame_index 做关联
  ├── iqa28 的第 5 帧 + iqa36 的第 5 帧 + OX24 的第 5 帧 → 一组
  └── 如果某路丢了一帧，sync_set 等待超时后会跳过等待

  为什么需要 frame_size=2?
  ├── 单帧融合: OCR_FUNC25 融合 7 路输出的单帧结果
  ├── 两帧聚合: integration_result_article18 再做一次跨帧 EMA
  └── 两帧 EMA 后输出最终分数 → 消除单帧噪声
```

**async_depth 流水线深度**：

```text
async_depth = 25 的含义:
  ├── 最多允许 25 帧同时在流水线中（从 ProcessImageMulti 到结果返回）
  ├── 不是 25 帧并行推理，而是 25 帧的输入已进入 pipeline 等待排序
  │
  ├── 帧进入流程:
  │   ├── Frame N → ProcessImageMulti → dhnnx 入队 (pending)
  │   ├── Frame N+1 → ProcessImageMulti → dhnnx 入队 (pending)
  │   ├── ...
  │   ├── dhnnx 内部线程逐个出队执行: Frame N → 7路算子 → sync_set → 融合 → 输出
  │   └── Frame N 输出后 → Frame N+1 开始执行
  │
  ├── 当队列积压到 25 帧 → ProcessImageMulti 阻塞等待
  │   └─ 生产者(解码)速度 > 消费者(NPU推理)速度时的背压保护
  │
  └── max_camera_count=10: 10 个摄像头共享 25 帧深度
      每个摄像头平均 2.5 帧在 pipeline 中
```

#### 2.8.3 整体推理链路

```text
输入帧 (NV12, ACL物理地址)
  │
  ├── VQRS应用层预处理 (CAlgorithmBigVqa)
  │   ├── I420 → NV12 (CPicConvert::Yuv420pToNv12)
  │   ├── aclrtMallocHost → 主机侧虚拟内存
  │   ├── memcpy → NV12数据拷入主机内存
  │   ├── aclrtMalloc → 设备侧物理内存
  │   └─ aclrtMemcpy(HOST_TO_DEVICE) → 主机→设备同步
  │
  ├── dhnnx 层 (模型加载 + 前处理 + 后处理)
  │   ├── 解析 .nnx 模型文件 (格式版本 1.2.0)
  │   ├── 加载模型权重到 NPU 共享缓冲区 (91MB)
  │   ├── 执行 DVPP 前处理 (缩放/格式转换/归一化)
  │   ├── 调用 DaVinci 执行 NPU 推理
  │   └─ 后处理 (特征提取/阈值判定/KNN分类)
  │
  ├── DaVinci NPU 层 (推理调度)
  │   ├── 接收 dhnnx 下发的推理请求
  │   ├── 输入数据已在 Device侧 (VQRS已搬运)
  │   ├── NPU 执行模型推理 (sun002 DaVinci引擎)
  │   ├── 输出结果在 NPU 共享缓冲区内流转 (无需Host↔Device往返)
  │   └─ 最终结果拷贝回 Host侧
  │
  └── 流水线内部数据流转
      ├── CLIP骨干输出3072维特征 → 直接在NPU缓冲区内传递给矩阵映射
      ├── 矩阵映射输出31个分数 → 在NPU缓冲区内传递给FUNC25
      ├── 传统算法在CPU执行 → 结果写入共享结构体
      ├── 小模型NNX推理结果 → 后处理后写入MemQueueVQAIQA
      └─ FUNC25汇聚全部结果 → 封装为dhivs_detect_result_t
```

与小模型诊断的关键区别：VQRS 应用层负责 ACL 内存搬运（Host→Device），图像数据在进入 dhnnx 之前就已经在 Device 侧了。dhnnx 内部的 NPU 推理、特征传递都在 91MB 共享缓冲区内完成，不需要反复 Host↔Device 拷贝。CLIP 骨干→权重矩阵的特征传递也在 NPU 内完成，避免了 3072 维特征向量跨总线搬运的延迟。

##### 2.8.4.1 CLIP 视觉-语言预训练原理

CLIP（Contrastive Language-Image Pre-training）是 OpenAI 2021 年发布的视觉-语言预训练模型，核心创新是**通过对比学习让图像和文本编码到同一特征空间**。

**训练过程**：

```text
CLIP 训练数据: 4 亿对 (图像, 文本描述) 从互联网自动收集

训练目标: 让匹配的图文对特征相近，不匹配的图文对特征远离

每次训练迭代:

Step 1: 编码
  ├── 图像编码器 (ViT) → 图像特征 I₁, I₂, ..., Iₙ (每张图 768/1024 维)
  └─ 文本编码器 (Transformer) → 文本特征 T₁, T₂, ..., Tₙ (每段文本同维)

Step 2: 归一化
  └─ I_i = I_i / ||I_i||₂  (L2 归一化，投影到单位超球面)
  └─ T_j = T_j / ||T_j||₂

Step 3: 对比损失计算
  ├── 正样本: (I₁,T₁), (I₂,T₂), ... → 应该距离近
  ├── 负样本: (I₁,T₂), (I₁,T₃), ... → 应该距离远
  └─ 余弦相似度矩阵 S[i,j] = I_i · T_j  (归一化后内积 = 余弦相似度)

  对于图像 I_i:
  ├── 正确文本是 T_i → 目标: S[i,i] 最大
  ├── 其他文本是负样本 → 目标: S[i,j≠i] 最小
  └─ 损失 = CrossEntropy(S[i,:], label=i)
     └─ 即：让 S[i,i] 的 softmax 概率趋近 1，S[i,j≠i] 的概率趋近 0

  同理对文本 T_i:
  └─ 损失 = CrossEntropy(S[:,i], label=i)

  总损失 = (图像侧损失 + 文本侧损失) / 2

训练效果:
  ├── 4 亿对训练后，ViT 和文本 Transformer 输出的特征向量在同一空间
  ├── cosine_similarity(I("一只猫的图片"), T("a photo of a cat")) ≈ 0.9
  ├── cosine_similarity(I("一只猫的图片"), T("a photo of a dog")) ≈ 0.3
  └─ 这意味着 ViT 特征向量天然携带了语义信息——
     不是单纯编码视觉纹理，而是编码了"这张图是什么"的语义理解
```

**为什么 CLIP 预训练对 VQA 有根本性意义？**

```text
传统 CNN (小模型诊断):
  ├── 训练目标: 分类（偏色/黑白/遮挡...）→ 只学会这些特定类别
  ├── 特征空间: 只在训练类别上可区分
  ├── 遇到新异常: 无法理解（没有训练过"路面有大坑"）
  └─ 零样本能力: 无

CLIP ViT (大模型诊断):
  ├── 训练目标: 图文对齐（4亿对）→ 学会所有视觉语义概念
  ├── 特征空间: 在整个视觉语义空间上可区分
  ├── 遇到新异常: 能理解（CLIP 见过"雾天"的图文描述）
  └─ 零样本能力: 有（用文本 prompt 即可判断，无需额外训练）

关键区别:
  CNN 特征编码的是 "这张图看起来像什么纹理/颜色模式"
  CLIP 特征编码的是 "这张图在语义上是什么内容/场景"

  → CNN 可以区分"偏红 vs 正常"（因为训练过偏红样本）
  → CLIP 可以区分"雾天 vs 正常"（即使没训练过雾天 VQA 样本，
    因为 CLIP 已经在 4 亿图文对中学会了"雾天"的语义概念）
  → 这就是为什么 Matrix 能产出天气类/遮挡细分类等传统算法无法覆盖的指标
```

##### 2.8.4.2 Vision Transformer (ViT) 内部工作原理

ViT 将 Transformer 架构（原本用于自然语言处理）应用于图像理解。核心思想：**把图像切成小块（patch），每个 patch 当作一个"词"，用 Transformer 处理这些"词"的序列**。

**Step 1: Patch Embedding — 图像切分与嵌入**

```text
输入: 336×336×3 RGB 图像
patch_size = 14 (每个 patch 是 14×14 像素)

切分过程:
  336 / 14 = 24 → 横向 24 个 patch
  336 / 14 = 24 → 纵向 24 个 patch
  总共: 24 × 24 = 576 个 patch

每个 patch 包含:
  14 × 14 × 3 = 588 个像素值 (14宽 × 14高 × RGB 3通道)

线性投影:
  588 维像素向量 → 线性层 (矩阵乘法) → 1024 维嵌入向量

  数学: E_patch = W_proj × Flatten(patch) + b_proj
  ├── W_proj: (1024, 588) 的投影矩阵
  ├── b_proj: (1024,) 的偏置向量
  └─ 每个 patch 独立投影，权重矩阵 W_proj 共享（类似 CNN 的卷积核共享）

类比理解:
  ├── CNN 卷积核: 3×3×3=27 维 → 卷积输出 1 个像素 → 逐位置滑动
  ├── ViT patch 投影: 14×14×3=588 维 → 线性输出 1024 维 → 逐 patch 投影
  └─ 两者都是"局部区域 → 线性变换 → 输出特征"，只是粒度不同
     CNN 粒度细(3×3)，ViT 粒度粗(14×14)

576 个 patch 嵌入向量: [P₁, P₂, ..., P₅₇₆]  每个都是 1024 维
```

**CLS Token — 全局信息的锚点**

```text
额外添加一个特殊的 CLS (Class) token:

  CLS = 随机初始化的 1024 维向量 (训练时学习)

  输入序列变为: [CLS, P₁, P₂, ..., P₇₇₆]  共 577 个 token

  CLS token 的作用:
  ├── 它不对应任何具体的 patch，而是"全局分类信息"的载体
  ├── 在 24 层 Transformer 中，CLS 通过自注意力与所有 patch 交互
  │   └─ 逐渐"吸收"全局信息: "整张图的整体语义是什么?"
  └─ 最终 CLS token 的输出就是整张图的表示向量
     └─ 标准 CLIP 只取 CLS 输出作为图像特征
     └─ VQRS 的 BigVQA 实现额外取了最后 4 层隐藏状态（见下文）
```

**Position Embedding — 空间位置编码**

```text
Transformer 本身不知道 patch 的空间位置（它把序列当"词"处理，不分左右上下）
必须额外注入位置信息:

  Position Embedding = 577 个 1024 维向量 (1个CLS + 576个patch)
  ├── 每个 patch 位置有一个唯一的位置向量
  ├── 训练时学习（不是固定的 sinusoidal 编码）
  └─ 加到对应的 patch 嵌入上: token_i = P_i + Pos_i

  为什么需要位置编码?
  ├── 没有 Pos: patch(左上角天空) 和 patch(右下角地面) 被同等对待
  │   └─ Transformer 无法区分"天空在上面"和"地面在下面"
  ├── 有 Pos: Transformer 知道每个 patch 在图像中的空间位置
  │   └─ 可以学会"天空通常在上面"、"道路通常在中间"等空间规律
  └─ 这对 VQA 很重要:
     ├── 遮挡物位置: 树叶通常在上方，墙壁通常在侧面
     ├── 画面朝向: 朝天画面中地面/天空比例反转
     └─ 纯纹理分析无法捕获这些空间信息
```

**Step 2: Transformer Encoder — 自注意力机制**

ViT-L/14 包含 24 层 Transformer Encoder，每层核心组件是**多头自注意力 (Multi-Head Self-Attention)**。

```text
自注意力机制的核心问题:
  "对于当前 patch，其他哪些 patch 与它相关？应该关注多少？"

数学推导 (单头注意力):

Step 2a: 线性投影生成 Q, K, V
  ├── Q (Query) = X × W_Q    ← "我在找什么信息？"
  ├── K (Key)   = X × W_K    ← "我有什么信息可以提供？"
  └─ V (Value) = X × W_V    ← "我的实际信息内容是什么？"

  X: 577×1024 的输入矩阵 (577 个 token, 每个 1024 维)
  W_Q, W_K, W_V: 1024×1024 的投影矩阵 (训练时学习)

Step 2b: 计算注意力权重
  Attention_score = Q × Kᵀ / √d_k

  ├── Q × Kᵀ: 577×577 的矩阵
  │   └─ score[i,j] = Q_i · K_j = token_i 对 token_j 的关注程度
  │   └─ score[i,j] 越大 → token_i 越关注 token_j
  │
  └─ / √d_k: 缩放因子 (d_k = 1024)
     └─ 防止点积值过大导致 softmax 梯度消失
     └─ 数学证明: 当 d_k 大时，Q·K 的方差 = d_k，缩放后方差 = 1

Step 2c: Softmax 归一化
  Attention_weight = softmax(Attention_score)

  ├── weight[i,j] = exp(score[i,j]) / Σ_k exp(score[i,k])
  └─ 每个 token_i 对所有 token 的注意力权重总和 = 1
  └─ 权重分布: 高关注 → 权重接近 1，低关注 → 权重接近 0

Step 2d: 加权聚合
  Output = Attention_weight × V

  ├── output[i] = Σ_j weight[i,j] × V_j
  └─ token_i 的输出 = 它关注的所有 token 的信息加权和
  └─ 高权重的 token 贡献更多信息，低权重的 token 贡献较少

示例: patch_i = "画面左上角的天空区域"
  ├── 对 patch_j = "画面右上角的天空区域" → 高权重 (同类型区域)
  ├── 对 patch_k = "画面中间的建筑物" → 中权重 (相邻区域)
  ├── 对 patch_l = "画面底部的道路" → 低权重 (距离远、语义不同)
  └─ output_i ≈ 0.8×天空特征 + 0.15×建筑特征 + 0.05×道路特征
     └─ 融合了全局上下文，不再是孤立的局部信息
```

**多头注意力 (Multi-Head Attention)**：

```text
ViT-L/14 使用 12 个注意力头 (num_heads = 12)

为什么要多头?
  ├── 单头注意力: 只能学一种"关注模式"
  │   └─ 可能只学会"关注相同颜色区域"
  ├── 多头注意力: 每个头独立学一种"关注模式"
  │   ├── Head 1: 学会关注"色彩相似区域" → 对偏色检测有用
  │   ├── Head 2: 学会关注"纹理相似区域" → 对遮挡检测有用
  │   ├── Head 3: 学会关注"空间相邻区域" → 对边界检测有用
  │   ├── Head 4: 学会关注"全局语义一致区域" → 对场景分类有用
  │   ├── ...
  │   └─ 12 个头从 12 个不同角度理解图像

数学实现:
  ├── 每个头使用独立的 W_Q^h, W_K^h, W_V^h (维度: 1024×(1024/12=85.3))
  │   └─ 实际实现中 d_k = hidden_dim / num_heads = 1024 / 12 ≈ 85
  ├── 12 个头并行计算注意力 → 12 个输出向量 (每个 85 维)
  ├── Concat → 12 × 85 = 1020 维 ≈ 1024 维 (加上投影)
  └─ 最终线性投影 → 1024 维 (回到原始 hidden_dim)

  MultiHead_Output = Concat(Head₁, Head₂, ..., Head₁₂) × W_O
  W_O: (1024, 1024) 的输出投影矩阵
```

**Step 3: MLP 层 — 非线性特征变换**

```text
每层 Transformer 在自注意力之后还有 MLP (多层感知机):

  MLP 结构:
  ├── Linear(1024 → 4096)  ← 扩展: 将特征从 1024 维映射到 4096 维
  ├── GELU 激活            ← 非线性: 平滑的 ReLU 变体
  │   └─ GELU(x) = x × Φ(x)  (Φ 是标准正态分布的累积分布函数)
  │   └─ 比 ReLU 更平滑，在 x≈0 时不硬截断
  └─ Linear(4096 → 1024)  ← 压缩: 将特征从 4096 维映射回 1024 维

  MLP 的作用:
  ├── 自注意力层: 混合不同 token 的信息 (信息交互)
  ├── MLP 层: 对每个 token 独立做非线性变换 (特征加工)
  │   └─ 扩展到 4096 维 → 在高维空间做复杂非线性组合
  │   └─ 压缩回 1024 维 → 提取最关键的信息
  └─ 两层交替: 注意力 → MLP → 注意力 → MLP → ...

  每层完整流程:
  x_out = x + MultiHeadAttention(LayerNorm(x))    ← 残差连接 + LayerNorm
  x_out = x_out + MLP(LayerNorm(x_out))            ← 残差连接 + LayerNorm

  残差连接 (x + ...):
  └─ 保留原始信息，只叠加"增量信息"
  └─ 防止 24 层深层网络的信息丢失 (梯度消失)

  LayerNorm:
  └─ 对每个 token 的 1024 维特征做归一化
  └─ 稳定训练过程，防止特征值过大或过小
```

**Step 4: 24 层堆叠 — 深层语义理解**

```text
24 层 Transformer 的逐层理解能力:

Layer 1-4 (浅层): 局部纹理与边缘
  ├── patch 级注意力: 每个 patch 主要关注邻近 patch
  ├── 学会识别: 局部边缘、颜色梯度、小纹理模式
  └─ 类似 CNN 的浅层卷积核

Layer 5-12 (中层): 区域级语义
  ├── 注意力范围扩大: patch 开始关注远距离 patch
  ├── 学会识别: "天空区域"、"建筑物区域"、"道路区域"
  └─ 类似 CNN 的中层特征图

Layer 13-20 (深层): 全局语义组合
  ├── 注意力几乎全局: CLS token 与所有 patch 强关联
  ├── 学会识别: "室外白天场景"、"雨天场景"、"有人遮挡"
  └─ 类似 CNN 的深层特征图，但比 CNN 更灵活（注意力权重自适应）

Layer 21-24 (最终层): VQA 专用质量语义
  ├── 微调后的最终层编码了 VQA 特有的质量信息
  ├── 学会识别: "偏色画面"、"模糊画面"、"镜头脏污"
  ├── 这些是 CLIP 预训练时不会关注的细节
  │   └─ CLIP 预训练关注"猫 vs 狗"这种语义类别
  │   └─ VQA 微调让最终层转向关注"正常 vs 异常"的质量语义
  └─ 最终 4 层隐藏状态是最丰富的质量特征来源
```

##### 2.8.4.3 VQRS BigVQA 的 CLIP 特征提取策略

**标准 CLIP vs VQRS BigVQA 的关键差异**：

```text
标准 OpenAI CLIP ViT-L/14:
  ├── 输出: CLS token → 768 维 (投影到 text embedding 维度)
  ├── 用途: 图文检索（图像特征与文本特征比对）
  ├── 768 维已足够区分 "猫 vs 狗 vs 汽车" 等宏观语义类别

VQRS BigVQA 的实现:
  ├── 输出: 3072 维 (远大于标准 CLIP 的 768 维)
  ├── 用途: VQA 诊断（需要区分 "轻微偏色 vs 严重偏色 vs 正常" 等细微质量差异）
  ├── 3072 维包含更多信息: 多层隐藏状态 + 投影头

  为什么需要 3072 维而非 768 维?
  ├── 768 维: 足以区分宏观语义 ("这是猫" vs "这是狗")
  ├── VQA 需要: 区分细微质量差异 ("轻微模糊" vs "正常清晰")
  │   └─ 这类差异在 768 维空间中可能只占一个维度的微小偏移
  │   └─ 在 3072 维空间中有更多维度编码这些细微差异
  │   └─ 更高的特征维度 = 更细粒度的区分能力
  │
  └─ 具体实现:
     ├── 取 Layer 21-24 的隐藏状态: 各 1024 维 → Concat → 4096 维
     ├── 为什么要取多层而非单层?
     │   ├── Layer 24 单层: 只编码最抽象的全局语义
     │   ├── Layer 21-24 拼接: 同时编码局部纹理(L21) + 区域语义(L22-23) + 全局质量(L24)
     │   └─ 拼接保留了不同层次的特征信息，避免只保留最抽象层
     └─ 投影头: 4096 → 3072 (Linear + L2 Norm)
        └─ 压缩掉冗余信息，保留关键质量语义
```

**3072 维特征的几何结构**

```text
3072 维特征在超球面上的分布 (L2 归一化后):

正常画面特征:
  └─ 位于超球面上的 "正常质量语义区域"
  └─ 多个正常画面特征聚集在一起 (聚类中心)

偏色画面特征:
  └─ 偏离 "正常区域"，移向 "偏色语义区域"
  └─ 偏色越严重 → 距正常区域越远
  └─ 偏红/偏绿/偏蓝各有不同的偏移方向

遮挡画面特征:
  └─ 偏离正常区域，移向 "遮挡语义区域"
  └─ 树叶遮挡 vs 人为遮挡 vs 脏镜头各有不同偏移方向

模糊画面特征:
  └─ 沿 "清晰度维度" 偏移
  └─ 模糊程度越大 → 偏移越远

权重矩阵的作用:
  └─ 3072 维空间中有 31 个 "指标方向"
  └─ 每个 "指标方向" 由权重矩阵的一行定义
  └─ Score[i] = sigmoid(W_row_i · Feature + b_i)
     ├── W_row_i · Feature: 计算特征在 "指标方向 i" 上的投影长度
     ├── 投影长度 > 0 → 特征偏向 "异常" 方向 → sigmoid 输出高分数
     └─ 投影长度 < 0 → 特征偏向 "正常" 方向 → sigmoid 输出低分数

  示例 (偏色指标):
  ├── W_row_偏色 = [0.1, -0.3, 0.8, 0.05, ...] (3072 维权重)
  ├── 正常画面 Feature = [0.02, 0.01, 0.98, ...] → W·F = 0.02×0.1 + 0.01×(-0.3) + 0.98×0.8 + ... ≈ 0.75
  │   └─ 0.75 < 偏色阈值 → sigmoid(0.75) ≈ 0.68 → 但阈值可能设为 0.8 → 未告警
  └─ 偏色画面 Feature = [0.45, 0.03, 0.70, ...] → W·F = 0.45×0.1 + 0.03×(-0.3) + 0.70×0.8 + ... ≈ 0.6
     └─ sigmoid(0.6) ≈ 0.65 → 同样未告警？不对...

  更准确的解释:
  └─ sigmoid(W·F + b) 中 b 是偏置，用于校准正常/异常的分数基线
  └─ 训练时: 正常画面 → score ≈ 0~30, 异常画面 → score ≈ 70~100
  └─ b 的作用: 让 sigmoid 的输入整体偏移，使正常画面落在低分段

  这就是为什么权重矩阵只需一行就能工作:
  └─ CLIP 微调后的特征空间已经将 "正常" 和 "异常" 分开
  └─ 权重矩阵只是在 3072 维空间中 "选择" 正确的区分方向
  └─ 不需要多层神经网络做复杂映射——线性映射就够了
```

##### 2.8.4.4 CLIP 在 VQA 中的微调策略

```text
CLIP 预训练 → VQA 微调 的两阶段训练:

阶段 1: CLIP 预训练 (OpenAI 完成，不在 VQRS)
  ├── 数据: 4 亿图文对
  ├── 目标: 图文对齐 (对比学习)
  ├── 产出: ViT-L/14 视觉编码器 (理解所有视觉语义)
  └─ 581MB 模型权重 (ViT-L 参数量约 304M)

阶段 2: VQA 微调 (大华完成，不在 VQRS 运行时)
  ├── 数据: VQA 标注数据 (正常/异常监控画面 + 标签)
  ├── 目标: 让 CLIP 特征空间从 "语义类别区分" 转向 "质量异常区分"
  │
  ├── 微调方式:
  │   ├── 方式 A: 端到端微调 ViT + 新增投影头
  │   │   ├── 保留 ViT 前 20 层冻结 (保持预训练语义能力)
  │   │   ├── 微调 Layer 21-24 (转向质量语义)
  │   │   └─ 新增投影头 (1024→3072 维) + 权重矩阵 (3072→31 指标)
  │   │   └─ 损失函数: 各指标的 sigmoid 分数与标注标签的交叉熵
  │   │
  │   └─ 方式 B: 两步微调
  │   │   ├── Step 2a: 微调 ViT (冻结文本侧，只调视觉侧)
  │   │   │   └─ 用 VQA 正常/异常标注做对比学习
  │   │   │   └─ 正常画面 → 特征靠近 "正常中心"
  │   │   │   └─ 异常画面 → 特征偏离 "正常中心"
  │   │   │
  │   │   └─ Step 2b: 训练权重矩阵
  │   │       └─ 用微调后 ViT 提取所有训练图像的 3072 维特征
  │   │       └─ 对每个指标做线性回归: score = sigmoid(W·F + b)
  │   │       └─ 简单的 Logistic Regression，几分钟即可训练完成
  │
  └─ 微调的精妙之处:
      ├── CLIP 预训练赋予 ViT "理解所有视觉概念"的能力
      ├── VQA 微调只是 "引导" ViT 关注质量异常方向
      │   └─ 不需要从头训练——预训练权重是强大的初始化
      └─ 权重矩阵训练极简——线性回归在微调后的特征空间中已足够

  这也是为什么 BigVQA 新增指标零成本:
  ├── 新增指标只需在 3072 维特征空间中 "选择" 一个新方向
  ├── 训练新的权重矩阵行: W_new × Feature → score_new
  ├── 几十张标注图像即可完成线性回归
  └─ ViT 骨干不需要重新微调——3072 维特征已包含所有信息
```

##### 2.8.4.5 CLIP vs 传统 CNN 的本质区别

```text
传统 CNN (小模型诊断):
├── 训练方式: 从头训练（随机初始化 → 在 VQA 标注数据上学习）
├── 特征空间: 只在训练类别上可区分
├── 学习内容: 只学到了训练数据中出现过的异常模式
├── 网络深度: 3-10 层 (MobileNet/ResNet-18 级别)
├── 输出维度: 128 维 (足够区分 2-5 个类别)
├── 泛化方式: KNN 聚类中心 (可增量扩展，但 CNN 骨干不更新)
└─ 计算方式: 卷积 (局部连接，位置固定)

CLIP ViT (大模型诊断):
├── 训练方式: 预训练(4亿图文对) → 微调(VQA标注)
├── 特征空间: 在整个视觉语义空间上可区分
├── 学习内容: 理解所有视觉语义概念 (通过预训练) + 关注质量异常 (通过微调)
├── 网络深度: 24 层 Transformer (远深于 CNN)
├── 输出维度: 3072 维 (远高于 CNN 的 128 维)
├── 泛化方式: 权重矩阵线性解码 (零成本新增指标)
└─ 计算方式: 自注意力 (全局连接，位置自适应)

核心区别表格:

| 维度 | CNN (小模型) | ViT (大模型) |
|------|-------------|-------------|
| 连接方式 | 局部(3×3卷积核) | 全局(自注意力连接所有patch) |
| 位置信息 | 卷积位置隐式编码 | 显式 position embedding |
| 特征粒度 | 固定层次(低→高逐层抽象) | 自适应(注意力权重动态决定) |
| 理解方式 | 看纹理→看模式→看类别 | 看局部→看全局→看语义 |
| 输出信息 | 128维(只编码训练类别差异) | 3072维(编码全部质量语义) |
| 可扩展性 | 新增类别需加KNN中心 | 新增指标只需加矩阵行 |
| 预训练 | 无(从头训练) | 4亿图文对CLIP预训练 |
| 零样本能力 | 无 | 有(文本prompt即可判断) |
| 模型体积 | 几KB~65MB | 581MB |
| 推理耗时 | <1ms(CNN浅) ~ 8ms(CNN深) | 10-15ms(ViT-L) |

自注意力的关键优势 (为什么 ViT 比 CNN 更适合 VQA):

1. 全局上下文理解
   ├── CNN: 每层只看 3×3 邻域，全局信息需要多层逐级传递
   │   └─ 24 层 CNN 才能让左上角像素影响右下角像素
   ├── ViT: 自注意力让每个 patch 直接关注任何其他 patch
   │   └─ 1 层自注意力就能让左上角天空 patch 直接关注右下角地面 patch
   └─ 对 VQA 的影响:
       ├── 判断"画面偏色"需要看整张图的色彩分布 → ViT 一层即可
       ├── 判断"树叶遮挡"需要看遮挡物的全局位置 → ViT 直接建模
       └─ CNN 需要多层累积才能获得同等全局理解

2. 自适应关注模式
   ├── CNN: 卷积核权重固定 → 对所有图像用同一组滤波器
   │   └─ 无法区分 "应该关注色彩" 还是 "应该关注纹理"
   ├── ViT: 注意力权重动态计算 → 每张图像有不同的关注模式
   │   ├── 正常画面: 注意力均匀分布 (关注整图)
   │   ├── 遮挡画面: 注意力集中在遮挡区域 (关注异常)
   │   ├── 偏色画面: 注意力集中在色彩通道 (关注色偏)
   └─ 对 VQA 的影响:
       ├── 不同异常类型 → ViT 自动调整关注重点
       └─ CNN 无法做到这种自适应

3. 多头注意力的多角度理解
   ├── CNN: 单一特征图 → 每层输出一组固定特征
   ├── ViT: 12 个注意力头 → 12 个不同的理解角度同时存在
   │   ├── Head 1: 关注色彩 (偏色检测依赖)
   │   ├── Head 2: 关注纹理 (遮挡检测依赖)
   │   ├── Head 3: 关注清晰度 (模糊检测依赖)
   │   └─ ...
   └─ 对 VQA 的影响:
       ├── 一个 ViT 模型同时产出多种质量信息
       └─ 这就是为什么一个 CLIP 骨干可以覆盖 31 个指标
          而 CNN 只能覆盖 1 个指标 (需要 6 个独立 CNN)
```

#### 2.8.5 权重矩阵模型结构

```text
┌──────────────────────────────────────────────────────┐
│ Weight_Matrix (Weight_Matrix_sun002_davinci-1.nnx)    │
│                                                      │
│  输入: 3072维CLIP特征向量 (FEATINPUT模式)             │
│   ↓                                                  │
│  单层线性映射 (无隐藏层)                              │
│  Y = sigmoid(W × X + b)                              │
│  W: (200, 3072) FP16 → 当前激活前31行                │
│  b: (200,) FP16 → 当前激活前31个                     │
│   ↓                                                  │
│  sigmoid归一化 → [0,1]区间分数                        │
│   ↓                                                  │
│  输出:                                                │
│  ├── IQA分支: 31个质量指标分数 (indicator_map)        │
│  └─ SERVICETYPE分支: 场景分类分数 (service_type=66)   │
├──────────────────────────────────────────────────────┤
│ 模型体积: 187KB                                      │
│ 3072 × 31 × 2(FP16) = 190KB ← 精确吻合              │
│ (实际存储200行, 当前激活31行, 预留169行扩展)          │
│                                                      │
│ 扩展方式:                                            │
│  新增指标只需激活权重矩阵的对应行, 无需重新训练CLIP   │
│  3072维CLIP特征已隐含编码所有质量信息                 │
│  权重矩阵只是在特征空间中"选择"对应维度并归一化       │
└──────────────────────────────────────────────────────┘
```

#### 2.8.6 各NNX子模型结构

小模型诊断使用 CNN+KNN 两阶段架构，大模型诊断的子模型有所不同：

```text
模型分类
├── 轻量分类网络 (iqa31黑白 / iqa32偏色)
│   ├── 3-5层小CNN (几万参数)
│   └─ 输出: 类别概率 (2类/4类)
│   └─ 无KNN后处理, 直接输出分类结果
│
├── 目标检测骨干 (iqa36遮挡)
│   ├── 轻量级检测器 (YOLOv5s变体)
│   └─ 输出: bounding box + 分类 + 置信度
│
├── Siamese差异网络 (iqa33变更)
│   ├── 双分支特征提取 → 差异特征融合
│   └─ 输出: 变更区域掩码 + 置信度
│
├── 几何变换网络 (iqa34抖动PTZ)
│   ├── BiGeoNet: 学习帧间几何变换场
│   └─ 多任务输出头: 抖动指标 + PTZ方向分类
│
└── 视觉大模型 (OX23 CLIP + OX24 矩阵)
    ├── CLIP ViT-L/14: 3072维特征提取
    └─ 权重矩阵: 3072→31线性映射
```

与小模型诊断的核心区别：大模型诊断不再使用 KNN 分类器后处理，而是直接用分类头或检测头输出结果。CLIP 骨干+权重矩阵构成了一个全新的"特征提取+线性解码"范式，替代了传统 CNN+KNN 的"特征提取+聚类匹配"范式。

#### 2.8.7 NPU 调度与资源管理

```text
NPU 共享缓冲区 (91MB)
  │
  ├── 所有算子共享同一片NPU内存
  │   ├── CLIP推理中间激活值 (~500MB峰值, 分层释放)
  │   ├── CLIP输出3072维特征 → 矩阵输入 (缓冲区内直传)
  │   ├── 矩阵输出31个分数 → FUNC25输入 (缓冲区内直传)
  │   ├── 小模型推理中间值 (~20MB峰值)
  │   └─ MemQueueVQAIQA缓存 (~5MB)
  │
  ├── 时分复用调度
  │   ├── 每帧周期: CLIP骨干(~10-15ms) → 矩阵映射(~0.1ms)
  │   │              → 5个小模型合计(~5-8ms)
  │   └─ 控制帧率: 每4帧推理一次 (control=[4])
  │      实际NPU负载 ~7-8次推理周期/秒
  │
  └── 多摄像头管理
      max_camera_count=10, maxCameraNum≤10
      每摄像头独立通道, 共享NPU算力
```

7路并行推理在 NPU 上是时分复用而非真正并行——sun002 的 AI Core 数量有限，按优先级依次调度。CLIP 骨干推理时间最长（ViT-L 约 10-15ms/帧），其他小模型合计约 5-8ms。3072 维特征在 NPU 缓冲区内直接传递给权重矩阵，避免了跨总线搬运。

#### 2.8.9 CLIP 大模型在 VQA 中的独特价值

1. **统一特征空间替代独立特征工程**：传统 VQA 为每个指标设计独立的 CNN 特征提取器（偏色有自己的CNN，黑白有自己的CNN）；CLIP 用一个 3072 维向量表达所有视觉信息，权重矩阵做维度解耦——架构上大幅简化，新增指标零成本。

2. **零样本视觉语义理解**：CLIP 在大规模图文对上的预训练使其能理解复杂语义场景——有没有物体遮挡、画面是否内容变更、是否属于特定异常场景。传统 KNN 分类器依赖训练数据覆盖的场景类型，遇到未见过的异常模式容易漏报。

3. **特征一致性驱动时序分析**：CLIP 的 3072 维特征作为帧的语义指纹，跨帧比对自然地检测场景切换（剧烈变化）、持续抖动（帧间特征偏移）、画面冻结（特征几乎不变）。传统算法需要为每种时序模式设计独立的帧间差分策略。

4. **200属性槽的可扩展性**：OCMULTIATTR 的 attr_num=200 意味着最多支持 200 个质量指标输出，当前只用了 31 个。新增指标只需要在权重矩阵增加一行并微调，无需重新设计整个流水线或训练新模型。

5. **语义级诊断项的优势**：基于 CLIP 微调的大模型诊断具有一定的语义理解能力，对于需要"理解画面内容才能判定"的诊断项——如遮挡（需要理解"这是什么遮挡物"）、偏色（需要理解"画面应该是什么颜色"）、场景变化（需要理解"这是不同场景而非光照变化"）——比小模型效果好。原因在于这些诊断项的判定依赖对画面整体语义的解读，而非局部像素统计：

```text
诊断项的两大类别:

客观统计型 (小模型擅长):
  ├── 判断标准: 像素级数值是否超过阈值
  ├── 亮度: Y通道均值 > 230 → 过曝 (纯数值判定)
  ├── 对比度: Y通道动态范围 < 50 → 低对比度 (纯数值判定)
  ├── 冻结: 帧间差分均值 < 0.01 → 冻结 (纯数值判定)
  ├── 清晰度: 拉普拉斯方差 < 100 → 模糊 (纯数值判定)
  ├── 黑屏: Y均值 < 10 且方差 < 5 → 黑屏 (纯数值判定)
  └─ 特点: 不需要理解"画面是什么"，只需统计像素数值
     └─ 传统算法精确可靠，CLIP 在这些指标上反而不如传统算法
        └─ CLIP 特征编码语义信息，数值级精度不如像素统计

语义理解型 (大模型擅长):
  ├── 判断标准: 需要理解画面内容才能判定是否异常
  ├── 遮挡: 需要理解"遮挡物是什么" (树叶/树干/电线杆/配电箱)
  │   └─ 传统算法: 只能做二分类 (有遮挡/无遮挡)
  │   └─ CLIP: 能做 14 类细分类 (树叶/红旗/电线/树干/电线杆/雨棚/...)
  ├── 偏色: 需要理解"这个场景正常应该是什么颜色"
  │   └─ 传统算法: 统计UV通道偏移 → 只能判断数值级偏色
  │   └─ CLIP: 理解场景语义 → 室外白天正常偏暖、夜间正常偏冷 → 区分合理色偏和异常色偏
  ├── 场景变化: 需要理解"这是不同场景，而非同一场景的光照变化"
  │   └─ 传统算法: 背景图差分 → 无法区分场景切换和光照渐变
  │   └─ CLIP: 语义级比对 → 理解内容差异而非像素差异
  ├── 天气: 需要理解"画面呈现的是雾/雨/雪的视觉效果"
  │   └─ 传统算法: 无法检测（没有像素级特征可统计）
  │   └─ CLIP: 语义理解（见过大量雾天/雨天/雪天的图文对）
  ├── 蜘蛛网: 需要理解"这种纹理模式是蜘蛛网而非普通噪声"
  │   └─ 传统算法: 容易与噪声/条纹混淆
  │   └─ CLIP: 语义理解"蜘蛛网是一种有特定形状的遮挡物"
  ├── 保护膜/紫边/逆光: 需要理解"这种特定视觉效果由镜头问题而非场景内容导致"
  │   └─ 传统算法: 很难区分保护膜模糊和场景本身模糊
  │   └─ CLIP: 理解"清晰场景上叠加了均匀模糊 = 保护膜"
  └─ 特点: 需要语义理解，纯像素统计无法判定
     └─ CLIP 的语义编码能力是核心优势
     └─ 但 CLIP 的分数精度不如像素统计 → 碰撞指标需双源加权融合

这就是为什么 BigVQA 的融合策略设计为"双源加权":
  ├── 客观统计型指标 → 传统算法为主 (权重高)
  ├── 语义理解型指标 → CLIP/Matrix为主 (权重高)
  └── 双源覆盖的指标 → 加权融合 (取各自优势)
```

| 模型文件               | 大小        | 类型                                 |
| ---------------------- | ----------- | ------------------------------------ |
| gme_qwen2_vl_2b.kllm   | 3.99GB      | GME-Qwen2-VL-2B 多模态嵌入模型主分片 |
| gme_qwen2_vl_2b.kllm.1 | 130MB       | 模型扩展分片                         |
| **模型总计**           | **~4.12GB** | 远大于 BigVQA 的 726MB               |

核心模型是 **GME-Qwen2-VL-2B**（General Multimodal Embedding model based on Qwen2-VL-2B），这是阿里巴巴开源的多模态嵌入模型，专门为图文检索场景训练。3.99GB 的模型体积对应 Qwen2-VL-2B 的 ~1.5B 参数（含视觉编码器 ViT + 语言模型 Qwen2-1.5B），`.kllm` 是大华针对大语言模型的自定义加密打包格式。

### 3.2 算法流水线 (graph.proto)

TSA 包含两条独立的 Pipeline，通过 `scene_mask` 区分：

```text
Pipeline 1: 特征提取 (SCENE_FEATURE)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
输入帧 + per_frame_info
  → integration_io_article77 (Pipeline入口)
  → OCR_OX78 (GME-Qwen2-VL-2B 特征提取)
     ├── image_mode=0: 提取图像视觉嵌入
     └── feature_size=6144 输出
  → integration_result_article79 (结果格式化)
     → custom_result (6144维特征向量)
     → detect_result (SDK标准检测结果)

Pipeline 2: 推理比对 (SCENE_CUSTOM_1)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
文本 prompt + 空帧(仅携带per_frame_cfg)
  → integration_io_article65 (Pipeline入口)
  → OCR_OX75 (GME-Qwen2-VL-2B 文本嵌入)
     ├── prompt_mode=1: 提取文本语义嵌入
     ├── feature_extract_mode=TEXT_EMBEDDING
     └── feature_size=6144 输出
  → general_fm76 (QBIC特征比对)
     ├── compare_mode=3, topn=1000
     ├── control=[1012,1013,1014] (QBIC比对码)
     └─ 在特征库中搜索 TopK 匹配
  → OCR_FUNC80 (SUBFUNC_IQAFM 逻辑处理)
  → integration_result_article62 (结果格式化)
     → custom_result (比对匹配列表)
     → detect_result (SDK标准检测结果)
```

两条 Pipeline 共享同一份 `gme_qwen2_vl_2b.kllm` 模型文件，只是运行模式不同：Pipeline 1 走图像编码路径，Pipeline 2 走文本编码路径。这体现了 GME 模型的双塔（Dual-Tower）设计——图像和文本分别编码到同一特征空间，再通过余弦相似度比对。

### 3.3 核心模型原理

#### 3.3.1 GME-Qwen2-VL-2B 多模态嵌入模型

GME（General Multimodal Embedding）是基于 Qwen2-VL-2B 构建的多模态嵌入模型，核心架构：

```text
┌──────────────────────────────────────────────────────────────┐
│ GME-Qwen2-VL-2B                                             │
│                                                              │
│ 图像编码路径 (OCR_OX75/78, image_mode=0):                    │
│                                                              │
│   输入图像 (max_pixels ≤ 8M, min_pixels ≥ 3136)             │
│     │                                                        │
│     ├── ViT 视觉编码器 (Qwen2-VL 的 ViT)                    │
│     │   ├── patch_size=14, factor=28                         │
│     │   ├── 动态分辨率: 自动调整到最优 patch 数              │
│     │   └─ 输出: 视觉 token 序列                              │
│     │                                                        │
│     ├── Qwen2 语言模型 (1.5B 参数)                           │
│     │   ├── 接收视觉 token + 特殊指令                        │
│     │   └─ 输出: 最后一层隐藏状态                              │
│     │                                                        │
│     └── 投影头 → 6144 维特征向量                             │
│         ├── custom_attr_label=204 (204个语义类别)            │
│         └─ L2 归一化 (feat_norm=1)                           │
│                                                              │
│ 文本编码路径 (OCR_OX75, prompt_mode=1):                      │
│                                                              │
│   输入文本 prompt                                            │
│     │                                                        │
│     ├── Qwen2 语言模型 (1.5B 参数)                           │
│     │   ├── 文本 tokenization + embedding                    │
│     │   └─ 输出: 文本语义表示                                 │
│     │                                                        │
│     └── 投影头 → 6144 维特征向量                             │
│         └─ L2 归一化 → 与图像特征在同一空间                   │
│                                                              │
│ 比对: cosine_similarity(img_feat, txt_feat)                   │
│   同一空间 → 文本描述直接匹配图像语义                        │
└──────────────────────────────────────────────────────────────┘
```

**关键参数解读**：

- `feature_size=6144`：6144 = 204 × 3072 / 2（FP16），意味着模型输出 204 个语义类别的 3072 维 CLIP 式特征，压缩为 FP16 后 6144 字节存储。与 BigVQA 的 `custom_attr_label=205` 相近，GME 和 BigVQA 的 CLIP backbone 共享了类似的语义标签体系。
- `max_pixels=8388608`（8M像素）：支持最高 ~4K 分辨率输入（如 2816×2816），远大于 CLIP 的 336×336。Qwen2-VL 使用动态分辨率机制，根据 `factor=28` 自动分块。
- `patch_size=14`：与 CLIP ViT-L/14 一致的 patch 大小。
- `prompt="Did a traffic accident occur on the road?"`：配置中的默认提示词是交通事故检测，但实际运行时 VQRS 会替换为用户输入的搜索文本。
- `.kllm` 格式：大华针对大语言模型的加密打包格式，类似 `.nnx` 但专门用于 LLM 级别的大模型（4GB+），可能包含模型分片、量化参数和推理配置。

#### 3.3.2 QBIC 特征比对

`general_fm76` 是 QBIC（Query By Image Content）特征比对算子：

```text
输入: 文本嵌入特征 (6144维) + QBIC 底库句柄
  │
  ├── compare_mode=3 (余弦相似度比对)
  ├── topn=1000 (返回 Top-1000 匹配)
  ├── compare_thresh=1 (最低相似度阈值 1%)
  ├── match_db_mode=0 (正报库模式)
  ├── mem_size=6184 (内存配置)
  │
  ├── control=[1012, 1013, 1014]
  │   1012: 注册 QBIC 底库句柄
  │   1013: 设置比对目标过滤
  │   1014: 设置活跃底库和相似度阈值
  │
  └── 输出: TopK 匹配结果列表
      每个匹配项包含: imageId, similarity, channelCode, imageUrl
```

QBIC 是大华的特征向量搜索引擎，类似于 Milvus/FAISS 的向量数据库。底库中存储了摄像头历史图像的 6144 维特征向量，比对时计算文本特征与库中所有图像特征的余弦相似度，返回 TopK 最匹配的结果。

### 3.4 VQRS 集成实现

#### 3.4.1 算法封装层

**CAlgorithmTsFeature**（特征提取）和 **CAlgorithmTsInference**（推理比对）共享同一 `libdhivs_sdk_vqatsa.so`，通过 `SharedVqatsaInit` 统一初始化，仅 `scene_mask` 不同：

| 算法类                | scene_mask               | Pipeline   | 作用               |
| --------------------- | ------------------------ | ---------- | ------------------ |
| CAlgorithmTsFeature   | DHIVS_VDS_SCENE_FEATURE  | Pipeline 1 | 图像→6144维特征    |
| CAlgorithmTsInference | DHIVS_VDS_SCENE_CUSTOM_1 | Pipeline 2 | 文本→特征→QBIC比对 |

**特征提取流程**（CAlgorithmTsFeature::HandleAlgorithmAnalyse）：

```text
1. 构造 dhivs_pic_v2_t:
   ├── buffer_addr1: YUV420 虚拟地址 (addr1=Y, addr2=U, addr3=V)
   ├── image_info: color_space=YUV420, channel=3
   └── 与 BigVQA 不同: 无 ACL 双地址映射，使用 CPU 内存直接送入
       (TsFeature 不需要 NPU 侧预搬运，SDK 内部处理)

2. 异步回调: RegProcessDoneCallBack → ProcessImageMulti
   └─ promise/future 模式等待结果

3. 结果提取: GetResults → 6144 维特征向量
   └─ 写入 QbicStore 底库或返回给调用方
```

**推理比对流程**（CAlgorithmTsInference::HandleAlgorithmAnalyse）：

```text
1. 构造 dhivs_text_info_t:
   ├── value = 用户输入的文本 prompt
   ├── encode_type = UTF-8
   └─ length = prompt 字符长度

2. 构造 dhivs_vlm_input_perframe_t:
   ├── type = DHVIS_VDS_PER_FRAME_CFG_COMMON_CFG_VLM
   ├── text = &stTextInfo (文本指针)
   └─ feature_extract_mode = DHIVS_VLM_FEATURE_MODE_TEXT_EMBEDDING
      (纯文本嵌入模式，不需要图像)

3. 构造 dhivs_pic_v2_t 空帧:
   └─ 不携带实际图像数据，仅通过 per_frame_cfg 传递文本配置
      dhivs_pic_v2_t stDummyPic;  // 空帧
      stDummyPic.per_frame_cfg = &stFrameCfg;

4. ProcessImageMulti(pVdsHdlTemp->pHandle, 1, pPics, NULL)
   └─ Pipeline 2 执行: 文本→GME嵌入→6144维→QBIC比对→TopK结果

5. 异步等待结果: promise/future → GetResults → ReleaseResults
```

**规则配置**（CAlgorithmTsInference::HandleAlgorithmAnalyseRules）：

```text
1. 清空缓存 → HandleAlgorithmAnalyseCache
2. 注册 QBIC 句柄 (DHVIS_VDS_ALGORITHM_STRUCT_TYPE_QBIC_ALGHANDLE):
   └─ 将 CQbicStore 的 pHandleQbic 注入到 VDS Pipeline
   └─ general_fm76 通过 QBIC 句柄访问底库执行比对
3. 比对目标过滤 (DHIVS_VDS_ALGORITHM_STRUCT_TYPE_OBJ_COMPARE_CFG_INFO):
   └─ obj_type = DHIVS_OBJ_TYPE_PRO_ANYTHING (不限目标类型)
   └─ pdb_ids = 特征库 dbId
4. 活跃底库选择 (DHVIS_VDS_ALGORITHM_STRUCT_TYPE_ACTIVE_DB):
   └─ dbId = 特征库 ID
   └─ similarity = nSimilarityThreshold / 100.0 (归一化到[0,1])
   └─ pos_neg_db = 0 (正报库模式)
```

### 3.5 与 BigVQA 的关系

TSA 和 BigVQA 共享 `ENABLE_BIGVQA` 编译宏和 `libdhivs_sdk_vqatsa.so` 初始化流程（`SharedVqatsaInit`），但在运行时使用不同的 scene_mask 激活不同的 Pipeline 分支：

| 维度     | BigVQA (VQA诊断)          | TSA (文搜图)              |
| -------- | ------------------------- | ------------------------- |
| SDK 库   | libdhivs_sdk_vqavlm.so    | libdhivs_sdk_vqatsa.so    |
| 核心模型 | CLIP ViT-L/14@336 (581MB) | GME-Qwen2-VL-2B (4.12GB)  |
| 模型架构 | 纯视觉编码器              | 视觉-语言双塔嵌入模型     |
| 特征维度 | 3072 (FP32) → 31指标      | 6144 (FP16, 204属性)      |
| 输出     | 28+诊断项分数+状态        | TopK 匹配图像列表         |
| Pipeline | 单条(7路并行→融合)        | 双条(特征提取 / 推理比对) |
| 输入     | YUV图像帧                 | 图像帧 / 文本prompt       |
| NPU内存  | 91MB 共享缓冲区(预设)     | 动态获取(-1)              |
| 图像格式 | NV12 + ACL双地址          | YUV420 + CPU地址          |
| 场景     | DHIVS_VDS_SCENE_DEFAULT   | FEATURE / CUSTOM_1        |

BigVQA 诊断过程中会自动调用 `ExtractAndDispatchImageFeature` 将诊断图像的 6144 维特征入库到 QBIC，为后续文搜图提供检索数据源——两个子系统形成"诊断建库→检索查询"的闭环。

### 3.6 关键推断

1. **TSA 与 BigVQA 共享初始化但独立运行**：两者通过 `SharedVqatsaInit` 统一初始化，但运行时分别加载 `libdhivs_sdk_vqavlm.so`（BigVQA）和 `libdhivs_sdk_vqatsa.so`（TSA），scene_mask 决定 Pipeline 分支，互不干扰。

2. **GME-Qwen2-VL-2B 的双塔设计**：同一模型文件通过 `image_mode=0`（图像编码）和 `prompt_mode=1`（文本编码）两种模式复用，图像和文本分别编码到同一 6144 维特征空间，余弦相似度直接比对——这是文搜图"以文搜图"能力的核心。

3. **QBIC 底库的 DB+SDK 双写策略**：特征入库时先写数据库持久化，再写 QBIC SDK 内存底库；删除时先删 SDK 再删 DB。这种顺序设计确保服务重启后可通过 DB 恢复底库，避免数据丢失。

4. **TSA 的 NPU 内存动态获取**：`DHOP_SET_MAX_WORKSIZE=-1` 表示 TSA 不预设 NPU 共享缓冲区大小，运行时动态申请。这与 BigVQA 的固定 91MB 策略不同，因为 TSA 推理频率低（用户查询触发），不需要常驻大内存。

5. **自定义告警闭环依赖 TSA 完整链路**：BigVQA 诊断时提取的 6144 维 GME 特征与文搜图查询使用同一特征空间，因此自定义告警的文本 prompt 可以直接与诊断图像特征做 QBIC 比对——BigVQA 和 TSA 在特征层面是互通的。
