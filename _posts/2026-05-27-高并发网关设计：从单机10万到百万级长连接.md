### 引言

网关（Gateway）是几乎所有后端系统的入口节点——流量的第一道关卡。在我参与的IM系统和IoT平台中，单机网关需要承载50万+的长连接，每秒处理10万+的消息转发。这对网络模型、内存管理、限流策略都提出了极高的要求。

这篇文章总结我在设计和优化高并发网关过程中的工程经验，从Reactor线程模型到内存池设计，从限流算法到优雅停机。

---

### 1. 网络模型：Multi-Reactor

#### 1.1 为什么不是一个Reactor？

单Reactor单线程（Redis模式）的上限在10万QPS左右。瓶颈在于：
- 单线程不能利用多核
- IO和业务处理串行，任何一个慢操作会阻塞所有连接

#### 1.2 主从Reactor模型

```
┌──────────────────────────────────────────────────────────────────┐
│                        Main Reactor                               │
│                    (单线程，只负责accept)                         │
│                                                                  │
│   listen_fd → epoll_wait → accept → 分发给Sub Reactor          │
└────────────────────────┬─────────────────────────────────────────┘
                         │ 轮询分发（Round Robin）
         ┌───────────────┼───────────────┐
         ▼               ▼               ▼
┌─────────────┐  ┌─────────────┐  ┌─────────────┐
│ Sub Reactor │  │ Sub Reactor │  │ Sub Reactor │
│  (线程 1)   │  │  (线程 2)   │  │  (线程 N)   │
│             │  │             │  │             │
│ epoll管理   │  │ epoll管理   │  │ epoll管理   │
│ 5万个连接   │  │ 5万个连接   │  │ 5万个连接   │
│             │  │             │  │             │
│ 读/写/编解码│  │ 读/写/编解码│  │ 读/写/编解码│
└─────────────┘  └─────────────┘  └─────────────┘
                         │
                         ▼ (业务逻辑)
              ┌─────────────────────┐
              │    Worker线程池      │
              │  (CPU密集型处理)     │
              └─────────────────────┘
```

#### 1.3 关键设计决策

```cpp
// 连接分发策略
class ConnectionDispatcher {
    std::vector<SubReactor*> sub_reactors_;
    std::atomic<size_t> next_index_{0};

public:
    SubReactor* dispatch() {
        // Round Robin（最简单，负载最均匀）
        size_t idx = next_index_.fetch_add(1) % sub_reactors_.size();
        return sub_reactors_[idx];
    }

    // 更优方案：根据当前负载选择最空闲的Reactor
    SubReactor* dispatchByLoad() {
        SubReactor* lightest = sub_reactors_[0];
        for (auto* r : sub_reactors_) {
            if (r->connectionCount() < lightest->connectionCount())
                lightest = r;
        }
        return lightest;
    }
};
```

**SubReactor数量**：通常设为CPU核数，或核数-1（留一核给MainReactor和OS）。

### 2. 连接管理

#### 2.1 连接对象设计

```cpp
class Connection {
public:
    enum class State { Connecting, Connected, Closing, Closed };

    int fd() const { return fd_; }
    State state() const { return state_; }

    // 发送数据（线程安全，可跨线程调用）
    void send(const Buffer& data) {
        if (isInLoopThread()) {
            sendInLoop(data);
        } else {
            // 跨线程发送：投递到所属Reactor的任务队列
            loop_->queueInLoop([this, data]() {
                sendInLoop(data);
            });
        }
    }

private:
    int fd_;
    State state_;
    EventLoop* loop_;           // 所属的SubReactor
    Buffer input_buffer_;       // 接收缓冲区
    Buffer output_buffer_;      // 发送缓冲区
    TimePoint last_active_;     // 最后活跃时间（用于超时踢除）
    void* user_data_;           // 业务层自定义数据
};
```

#### 2.2 连接超时管理——时间轮

管理50万连接的超时踢除，不能用简单的遍历。时间轮是最优方案：

```cpp
// 层级时间轮（Hierarchical Timing Wheel）
class TimingWheel {
    static constexpr int SLOTS = 256;       // 每层256个槽
    static constexpr int TICK_MS = 100;     // 每个刻度100ms

    struct Slot {
        std::list<Connection*> connections;
    };

    std::array<Slot, SLOTS> wheel_;
    int current_slot_ = 0;

public:
    // 添加连接（超时时间 = N * TICK_MS）
    void add(Connection* conn, int timeout_ticks) {
        int slot = (current_slot_ + timeout_ticks) % SLOTS;
        wheel_[slot].connections.push_back(conn);
    }

    // 每个tick调用，踢除超时连接
    void tick() {
        current_slot_ = (current_slot_ + 1) % SLOTS;
        for (Connection* conn : wheel_[current_slot_].connections) {
            conn->forceClose("timeout");
        }
        wheel_[current_slot_].connections.clear();
    }

    // 连接活跃时"续命"：从旧槽移到新槽
    void refresh(Connection* conn, int timeout_ticks) {

        // 插入新槽
    }
};

### 3. 内存管理

#### 3.1 为什么需要内存池？

50万长连接，每个连接的读写缓冲区如果都走系统malloc：
- 碎片化严重（频繁的小块分配/释放）
- malloc本身有锁（多线程竞争）
- 内存分配延迟不可控

#### 3.2 对象池（Connection Pool）

```cpp
template<typename T, size_t BlockSize = 4096>
class ObjectPool {
    struct Block {
        alignas(T) char data[sizeof(T)];
        Block* next;
    };

    Block* free_list_ = nullptr;
    std::vector<void*> chunks_;  // 整块分配的内存
    std::mutex mutex_;

public:
    T* allocate() {
        std::lock_guard<std::mutex> lock(mutex_);
        if (!free_list_) {
            expandPool();
        }
        Block* block = free_list_;
        free_list_ = block->next;
        return reinterpret_cast<T*>(block->data);
    }

    void deallocate(T* ptr) {
        std::lock_guard<std::mutex> lock(mutex_);
        Block* block = reinterpret_cast<Block*>(ptr);
        block->next = free_list_;
        free_list_ = block;
    }

private:
    void expandPool() {
        // 一次分配一大块，切分成多个Block
        size_t count = BlockSize / sizeof(Block);
        Block* chunk = static_cast<Block*>(::operator new(count * sizeof(Block)));
        chunks_.push_back(chunk);

        for (size_t i = 0; i < count - 1; ++i) {
            chunk[i].next = &chunk[i + 1];
        }
        chunk[count - 1].next = free_list_;
        free_list_ = chunk;
    }
};
```

#### 3.3 Buffer设计（参考muduo）

```cpp
class Buffer {
    // 布局: [prependable][readable][writable]
    //       0          readIdx    writeIdx      capacity
    std::vector<char> buffer_;
    size_t read_index_ = 0;
    size_t write_index_ = 0;

    static constexpr size_t kPrepend = 8;      // 预留空间（填协议头）
    static constexpr size_t kInitialSize = 1024;

public:
    Buffer() : buffer_(kPrepend + kInitialSize),
               read_index_(kPrepend), write_index_(kPrepend) {}

    size_t readableBytes() const { return write_index_ - read_index_; }
    size_t writableBytes() const { return buffer_.size() - write_index_; }

    // 从fd读取数据（用readv + 栈上临时缓冲区，避免预分配过大buffer）
    ssize_t readFd(int fd) {
        char extrabuf[65536];  // 栈上64KB临时缓冲区
        struct iovec vec[2];
        size_t writable = writableBytes();

        vec[0].iov_base = writeBegin();
        vec[0].iov_len = writable;
        vec[1].iov_base = extrabuf;
        vec[1].iov_len = sizeof(extrabuf);

        // readv一次系统调用读取两块buffer
        ssize_t n = readv(fd, vec, 2);
        if (n > 0) {
            if (static_cast<size_t>(n) <= writable) {
                write_index_ += n;
            } else {
                write_index_ = buffer_.size();
                append(extrabuf, n - writable);
            }
        }
        return n;
    }
};
```

### 4. 流量控制与限流

#### 4.1 令牌桶算法

```cpp
class TokenBucket {
    double rate_;              // 令牌生成速率（个/秒）
    double capacity_;          // 桶容量
    double tokens_;            // 当前令牌数
    TimePoint last_time_;      // 上次补充时间
    std::mutex mutex_;

public:
    TokenBucket(double rate, double capacity)
        : rate_(rate), capacity_(capacity), tokens_(capacity),
          last_time_(Clock::now()) {}

    bool tryConsume(double tokens = 1.0) {
        std::lock_guard<std::mutex> lock(mutex_);
        refill();
        if (tokens_ >= tokens) {
            tokens_ -= tokens;
            return true;
        }
        return false;  // 限流
    }

private:
    void refill() {
        auto now = Clock::now();
        double elapsed = duration_cast<milliseconds>(now - last_time_).count() / 1000.0;
        tokens_ = std::min(capacity_, tokens_ + elapsed * rate_);
        last_time_ = now;
    }
};
```

#### 4.2 滑动窗口限流（更精确）

```cpp
class SlidingWindowRateLimiter {
    int window_size_ms_;       // 窗口大小（毫秒）
    int max_requests_;         // 窗口内最大请求数
    std::deque<TimePoint> requests_;
    std::mutex mutex_;

public:
    SlidingWindowRateLimiter(int window_ms, int max_req)
        : window_size_ms_(window_ms), max_requests_(max_req) {}

    bool allow() {
        std::lock_guard<std::mutex> lock(mutex_);
        auto now = Clock::now();
        auto window_start = now - milliseconds(window_size_ms_);

        // 清除过期请求
        while (!requests_.empty() && requests_.front() < window_start) {
            requests_.pop_front();
        }

        if (requests_.size() < max_requests_) {
            requests_.push_back(now);
            return true;
        }
        return false;  // 限流
    }
};
```

### 5. 优雅停机与热升级

#### 5.1 优雅停机流程

```
收到SIGTERM
    ↓
1. 停止accept新连接
    ↓
2. 向所有连接发送"即将关闭"通知
    ↓
3. 等待已有请求处理完成（超时30s）
    ↓
4. 强制断开剩余连接
    ↓
5. 释放资源，退出进程
```

```cpp
class GracefulShutdown {
    std::atomic<bool> shutting_down_{false};
    std::atomic<int> active_requests_{0};

public:
    void shutdown() {
        shutting_down_ = true;

        // 1. 停止accept
        main_reactor_->removeChannel(listen_channel_);

        // 2. 通知所有客户端
        for (auto& [fd, conn] : connections_) {
            conn->send(makeGoAwayFrame());
        }

        // 3. 等待活跃请求完成
        auto deadline = Clock::now() + seconds(30);
        while (active_requests_.load() > 0 && Clock::now() < deadline) {
            std::this_thread::sleep_for(milliseconds(100));
        }

        // 4. 强制关闭
        for (auto& [fd, conn] : connections_) {
            conn->forceClose("server shutting down");
        }
    }

    // 每个请求开始时+1，结束时-1
    void onRequestBegin() { active_requests_++; }
    void onRequestEnd() { active_requests_--; }
};
```

#### 5.2 热升级（Zero Downtime Upgrade）

核心思想：新旧进程通过Unix Domain Socket传递listen fd。

```
旧进程                                新进程
  │                                    │
  │  1. fork新进程                     │
  │  2. 通过UDS传递listen_fd ────────→ │
  │  3. 停止accept                     │  4. 开始accept
  │  5. 等待旧连接处理完               │  5. 服务新连接
  │  6. 退出                           │
```

```cpp
// 通过Unix Socket传递文件描述符
void sendFd(int uds_fd, int fd_to_send) {
    struct msghdr msg = {};
    char buf[CMSG_SPACE(sizeof(int))];
    msg.msg_control = buf;
    msg.msg_controllen = sizeof(buf);

    struct cmsghdr* cmsg = CMSG_FIRSTHDR(&msg);
    cmsg->cmsg_level = SOL_SOCKET;
    cmsg->cmsg_type = SCM_RIGHTS;
    cmsg->cmsg_len = CMSG_LEN(sizeof(int));
    *((int*)CMSG_DATA(cmsg)) = fd_to_send;

    sendmsg(uds_fd, &msg, 0);
}
```

### 总结

高并发网关的核心设计原则：

1. **分层解耦**：网络层（Reactor）、协议层（编解码）、业务层（Handler）职责分离
2. **零拷贝**：Buffer设计避免无意义的内存拷贝
3. **池化资源**：连接对象、Buffer、线程都用池管理
4. **异步化**：任何可能阻塞的操作（DNS查询、日志写入）都走异步
5. **可观测性**：连接数、延迟、内存水位等指标实时暴露

记住：**架构不是一步到位的，而是从简单开始逐步演进。** 先实现一个正确的单Reactor，再根据压测结果决定是否需要多Reactor、内存池、无锁队列。过度设计的网关比简单可靠的方案更危险。
