### 引言

在我负责的IM网关系统中，曾因一次突发流量导致下游服务雪崩——消息转发服务的QPS从正常的5万飙升到30万，数据库连接池耗尽，整个集群瘫痪了20分钟。事后复盘，根本原因是**网关层缺少有效的限流机制**。

限流（Rate Limiting）是分布式系统的第一道防线。这篇文章从最基础的计数器算法讲起，逐步推演到生产级的令牌桶实现，最后介绍分布式场景下的Redis限流方案。每种算法都附带完整的C++实现代码。

### 1. 限流的本质

#### 1.1 为什么需要限流

```
┌────────────────────────────────────────────────────────────────┐
│               没有限流时的灾难链条                               │
│                                                                │
│  突发流量 → 服务过载 → 响应变慢 → 超时重试 → 流量翻倍         │
│                            ↓                                   │
│                       连接耗尽 → 级联故障 → 全系统雪崩          │
│                                                                │
│                                                                │
│               有限流时的优雅降级                                 │
│                                                                │
│  突发流量 → 限流器拦截 → 超额请求快速返回429                   │
│                            ↓                                   │
│                       服务稳定 → 核心流量正常处理               │
└────────────────────────────────────────────────────────────────┘
```

#### 1.2 限流维度

| 维度 | 示例 | 常用算法 |
|------|------|----------|
| 单机QPS | 每个服务实例限制1万QPS | 令牌桶/滑动窗口 |
| 用户级 | 每个用户每秒最多10次请求 | 滑动窗口 |
| API级 | /api/send 限制5000 QPS | 令牌桶 |
| 并发数 | 同时处理不超过200个请求 | 信号量/计数器 |

### 2. 固定窗口计数器

#### 2.1 原理

最简单的限流：将时间划分为固定窗口（如每1秒），窗口内计数超过阈值则拒绝。

```
时间线：
|-------- 窗口1 --------|-------- 窗口2 --------|
0s                      1s                      2s

窗口1内: 请求计数 <= 100 → 放行
         请求计数 > 100  → 拒绝
```

#### 2.2 C++实现

```cpp
#include <atomic>
#include <chrono>

class FixedWindowLimiter {
public:
    FixedWindowLimiter(int max_requests, int window_seconds)
        : max_requests_(max_requests)
        , window_duration_(window_seconds) {}

    bool allow() {
        auto now = std::chrono::steady_clock::now();
        auto current_window = std::chrono::duration_cast<std::chrono::seconds>(
            now.time_since_epoch()).count() / window_duration_;

        // 窗口切换，重置计数
        int64_t window = window_start_.load(std::memory_order_relaxed);
        if (current_window != window) {
            // CAS更新窗口（只有一个线程能成功）
            if (window_start_.compare_exchange_strong(window, current_window)) {
                counter_.store(0, std::memory_order_relaxed);
            }
        }

        // 原子递增，检查是否超限
        int count = counter_.fetch_add(1, std::memory_order_relaxed);
        return count < max_requests_;
    }

private:
    int max_requests_;
    int window_duration_;  // 窗口大小（秒）
    std::atomic<int64_t> window_start_{0};
    std::atomic<int> counter_{0};
};
```

#### 2.3 致命缺陷：窗口边界突刺

```
假设限制: 100 QPS（每秒100个请求）

实际场景：
|---窗口1---|---窗口2---|
      ↑                ↑
   0.9s时来了100个    1.0s时来了100个
   
在 [0.9s, 1.1s] 这200ms内实际通过了200个请求！
瞬时QPS = 200/0.2 = 1000 —— 远超限制！
```

**结论**：固定窗口只适合精度要求不高的场景。生产环境应使用滑动窗口或令牌桶。

### 3. 滑动窗口计数器

#### 3.1 原理

将窗口细分为多个小格子（slot），通过"滑动"来避免边界突刺：

```
窗口大小: 1s，分为10个slot（每个100ms）

时间:  |s1|s2|s3|s4|s5|s6|s7|s8|s9|s10|
       └──────── 当前窗口 ────────────┘

每100ms向右滑动一格，丢弃最旧的slot，新增最新slot
窗口内所有slot的计数之和 <= 阈值
```

#### 3.2 C++实现（环形Buffer）

```cpp
#include <atomic>
#include <array>
#include <chrono>

template<int SLOTS = 10>
class SlidingWindowLimiter {
public:
    SlidingWindowLimiter(int max_requests, int window_ms)
        : max_requests_(max_requests)
        , window_ms_(window_ms)
        , slot_ms_(window_ms / SLOTS) {}

    bool allow() {
        auto now_ms = currentTimeMs();
        int current_slot = (now_ms / slot_ms_) % SLOTS;

        // 清理过期的slot
        cleanExpiredSlots(now_ms);

        // 计算窗口内总数
        int total = 0;
        for (int i = 0; i < SLOTS; ++i) {
            total += slots_[i].load(std::memory_order_relaxed);
        }

        if (total >= max_requests_) {
            return false;  // 超限
        }

        // 当前slot计数+1
        slots_[current_slot].fetch_add(1, std::memory_order_relaxed);
        return true;
    }

private:
    int max_requests_;
    int window_ms_;
    int slot_ms_;
    std::array<std::atomic<int>, SLOTS> slots_{};
    std::atomic<int64_t> last_clean_time_{0};

    int64_t currentTimeMs() {
        return std::chrono::duration_cast<std::chrono::milliseconds>(
            std::chrono::steady_clock::now().time_since_epoch()).count();
    }

    void cleanExpiredSlots(int64_t now_ms) {
        int64_t last = last_clean_time_.load(std::memory_order_relaxed);
        int64_t elapsed = now_ms - last;

        if (elapsed >= slot_ms_) {
            if (last_clean_time_.compare_exchange_strong(last, now_ms)) {
                // 清理过期slot的数量
                int slots_to_clear = std::min((int)(elapsed / slot_ms_), SLOTS);
                int start = ((last / slot_ms_) + 1) % SLOTS;
                for (int i = 0; i < slots_to_clear; ++i) {
                    slots_[(start + i) % SLOTS].store(0, std::memory_order_relaxed);
                }
            }
        }
    }
};
```

### 4. 漏桶算法（Leaky Bucket）

#### 4.1 原理

漏桶如同一个固定流速出水的水桶——无论入水速率多快，出水（处理请求）的速率恒定：

```
          请求流入（不均匀）
            │ │ │ ││ │
            ▼ ▼ ▼ ▼▼ ▼
       ┌──────────────────┐
       │                  │  ← 桶满则溢出（拒绝）
       │    ████████████  │
       │    ████████████  │  ← 桶（缓冲队列）
       │    ████████████  │
       └────────┬─────────┘
                │
                ▼ 匀速流出（固定速率处理）
         ──────────────────
         1req/10ms  1req/10ms
```

**特点**：输出速率绝对均匀，适合**流量整形**（如发送方控速），但不适合突发流量的场景。

#### 4.2 C++实现

```cpp
class LeakyBucket {
public:
    // rate: 每秒流出速率, capacity: 桶容量
    LeakyBucket(double rate, int capacity)
        : rate_(rate)
        , capacity_(capacity)
        , water_(0) {}

    bool allow() {
        auto now = std::chrono::steady_clock::now();

        // 计算自上次以来漏掉的水量
        std::lock_guard<std::mutex> lock(mutex_);
        double elapsed = std::chrono::duration<double>(now - last_time_).count();
        water_ = std::max(0.0, water_ - elapsed * rate_);
        last_time_ = now;

        // 尝试加水
        if (water_ < capacity_) {
            water_ += 1.0;
            return true;   // 放行
        }
        return false;      // 桶满，拒绝
    }

private:
    double rate_;       // 漏水速率（请求/秒）
    int capacity_;      // 桶容量
    double water_;      // 当前水位
    std::mutex mutex_;
    std::chrono::steady_clock::time_point last_time_ = std::chrono::steady_clock::now();
};
```

**缺点**：无法处理合理的突发流量。比如系统能承受瞬间200 QPS，但漏桶只允许匀速100 QPS通过，浪费了处理能力。

### 5. 令牌桶算法（Token Bucket）

#### 5.1 原理

令牌桶是漏桶的进化——允许一定程度的突发，同时保证长期平均速率：

```
      令牌以固定速率生成
           │ │ │
           ▼ ▼ ▼
     ┌──────────────────┐
     │ ○ ○ ○ ○ ○ ○ ○ ○ │  ← 桶满则不再生成新令牌
     │ ○ ○ ○ ○ ○ ○ ○ ○ │  ← 令牌桶（capacity = 最大突发量）
     └──────────┬───────┘
                │ 取令牌
                ▼
          请求到来时消耗一个令牌
          ├── 有令牌 → 放行
          └── 无令牌 → 拒绝/等待

关键参数：
  rate     = 100 tokens/sec  （长期平均速率）
  capacity = 200 tokens      （最大突发量）
  
  正常情况：消耗速率 ≈ 生成速率，稳定100 QPS
  突发情况：桶满时有200个令牌，可瞬间处理200个请求
```

#### 5.2 生产级C++实现（无锁版本）

```cpp
#include <atomic>
#include <chrono>
#include <algorithm>

class TokenBucket {
public:
    // rate: 令牌生成速率(个/秒), burst: 桶容量(最大突发)
    TokenBucket(double rate, double burst)
        : rate_(rate)
        , burst_(burst)
        , tokens_(burst)  // 初始满桶
        , last_refill_(now_us()) {}

    // 尝试获取一个令牌
    bool tryAcquire(int tokens = 1) {
        refill();

        double current = tokens_.load(std::memory_order_relaxed);
        while (current >= tokens) {
            if (tokens_.compare_exchange_weak(
                    current, current - tokens,
                    std::memory_order_relaxed)) {
                return true;
            }
            // CAS失败，current已被更新，重试
        }
        return false;  // 令牌不足
    }

    // 获取当前令牌数（诊断用）
    double available() const {
        return tokens_.load(std::memory_order_relaxed);
    }

private:
    double rate_;    // tokens/second
    double burst_;   // max tokens
    std::atomic<double> tokens_;
    std::atomic<int64_t> last_refill_;

    void refill() {
        int64_t now = now_us();
        int64_t last = last_refill_.load(std::memory_order_relaxed);
        int64_t elapsed_us = now - last;

        if (elapsed_us <= 0) return;

        // 计算应补充的令牌数
        double new_tokens = (elapsed_us / 1000000.0) * rate_;
        if (new_tokens < 1.0) return;  // 避免频繁更新

        if (last_refill_.compare_exchange_strong(last, now,
                std::memory_order_relaxed)) {
            // 补充令牌（不超过burst）
            double current = tokens_.load(std::memory_order_relaxed);
            double target = std::min(current + new_tokens, burst_);
            tokens_.store(target, std::memory_order_relaxed);
        }
    }

    static int64_t now_us() {
        return std::chrono::duration_cast<std::chrono::microseconds>(
            std::chrono::steady_clock::now().time_since_epoch()).count();
    }
};
```

#### 5.3 使用示例

```cpp
int main() {
    // 限制：平均100 QPS，允许突发200
    TokenBucket limiter(100.0, 200.0);

    // 模拟请求处理
    for (int i = 0; i < 1000; ++i) {
        if (limiter.tryAcquire()) {
            processRequest(i);  // 放行
        } else {
            rejectRequest(i);   // 返回429 Too Many Requests
        }
    }
}
```

### 7. 分布式限流：Redis方案

单机限流只能保护单个实例，集群级限流需要共享状态。

#### 7.1 Redis + Lua 令牌桶

```lua
-- token_bucket.lua
-- KEYS[1] = 限流key
-- ARGV[1] = rate (tokens/second)
-- ARGV[2] = burst (max tokens)
-- ARGV[3] = now (当前时间戳，微秒)
-- ARGV[4] = requested (请求的令牌数)

local key = KEYS[1]
local rate = tonumber(ARGV[1])
local burst = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local requested = tonumber(ARGV[4])

-- 获取当前状态
local data = redis.call('HMGET', key, 'tokens', 'last_refill')
local tokens = tonumber(data[1]) or burst  -- 首次默认满桶
local last_refill = tonumber(data[2]) or now

-- 计算令牌补充
local elapsed = (now - last_refill) / 1000000.0  -- 转换为秒
local new_tokens = elapsed * rate
tokens = math.min(tokens + new_tokens, burst)

-- 尝试获取令牌
local allowed = 0
if tokens >= requested then
    tokens = tokens - requested
    allowed = 1
end

-- 更新状态
redis.call('HMSET', key, 'tokens', tokens, 'last_refill', now)
redis.call('EXPIRE', key, math.ceil(burst / rate) + 1)  -- 自动过期

return allowed
```

#### 7.3 分布式限流的注意事项

```
1. 时钟偏差问题
   ├── 不同机器的时钟可能有几十ms偏差
   ├── 解决：使用Redis服务端时间（TIME命令），或容忍小误差
   └── 建议：对于秒级限流，几十ms偏差可接受

2. Redis单点问题
   ├── 方案A：Redis集群 + 各节点独立限流（总限额/节点数）
   ├── 方案B：Redis Sentinel + 主从切换
   └── 方案C：本地+远程双层限流（本地令牌桶做第一层）

3. 性能考量
   ├── 单次Redis调用RTT ≈ 0.1-0.5ms
   ├── 高QPS场景（10万+）每次请求都查Redis不现实
   └── 解决：批量获取令牌（每次取100个到本地）+ 本地消费

4. 限流粒度
   ├── 全局限流：一个key控制整个服务
   ├── 用户级限流：rate_limit:{user_id}
   └── 接口级限流：rate_limit:{api_path}
```

### 8. 生产实践：网关限流策略

#### 8.1 多层限流架构

```
┌──────────────────────────────────────────────────────────────┐
│                      限流架构（从外到内）                       │
│                                                              │
│  Layer 1: Nginx层                                            │
│  ├── limit_req模块（漏桶算法）                                │
│  ├── 粗粒度，防DDoS                                          │
│  └── 限制：10000 req/s per IP                                │
│                                                              │
│  Layer 2: 网关层（自研/Kong/Envoy）                           │
│  ├── 令牌桶（本地 + Redis分布式）                             │
│  ├── 细粒度：用户级/API级                                     │
│  └── 限制：用户100 req/s, API 5000 req/s                     │
│                                                              │
│  Layer 3: 服务层                                              │
│  ├── 信号量（控制并发数）                                     │
│  ├── 熔断器（Hystrix/Sentinel风格）                           │
│  └── 限制：最大并发200, 错误率>50%触发熔断                    │
└──────────────────────────────────────────────────────────────┘
```

#### 8.2 限流的三种响应策略

```cpp
enum class LimitAction {
    REJECT,     // 直接拒绝（返回429）
    QUEUE,      // 排队等待（漏桶模式）
    DEGRADE     // 服务降级（返回缓存数据/简化结果）
};

// 根据请求优先级选择策略
LimitAction decideLimitAction(const Request& req) {
    if (req.priority() == Priority::HIGH) {
        return LimitAction::QUEUE;      // VIP用户排队等
    }
    if (req.hasCache()) {
        return LimitAction::DEGRADE;    // 有缓存就降级返回
    }
    return LimitAction::REJECT;         // 普通请求直接拒绝
}
```

### 9. 总结

核心要点回顾：

1. **固定窗口**实现简单但有边界突刺问题，仅适合粗略统计
2. **滑动窗口**通过细分slot解决突刺，适合精确限流
3. **漏桶**保证绝对匀速输出，适合流量整形场景
4. **令牌桶**兼顾突发和平均速率，是**生产环境最常用的方案**
5. **分布式限流**用Redis + Lua保证原子性，注意时钟偏差和性能
6. 生产环境应采用**多层限流**（Nginx → 网关 → 服务），不同层负责不同粒度

选型建议：如果只选一种，**令牌桶**是首选——它允许合理突发（利用系统弹性），同时保证长期速率不超限。
