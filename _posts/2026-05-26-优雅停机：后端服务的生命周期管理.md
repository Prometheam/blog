上个月我们有个服务在滚动更新时出现了短暂的 502 错误，排查后发现是优雅停机的时序没处理好。这个问题看似简单，实际上涉及信号处理、连接排空、K8s 生命周期等多个层面。把这次排查和修复过程整理出来，供参考。

## 为什么优雅停机如此重要

粗暴地 kill 一个后端进程会导致：
- 正在处理的请求被截断，客户端收到 connection reset
- 写到一半的数据库事务被回滚（好情况）或留下脏数据（坏情况）
- 发到一半的消息丢失，下游状态不一致

在微服务架构下这些问题会被放大——一个服务的中断可能触发上游的重试风暴。

## 信号处理基础

Linux 下停服的标准信号是 SIGTERM，K8s 也是先发 SIGTERM，超时后发 SIGKILL：

```
K8s Pod 终止时序:
  ┌─────────────────────────────────────────────────┐
  │ 1. preStop hook 执行                             │
  │ 2. SIGTERM 发送给 PID 1                          │
  │ 3. 等待 terminationGracePeriodSeconds (默认30s)  │
  │ 4. SIGKILL 强杀                                  │
  └─────────────────────────────────────────────────┘
```

信号处理函数有严格限制——只能调用 async-signal-safe 函数。我的做法是在 handler 里只设置一个 atomic flag，主循环检测到后走正常关闭流程：

```cpp
static std::atomic<bool> g_shutdown_requested{false};

void signal_handler(int sig) {
    g_shutdown_requested.store(true, std::memory_order_relaxed);
}

// 注册时屏蔽其他信号，避免handler被中断
struct sigaction sa{};
sa.sa_handler = signal_handler;
sigemptyset(&sa.sa_mask);
sigaddset(&sa.sa_mask, SIGTERM);
sigaddset(&sa.sa_mask, SIGINT);
sa.sa_flags = 0;  // 不用 SA_RESTART，让阻塞调用返回EINTR
sigaction(SIGTERM, &sa, nullptr);
sigaction(SIGINT, &sa, nullptr);
```

## 优雅停机的标准流程

一个成熟的后端服务应该按以下顺序关闭：

```
收到 SIGTERM
    │
    ▼
┌─────────────────────────┐
│ 1. 标记健康检查为不健康   │  ← readiness probe 开始返回503
│    (停止接收新流量)       │
└───────────┬─────────────┘
            │ 等待 LB 感知 (2-3s)
            ▼
┌─────────────────────────┐
│ 2. 停止accept新连接      │  ← 关闭listening socket
└───────────┬─────────────┘
            │
            ▼
┌─────────────────────────┐
│ 3. 等待在途请求完成       │  ← 带超时，比如15s
│    (connection draining) │
└───────────┬─────────────┘
            │
            ▼
┌─────────────────────────┐
│ 4. 关闭下游连接          │  ← DB连接池、MQ producer
│    刷写缓冲区            │
└───────────┬─────────────┘
            │
            ▼
┌─────────────────────────┐
│ 5. 释放分布式锁/续约     │  ← etcd lease、Redis lock
│    注销服务注册           │
└───────────┬─────────────┘
            │
            ▼
        进程退出
```

## K8s 中的时序陷阱

我们踩的坑在第1步和第2步之间。K8s 从 Endpoint 中摘除 Pod 和发送 SIGTERM 是**并行**的，不是先后关系：

```
                    ┌── Endpoint Controller 摘除Pod (异步通知各Node的kube-proxy)
Pod 进入Terminating─┤
                    └── 执行preStop → 发SIGTERM

问题: SIGTERM到达时，某些Node的iptables规则可能还没更新
      → 新请求仍然路由到正在关闭的Pod → 502!
```

解决办法是在 preStop 中 sleep 几秒，给 Endpoint 变更时间传播：

```yaml
lifecycle:
  preStop:
    exec:
      command: ["sh", "-c", "sleep 5"]
terminationGracePeriodSeconds: 40  # 5s preStop + 30s drain + 5s buffer
```

## C++ 连接排空实现

我们基于 epoll 的服务框架里，connection draining 的核心逻辑：

```cpp
class Server {
    std::atomic<bool> draining_{false};
    std::atomic<int> active_requests_{0};
    std::condition_variable drain_cv_;
    std::mutex drain_mutex_;

public:
    void initiate_shutdown() {
        // 1. 关闭 listening fd，不再 accept
        close(listen_fd_);

        // 2. 标记排空状态
        draining_.store(true, std::memory_order_release);

        // 3. 等待在途请求完成，最多15s
        std::unique_lock lock(drain_mutex_);
        bool drained = drain_cv_.wait_for(lock, 15s, [this] {
            return active_requests_.load() == 0;
        });

        if (!drained) {
            LOG_WARN("Drain timeout, {} requests still active",
                     active_requests_.load());
            // 强制关闭剩余连接
            force_close_all_connections();
        }

        // 4. 关闭下游资源
        db_pool_.shutdown();
        mq_producer_.flush_and_close();
    }

    // 每个请求开始时调用
    bool try_acquire_request() {
        if (draining_.load(std::memory_order_acquire)) {
            return false;  // 拒绝新请求，返回503
        }
        active_requests_.fetch_add(1);
        return true;
    }

    // 每个请求结束时调用
    void release_request() {
        if (active_requests_.fetch_sub(1) == 1) {
            drain_cv_.notify_one();
        }
    }
};
```

## 数据库事务处理

关闭过程中最怕的是长事务。我的策略是：
1. 设置事务超时（比 drain timeout 短）
2. 对于写操作：允许完成当前事务，但不开启新事务
3. 对于读操作：可以直接中断，客户端重试即可

## 健康检查设计

Readiness 和 Liveness 的语义必须分清：

```
┌──────────────────────────────────────────────┐
│ /health/live  → 进程是否存活(liveness)        │
│   返回200: 进程正常                           │
│   返回5xx: K8s会重启Pod                       │
│                                              │
│ /health/ready → 是否能接受流量(readiness)     │
│   返回200: 可以接受请求                       │
│   返回503: 从Service Endpoint中摘除           │
│   停机时: 立即返回503                         │
└──────────────────────────────────────────────┘
```

关键点：停机时 liveness 仍应返回 200，否则 K8s 可能在 drain 期间就重启 Pod，导致 SIGKILL 提前到来。

## 分布式环境的额外考虑

如果服务持有分布式锁或 etcd lease，停机前必须主动释放：

- **etcd/ZK lease**：主动 Revoke，不要等 TTL 自然过期（可能要 30s）
- **Redis 分布式锁**：DEL 释放，避免其他节点等锁超时
- **消息队列 Consumer**：通知 Broker rebalance，而不是等心跳超时

这些动作应该在连接排空**之后**、进程退出**之前**执行，否则可能有其他节点接管了你的工作，但你还在处理旧请求。

经过这次优化，我们的滚动更新期间 502 错误从每次 50-100 个降到了 0。优雅停机看起来是个小事，但做好了，整个系统的可用性能提升一个档次。
