随着大模型和RAG架构的普及，向量数据库成了AI基础设施的核心组件。作为后端开发，我需要理解它的底层索引算法才能做出正确的技术选型和参数调优。本文深入分析向量检索的核心算法HNSW，并分享工程实践中的经验。

## 为什么需要向量数据库

传统数据库擅长精确匹配和范围查询，但无法处理语义相似性搜索：

```
"如何解决内存泄漏" ←→ "memory leak排查方法"
  ↑ 文本不同，但语义相近，余弦相似度 > 0.85

Embedding Model 将文本映射到高维向量空间：
  text → [0.12, -0.45, 0.78, ..., 0.33]  (768维或1536维)
```

应用场景：语义搜索、RAG（检索增强生成）、推荐系统、图片搜索、异常检测。

## 距离度量

```
+------------------+------------------+-------------------------+
| 度量             | 公式             | 适用场景                |
+------------------+------------------+-------------------------+
| L2 (欧氏距离)   | √Σ(ai-bi)²      | 绝对距离敏感的场景       |
| Cosine (余弦)   | 1 - (a·b)/(|a||b|) | 文本语义相似度        |
| Inner Product    | Σ(ai×bi)         | 归一化后的向量，等价cos  |
+------------------+------------------+-------------------------+
```

实践中，如果Embedding模型输出已归一化（模长为1），Inner Product等价于Cosine且计算更快。

## 索引算法演进

```
暴力搜索 → IVF → PQ → HNSW
  O(N)      O(√N)  压缩   O(logN)

┌──────────┬────────────┬────────────┬──────────────────┐
│ 算法     │ 构建时间   │ 查询速度   │ 内存占用          │
├──────────┼────────────┼────────────┼──────────────────┤
│ Flat     │ O(1)       │ O(N)       │ N×D×4 bytes      │
│ IVF      │ O(N)       │ O(N/nlist) │ N×D×4 + 聚类中心  │
│ PQ       │ O(N)       │ O(N)       │ N×M bytes (M<<D)  │
│ HNSW     │ O(N×logN)  │ O(logN)    │ N×(D×4 + M×8)    │
└──────────┴────────────┴────────────┴──────────────────┘
```

- **IVF**：将向量空间聚类为nlist个桶，查询时只搜索最近的nprobe个桶
- **PQ**：将D维向量分成M个子空间，每个子空间量化为1字节编码，64倍压缩
- **HNSW**：构建多层近邻图，从稀疏的高层逐步下降到稠密的底层，效率最高

## HNSW深度解析

HNSW（Hierarchical Navigable Small World）是当前最主流的ANN索引算法：

```
Layer 2 (最稀疏):  A ────────────── F
                   │                │
Layer 1:           A ── C ── D ── F ── H
                   │    │    │    │    │
Layer 0 (最稠密):  A─B─C─D─E─F─G─H─I─J─K

搜索过程（查找与Q最近的K个点）：
1. 从Layer 2的入口点A开始，贪心移动到F（因为F更近Q）
2. 下降到Layer 1，从F出发探索更多邻居
3. 下降到Layer 0，做精细搜索，维护大小为ef的候选集
4. 返回候选集中最近的K个点
```

**构建算法**：插入新节点时，随机决定其最高层（概率递减），在每层中寻找M个最近邻并建立双向边。

核心参数：

```
┌──────────────────┬──────────────────────────────────────┐
│ 参数             │ 作用                                 │
├──────────────────┼──────────────────────────────────────┤
│ M                │ 每层最大连接数，越大recall越高但内存增 │
│                  │ 推荐值：16~64                         │
├──────────────────┼──────────────────────────────────────┤
│ efConstruction   │ 构建时的候选集大小，越大索引质量越高   │
│                  │ 推荐值：100~500，构建后不可改          │
├──────────────────┼──────────────────────────────────────┤
│ efSearch         │ 搜索时的候选集大小，越大recall越高     │
│                  │ 推荐值：≥ topK，运行时可调             │
└──────────────────┴──────────────────────────────────────┘
```

性能与Recall的关系（100万768维向量实测）：

```
efSearch=64:   Recall@10=0.92, QPS=3500
efSearch=128:  Recall@10=0.97, QPS=2200
efSearch=256:  Recall@10=0.99, QPS=1100
efSearch=512:  Recall@10=0.995, QPS=550
```

## Milvus架构解析

Milvus是目前最成熟的开源向量数据库，采用存算分离架构：

```
                    ┌─────────────┐
                    │  SDK/Client │
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │   Proxy     │  (路由 + 鉴权)
                    └──────┬──────┘
            ┌──────────────┼──────────────┐
     ┌──────▼──────┐ ┌────▼────┐ ┌───────▼───────┐
     │  Query Node │ │Data Node│ │  Index Node   │
     │ (搜索服务)  │ │(写入)   │ │  (构建索引)   │
     └──────┬──────┘ └────┬────┘ └───────────────┘
            │              │
     ┌──────▼──────────────▼──────┐
     │     Object Storage (S3)    │  ← Segment文件
     └────────────────────────────┘
```

关键概念：
- **Segment**：数据分片单元，分为Growing（可写）和Sealed（只读、已建索引）
- **标量过滤**：先通过标量索引（倒排）缩小候选集，再做向量搜索
- **一致性级别**：Strong / Bounded Staleness / Eventually

## 完整的检索Pipeline

```
用户Query
    │
    ▼
┌──────────────┐
│ Embedding    │  text → vector (768d)
│ Model        │  推荐：bge-large-zh, text-embedding-3-large
└──────┬───────┘
       │
       ▼
┌──────────────┐
│ Vector DB    │  ANN检索 Top-50 候选
│ (HNSW Index) │
└──────┬───────┘
       │
       ▼
┌──────────────┐
│ Reranker     │  Cross-Encoder精排 Top-50 → Top-5
│ (bge-reranker│  精度远高于向量相似度
└──────┬───────┘
       │
       ▼
┌──────────────┐
│ LLM生成      │  基于Top-5文档生成回答
└──────────────┘
```

Reranker是关键环节：向量检索是双塔模型（query和doc独立编码），召回率高但精度有限；Reranker用Cross-Encoder对query-doc对做联合编码，精度大幅提升但速度慢，所以只对Top-N做精排。

## 生产环境注意事项

1. **分片策略**：按业务维度分Partition（如按租户），避免全库扫描
2. **增量索引**：新数据写入Growing Segment，后台异步Compact和建索引
3. **热加载**：索引更新时不中断服务，通过Segment切换实现
4. **资源隔离**：读写分离（QueryNode和DataNode独立扩缩容）
5. **监控指标**：Recall（需定期用暴力搜索验证）、P99延迟、索引构建延迟

// C++中使用FAISS的示例
#include <faiss/IndexHNSW.h>

// 构建索引
int d = 768;  // 向量维度
faiss::IndexHNSWFlat index(d, 32);  // M=32
index.hnsw.efConstruction = 200;
index.add(n, vectors);  // 批量添加向量
faiss::write_index(&index, "my_index.faiss");

// 搜索
index.hnsw.efSearch = 128;
std::vector<float> distances(k);
std::vector<faiss::idx_t> labels(k);
index.search(1, query_vec, k, distances.data(), labels.data());
```

向量数据库的核心挑战不在算法本身，而在工程化：如何在持续写入的同时保证搜索性能、如何在数十亿向量规模下控制成本、如何保证索引更新的实时性。理解了HNSW的原理和各方案的架构差异，才能在实际项目中做出合理的技术决策。
