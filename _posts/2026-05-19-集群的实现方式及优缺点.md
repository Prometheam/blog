在分布式系统中，集群是实现高可用、高性能和可扩展性的核心手段。不同的集群方式适用于不同的业务场景，本文梳理五种主流集群实现方式及其优缺点。

---

## 1. 主从复制（Master-Slave）

### 架构

一个主节点负责写入，多个从节点负责读取，主节点将数据同步到从节点。

```
        ┌──────────┐
        │  Client  │
        └────┬─────┘
             │ write
        ┌────▼─────┐
        │  Master  │
        └──┬───┬───┘
     sync  │   │  sync
    ┌──────▼┐ ┌▼──────┐
    │ Slave │ │ Slave │  ← read
    └───────┘ └───────┘
```

### 典型应用

MySQL 主从复制、Redis Sentinel、PostgreSQL Streaming Replication

### 优点

- 实现简单，读写分离提升读性能
- 从节点可作为备份，故障时手动/自动切换
- 读请求可以水平扩展（增加从节点）

### 缺点

- 写入仍是单点瓶颈，无法水平扩展写能力
- 主从同步有延迟，存在数据不一致窗口
- 主节点故障需要选举/切换，有短暂不可用

---

## 2. 对等集群（Peer-to-Peer）

### 架构

所有节点地位相等，都可以接受读写请求，节点间互相同步数据。

```
    ┌────────┐     ┌────────┐
    │ Node A │◄───►│ Node B │
    └───┬────┘     └────┬───┘
        │               │
        │  ┌────────┐   │
        └─►│ Node C │◄──┘
           └────────┘
    所有节点对等，互相同步
```

### 典型应用

Cassandra、CouchDB、Elasticsearch、Riak

### 优点

- 无单点故障，任意节点宕机不影响整体
- 读写都可水平扩展
- 部署和运维较灵活

### 缺点

- 一致性难保证（通常是最终一致性）
- 写冲突需要解决（向量时钟、Last-Write-Wins 等）
- 网络通信开销大（每个节点都要互相同步）

---

## 3. 分片集群（Sharding/Partitioning）

### 架构

将数据按规则（哈希、范围等）分散到不同节点，每个节点只负责一部分数据。

```
    Client Request (key = "user:1001")
           │
           │  hash(key) % 3 = 1
           ▼
    ┌──────────┐  ┌──────────┐  ┌──────────┐
    │ Shard 0  │  │ Shard 1  │  │ Shard 2  │
    │ key 0-99 │  │key 100-199│ │key 200-299│
    └──────────┘  └──────────┘  └──────────┘
```

### 典型应用

Redis Cluster、MongoDB Sharding、TiDB、HBase

### 分片策略

| 策略 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| 哈希分片 | `hash(key) % N` | 数据分布均匀 | 扩容需 rehash |
| 范围分片 | 按 key 范围划分 | 范围查询高效 | 容易数据倾斜 |
| 一致性哈希 | 哈希环 + 虚拟节点 | 扩容影响小 | 实现稍复杂 |

### 优点

- 读写性能线性扩展
- 单节点数据量小，查询效率高
- 支持海量数据存储

### 缺点

- 跨分片查询/事务复杂且性能差
- 数据倾斜问题（热点 key）
- 扩容缩容需要数据迁移
- 运维复杂度高

## 4. 一致性协议集群（Consensus-based）

### 架构

通过 Raft、Paxos 等一致性协议选举 Leader，所有写入经 Leader 同步到多数节点后确认。

```
    Client
      │ write
      ▼
    ┌────────┐  replicate  ┌──────────┐
    │ Leader │────────────►│ Follower │
    └────┬───┘             └──────────┘
         │  replicate      ┌──────────┐
         └────────────────►│ Follower │
                           └──────────┘
    多数节点确认后才返回成功
```

### 典型应用

etcd（Raft）、ZooKeeper（ZAB）、TiKV（Multi-Raft）、Consul

### Raft 协议核心流程

1. **Leader 选举**：当 Leader 失联时，Follower 发起投票选新 Leader
2. **日志复制**：Leader 将写入作为日志条目复制到 Follower
3. **提交确认**：多数节点（N/2 + 1）确认后，日志被提交
4. **状态机应用**：已提交的日志应用到状态机

### 优点

- 强一致性保证（线性一致性）
- 自动故障检测和 Leader 选举
- 数据不丢失（多数派写入）

### 缺点

- 写入性能受限（需要多数节点确认，受网络延迟影响）
- 节点数量通常为奇数（3/5/7），扩展性有限
- 实现复杂度高
- 网络分区时少数派不可用（CP 系统）

## 5. 代理集群（Proxy-based）

### 架构

客户端请求统一发送到代理层，由代理层路由到后端真实节点。

```
    Client ──► Proxy ──┬──► Node A
                       ├──► Node B
                       └──► Node C
```

### 典型应用

Twemproxy、Codis、MySQL Proxy、HAProxy、Nginx 负载均衡

### 优点

- 客户端无感知，不需要修改客户端代码
- 代理层可以做负载均衡、读写分离、故障转移
- 后端节点可以灵活增减
- 可以做协议转换、监控、限流等

### 缺点

- 代理层本身是单点/瓶颈（需要代理层也做高可用）
- 多一跳网络延迟
- 代理层无法支持所有命令（如 Redis 跨节点多 key 操作）
- 代理层状态管理复杂

## 对比总结

| 方式 | 一致性 | 写扩展 | 读扩展 | 复杂度 | 适用场景 |
|------|--------|--------|--------|--------|----------|
| 主从复制 | 弱一致 | ❌ | ✅ | 低 | 读多写少、简单高可用 |
| 对等集群 | 最终一致 | ✅ | ✅ | 中 | 高可用、容忍最终一致 |
| 分片集群 | 取决于实现 | ✅ | ✅ | 高 | 海量数据、高吞吐 |
| 一致性协议 | 强一致 | ❌ | ⚠️ | 高 | 元数据、配置中心 |
| 代理集群 | 取决于后端 | ⚠️ | ✅ | 中 | 客户端无侵入需求 |

## 实际生产中的组合方案

实际架构通常**组合多种方式**：

| 系统 | 组合方式 |
|------|----------|
| **Redis Cluster** | 分片 + 每个分片内主从复制 |
| **TiDB** | 分片（Region）+ 每个 Region 内 Raft 协议 |
| **MongoDB** | 分片 + 每个分片内副本集（主从 + 自动选举） |
| **Kafka** | 分片（Partition）+ 每个 Partition 内主从复制 |
| **MySQL 集群** | 代理（MyCat/ShardingSphere）+ 后端主从复制 |

---

## 选型建议

选择集群方案时，核心考虑以下因素：

1. **一致性要求**：强一致选一致性协议，最终一致选对等/Saga
2. **数据规模**：数据量大选分片，数据量小选主从或一致性协议
3. **读写比例**：读多写少选主从，读写均衡选分片或对等
4. **可用性要求**：极高可用选对等集群（无单点），可接受短暂不可用选主从
5. **运维能力**：团队小选简单方案（主从/代理），团队强选分片/Raft
