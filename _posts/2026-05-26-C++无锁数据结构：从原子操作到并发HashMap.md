最近在优化我们网关的连接池时，mutex 在高并发场景下成了瓶颈。于是我花了两周时间把核心数据结构替换为无锁实现，性能提升了约 40%。这篇文章记录一下这个过程中的思考和踩坑。

## 三种非阻塞进度保证

先厘清概念，这三个层次经常被混淆：

```
+------------------+----------------------------------------+
| 保证级别          | 含义                                   |
+------------------+----------------------------------------+
| Wait-Free        | 每个线程在有限步内完成操作               |
| Lock-Free        | 至少有一个线程在有限步内完成操作          |
| Obstruction-Free | 无竞争时单线程能在有限步内完成            |
+------------------+----------------------------------------+
```

实际工程中 Lock-Free 是最常用的折中——比 Wait-Free 简单得多，又能避免 mutex 带来的优先级反转和线程饿死问题。

## Treiber Stack：最经典的无锁结构

无锁栈是入门级实现，核心就一个 CAS 循环：

```cpp
template<typename T>
class LockFreeStack {
    struct Node {
        T data;
        Node* next;
        Node(T val) : data(std::move(val)), next(nullptr) {}
    };
    std::atomic<Node*> head_{nullptr};

public:
    void push(T val) {
        auto* node = new Node(std::move(val));
        node->next = head_.load(std::memory_order_relaxed);
        // CAS 失败则自旋重试，head_ 被别的线程改了
        while (!head_.compare_exchange_weak(
            node->next, node,
            std::memory_order_release,
            std::memory_order_relaxed)) {}
    }

    std::optional<T> pop() {
        Node* old_head = head_.load(std::memory_order_acquire);
        while (old_head &&
               !head_.compare_exchange_weak(
                   old_head, old_head->next,
                   std::memory_order_acq_rel,
                   std::memory_order_acquire)) {}
        if (!old_head) return std::nullopt;
        T val = std::move(old_head->data);
        // 这里 delete old_head 是不安全的！
        return val;
    }
};
```

看起来简洁，但 `pop()` 里那行注释揭示了无锁编程最大的噩梦——**内存回收**。

## ABA 问题与内存回收

假设线程 A 读到 `head = X`，被调度出去。线程 B 弹出 X 并释放，又 push 了新节点恰好分配到同一地址 X。线程 A 恢复后 CAS 成功，但 `X->next` 已经是野指针了。

```
时间线:
  T1: 线程A读 head=X, X->next=Y
  T2: 线程B pop X, pop Y, push Z(地址恰好=X)
  T3: 线程A CAS(X, Y) 成功! 但Y已释放 → 灾难
```

三种主流解决方案对比：

```
+----------------+----------+----------+-------------+
| 方案            | 延迟回收 | 内存开销 | 实现复杂度   |
+----------------+----------+----------+-------------+
| Tagged Pointer | 低       | 低       | 中（需双宽CAS）|
| Hazard Pointer | 中       | O(N*K)   | 高           |
| Epoch-Based    | 高       | 低       | 中           |
+----------------+----------+----------+-------------+
```

我在项目中选择了 Epoch-Based Reclamation（EBR），因为它的读侧开销最小——进入临界区只需递增一个线程局部计数器。缺点是如果某个线程长时间不推进 epoch，垃圾会堆积。

## 无锁 HashMap 设计

真正有工程价值的是并发 HashMap。我参考了 Split-Ordered Lists 的思路：

```
Bucket Array (可原子扩容):
  [0] → 0 → 4 → 8 → ...
  [1] → 1 → 5 → 9 → ...
  [2] → 2 → 6 → 10 → ...
  [3] → 3 → 7 → 11 → ...

所有节点实际在同一条链表上，bucket只是"快捷入口"
通过 bit-reversal 排序使扩容时无需移动节点
```

关键操作都是 CAS-based 的链表插入/删除。对比 Java ConcurrentHashMap 的分段锁方案：

```
              | Split-Ordered (Lock-Free) | Striped Locks (Java风格) |
--------------+---------------------------+-------------------------+
| 读操作       | 无等待                     | 可能阻塞于写锁           |
| 写冲突       | CAS重试                   | 锁单个segment            |
| 扩容         | 渐进式，不阻塞读写         | 需要锁所有segments       |
| 实现复杂度   | 极高                       | 中等                     |
| 调试难度     | 噩梦级                     | 正常                     |
```

## 性能实测

在 96 核机器上用不同线程数跑 80% 读 + 20% 写的混合负载：

```
Throughput (Mops/s):
  Threads:     4      16      64      96
  mutex:      12.3    8.7     4.2     3.1   ← 严重退化
  spinlock:   14.1   11.2     6.8     5.4
  lock-free:  13.8   22.4    31.6    35.2   ← 近线性扩展
```

低竞争（4线程）时 mutex 反而更快，因为无锁的 CAS 重试和内存屏障有开销。但到 64 线程以上，无锁方案的优势就非常明显了。

## 什么时候不该用无锁

说实话，我现在对无锁数据结构的态度是**能不用就不用**：

1. **调试地狱**：数据竞争 bug 可能在线上跑几天才复现一次，TSan 也不一定能捕获所有 memory order 错误
2. **正确性验证难**：我们用了 CDSChecker 做形式化验证，学习曲线极陡
3. **性能不一定更好**：如果竞争不激烈，一把 mutex 加 `std::unordered_map` 足够了
4. **内存回收复杂**：EBR/HP 本身就是一套小型 GC，引入了额外的工程负担

我的建议是：先用 `std::shared_mutex` 做读写分离，profile 证明锁是瓶颈后再考虑无锁方案。而且优先选择经过生产验证的库（如 folly::ConcurrentHashMap、libcds），不要自己从零实现。

九年来我见过太多"为了无锁而无锁"的代码，最后出了诡异 bug 没人敢改。**正确性永远优先于性能。**
