在微服务架构中，一个业务操作往往需要跨多个服务协调完成，传统的单机事务（ACID）无法直接应用。分布式事务解决方案应运而生，旨在保证跨服务数据的一致性。本文介绍四种主流方案：2PC、3PC、TCC 和 Saga。

---

## 2PC（两阶段提交）

### 1. 概念

2PC 全称两阶段提交协议（Two-Phase Commit），是分布式系统中用于保证原子性的经典算法。

**核心目标**：确保一个涉及多个独立节点的分布式事务，要么全部成功（所有节点全部提交），要么全部失败（所有节点全部回滚）。它不允许出现部分节点成功、部分节点失败的状态。

### 2. 核心角色

在一个 2PC 事务中，通常包含两个角色：

- **协调者（Coordinator）**：只有一个。负责统一管理整个分布式事务的流程，驱动参与者进行提交或回滚。通常由应用程序、中间件或数据库担任。
- **参与者（Participant）**：有多个。每个参与者负责管理自身数据操作（本地事务），并根据协调者的指令执行最终的提交或回滚。

### 3. 协议的两个阶段

#### 第一阶段：投票阶段（Prepare）

这个阶段的目的是"询问"所有参与者是否准备好提交。

1. 协调者向所有参与者发送 `PREPARE` 请求（或称 `VOTE_REQUEST`），其中包含需要执行的事务信息。
2. 每个参与者收到请求后，会执行本地事务的所有操作（但不提交），将 undo 和 redo 信息写入日志（为了故障恢复）。
3. 参与者根据自身情况，向协调者投票：
   - 如果本地事务执行成功，参与者回复 `YES`（或 `AGREEMENT`），表示已准备好提交。
   - 如果本地事务执行失败（如违反约束、网络中断等），参与者回复 `NO`（或 `ABORT`）。

> **关键点**：参与者在回复 YES 后，就进入了一种"不确定状态"。它已经承诺会服从协调者的最终指令（提交或回滚），在收到最终指令前，它必须锁定其持有的相关资源，阻止其他事务访问。这是 2PC 的一个主要缺点。

#### 第二阶段：提交/回滚阶段（Commit/Rollback）

这个阶段的目的是根据第一阶段的投票下达最终指令。

**情况一：所有参与者都回复 YES**

1. 协调者决定提交事务
2. 协调者向所有参与者发送 `COMMIT` 请求
3. 参与者收到 `COMMIT` 请求后，正式提交其本地事务，释放持有的锁和资源
4. 参与者完成提交后，向协调者发送 `ACK` 确认消息
5. 协调者收到所有参与者的 `ACK` 消息后，整个分布式事务完成

**情况二：任何一个或多个参与者回复 NO 或超时未响应**

1. 协调者决定回滚事务
2. 协调者向所有参与者发送 `ROLLBACK` 请求
3. 参与者收到 `ROLLBACK` 请求后，利用之前写入的 undo 日志回滚其本地事务，释放持有的锁和资源
4. 参与者完成回滚后，向协调者发送 `ACK` 确认消息
5. 协调者收到所有参与者的 `ACK` 消息后，整个分布式事务终止

### 4. 优缺点

**优点**：
- 严格保证了分布式事务的原子性
- 实现相对简单，被广泛应用于数据库（如 XA 协议）

**缺点**：
- **同步阻塞**：最大的问题。参与者投票 YES 后到收到最终指令前，持有的资源锁一直被占用，其他事务必须等待。如果协调者宕机，锁将一直被持有，导致系统"卡住"。
- **单点故障**：协调者一旦在发送 PREPARE 之后宕机，所有参与者将处于"不确定"状态，资源被无限期锁定。
- **数据不一致**：第二阶段中，如果协调者只发送了部分 COMMIT 消息后宕机，部分参与者提交而其他参与者未提交，导致数据不一致。

## 3PC（三阶段提交）

### 1. 概念

3PC 是对 2PC 的改进，将第一阶段拆分为两步，引入超时机制来降低阻塞问题。三个阶段分别是：**CanCommit**、**PreCommit**、**DoCommit**。

### 2. 三个阶段

#### 第一阶段：CanCommit

1. 协调者向所有参与者发送 `CanCommit` 请求，询问是否可以执行事务。
2. 参与者判断自身条件（资源是否可用、是否满足约束等），回复 `YES` 或 `NO`。
3. 这个阶段**不执行实际操作、不锁定资源**，只是一次"轻量级预检"。

#### 第二阶段：PreCommit

如果所有参与者回复 YES：

1. 协调者发送 `PreCommit` 请求
2. 参与者执行事务操作（但不提交），记录 undo/redo 日志
3. 参与者回复 `ACK` 表示准备就绪

如果有参与者回复 NO 或超时：

1. 协调者发送 `ABORT` 请求
2. 参与者中断事务

#### 第三阶段：DoCommit

如果协调者收到所有 ACK：

1. 协调者发送 `DoCommit` 请求
2. 参与者正式提交事务，释放资源
3. 参与者回复 `ACK`

**关键改进——超时机制**：
- 如果参与者在 PreCommit 阶段后长时间没收到协调者的 `DoCommit` 指令，参与者会**自动提交**（因为进入 PreCommit 说明所有人都准备好了，大概率应该提交）
- 这解决了 2PC 中协调者宕机导致参与者无限阻塞的问题

### 3. 对比 2PC 的改进

| 对比项 | 2PC | 3PC |
|--------|-----|-----|
| 阻塞问题 | 协调者宕机则无限阻塞 | 参与者超时后自动提交 |
| 阶段数 | 2 个 | 3 个 |
| 数据一致性 | 可能不一致 | 降低了不一致概率但未完全消除 |
| 性能 | 较好 | 多一轮通信，性能稍差 |
| 实际应用 | 广泛（XA） | 较少使用 |

### 4. 缺点

- 多一轮网络通信，延迟更高
- 在网络分区场景下仍可能出现数据不一致（参与者超时自动提交，但实际应该回滚）
- 实现复杂度高，实际工程中很少使用

## TCC（Try-Confirm-Cancel）

### 1. 概念

TCC 是一种**业务层面**的分布式事务方案，将每个业务操作分为三个步骤：Try（预留）、Confirm（确认）、Cancel（取消）。

与 2PC 不同的是，TCC 不依赖数据库的事务机制，而是由业务代码自己实现"预留-确认-取消"的逻辑。

### 2. 三个阶段

#### Try 阶段（资源预留）

- 检查业务条件是否满足
- 预留必要的业务资源（冻结、锁定）
- **不执行真正的业务操作**

示例：转账场景中，Try 阶段将转出账户的金额从"可用余额"冻结到"冻结金额"中。

#### Confirm 阶段（确认提交）

- 所有参与者的 Try 都成功后执行
- 真正执行业务操作，使用 Try 阶段预留的资源
- **要求幂等**（可能重试）

示例：将冻结金额扣除，将转入账户可用余额增加。

#### Cancel 阶段（取消回滚）

- 任一参与者 Try 失败时执行
- 释放 Try 阶段预留的资源
- **要求幂等**（可能重试）

示例：将冻结金额释放回可用余额。

### 3. 执行流程

```
业务发起方
    │
    ├─ Try(服务A)  ─── 成功
    ├─ Try(服务B)  ─── 成功
    ├─ Try(服务C)  ─── 成功
    │
    │  全部成功 → Confirm
    ├─ Confirm(服务A)
    ├─ Confirm(服务B)
    └─ Confirm(服务C)

    │  任一失败 → Cancel
    ├─ Cancel(服务A)
    ├─ Cancel(服务B)
    └─ Cancel(服务C)
```

### 4. 优缺点

**优点**：
- **无长时间锁占用**：Try 阶段只是冻结资源，不加数据库锁
- **最终一致性**：通过重试 + 幂等保证最终一致
- **灵活性高**：完全由业务代码控制，不依赖底层数据库支持
- **性能好**：没有全局锁，并发度高

**缺点**：
- **业务侵入大**：每个服务都需要实现 Try/Confirm/Cancel 三个接口
- **开发成本高**：需要考虑幂等性、空回滚、悬挂等问题
- **一致性保证依赖框架**：需要可靠的 TCC 框架（如 Seata、ByteTCC）来协调

### 5. 需要处理的异常场景

| 异常场景 | 说明 | 处理方式 |
|----------|------|----------|
| 空回滚 | Cancel 被调用，但对应的 Try 从未执行过 | Cancel 中检查 Try 是否执行过，未执行则直接返回成功 |
| 悬挂 | Cancel 先于 Try 到达（网络乱序） | Try 执行前检查是否已 Cancel，若已取消则拒绝执行 |
| 幂等 | Confirm/Cancel 可能被重复调用 | 通过事务状态表或唯一 ID 保证幂等 |

## Saga

### 1. 概念

Saga 是一种**长事务解决方案**，将一个分布式事务拆分为多个本地事务（称为子事务），每个子事务都有对应的**补偿操作**。如果某个子事务失败，则按反向顺序执行前面已成功子事务的补偿操作。

Saga 最早由 Hector Garcia-Molina 和 Kenneth Salem 在 1987 年的论文中提出。

### 2. 核心思想

```
T1 → T2 → T3 → ... → Tn          正向事务链
C1 ← C2 ← C3 ← ... ← Cn          对应补偿链

如果 T3 失败：执行 C2 → C1（反向补偿）
```

- 每个 `Ti` 是一个本地事务，独立提交
- 每个 `Ci` 是 `Ti` 的补偿操作（语义上的逆操作）
- 不保证隔离性，是一种**最终一致性**方案

### 3. 两种执行模式

#### 编排模式（Choreography）

- 没有中心协调者
- 每个服务完成本地事务后，发布事件通知下一个服务
- 服务之间通过事件（消息队列）驱动

```
订单服务 ──创建订单──→ 库存服务 ──扣减库存──→ 支付服务 ──扣款──→ 完成
    │                     │                     │
    └── 补偿：取消订单 ←── 补偿：恢复库存 ←── 补偿：退款 ←── 失败
```

**优点**：简单、松耦合、无单点故障
**缺点**：流程分散难追踪、服务多时逻辑复杂、循环依赖风险

#### 编排模式（Orchestration）

- 有一个中心**协调器（Orchestrator）**
- 协调器负责调用各服务、决定执行顺序、触发补偿

```
协调器
  ├─ 调用: 订单服务.创建订单()
  ├─ 调用: 库存服务.扣减库存()
  ├─ 调用: 支付服务.扣款()
  │
  │  支付失败 →
  ├─ 补偿: 库存服务.恢复库存()
  └─ 补偿: 订单服务.取消订单()
```

**优点**：流程集中可控、易于追踪和调试、避免循环依赖
**缺点**：协调器是单点、实现复杂度较高

### 4. 优缺点

**优点**：
- **无锁**：每个子事务独立提交，不持有跨服务的锁
- **高可用**：适合长流程业务（如订单流、审批流）
- **性能好**：不需要等待所有参与者准备完毕
- **适合微服务**：天然适配事件驱动架构

**缺点**：
- **不保证隔离性**：中间状态对外可见（如订单已创建但支付未完成）
- **补偿逻辑复杂**：有些操作难以补偿（如发送邮件、调用外部 API）
- **最终一致性**：不适合对实时一致性要求极高的场景

### 5. 适用场景

- 电商订单流程（创建订单 → 扣库存 → 支付 → 发货）
- 旅行预订（订机票 → 订酒店 → 订租车）
- 跨行转账
- 审批流程

## 四种方案对比

| 对比维度 | 2PC | 3PC | TCC | Saga |
|----------|-----|-----|-----|------|
| 一致性 | 强一致 | 强一致 | 最终一致 | 最终一致 |
| 性能 | 低（全局锁） | 低（多轮通信） | 高 | 高 |
| 业务侵入 | 无 | 无 | 高（3个接口） | 中（补偿接口） |
| 实现复杂度 | 低 | 高 | 高 | 中 |
| 隔离性 | 有 | 有 | 有（Try 冻结） | 无 |
| 适用场景 | 数据库层面 | 理论研究 | 短流程、高一致性 | 长流程、高可用 |
| 典型框架 | XA、MySQL XA | 少见 | Seata TCC、ByteTCC | Seata Saga、Temporal |

---

## 总结

选择分布式事务方案时，核心考虑三个因素：

1. **一致性要求**：强一致选 2PC/TCC，最终一致选 Saga
2. **性能要求**：高并发选 TCC/Saga，低频可用 2PC
3. **业务复杂度**：简单短事务用 TCC，长流程用 Saga，跨数据库用 2PC

在实际微服务架构中，**TCC** 和 **Saga** 是最常用的方案，通常借助框架（如阿里 Seata）来降低实现成本。
