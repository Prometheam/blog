做 C++ 后端开发，迟早要和 Linux 调度器打交道。当你的服务 P99 延迟抖动、CPU 利用率上不去、或者实时任务被饿死时，理解调度器的工作原理就不再是"可选知识"了。这篇文章记录我这些年对 Linux 调度子系统的理解。

## CFS：完全公平调度器

自 Linux 2.6.23 起，CFS 成为默认调度器。核心思想很优雅——**跟踪每个进程的虚拟运行时间（vruntime），始终选择 vruntime 最小的进程执行**。

```
CFS 运行队列（红黑树）:

         [vruntime=50ms]
         /              \
  [vruntime=30ms]   [vruntime=80ms]  ← 最右节点：运行最多
        /
 [vruntime=10ms]  ← 最左节点：下一个被调度
```

### vruntime 的计算

```
vruntime += delta_exec * (NICE_0_WEIGHT / weight)
```

nice 值为 0 的进程 weight = 1024。nice 每 +1，weight 约降 22%。这意味着 nice -5 的进程获得的 CPU 时间大约是 nice 0 的 3 倍。

### 时间片：target latency 与 minimum granularity

CFS 没有固定时间片，而是用两个参数动态计算：

- `sched_latency_ns`（默认 6ms）：一轮调度周期，所有可运行进程各运行一次
- `sched_min_granularity_ns`（默认 0.75ms）：单次最小运行时间

当可运行进程数 > `sched_latency / min_granularity = 8` 时，每个进程的时间片 = min_granularity，调度周期自动拉长。

## 实时调度策略

Linux 提供三种实时调度策略，优先级高于 CFS：

```
┌────────────────────────────────────────────────────────┐
│  优先级   │  策略            │  行为                    │
├───────────┼──────────────────┼──────────────────────────┤
│  最高     │  SCHED_DEADLINE  │  EDF 调度，保证截止时间  │
│  高       │  SCHED_FIFO      │  先到先服务，不抢占同级  │
│  中高     │  SCHED_RR        │  时间片轮转（默认100ms） │
│  普通     │  SCHED_OTHER     │  CFS 调度               │
└────────────────────────────────────────────────────────┘
```

实际使用中，我在低延迟网关服务里用过 `SCHED_FIFO`：

```cpp
#include <sched.h>
#include <pthread.h>

void SetRealtimePriority(pthread_t tid, int priority) {
    struct sched_param param;
    param.sched_priority = priority;  // 1-99, 越大越优先
    int ret = pthread_setschedparam(tid, SCHED_FIFO, &param);
    if (ret != 0) {
        // 需要 CAP_SYS_NICE 权限
        perror("pthread_setschedparam");
    }
}
```

注意：实时线程如果死循环会导致系统挂起，生产环境务必设置 `/proc/sys/kernel/sched_rt_runtime_us`（默认 950000，即 RT 进程最多占 95% CPU）。

## SCHED_DEADLINE：截止时间调度

Linux 3.14 引入，适合周期性实时任务。指定三个参数：

```
runtime / deadline / period
  ↓         ↓         ↓
每个周期内，任务在 deadline 前必须获得 runtime 的 CPU 时间

示例：音频处理线程
  period   = 10ms（每10ms处理一帧）
  deadline = 8ms（必须在8ms内完成）
  runtime  = 2ms（实际需要2ms CPU）
```

```cpp
#include <linux/sched.h>

struct sched_attr attr = {};
attr.size = sizeof(attr);
attr.sched_policy = SCHED_DEADLINE;
attr.sched_runtime  =  2000000;  // 2ms (ns)
attr.sched_deadline =  8000000;  // 8ms
attr.sched_period   = 10000000;  // 10ms
sched_setattr(0, &attr, 0);
```

## CPU 亲和性与 NUMA 调度

多核系统上，进程在 CPU 间迁移会导致缓存失效。关键路径线程应绑核：

```bash
# 将进程 PID 绑定到 CPU 2-3
taskset -pc 2-3 $PID

# 启动时直接绑定
taskset -c 0-3 ./my_server
```

NUMA 架构下，跨节点访存延迟可达本地的 2-3 倍。调度器通过 `numa_balancing` 自动迁移页面，但对延迟敏感的服务建议手动控制：

```bash
# 在 NUMA node 0 上分配内存并运行
numactl --cpunodebind=0 --membind=0 ./my_server
```

## cgroup CPU 带宽控制

容器环境下，cgroup v2 的 CPU 控制器用 `cpu.max` 限制带宽：

```bash
# 格式: quota period (微秒)
# 限制该 cgroup 每 100ms 最多用 200ms CPU（即 2 核）
echo "200000 100000" > /sys/fs/cgroup/my_service/cpu.max
```

踩坑经验：`cpu.cfs_quota_us` 是全局配额，不是 per-core。设置 200ms/100ms 周期时如果只有单线程，实际只能用满 1 核，另 1 核的配额浪费了。多线程服务才能充分利用配额。

## 调度延迟分析与调优

使用 `perf sched` 分析调度延迟：

```bash
# 记录 5 秒调度事件
perf sched record -- sleep 5

# 查看延迟统计
perf sched latency --sort max

# 查看 CPU 切换时间线
perf sched timehist
```

常见调优手段：

```bash
# 查看/设置实时优先级
chrt -p $PID
chrt -f 50 ./realtime_task    # SCHED_FIFO, priority=50

# 减少调度延迟：缩短 sched_latency（进程少时）
sysctl kernel.sched_latency_ns=3000000

# 关闭 NUMA balancing（已手动绑核时）
sysctl kernel.numa_balancing=0
```

## 实战总结

| 场景 | 建议 |
|------|------|
| 普通后端服务 | CFS 默认即可，关注 cgroup 配额 |
| 低延迟网关/交易系统 | SCHED_FIFO + 绑核 + 关闭 irqbalance |
| 音视频处理 | SCHED_DEADLINE，精确控制周期 |
| 容器混部 | cpu.max 限制 + cpu.weight 相对权重 |

这些年的体会：调度器调优是最后手段，先确保应用层没有锁竞争、内存分配瓶颈等问题。内核调度器已经非常聪明，大多数时候不需要你教它怎么做——但当你确实需要确定性延迟时，理解这些机制就是你的武器。
