### 引言

系统设计面试不是考你背方案，而是考你的工程思维：如何在约束条件下做出合理的技术选型，如何量化需求并推导出架构参数，如何识别瓶颈并提出扩展方案。

本文用4个经典题目（短链服务、消息队列、搜索引擎、Feed流）展示系统设计的思维框架和回答模板。

---

### 1. 系统设计思维框架

```
  系统设计5步法（每题都用这个框架）：

  Step 1: 需求澄清 (5分钟)
  ──────────────────────
  - 功能需求：核心用例是什么？
  - 非功能需求：QPS、延迟、可用性、一致性
  - 规模估算：用户量、数据量、存储量

  Step 2: 高层架构 (5分钟)
  ──────────────────────
  - 画出核心组件和数据流
  - 确定API接口
  - 数据模型设计

  Step 3: 核心组件设计 (15分钟)
  ──────────────────────
  - 存储选型（SQL vs NoSQL vs Cache）
  - 算法选择
  - 关键流程的时序

  Step 4: 扩展性设计 (10分钟)
  ──────────────────────
  - 瓶颈分析
  - 分片策略
  - 缓存策略
  - 异步化

  Step 5: 额外讨论 (5分钟)
  ──────────────────────
  - 监控告警
  - 容错和降级
  - 安全考虑
```

### 2. 题目一：短链服务

**需求**：输入长URL，返回短URL；访问短URL重定向到长URL。

```
  规模估算：
  - 每天创建100万条短链
  - 读写比 100:1 → 每天1亿次重定向
  - 保留5年 → 18亿条记录
  - 每条(短码6位+长URL 200字节) → ~360GB存储

  QPS:
  - 写: 100万/86400 ≈ 12 QPS（低）
  - 读: 1亿/86400 ≈ 1200 QPS（中）
  - 峰值5倍: 6000 QPS

  延迟要求: 重定向 < 50ms（P99）
```

```
  架构设计：

  ┌────────┐      ┌──────────────┐      ┌──────────────┐
  │ Client │─────→│   API Server │─────→│   Database   │
  └────────┘      └──────┬───────┘      └──────────────┘
                         │
                   ┌─────▼─────┐
                   │   Cache   │ (Redis: 热门短链)
                   └───────────┘

  核心设计决策：

  1. 短码生成：
     方案A: 自增ID + Base62编码 → 简单，但可预测
     方案B: 随机生成 + 碰撞检测 → 不可预测，但需检查唯一
     方案C: 预生成短码池 → 高效，但需要后台服务维护

     推荐: 分布式ID生成(Snowflake) + Base62
     6位Base62: 62^6 = 568亿种 → 足够5年使用

  2. 存储：
     - MySQL/PostgreSQL (主存储)
     - Redis (缓存热门短链, TTL=24h)
     - 读多写少 → 缓存命中率高(>95%)

  3. 重定向：
     - 301 永久重定向: 浏览器缓存，减少服务压力，但无法统计
     - 302 临时重定向: 每次都经过服务，可以统计访问量
     → 推荐302 + 服务端异步记录统计
```

```
  短码生成（Base62编码）：

  uint64_t id = snowflakeGenerator.nextId();  // 全局唯一ID
  std::string shortCode = base62Encode(id);   // 如 "aB3x9K"

  base62字符集: a-z(26) + A-Z(26) + 0-9(10) = 62

  优化：
  - 热门短链缓存到Redis (SET short:aB3x9K "https://original-url" EX 86400)
  - 长URL去重(查找是否已存在) → 同一长URL返回相同短码
  - 自定义短码(vanity URL) → 先检查是否已被占用
```

### 3. 题目二：消息队列

**需求**：设计一个类Kafka的分布式消息队列。

```
  需求澄清：
  - 吞吐: 百万级消息/秒
  - 延迟: P99 < 10ms
  - 持久化: 消息不丢失
  - 有序性: 分区内有序
  - 消费模式: 推/拉均支持
  - 回溯: 支持从任意位置重新消费

  数据模型：
  Topic → 多个Partition → 每个Partition是有序日志
```

```
  架构设计：

  Producer                         Broker Cluster                    Consumer Group
  ┌────────┐                    ┌─────────────────────┐           ┌────────────┐
  │Producer│─── Partition Key ─→│ Broker 0            │←── pull ──│Consumer 0  │
  │        │    (决定发到哪个   │  Partition 0        │           │(负责P0)    │
  └────────┘     Partition)     │  Partition 1        │           └────────────┘
  ┌────────┐                    ├─────────────────────┤           ┌────────────┐
  │Producer│────────────────────│ Broker 1            │←── pull ──│Consumer 1  │
  │        │                    │  Partition 2        │           │(负责P1+P2) │
  └────────┘                    │  Partition 3        │           └────────────┘
                                └─────────────────────┘

  核心设计：

  1. 存储模型（Partition = 追加写日志文件）：
     ┌────────────────────────────────────────────┐
     │ Segment 0     │ Segment 1     │ Segment 2  │
     │ 0000.log      │ 1000.log      │ 2000.log   │
     │ 0000.index    │ 1000.index    │ 2000.index  │
     │ (消息0-999)   │ (消息1000-1999)│ (消息2000+)│
     └────────────────────────────────────────────┘
     - 顺序追加写（磁盘顺序写 > 500MB/s）
     - 按offset索引（稀疏索引，二分查找）
     - 过期segment整文件删除（高效GC）

  2. 复制 & 高可用：
     - 每个Partition有1个Leader + N个Follower
     - 写入走Leader，Follower异步/同步复制
     - ISR(In-Sync Replica)集合 → Leader挂了从ISR中选新Leader
     - acks=all: 所有ISR确认才返回（最强持久性）

  3. Consumer Group：
     - 一个Partition只能被一个Consumer消费（保证分区内有序）
     - Consumer数 <= Partition数（多余的Consumer空闲）
     - Offset存储在Broker(或ZooKeeper)，支持任意位置回溯

  4. 高吞吐优化：
     - 批量发送（Producer攒一批再发）
     - 零拷贝(sendfile)发给Consumer
     - Page Cache利用（顺序读命中率极高）
     - 压缩（Snappy/LZ4）
```

### 4. 题目三：搜索引擎

**需求**：设计一个支持全文搜索的系统（类Elasticsearch简化版）。

```
  核心组件：

  文档写入路径：
  Document → Tokenizer(分词) → Inverted Index(倒排索引) → 持久化

  搜索路径：
  Query → Tokenizer → 查倒排索引 → 评分(TF-IDF/BM25) → 排序 → Top-K结果

  倒排索引结构：
  ┌────────────────────────────────────────────────────┐
  │ Term      │ Document Frequency │ Posting List      │
  ├───────────┼───────────────────┼───────────────────┤
  │ "redis"   │ 3                  │ [doc1, doc5, doc8]│
  │ "mysql"   │ 5                  │ [doc2,doc3,doc5,doc7,doc9]│
  │ "分布式"  │ 4                  │ [doc1,doc3,doc5,doc6]│
  └───────────┴───────────────────┴───────────────────┘

  搜索"redis 分布式" → 取两个posting list的交集 → [doc1, doc5]
  对交集文档计算BM25相关性分数 → 排序 → 返回Top 10

  扩展性设计：
  - 文档分片(Shard): 按文档ID哈希分到N个分片
  - 搜索时: 查询广播到所有分片 → 每个分片返回Top-K → 协调节点合并排序
  - 副本(Replica): 每个分片多副本，搜索请求负载均衡到副本
```

### 5. 题目四：Feed流（类朋友圈/微博）

**需求**：用户发布内容，关注者能看到按时间排序的Feed。

```
  核心挑战：大V（百万粉丝）发一条内容 → 百万人的Feed要更新

  两种模型对比：

  推模型(Fan-out on Write / Push)：
  ────────────────────────────
  发布时：将内容推送到所有粉丝的Feed收件箱
  读取时：直接读自己的收件箱（已排好序）

  优点：读取极快（已预计算）
  缺点：大V发布代价高（百万次写入）、存储浪费

  拉模型(Fan-out on Read / Pull)：
  ────────────────────────────
  发布时：只写入自己的发件箱
  读取时：从关注的所有人的发件箱拉取、合并排序

  优点：写入简单
  缺点：读取慢（需要合并N个人的时间线）

  混合模型（推荐）：
  ────────────────────────────
  - 普通用户(粉丝<1万): 推模型（发布时推给所有粉丝）
  - 大V(粉丝>1万): 拉模型（粉丝读取时去拉大V内容合并）
  - 活跃用户: 推模型（确保快速看到更新）
  - 不活跃用户: 不推送（登录时再拉取）
```

```
  混合Feed系统架构：

  发布流程：
  User发布 → 写入 Posts 表
           → 判断粉丝数
              ├─ < 10000: Fan-out Service 写入粉丝的Feed Cache
              └─ >= 10000: 不推送，标记为"pull-on-read"

  读取流程：
  User读Feed → 从Feed Cache读推送来的内容
            → 合并关注的大V的最新内容(拉取)
            → 按时间排序 → 返回Top N

  存储设计：
  - Posts表: user_id, content, created_at (MySQL分库分表)
  - Feed Cache: userId → SortedSet(score=timestamp, member=postId) (Redis)
  - Following关系: userId → Set(followingIds) (Redis/图数据库)
  - 大V列表: 缓存活跃大V的最新N条Post (Redis)
```

### 6. 回答模板总结

```
  系统设计面试回答结构：

  1. "让我先确认需求..." (展示沟通能力)
     - 用户量级？QPS？延迟要求？
     - 一致性 vs 可用性优先？
     - 有哪些核心用例？

  2. "我来估算一下规模..." (展示量化思维)
     - 日活/QPS/存储量计算
     - 推导出需要多少台机器

  3. "高层架构是这样..." (先画大图)
     - 客户端 → LB → 服务层 → 存储层
     - 确定API和数据模型

  4. "核心设计决策是..." (展示深度)
     - 为什么选这个数据库？
     - 为什么用这个算法？
     - Trade-off是什么？

  5. "如果要扩展..." (展示经验)
     - 瓶颈在哪？如何分片？
     - 缓存策略？一致性保证？
     - 降级方案？

  关键心法：
  - 没有"标准答案"，重要的是推导过程
  - 先广度后深度（先画全貌再深入关键点）
  - 主动说trade-off（展示工程判断力）
  - 数字驱动（QPS、延迟、存储量要算出来）
```

### 总结

系统设计的核心思维：

1. **需求驱动架构**：先量化（QPS、存储、延迟），再选方案
2. **Trade-off无处不在**：一致性vs可用性、性能vs成本、复杂度vs灵活度
3. **分而治之**：分片、分层、分区——把大问题拆成小问题
4. **读写分离是基本功**：缓存解决读、异步解决写、消息队列解耦
5. **没有银弹**：每个方案都有适用场景，系统设计是选择题不是填空题
6. **从简单开始演进**：先实现核心功能，再逐步添加扩展性设计

系统设计能力的本质是"在不确定性中做出合理决策"。这不是背方案能解决的，而是需要大量实际项目经验+系统性思维训练。
