在后端服务开发中，数据库连接池是基础设施级别的组件。我曾在一个日均请求量过亿的项目中，因为连接池配置不当导致数据库被打爆。今天分享连接池的设计思路和 C++ 实现。

## 为什么需要连接池

每次建立数据库连接的开销：

```
客户端                        数据库服务器
   |--- TCP SYN ------------->|
   |<-- TCP SYN+ACK ---------|   ~0.5ms (同机房)
   |--- TCP ACK ------------->|
   |--- Auth Request -------->|
   |<-- Auth Challenge -------|   ~1ms
   |--- Auth Response ------->|
   |<-- Auth OK --------------|
   |--- SET charset/timezone->|   ~0.5ms
   |<-- OK -------------------|
   总计: ~3-5ms per connection
```

如果每个请求都建立新连接，QPS 1万时仅连接建立就消耗 30-50 秒的累计时延。连接池通过复用已建立的连接，将这个开销摊平为零。

## 核心设计参数

```
+--------------------------------------------------+
|              Connection Pool                       |
|                                                    |
|  min_idle: 5      最少保持的空闲连接数              |
|  max_size: 20     连接池最大容量                    |
|  idle_timeout: 600s   空闲连接回收时间              |
|  max_lifetime: 3600s  连接最大存活时间              |
|  connect_timeout: 3s  建立连接超时                  |
|  validation_interval: 30s  健康检查间隔            |
|                                                    |
|  [idle_queue]  <--- 空闲连接 LIFO 栈              |
|  [active_set]  <--- 正在使用的连接集合             |
+--------------------------------------------------+
```

## C++ 实现：线程安全的连接池

```cpp
class ConnectionPool {
public:
    explicit ConnectionPool(const PoolConfig& config)
        : config_(config), running_(true) {
        // 预创建最小空闲连接
        for (int i = 0; i < config_.min_idle; ++i) {
            idle_conns_.push(createConnection());
        }
        // 启动后台维护线程
        maintenance_thread_ = std::thread(&ConnectionPool::maintain, this);
    }

    // RAII 连接守卫，析构时自动归还
    class ConnectionGuard {
        ConnectionPool* pool_;
        std::unique_ptr<Connection> conn_;
    public:
        ConnectionGuard(ConnectionPool* pool, std::unique_ptr<Connection> c)
            : pool_(pool), conn_(std::move(c)) {}
        ~ConnectionGuard() { if (conn_) pool_->release(std::move(conn_)); }
        Connection* operator->() { return conn_.get(); }
        Connection& operator*() { return *conn_; }
        // 禁止拷贝，允许移动
        ConnectionGuard(const ConnectionGuard&) = delete;
        ConnectionGuard(ConnectionGuard&&) = default;
    };

    ConnectionGuard acquire(std::chrono::milliseconds timeout) {
        std::unique_lock<std::mutex> lock(mutex_);
        auto deadline = std::chrono::steady_clock::now() + timeout;

        while (idle_conns_.empty()) {
            if (total_count_ < config_.max_size) {
                // 池未满，创建新连接
                ++total_count_;
                lock.unlock();
                auto conn = createConnection();
                return ConnectionGuard(this, std::move(conn));
            }
            // 池已满，等待归还
            if (cv_.wait_until(lock, deadline) == std::cv_status::timeout) {
                throw PoolExhaustedException("connection pool timeout");
            }
        }
        auto conn = std::move(idle_conns_.top());
        idle_conns_.pop();
        return ConnectionGuard(this, std::move(conn));
    }

private:
    void release(std::unique_ptr<Connection> conn) {
        std::lock_guard<std::mutex> lock(mutex_);
        if (!conn->isValid() || conn->age() > config_.max_lifetime) {
            --total_count_;  // 丢弃坏连接
            return;
        }
        conn->resetState();  // 重置会话状态
        idle_conns_.push(std::move(conn));
        cv_.notify_one();
    }

    void maintain() {
        while (running_) {
            std::this_thread::sleep_for(config_.validation_interval);
            std::lock_guard<std::mutex> lock(mutex_);
            // 回收超时空闲连接，保持min_idle
            evictIdle();
            // 健康检查
            validateConnections();
        }
    }

    PoolConfig config_;
    std::stack<std::unique_ptr<Connection>> idle_conns_;
    std::mutex mutex_;
    std::condition_variable cv_;
    int total_count_ = 0;
    std::atomic<bool> running_;
    std::thread maintenance_thread_;
};
```

## 连接健康检查

不能盲目信任池中的连接。MySQL 默认 `wait_timeout=28800s`，但网络中断、服务端重启都可能导致连接失效：

```cpp
bool Connection::isValid() {
    // 方式1：mysql_ping（轻量，但有网络往返）
    if (mysql_ping(handle_) != 0) return false;
    // 方式2：执行验证SQL
    // return execute("SELECT 1").ok();
    // 方式3：检查上次活跃时间（无网络开销）
    return (now() - last_active_) < config_.idle_timeout;
}
```

实际生产中，我采用分层策略：获取连接时检查时间戳，超过 30 秒才执行 ping。

## 池耗尽策略

```
策略          | 行为                | 适用场景
--------------+---------------------+------------------
Wait          | 阻塞等待，带超时     | 大多数场景
Reject        | 立即抛异常           | 快速失败，防雪崩
Grow          | 临时超出max_size     | 突发流量，需监控
CallerRunsDB  | 不走池，直接连接     | 兜底方案
```

我的经验是默认用 Wait + 合理超时，配合监控告警。如果等待队列长度持续增长，说明需要扩容。

## 连接泄漏检测

连接被获取后如果长时间不归还，很可能是代码 bug（忘了关闭、异常路径没归还）：

```cpp
void ConnectionPool::detectLeak() {
    auto now = steady_clock::now();
    for (auto& [conn_id, borrow_time] : active_connections_) {
        if (now - borrow_time > config_.leak_detection_threshold) {
            LOG_WARN("Possible connection leak: conn={}, held for {}s, "
                     "borrowed at:\n{}", conn_id,
                     duration_cast<seconds>(now - borrow_time).count(),
                     borrow_stacktrace_[conn_id]);
        }
    }
}
```

借鉴 HikariCP 的做法，在 `acquire()` 时记录调用栈（Debug 模式），泄漏时打印完整的获取位置。

## 生产调优经验

连接池大小的经验公式（来自 HikariCP 作者）：

```
pool_size = Tn × (Cm - 1) + 1

Tn = 最大并发线程数
Cm = 单个请求需要的最大同时连接数
```

对于大多数 Web 服务，Cm=1，所以 `pool_size ≈ 线程数`。但实际中我建议 `pool_size = CPU核数 × 2 + 磁盘数`（PostgreSQL 官方建议），通常 10-20 就足够了。

监控指标：
- `pool.active` — 活跃连接数
- `pool.idle` — 空闲连接数
- `pool.wait_time_p99` — 获取连接等待时间 P99
- `pool.timeout_total` — 超时次数累计
- `pool.create_total` — 连接创建总次数

当 `wait_time_p99` 超过 100ms 或 `timeout_total` 持续增长时，就该扩容或排查慢查询了。

## 总结

好的连接池是"隐形"的——业务代码只管获取和使用，所有复杂性被封装在池内部。用 RAII 保证归还，用条件变量避免忙等，用后台线程做维护，这些是 C++ 实现连接池的核心模式。
