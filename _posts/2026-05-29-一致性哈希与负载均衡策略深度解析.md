做后端这些年，负载均衡是绕不开的话题。从最早用 Nginx 的 Round Robin 到后来自己写一致性哈希模块，踩过不少坑。今天系统梳理一下这块的设计思路。

## 取模哈希的致命缺陷

最朴素的方案：`node = hash(key) % N`。看起来简单高效，但节点数 N 一旦变化，几乎所有 key 的映射都会改变。假设有 4 个缓存节点，扩容到 5 个时，约 80% 的缓存失效，瞬间打穿后端数据库——我在 2019 年的一次线上扩容中亲历过这种雪崩。

## 一致性哈希：哈希环原理

一致性哈希的核心思想是将哈希空间组织成一个环：

```
           0 (2^32)
            |
     Node-C *----* Node-A
           /      \
          |   环   |
           \      /
     Node-D *----* Node-B
            |
         2^31
```

Key 在环上顺时针找到的第一个节点即为目标节点。节点增删时，只影响环上相邻区间的 key，数据迁移量从 O(N) 降到 O(K/N)。

## 虚拟节点：解决数据倾斜

物理节点少时，哈希环上分布极不均匀。解决方案是为每个物理节点创建多个虚拟节点：

```
物理节点 A → VNode-A#0, VNode-A#1, ... VNode-A#149
物理节点 B → VNode-B#0, VNode-B#1, ... VNode-B#149

环上分布:
  ...--A#23--B#71--A#108--B#5--A#67--B#142--...
```

生产经验：虚拟节点数 150~200 时，标准差已经能控制在 5% 以内。

## 有界负载一致性哈希（Google, 2016）

Google 提出的改进：为每个节点设定负载上限 `capacity = avg_load * (1 + ε)`。当目标节点负载已满时，沿环继续查找下一个未满节点。ε 取 0.25 时效果较好，既保证均衡又维持较低的迁移率。

## Jump Consistent Hash

Google 另一个方案，零内存开销、O(ln n) 时间复杂度：

```cpp
int32_t JumpConsistentHash(uint64_t key, int32_t num_buckets) {
    int64_t b = -1, j = 0;
    while (j < num_buckets) {
        b = j;
        key = key * 2862933555777941757ULL + 1;
        j = (b + 1) * (double(1LL << 31) / double((key >> 33) + 1));
    }
    return b;
}
```

优点是分布均匀且无需存储环结构，缺点是只能移除尾部节点，不支持任意节点下线——适合节点编号固定的场景（如分片存储）。

## 负载均衡策略对比

```
┌──────────────────┬───────────┬────────────────────────────┐
│ 策略             │ 复杂度    │ 适用场景                   │
├──────────────────┼───────────┼────────────────────────────┤
│ Round Robin      │ O(1)      │ 无状态服务，节点同配置     │
│ Weighted RR      │ O(1)      │ 节点性能异构               │
│ Least Conn       │ O(log N)  │ 长连接，请求耗时差异大     │
│ IP Hash          │ O(1)      │ 简单会话保持               │
│ Consistent Hash  │ O(log N)  │ 缓存层，有状态分片         │
│ P2C (两次随机)   │ O(1)      │ gRPC 等高吞吐场景         │
└──────────────────┴───────────┴────────────────────────────┘
```

## C++ 实现：带虚拟节点的一致性哈希

```cpp
#include <map>
#include <string>
#include <functional>
#include <fmt/format.h>

class ConsistentHash {
public:
    explicit ConsistentHash(int replicas = 150) : replicas_(replicas) {}

    void AddNode(const std::string& node) {
        for (int i = 0; i < replicas_; ++i) {
            uint32_t h = Hash(fmt::format("{}#{}", node, i));
            ring_[h] = node;
        }
    }

    void RemoveNode(const std::string& node) {
        for (int i = 0; i < replicas_; ++i) {
            uint32_t h = Hash(fmt::format("{}#{}", node, i));
            ring_.erase(h);
        }
    }

    std::string GetNode(const std::string& key) const {
        if (ring_.empty()) return "";
        uint32_t h = Hash(key);
        auto it = ring_.lower_bound(h);
        if (it == ring_.end()) it = ring_.begin(); // 绕环
        return it->second;
    }

private:
    uint32_t Hash(const std::string& s) const {
        // MurmurHash3 finalizer, 生产中建议用 xxHash
        uint32_t h = std::hash<std::string>{}(s);
        h ^= h >> 16; h *= 0x85ebca6b;
        h ^= h >> 13; h *= 0xc2b2ae35;
        h ^= h >> 16;
        return h;
    }

    int replicas_;
    std::map<uint32_t, std::string> ring_;
};
```

## 生产选型经验

九年来的一些实践总结：

1. **缓存层（Redis Cluster 前置）**：一致性哈希 + 虚拟节点，权重按内存容量设置
2. **无状态微服务**：P2C（Power of Two Choices）或加权轮询，gRPC 内建的 pick_first 在长连接下负载极不均
3. **数据库分片**：Jump Consistent Hash，分片数固定时最优
4. **网关层**：Least Connections + 慢启动（新节点逐步加权），避免冷节点被瞬时流量打死

选策略不要追求"最优解"，要结合业务特征：请求是否有状态、节点是否同构、是否频繁扩缩容。没有银弹，只有适合的工具。
