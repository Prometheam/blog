MySQL 是最流行的关系型数据库之一，本文从架构、索引、事务、性能调优、高可用五个维度深度剖析 MySQL 核心原理，并整理常见知识点。

---

## 一、核心架构

MySQL 采用分层架构，自上而下分为四层：

### 1. 连接层

- 负责处理客户端连接、授权认证、安全等
- 每个客户端连接都会在服务器进程中拥有一个线程
- 服务器负责缓存线程（线程池），不需要为每个新连接创建或销毁线程

### 2. 服务层（Server 层）

MySQL 的核心，包含以下组件：

| 组件 | 职责 |
|------|------|
| SQL 接口 | 接收用户 SQL 命令，返回查询结果 |
| 解析器 | 词法分析 + 语法分析，生成解析树 |
| 预处理器 | 检查表、列是否存在，生成新解析树 |
| 查询优化器 | 重写查询、决定表读取顺序、选择索引，生成执行计划 |
| 缓存/缓冲区 | 查询缓存（MySQL 8.0 已移除）、缓冲池、键缓冲区 |

### 3. 存储引擎层

MySQL 采用插件式存储引擎架构，存储引擎是**表级别**的：

| 引擎 | 事务 | 锁 | 索引 | 特点 |
|------|------|------|------|------|
| **InnoDB** | ✅ | 行锁 | 聚簇索引 | 支持 MVCC、外键，默认引擎 |
| **MyISAM** | ❌ | 表锁 | 非聚簇索引 | 读多写少，不支持崩溃恢复 |
| **Memory** | ❌ | 表锁 | 哈希/B+树 | 数据存内存，重启丢失 |
| **Archive** | ❌ | 行锁 | 无 | 只支持 INSERT/SELECT，高压缩比 |

### 4. 文件系统层

将数据和日志存储在文件系统上，不同存储引擎有不同文件格式。

## 二、索引：B+Tree 深度剖析

### 为什么是 B+Tree？

| 对比 | B+Tree | B-Tree | Hash |
|------|--------|--------|------|
| 非叶子节点存数据 | ❌ 只存键 | ✅ | - |
| 单页容纳键数 | 多（树更矮） | 少 | - |
| 范围查询 | ✅ 叶子双向链表 | ❌ 需回溯 | ❌ 不支持 |
| 等值查询 | O(logN) | O(logN) | O(1) |
| 全表顺序扫描 | ✅ 高效 | ❌ | ❌ |

### InnoDB 的聚簇索引

- **聚簇索引**：表数据按主键顺序存储，数据即索引。没有主键时 InnoDB 会创建隐藏的 `ROWID`
- **二级索引**：叶子节点存储的是**主键值**（非物理地址），查询完整数据需要**回表**

```
二级索引查询过程：
  二级索引 → 找到主键值 → 聚簇索引 → 找到完整数据行（回表）
```

### 最左前缀原则

索引 `(a, b, c)` 的使用规则：

| 查询条件 | 是否使用索引 |
|----------|------------|
| `WHERE a=x AND b=y AND c=z` | ✅ 全部使用 |
| `WHERE a=x AND b=y` | ✅ 使用 a, b |
| `WHERE a=x` | ✅ 使用 a |
| `WHERE b=y` | ❌ 不使用 |
| `WHERE a=x AND c=z` | ⚠️ 只使用 a |
| `ORDER BY a, b` | ✅ 使用索引排序 |

### 索引下推（ICP, Index Condition Pushdown）

MySQL 5.6 引入。在二级索引层就过滤不满足条件的记录，减少回表次数。

```
无 ICP：二级索引 → 所有 a=x 的记录回表 → Server 层过滤 b=y
有 ICP：二级索引 → 在索引层过滤 a=x AND b=y → 只回表满足条件的行
```

### 覆盖索引

索引包含了查询所需的**所有字段**，无需回表。`EXPLAIN` 中 `Extra` 列显示 `Using index`。

## 三、事务与锁

### ACID 靠什么保证？

| 特性 | 保证机制 |
|------|----------|
| **A**（原子性） | undo log（回滚日志） |
| **C**（一致性） | A + I + D 共同保证（最终目标） |
| **I**（隔离性） | 锁 + MVCC |
| **D**（持久性） | redo log + WAL 机制 |

### Redo Log 与 Undo Log

**Redo Log（重做日志）**：
- 物理日志，记录"在某个数据页上做了什么修改"
- WAL 机制：事务提交时先写 redo log（顺序写，快），再择机刷脏页（随机写，慢）
- `innodb_flush_log_at_trx_commit=1` 保证每次提交都刷盘

**Undo Log（回滚日志）**：
- 逻辑日志，记录数据修改前的镜像
- 用途：事务回滚（原子性）+ MVCC（隔离性）

### MVCC（多版本并发控制）

核心组件：**undo log 链** + **ReadView**

```
每行数据的隐藏字段：
┌──────────┬────────────┬──────────────┐
│ 数据列   │ DB_TRX_ID  │ DB_ROLL_PTR  │
│          │ 最后修改的 │ 指向 undo    │
│          │ 事务 ID    │ log 的指针   │
└──────────┴────────────┴──────────────┘
```

工作原理：
1. 每个事务有唯一事务 ID
2. 事务启动时生成 ReadView（包含当前所有活跃事务 ID）
3. 查询时沿 undo log 链找到第一个在 ReadView 创建前已提交的版本
4. 实现**非锁定读**（快照读）

### 隔离级别

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 实现方式 |
|----------|------|-----------|------|----------|
| 读未提交 | ✅ | ✅ | ✅ | 无保护 |
| 读已提交（RC） | ❌ | ✅ | ✅ | 每次 SELECT 生成新 ReadView |
| 可重复读（RR） | ❌ | ❌ | ❌* | 事务开始时生成 ReadView + 间隙锁 |
| 串行化 | ❌ | ❌ | ❌ | 所有读加共享锁 |

> *InnoDB 在 RR 级别通过 Next-Key Lock 解决了幻读问题

### 锁机制

**锁类型**：
- **行锁**：在索引上实现。如果查询没走索引，会升级为表锁
- **间隙锁（Gap Lock）**：锁住索引记录之间的间隙，防止幻读
- **Next-Key Lock**：行锁 + 间隙锁，锁住一个左开右闭区间 `(a, b]`
- **意向锁**：表级锁，用于快速判断表内是否有行级锁

**死锁处理**：
- `innodb_deadlock_detect=on`：开启死锁检测（默认）
- `innodb_lock_wait_timeout`：锁等待超时时间
- 避免方法：按相同顺序访问资源、保持事务简短、降低隔离级别

## 四、性能调优

### 一条 SQL 查询语句的执行过程

```
客户端 → 连接器 → [查询缓存(8.0已移除)] → 解析器 → 预处理器 → 优化器 → 执行器 → 存储引擎 → 返回结果
```

### EXPLAIN 关键字段

| 字段 | 说明 | 优化目标 |
|------|------|----------|
| `type` | 访问类型 | 至少达到 `range` |
| `key` | 实际使用的索引 | 不应为 NULL |
| `rows` | 预估扫描行数 | 越小越好 |
| `Extra` | 额外信息 | 关注下方说明 |

**type 从好到坏**：`system` > `const` > `eq_ref` > `ref` > `range` > `index` > `ALL`

**Extra 关键值**：
- `Using index`：覆盖索引 ✅
- `Using filesort`：额外排序，需优化 ⚠️
- `Using temporary`：使用临时表，需优化 ⚠️

### 慢查询分析流程

1. 开启慢查询日志：`slow_query_log=1`
2. 使用 `pt-query-digest` 或 `mysqldumpslow` 分析
3. 对慢 SQL 用 `EXPLAIN` 查看执行计划
4. 针对性优化（加索引、改写 SQL、调整配置）

### SQL 优化要点

- 避免 `SELECT *`，只查需要的列
- 避免在 WHERE 中对字段做函数操作（索引失效）
- 用 JOIN 代替子查询
- 大数据量分页用 `WHERE id > last_id LIMIT N` 代替 `OFFSET`
- 避免 `!=`、`<>`、`OR`（可能导致索引失效）

### 系统参数调优

| 参数 | 说明 | 建议 |
|------|------|------|
| `innodb_buffer_pool_size` | Buffer Pool 大小 | 设为物理内存的 50%-80% |
| `innodb_log_buffer_size` | redo log 缓冲区 | 写密集型适当调大 |
| `innodb_flush_log_at_trx_commit` | redo log 刷盘策略 | 1=每次提交刷盘（最安全） |
| `max_connections` | 最大连接数 | 根据并发量调整 |

## 五、高可用与扩展

### 主从复制

**原理**：

```
Master                          Slave
  │                               │
  │  binlog (二进制日志)           │
  ├──────────────────────────────►│ I/O Thread 拉取
  │                               │ 写入 relay log
  │                               │ SQL Thread 重放
  │                               ▼
```

**延迟问题**：
- 原因：单线程应用（5.6+ 支持并行复制）、从库配置低、网络延迟、大事务
- 解决：并行复制、从库升配、缩短事务、半同步复制

### 高可用方案

| 方案 | 特点 |
|------|------|
| **MHA** | 传统方案，基于主从复制，自动故障转移 |
| **MGR** | 官方方案，基于 Paxos，支持多主写入，数据强一致 |
| **Orchestrator** | GitHub 开源，自动故障检测和转移 |

### 扩展方案

**读写分离**：
- 写主库，读从库
- 注意主从延迟导致的"读不到刚写入数据"问题

**分库分表**：

| 方式 | 说明 | 适用场景 |
|------|------|----------|
| 垂直分库 | 按业务模块分到不同数据库 | 业务解耦 |
| 垂直分表 | 将大字段拆分到扩展表 | 减小行宽 |
| 水平分片 | 按分片键将数据分到多个库表 | 单表数据量过大 |

**中间件**：ShardingSphere、Vitess、MyCat

## 六、常见知识点速查

### CHAR vs VARCHAR

| 对比 | CHAR | VARCHAR |
|------|------|---------|
| 长度 | 固定 | 可变 |
| 存储 | 右侧空格填充 | 实际长度 + 1-2 字节长度标识 |
| 检索 | 去掉尾部空格 | 原样返回 |
| 适用 | 定长数据（如 MD5） | 变长数据（如姓名） |

### 索引类型

| 类型 | 说明 |
|------|------|
| PRIMARY KEY | 主键索引，唯一且非空 |
| UNIQUE | 唯一索引，允许空值 |
| INDEX | 普通索引，无唯一性限制 |
| 复合索引 | 多列组合索引，遵循最左前缀 |
| FULLTEXT | 全文索引，用于全文搜索 |

### 日志系统

| 日志 | 类型 | 用途 |
|------|------|------|
| redo log | 物理日志，InnoDB 层 | 崩溃恢复（持久性） |
| undo log | 逻辑日志，InnoDB 层 | 事务回滚 + MVCC |
| binlog | 逻辑日志，Server 层 | 主从复制 + 数据恢复 |

### 性能监控

```sql
-- 查看系统状态
SHOW STATUS;

-- 查看当前连接和线程
SHOW PROCESSLIST;

-- 查看 InnoDB 状态
SHOW ENGINE INNODB STATUS;

-- Buffer Pool 命中率
SHOW STATUS LIKE 'Innodb_buffer_pool%';
```

### 备份与恢复

```bash
# 逻辑备份
mysqldump -u root -p database_name > backup.sql

# 恢复
mysql -u root -p database_name < backup.sql

# 物理备份（推荐生产使用）
xtrabackup --backup --target-dir=/backup/
```
