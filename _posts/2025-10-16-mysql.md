MySQL 是最流行的关系型数据库之一。本文从架构、索引、事务、性能调优、高可用五个维度深度剖析 MySQL 核心原理，覆盖面试高频考点和生产实践要点。

## 一、核心架构

MySQL 采用分层架构，自上而下分为四层：

```
┌─────────────────────────────────────────┐
│            连接层 (Connection)            │
│  连接管理、授权认证、线程池、SSL         │
├─────────────────────────────────────────┤
│            服务层 (Server)                │
│  SQL接口 → 解析器 → 优化器 → 执行器     │
├─────────────────────────────────────────┤
│          存储引擎层 (Storage Engine)      │
│  InnoDB │ MyISAM │ Memory │ Archive     │
├─────────────────────────────────────────┤
│          文件系统层 (File System)         │
│  数据文件 │ 日志文件 │ 配置文件           │
└─────────────────────────────────────────┘
```

### 1. 连接层

- 负责处理客户端连接、授权认证、安全等
- 每个客户端连接都会在服务器进程中拥有一个线程
- 服务器负责缓存线程（线程池），不需要为每个新连接创建或销毁线程
- 连接建立后如果长时间空闲，由 `wait_timeout`（默认8小时）控制自动断开

### 2. 服务层（Server 层）

MySQL 的核心，包含以下组件：

| 组件 | 职责 |
|------|------|
| SQL 接口 | 接收用户 SQL 命令，返回查询结果。支持 DML/DDL/视图/存储过程/触发器 |
| 解析器（Parser） | 词法分析 + 语法分析，生成 AST（抽象语法树） |
| 预处理器 | 语义检查（表/列是否存在、权限校验），展开 `*` 为具体列 |
| 查询优化器 | 基于成本模型（CBO），决定 JOIN 顺序、索引选择、子查询重写 |
| 执行器 | 调用存储引擎接口执行计划，控制结果集返回 |

**查询优化器的关键决策**：
- 多表 JOIN 的表连接顺序（穷举/贪心算法）
- 是否使用索引、选择哪个索引
- 子查询改写为 JOIN
- 衍生表（Derived Table）的合并优化
- ORDER BY 是否能利用索引避免排序

### 3. 存储引擎层

MySQL 采用插件式存储引擎架构，存储引擎是**表级别**的：

| 引擎 | 事务 | 锁粒度 | 索引结构 | 崩溃恢复 | 适用场景 |
|------|------|--------|---------|---------|---------|
| **InnoDB** | ✅ | 行锁 | 聚簇索引（B+Tree） | ✅ redo log | OLTP，默认引擎 |
| **MyISAM** | ❌ | 表锁 | 非聚簇索引（B+Tree） | ❌ | 读多写少、全文检索 |
| **Memory** | ❌ | 表锁 | 哈希 / B+Tree | ❌ 重启丢失 | 临时表、缓存 |
| **Archive** | ❌ | 行锁 | 无索引 | ❌ | 日志归档（高压缩比） |

### 4. 文件系统层

InnoDB 核心文件：

| 文件 | 说明 |
|------|------|
| `ibdata1` | 系统表空间（共享），存储 undo log、数据字典 |
| `*.ibd` | 独立表空间（每表一个），存储数据和索引 |
| `ib_logfile0/1` | redo log 文件（循环写入） |
| `mysql-bin.000001` | binlog 文件 |
| `*.frm` | 表结构定义（MySQL 8.0 已移除，改用数据字典） |

## 二、索引原理

### B+Tree 为什么适合数据库？

**磁盘 I/O 是关键瓶颈**。数据库的索引结构设计目标是：用最少的磁盘 I/O 次数找到数据。

B+Tree 的设计决策：

| 设计特征 | 原因 | 效果 |
|---------|------|------|
| 非叶子节点只存键 | 一个 16KB 页能存更多键（约 1200 个） | 树高度通常只有 2-4 层 |
| 叶子节点存完整数据 | 数据集中存储 | 减少随机 I/O |
| 叶子节点双向链表 | 支持范围扫描和全表顺序读 | `BETWEEN`/`ORDER BY` 高效 |
| 所有查询必须到叶子 | 查询时间稳定 | 性能可预测 |

**高度计算示例**：
```
假设：主键 BIGINT(8字节)，指针(6字节)，页大小 16KB
每个非叶子节点存储键数 ≈ 16384 / (8+6) ≈ 1170
├── 2 层：1170 × 1170 ≈ 136 万行
├── 3 层：1170 × 1170 × 1170 ≈ 16 亿行
└── 结论：几乎所有表查询只需 2-3 次磁盘 I/O
```

### 聚簇索引 vs 非聚簇索引

```
聚簇索引（InnoDB 主键索引）：
┌─────────┐
│ 非叶子   │ ── 只存主键值 + 子页指针
├─────────┤
│ 叶子节点 │ ── 存储完整数据行（主键顺序排列）
└─────────┘

二级索引（非聚簇）：
┌─────────┐
│ 非叶子   │ ── 存索引列值 + 子页指针
├─────────┤
│ 叶子节点 │ ── 存储索引列值 + 对应的主键值
└─────────┘
```

**回表查询**：通过二级索引找到主键 → 再通过聚簇索引找完整行数据。这是很多性能问题的根源。

**为什么 InnoDB 要求有主键？**
- 如果没定义主键，InnoDB 会选一个非空唯一索引作为聚簇索引
- 都没有时，InnoDB 会创建隐藏的 6 字节 `ROW_ID` 列作为聚簇索引
- 建议：使用自增整型主键（顺序插入，避免页分裂）

### 索引失效的常见场景

| 场景 | 示例 | 原因 |
|------|------|------|
| 对索引列做运算 | `WHERE YEAR(create_time) = 2025` | 无法直接在 B+Tree 上比较 |
| 隐式类型转换 | `WHERE phone = 13800138000`（phone 是 varchar） | 相当于对 phone 做了 CAST |
| LIKE 左模糊 | `WHERE name LIKE '%abc'` | B+Tree 按前缀排序，左模糊无法定位 |
| OR 条件未全部有索引 | `WHERE a=1 OR b=2`（b 无索引） | 需全表扫描找 b=2 |
| 不满足最左前缀 | 索引(a,b,c)，查 `WHERE b=1` | 跳过了最左列 a |
| `!=` / `NOT IN` | `WHERE status != 1` | 结果集通常很大，优化器选择全表扫描 |
| IS NULL / IS NOT NULL | 取决于数据分布 | NULL 值比例高时可能不走索引 |

### 索引下推（ICP）

MySQL 5.6+ 引入。对联合索引 `(name, age)`：

```sql
SELECT * FROM user WHERE name LIKE '张%' AND age = 25;
```

```
无 ICP（5.5及以前）：
  索引查找 name LIKE '张%' → 回表获取完整行 → Server 层过滤 age=25
  假设匹配 name 的有 1000 行，全部回表

有 ICP（5.6+）：
  索引查找 name LIKE '张%' → 在索引层直接判断 age=25 → 只回表满足两个条件的行
  假设最终只有 50 行满足，只回表 50 次
```

### 覆盖索引

如果查询列全部包含在索引中，无需回表：

```sql
-- 索引: idx_name_age(name, age)
SELECT name, age FROM user WHERE name = '张三';
-- EXPLAIN: Extra 显示 "Using index"（覆盖索引）

SELECT name, age, email FROM user WHERE name = '张三';
-- 需要回表获取 email 列
```

**优化技巧**：经常一起查询的字段可以建联合索引来实现覆盖索引。

## 三、事务与锁

### ACID 的底层实现

```
┌──────────┬────────────────────────────────────┐
│ 特性      │ 实现机制                           │
├──────────┼────────────────────────────────────┤
│ Atomicity │ undo log（回滚到事务开始前状态）    │
│ Consistency│ A + I + D 共同保证（最终目标）     │
│ Isolation │ MVCC + 锁机制                      │
│ Durability│ redo log + WAL + doublewrite       │
└──────────┴────────────────────────────────────┘
```

### Redo Log 深入

**为什么需要 redo log？直接刷数据页不行吗？**

数据页是 16KB 随机写，redo log 是顺序追加写。在一次事务中可能修改多个散落在磁盘各处的数据页，如果每次提交都刷数据页，随机 I/O 会非常慢。redo log 将这些随机写转化为顺序写（WAL），大幅提升写入性能。

```
事务提交过程：
1. 修改 Buffer Pool 中的数据页（内存操作，快）
2. 生成 redo log 写入 Log Buffer
3. Log Buffer 刷入磁盘 redo log 文件（顺序写，快）
4. 返回客户端"提交成功"
5. 后台线程择机将脏页刷入数据文件（Checkpoint）
```

**redo log 的循环写入**：

```
         write pos（当前写入位置）
            ↓
┌─────┬─────┬─────┬─────┐
│ file│ file│ file│ file│
│  0  │  1  │  2  │  3  │
└─────┴─────┴─────┴─────┘
                    ↑
              checkpoint（已刷盘位置）

write pos 追上 checkpoint 时，需要暂停写入，先推进 checkpoint（刷脏页）
```

**`innodb_flush_log_at_trx_commit` 参数**：

| 值 | 行为 | 安全性 | 性能 |
|---|------|--------|------|
| 0 | 每秒刷盘一次 | 可能丢 1 秒数据 | 最快 |
| 1 | 每次提交都刷盘 | 不丢数据 | 最慢（默认） |
| 2 | 每次提交写 OS 缓存，每秒 fsync | OS 崩溃丢 1 秒 | 折中 |

### Undo Log 深入

undo log 不仅用于回滚，还是 MVCC 的基石：

```
数据行的版本链（通过 DB_ROLL_PTR 串联）：

当前版本（trx_id=100）
    │ DB_ROLL_PTR
    ▼
undo log（trx_id=80 的旧版本）
    │ DB_ROLL_PTR
    ▼
undo log（trx_id=50 的更旧版本）
    │
    ▼
  ...
```

### MVCC 机制详解

**ReadView 的四个关键字段**：

| 字段 | 含义 |
|------|------|
| `m_ids` | 创建 ReadView 时所有活跃（未提交）的事务 ID 列表 |
| `min_trx_id` | m_ids 中的最小值 |
| `max_trx_id` | 系统下一个要分配的事务 ID（当前最大 ID + 1） |
| `creator_trx_id` | 创建该 ReadView 的事务自身 ID |

**可见性判断规则**（对某行数据的 `DB_TRX_ID`）：

```
if (trx_id == creator_trx_id)
    → 可见（自己修改的）
else if (trx_id < min_trx_id)
    → 可见（在 ReadView 创建前已提交）
else if (trx_id >= max_trx_id)
    → 不可见（在 ReadView 创建后才出现的事务）
else if (trx_id in m_ids)
    → 不可见（ReadView 创建时还未提交）
else
    → 可见（已提交且不在活跃列表中）
```

**RC vs RR 的区别**：
- **RC（读已提交）**：每次 SELECT 都重新生成 ReadView → 能看到其他事务新提交的数据
- **RR（可重复读）**：事务第一次 SELECT 时生成 ReadView，后续复用 → 看到的是一致性快照

### 锁机制详解

**InnoDB 锁的层次结构**：

```
表级锁
├── 意向共享锁（IS）：事务想获取某行的 S 锁前，先加 IS
├── 意向排他锁（IX）：事务想获取某行的 X 锁前，先加 IX
└── 用途：快速判断表内是否有行锁，避免逐行检查

行级锁（在索引上实现）
├── Record Lock：锁住单条索引记录
├── Gap Lock：锁住索引记录之间的间隙（左开右开）
├── Next-Key Lock：Record + Gap，锁住 (a, b]
└── 插入意向锁：Insert 操作等待 Gap Lock 释放时使用
```

**Next-Key Lock 加锁规则**（RR 隔离级别下）：

1. 加锁的基本单位是 Next-Key Lock：`(前一个值, 当前值]`
2. 查找过程中访问到的对象才加锁
3. 唯一索引等值查询，命中记录时退化为 Record Lock
4. 唯一索引等值查询，未命中时退化为 Gap Lock
5. 非唯一索引等值查询，向右遍历到第一个不满足条件的值时，Next-Key Lock 退化为 Gap Lock

**死锁案例**：

```sql
-- 事务A
BEGIN;
UPDATE accounts SET balance = 100 WHERE id = 1;  -- 锁住 id=1
UPDATE accounts SET balance = 200 WHERE id = 2;  -- 等待 id=2 的锁

-- 事务B
BEGIN;
UPDATE accounts SET balance = 300 WHERE id = 2;  -- 锁住 id=2
UPDATE accounts SET balance = 400 WHERE id = 1;  -- 等待 id=1 的锁 → 死锁！
```

## 四、性能调优

### 一条 SQL 的完整执行流程

```
1. 客户端发送 SQL
2. 连接器：验证账号密码，获取权限
3. [查询缓存]：MySQL 8.0 已移除（缓存命中率低，失效频繁）
4. 解析器：词法分析（识别关键字、表名、列名）→ 语法分析（检查语法）
5. 预处理器：语义检查（表/列是否存在）、权限验证
6. 优化器：生成执行计划（选择索引、JOIN 顺序、是否排序等）
7. 执行器：调用存储引擎接口，逐行/批量获取数据
8. 存储引擎：从 Buffer Pool 或磁盘读取数据页，返回符合条件的行
9. 返回结果给客户端
```

### 一条 UPDATE 的执行流程

```
UPDATE user SET name='李四' WHERE id=1;

1. 执行器调用 InnoDB 接口，查找 id=1 的行
2. InnoDB 在 Buffer Pool 中查找（不在则从磁盘加载）
3. 将旧数据写入 undo log（为了回滚和 MVCC）
4. 在 Buffer Pool 中修改数据页（变为脏页）
5. 生成 redo log，写入 Log Buffer（prepare 状态）
6. 执行器生成 binlog，写入 binlog cache
7. 事务提交：
   a. redo log 写入磁盘（commit 状态）← 两阶段提交
   b. binlog 写入磁盘
8. 返回"更新成功"
```

**两阶段提交（保证 redo log 与 binlog 一致性）**：

```
redo log (prepare) → binlog 写入 → redo log (commit)
```

如果中途崩溃：
- binlog 未写入 → 回滚事务（redo log 是 prepare 状态）
- binlog 已写入 → 提交事务（用 binlog 恢复 redo log）

### EXPLAIN 深度解读

```sql
EXPLAIN SELECT * FROM orders o 
JOIN users u ON o.user_id = u.id 
WHERE u.age > 25 AND o.status = 'paid';
```

**核心字段详解**：

| 字段 | 说明 | 关键值解读 |
|------|------|-----------|
| `id` | 查询编号 | 相同则从上到下执行；不同则 id 大的先执行 |
| `select_type` | 查询类型 | SIMPLE/PRIMARY/SUBQUERY/DERIVED |
| `table` | 访问的表 | |
| `type` | 访问方式 | **最关键**，见下方 |
| `possible_keys` | 可能使用的索引 | |
| `key` | 实际使用的索引 | NULL 表示全表扫描 |
| `key_len` | 索引使用长度 | 可判断联合索引用了几列 |
| `ref` | 索引的哪一列被使用 | const/字段名 |
| `rows` | 预估扫描行数 | |
| `filtered` | 经过条件过滤后保留的比例 | |
| `Extra` | 额外信息 | 见下方 |

**type 访问类型（从好到坏）**：

| type | 含义 | 示例 |
|------|------|------|
| `system` | 表只有一行 | 系统表 |
| `const` | 主键/唯一索引等值查询 | `WHERE id = 1` |
| `eq_ref` | JOIN 时被驱动表走主键/唯一索引 | 多表 JOIN |
| `ref` | 非唯一索引等值查询 | `WHERE name = 'abc'` |
| `range` | 索引范围查询 | `WHERE id > 100` |
| `index` | 全索引扫描（覆盖索引） | 只查索引列 |
| `ALL` | 全表扫描 | **需要优化** |

**Extra 重要值**：

| Extra | 含义 | 是否需要优化 |
|-------|------|-------------|
| `Using index` | 覆盖索引，无需回表 | ✅ 好 |
| `Using where` | Server 层过滤 | 正常 |
| `Using index condition` | 索引下推（ICP） | ✅ 好 |
| `Using filesort` | 需要额外排序 | ⚠️ 考虑索引优化 |
| `Using temporary` | 使用临时表 | ⚠️ GROUP BY/ORDER BY 不同列 |
| `Using join buffer` | JOIN 未使用索引 | ⚠️ 需加索引 |

### 索引优化实战

**联合索引设计原则**：

```
1. 等值查询的列放前面
2. 范围查询的列放后面（范围查询后的列无法使用索引）
3. 排序/分组的列考虑加入索引

示例：SELECT * FROM orders WHERE user_id=1 AND status='paid' ORDER BY create_time DESC;
最佳索引：idx(user_id, status, create_time)
```

**大数据量分页优化**：

```sql
-- 慢：OFFSET 越大越慢（需要扫描并丢弃前 N 行）
SELECT * FROM orders ORDER BY id LIMIT 1000000, 10;

-- 快：延迟关联（先通过覆盖索引定位 ID，再回表取数据）
SELECT * FROM orders o
INNER JOIN (SELECT id FROM orders ORDER BY id LIMIT 1000000, 10) t
ON o.id = t.id;

-- 最快：游标分页（记住上一页最后的 ID）
SELECT * FROM orders WHERE id > 1000000 ORDER BY id LIMIT 10;
```

### Buffer Pool 原理

Buffer Pool 是 InnoDB **最核心的内存结构**，缓存数据页和索引页。

```
Buffer Pool 内存结构：
┌────────────────────────────────┐
│       Free List (空闲页)        │
├────────────────────────────────┤
│       LRU List (数据页)         │
│  ┌──────────────────────────┐  │
│  │   Young 区 (5/8)         │  │  ← 频繁访问的热数据
│  ├──────────────────────────┤  │
│  │   Old 区 (3/8)           │  │  ← 新加载的页先放这里
│  └──────────────────────────┘  │
├────────────────────────────────┤
│       Flush List (脏页)        │  ← 等待刷盘的修改过的页
└────────────────────────────────┘
```

**为什么 LRU 要分 Young/Old 区？**
- 防止全表扫描（如 `mysqldump`）将热数据从 Buffer Pool 中挤出
- 新加载的页先进入 Old 区，只有在 Old 区存活超过 `innodb_old_blocks_time`（默认 1 秒）后再次被访问，才会移入 Young 区

**监控 Buffer Pool**：

```sql
-- 命中率 = 1 - (物理读 / 逻辑读)
SHOW STATUS LIKE 'Innodb_buffer_pool_read%';
-- Innodb_buffer_pool_read_requests: 逻辑读次数
-- Innodb_buffer_pool_reads: 物理读次数（未命中 Buffer Pool）
-- 命中率低于 99% 考虑增大 Buffer Pool
```

## 五、高可用与扩展

### Binlog 与主从复制

**Binlog 的三种格式**：

| 格式 | 记录内容 | 优点 | 缺点 |
|------|---------|------|------|
| Statement | SQL 语句本身 | 日志量小 | 不确定函数(NOW/UUID)导致主从不一致 |
| Row | 每行数据变更前后的值 | 数据一致性最好 | 日志量大（推荐） |
| Mixed | 混合使用 | 折中 | 某些场景仍有问题 |

**主从复制的三种同步模式**：

| 模式 | 原理 | 数据安全 | 性能 |
|------|------|---------|------|
| 异步复制 | 主库不等从库确认 | 主库崩溃可能丢数据 | 最快 |
| 半同步复制 | 至少一个从库确认收到 binlog | 至少一份副本 | 较快 |
| 全同步复制 | 所有从库都确认执行完毕 | 最安全 | 最慢 |

**复制延迟优化**：

```
问题根源：从库单线程重放 → 跟不上主库多线程并发写入

解决方案：
├── 并行复制（5.6+ 库级别并行，5.7+ 基于 LOGICAL_CLOCK）
├── 大事务拆分（避免单事务修改大量数据）
├── 从库硬件升级
├── 延迟监控 + 读主库兜底
└── 半同步复制（保证数据传输到从库）
```

### 高可用架构

| 方案 | 原理 | 切换时间 | 数据一致性 | 适用场景 |
|------|------|---------|-----------|---------|
| **MHA** | 主从 + 故障自动切换 | 10-30秒 | 可能丢 1-2 个事务 | 传统方案，成熟稳定 |
| **MGR** | Paxos 协议多副本 | 秒级 | 强一致 | MySQL 官方，未来方向 |
| **Orchestrator** | 拓扑发现 + 自动切换 | 10-30秒 | 取决于复制模式 | GitHub 实践 |
| **InnoDB Cluster** | MGR + MySQL Shell + Router | 秒级 | 强一致 | 完整官方解决方案 |

### 分库分表

**什么时候需要分？**
- 单表行数超过 2000 万（经验值，取决于索引和查询模式）
- 单表磁盘超过 20GB
- QPS 超过单实例承载能力

**分片策略对比**：

| 策略 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 哈希取模 | `hash(shard_key) % N` | 数据均匀 | 扩容困难（需 rehash） |
| 范围分片 | `id 1-1000万 → shard0` | 扩容简单 | 热点问题（最新数据集中） |
| 一致性哈希 | 哈希环 + 虚拟节点 | 扩容影响小 | 实现复杂 |

**分库分表带来的问题**：
- 跨分片 JOIN：应用层拼接或冗余数据
- 分布式事务：TCC / Saga / 消息最终一致性
- 全局唯一 ID：雪花算法 / UUID / 号段模式
- 跨分片排序分页：各分片取数据后归并排序

## 六、日志系统全景

### 三大日志对比

| 维度 | redo log | undo log | binlog |
|------|----------|----------|--------|
| 所属层 | InnoDB 引擎层 | InnoDB 引擎层 | Server 层 |
| 日志类型 | 物理日志（页修改） | 逻辑日志（行旧值） | 逻辑日志（SQL/行变更） |
| 写入方式 | 循环写入（固定大小） | 追加写入 | 追加写入（新文件） |
| 用途 | 崩溃恢复（持久性） | 事务回滚 + MVCC | 主从复制 + 数据恢复 |
| 生命周期 | Checkpoint 后可覆盖 | 无活跃事务引用时回收 | 按保留策略删除 |

### Binlog 与 Redo Log 的区别

| 对比 | redo log | binlog |
|------|----------|--------|
| 谁写的 | InnoDB 引擎 | Server 层（所有引擎通用） |
| 内容 | 物理操作（"页X偏移Y写入Z"） | 逻辑操作（SQL/行数据） |
| 写时机 | 事务执行中持续写入 | 事务提交时一次性写入 |
| 空间管理 | 固定大小循环使用 | 追加写，需定期清理 |
| 崩溃恢复 | ✅ 可以 | ❌ 不能（缺少未提交事务信息） |

## 七、实战问题与解决方案

### 大事务的危害

- 锁持有时间长 → 阻塞其他事务
- undo log 膨胀 → 占用大量磁盘空间
- binlog 过大 → 主从延迟加剧
- 回滚时间长 → 如果需要回滚，耗时可能是执行时间的数倍

**解决**：拆分为小批量操作，如 `DELETE LIMIT 1000` 循环执行。

### Online DDL

MySQL 5.6+ 支持在线 DDL，但仍有限制：

| 操作 | 是否在线 | 是否重建表 | 说明 |
|------|---------|-----------|------|
| 添加索引 | ✅ | ❌ | 5.6+ 支持 |
| 删除索引 | ✅ | ❌ | 仅修改元数据 |
| 添加列 | ✅ | ✅ | 需要拷贝数据（8.0 INSTANT 除外） |
| 修改列类型 | ❌ | ✅ | 需要锁表 |
| 添加主键 | ❌ | ✅ | 需要重建表 |

**大表 DDL 推荐工具**：`pt-online-schema-change`、`gh-ost`

### COUNT(*) 性能问题

- InnoDB 没有缓存行数（因为 MVCC 下不同事务看到的行数不同）
- `COUNT(*)` ≈ `COUNT(1)` > `COUNT(主键)` > `COUNT(字段)`
- 优化方案：缓存计数（Redis）、触发器维护计数表、`SHOW TABLE STATUS`（近似值）

### 深分页问题

```sql
-- 问题：OFFSET 100万时，需要先扫描并丢弃前100万行
SELECT * FROM orders ORDER BY create_time DESC LIMIT 1000000, 20;

-- 方案1：延迟关联
SELECT o.* FROM orders o
INNER JOIN (SELECT id FROM orders ORDER BY create_time DESC LIMIT 1000000, 20) t
ON o.id = t.id;

-- 方案2：游标分页（需要前端记住上次最后的值）
SELECT * FROM orders 
WHERE create_time < '2025-01-01 12:00:00' 
ORDER BY create_time DESC LIMIT 20;

-- 方案3：业务上限制最大翻页数（如只允许翻100页）
```

## 八、面试高频考点速查

### 1. 为什么推荐自增主键？

- 顺序插入，避免页分裂（随机主键导致频繁页分裂和空间浪费）
- 二级索引叶子节点存的主键值更小（整型 vs UUID 字符串）
- 插入性能更好（不需要挪动已有数据）

### 2. 为什么 InnoDB 选择 B+Tree 而不是 B-Tree？

- B+Tree 非叶子节点不存数据 → 单页能存更多 key → 树更矮 → I/O 更少
- B+Tree 叶子节点有链表 → 范围查询和全表扫描高效
- B+Tree 所有查询到叶子才命中 → 性能稳定

### 3. 事务还没提交时宕机了怎么恢复？

- 利用 undo log 回滚未提交事务
- 利用 redo log 重做已提交但未刷盘的事务
- 两阶段提交保证 redo log 和 binlog 的一致性

### 4. 什么情况下行锁变表锁？

- 查询条件没有走索引（全表扫描时 InnoDB 锁住所有行）
- 解决：确保 WHERE 条件走索引

### 5. 如何解决主从延迟导致的读不到问题？

- 关键业务读主库（强制路由）
- 半同步复制（至少一个从库收到 binlog 才返回）
- 等待 GTID（`SELECT WAIT_FOR_EXECUTED_GTID_SET(gtid, timeout)`）
- 缓存兜底（写入时同步写缓存，短期内从缓存读）
