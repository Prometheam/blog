最近我们团队在昇腾 910B 上部署了 QWen-VL 系列的多模态大模型，支撑图片理解、文档 OCR 等业务场景。多模态模型和纯文本 LLM 相比，推理链路长了不少，优化点也更多。记录一下我们的部署实践。

## 多模态模型架构

视觉语言模型（VLM）的通用架构：

```
输入图片                    输入文本
  │                          │
  ▼                          │
┌──────────────┐             │
│ Vision Encoder│             │
│ (ViT/CLIP)   │             │
│ 输出: 视觉token│            │
└──────┬───────┘             │
       │                     │
       ▼                     │
┌──────────────┐             │
│  Projector   │             │
│ (MLP/QFormer)│             │
│ 对齐视觉&文本 │            │
│ embedding维度│             │
└──────┬───────┘             │
       │                     │
       ▼                     ▼
┌─────────────────────────────────┐
│         LLM Backbone            │
│   (QWen-7B / LLaMA等)          │
│   [img_tok1][img_tok2]...[文本] │
└─────────────────────────────────┘
```

一张 224×224 的图片经过 ViT-L 后会产生约 256 个 visual token，高分辨率模式（如 QWen-VL 的 448×448）则会产生 1024+ 个 token。这些 token 会被拼接到文本 token 前面送入 LLM。

## 在昇腾上的推理流水线

完整的推理流程涉及多个硬件单元协作：

```
┌─────────────────────────────────────────────────────────┐
│                    昇腾 910B                              │
│                                                         │
│  ┌─────────┐     ┌──────────┐     ┌─────────────────┐  │
│  │  DVPP   │────▶│ AI Core  │────▶│    AI Core      │  │
│  │图像解码  │     │ViT推理   │     │  LLM推理        │  │
│  │缩放/裁剪 │     │          │     │                 │  │
│  └─────────┘     └──────────┘     └─────────────────┘  │
│       │                │                    │           │
│       │ AIPP加速       │ Vision tokens      │ KV Cache  │
│       │ (色彩空间转换)  │                    │ (HBM)     │
└─────────────────────────────────────────────────────────┘
```

### DVPP 图像预处理

昇腾的 DVPP（Digital Vision Pre-Processing）模块提供硬件加速的图像解码和变换，避免在 CPU 上做这些操作：

```cpp
// DVPP 图像预处理流水线 (伪代码)
DvppProcess preprocessor;
preprocessor.Init(stream);

// 1. JPEG/PNG硬件解码
auto decoded = preprocessor.Decode(raw_image_data);

// 2. Resize到模型输入尺寸 (双线性插值, 硬件加速)
auto resized = preprocessor.Resize(decoded, {448, 448});

// 3. AIPP: 色彩空间转换 + 归一化 (集成在推理算子中)
//    BGR→RGB, /255.0, normalize(mean, std)
//    这步不需要单独调用，配置在模型的aipp_config中

// 输出: 448×448×3 的float16 tensor，已在Device内存中
```

DVPP 的优势是全程在 Device 侧完成，图像数据不需要在 Host 和 Device 之间搬运。对于批处理场景，这个节省非常可观。

### Vision Encoder 推理

ViT 模型本身是标准 Transformer，在昇腾上用 AscendCL 加载 om 模型执行：

```
ViT-L/14 @ 448×448:
  - Patch: 14×14 → 32×32 = 1024 patches
  - 输出: 1024 × 1024 维 visual tokens
  - 单图推理延迟: ~8ms (910B, fp16)
  - 批处理吞吐: ~200 images/s (batch=16)
```

### Projector 与 LLM 推理

Projector 通常是 2-3 层 MLP，计算量很小（<1ms）。关键是 LLM 推理阶段的 KV Cache 管理：

```
KV Cache 布局 (多模态):
┌─────────────────────────────────────────────────┐
│ [system_prompt] [visual_tokens ×1024] [user_text]│
│  └── 固定部分 ──┘└── 图像相关 ──────┘└── 变化 ─┘│
│                                                 │
│ Prefill阶段需处理: 1024(img) + N(text) 个token  │
│ 比纯文本请求的prefill慢很多!                     │
└─────────────────────────────────────────────────┘
```

## 核心优化策略

### 1. Visual Token 压缩

1024 个 visual token 太多了，我们用了几种压缩方案：

```
方法                    压缩比    精度损失    推荐场景
Average Pooling 2×2    4×        轻微       通用
Perceiver Resampler   可配置     中等       token预算严格
Dynamic Resolution    自适应     最小       生产首选

Dynamic Resolution (QWen-VL2的做法):
  小图/简单图 → 低分辨率 → 256 tokens
  大图/复杂图 → 高分辨率 → 1024 tokens
  根据图片内容动态选择，平衡质量和效率
```

### 2. 混合请求批处理

生产环境中，纯文本和多模态请求混合到达。我们的调度策略：

```
请求队列:
  [Text] [Text] [Image+Text] [Text] [Image+Text]

调度策略:
  ┌────────────────────────────────────────┐
  │ Continuous Batching with 分离式Prefill  │
  │                                        │
  │ Prefill队列: 文本和多模态请求分开排队    │
  │   - 纯文本batch: prefill很快           │
  │   - 多模态batch: 等ViT输出后再prefill  │
  │                                        │
  │ Decode阶段: 统一batch (都是逐token生成) │
  └────────────────────────────────────────┘
```

这样做的好处是：ViT 推理不会阻塞纯文本请求的 prefill，两者可以并行执行在不同的 AI Core 集群上。

### 3. 端到端延迟拆解

以单张图片 + 50 字提问，生成 200 token 回答为例：

```
阶段               延迟      占比    优化手段
DVPP解码+预处理     3ms       2%    硬件加速,无优化空间
ViT推理            8ms       5%    量化为INT8可到5ms
Projector          1ms       1%    可忽略
LLM Prefill       45ms      28%   token压缩减少序列长度
LLM Decode        105ms     64%   投机采样/量化
────────────────────────────────────
总计              ~162ms    100%
```

LLM Decode 仍然是主要瓶颈，和纯文本模型一样。但 Prefill 阶段因为多了 visual token，耗时明显增加。

```
                    ┌─────────────┐
                    │   Gateway   │

                    └──────┬──────┘
                           │
              ┌────────────┼────────────┐
              ▼            ▼            ▼
        ┌──────────┐ ┌──────────┐ ┌──────────┐

关键设计:
  - 图片预处理结果缓存: 同一张图多次引用不重复计算

  - ViT和LLM可以部署在不同卡上(异构调度)
```

## 踩坑记录

1. **HBM 内存规划**：910B 有 64GB HBM，7B 模型权重占约 14GB（fp16），KV Cache 要预留足够空间。visual token 多时 KV Cache 消耗会突增，需要做好 OOM 防护
2. **DVPP 格式限制**：DVPP 解码支持 JPEG/PNG，但对某些 Progressive JPEG 和 WebP 不支持，需要在前端做格式校验
3. **动态 shape 问题**：不同分辨率的图片导致 ViT 输入 shape 不一致，需要用 dynamic shape 编译或者做 padding bucket

多模态模型的部署比纯文本复杂不少，但用户体验的提升是质的飞跃。图片理解、文档解析、视频分析这些能力让 LLM 真正能处理现实世界的信息。昇腾平台虽然生态还在追赶，但硬件能力已经足够支撑这些场景了。
