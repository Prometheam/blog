做了九年 C++ 后端开发，我发现很多同事对虚函数的理解停留在"加了 virtual 就能多态"的层面。今天我想从编译器实现的角度，把 C++ 对象模型彻底讲透。

## 单继承下的虚表布局

先看最简单的情况：

```cpp
class Base {
public:
    virtual void foo() { cout << "Base::foo" << endl; }
    virtual void bar() { cout << "Base::bar" << endl; }
    int x = 1;
};

class Derived : public Base {
public:
    void foo() override { cout << "Derived::foo" << endl; }
    virtual void baz() { cout << "Derived::baz" << endl; }
    int y = 2;
};
```

在 GCC/Clang 的 Itanium ABI 下，对象内存布局如下：

```
Derived 对象内存布局 (sizeof = 16, 64位系统)
+-------------------+
| vptr (8 bytes)    | ---> Derived vtable
+-------------------+
| Base::x (4 bytes) |
+-------------------+
| Derived::y (4 b)  |
+-------------------+

Derived vtable 内容：
+-------------------+
| offset_to_top (0) |
+-------------------+
| typeinfo* (RTTI)  |
+-------------------+
| &Derived::foo     |  <-- 覆盖了 Base::foo
+-------------------+
| &Base::bar        |  <-- 继承未覆盖
+-------------------+
| &Derived::baz     |  <-- 新增虚函数追加在末尾
+-------------------+
```

关键点：vptr 始终在对象起始位置（偏移 0），这样通过基类指针调用虚函数时只需一次间接寻址。

用 GCC 可以导出类层次信息：

```bash
g++ -fdump-lang-class -c demo.cpp
# 生成 demo.cpp.001l.class 文件，包含 vtable 布局
```

## 多继承的内存布局与 thunk

多继承才是真正考验功底的地方：

```cpp
class A {
public:
    virtual void funcA() {}
    int a = 1;
};

class B {
public:
    virtual void funcB() {}
    int b = 2;
};

class C : public A, public B {
public:
    void funcA() override {}
    void funcB() override {}
    int c = 3;
};
```

C 对象的内存布局：

```
C 对象内存布局 (sizeof = 32, 64位系统含对齐)
+--------------------+
| vptr_A (8 bytes)   | ---> C 的主虚表 (for A)
+--------------------+
| A::a (4 bytes)     |
+--------------------+
| padding (4 bytes)  |
+--------------------+
| vptr_B (8 bytes)   | ---> C 的次虚表 (for B)
+--------------------+
| B::b (4 bytes)     |
+--------------------+
| C::c (4 bytes)     |
+--------------------+
```

当通过 `B*` 指针调用 `funcB()` 时，this 指针指向 vptr_B 的位置，但 `C::funcB()` 需要 this 指向对象起始。编译器生成 **thunk** 来调整：

```asm
; thunk for C::funcB (调整 this 指针)
_ZThn16_N1C5funcBEv:
    sub rdi, 16        ; this -= sizeof(A 子对象)
    jmp _ZN1C5funcBEv  ; 跳转到真正的 C::funcB
```

这就是为什么多继承有运行时开销——每次通过非主基类指针调用虚函数都要经过 thunk 调整。

## 虚继承与菱形问题

```cpp
class Animal {
public:
    virtual void speak() {}
    int weight = 0;
};

class Dog : virtual public Animal {
public:
    void speak() override {}
    int legs = 4;
};

class Robot : virtual public Animal {
public:
    int battery = 100;
};

class RoboDog : public Dog, public Robot {
public:
    int model = 1;
};
```

虚继承解决菱形问题的代价是引入 **虚基类表指针 (vbase_offset)**：

```
RoboDog 对象布局:
+-------------------------+
| Dog::vptr              | ---> Dog-in-RoboDog vtable
+-------------------------+
| Dog::legs              |
+-------------------------+
| Robot::vptr            | ---> Robot-in-RoboDog vtable
+-------------------------+
| Robot::battery         |
+-------------------------+
| RoboDog::model         |
+-------------------------+
| Animal::vptr           | ---> Animal虚基类子对象 (共享!)
+-------------------------+
| Animal::weight         |
+-------------------------+

vtable 中额外存储 vbase_offset:
用于从派生类定位共享的虚基类子对象
```

虚基类子对象被放在对象末尾，所有路径共享同一份。这使得 `sizeof(RoboDog)` 远大于简单相加——我在项目中见过因为滥用虚继承导致对象膨胀 3 倍的情况。

## RTTI 与 dynamic_cast 的代价

每个虚表都存储了 `type_info*` 指针，`typeid` 操作通过 vptr 间接获取：

```cpp
// 编译器生成的伪代码
const type_info& typeid(Base* p) {
    return *(p->vptr[-1]);  // type_info 在 vtable 的固定偏移
}
```

`dynamic_cast` 的实现远比想象中复杂。对于向下转型，它需要遍历继承图：

```cpp
Derived* d = dynamic_cast<Derived*>(base_ptr);
// 内部调用 __dynamic_cast():
// 1. 获取源对象的 type_info
// 2. 与目标 type_info 比较
// 3. 多继承时遍历继承关系图
// 4. 计算 this 指针偏移
// 复杂度: O(n)，n 为继承深度
```

我做过基准测试，在深度为 5 的继承层次中，`dynamic_cast` 比 `static_cast` 慢约 **15-30 倍**。在热路径上应该用 `static_cast` 或自己实现类型标记。

## 对象切片陷阱

```cpp
void process(Base obj) {  // 按值传递！
    obj.foo();  // 永远调用 Base::foo
}

Derived d;
process(d);  // 对象切片：Derived 部分被截断
```

这是因为按值传递会调用 Base 的拷贝构造，只拷贝 Base 子对象部分。vptr 被设置为 Base 的虚表——切片后对象就是一个纯粹的 Base。

**规则：多态类型永远用指针或引用传递。**

## sizeof 实战分析

```cpp
class Empty {};                    // sizeof = 1 (空类优化)
class WithVirtual {
    virtual void f() {};
};                                 // sizeof = 8 (仅 vptr)

class A { int x; virtual void f(){}; };  // sizeof = 16 (vptr + int + padding)
class B { int x; int y; };               // sizeof = 8
class C : public A, public B {};         // sizeof = 24
```

我经常用这个技巧检查对象大小是否符合预期：

```cpp
static_assert(sizeof(MyClass) == 64, "对象大小超出缓存行!");
```

在高性能场景下，一个缓存行 64 字节就是性能边界。对象超过这个大小，缓存命中率会显著下降。

## 实践启示

**为什么需要虚析构函数：**

```cpp
Base* p = new Derived();
delete p;  // 没有虚析构 -> 只调用 ~Base()，Derived 部分泄漏!
```

编译器不会自动把析构设为虚函数。我的团队规范：**任何有虚函数的类必须有虚析构函数**。

**虚函数调用的实际开销：**

```
直接调用:     call _ZN4Base3fooEv           ; 1条指令
虚函数调用:   mov rax, [rdi]               ; 加载 vptr
              call [rax + offset]           ; 间接调用
```

多一次内存访问 + 间接跳转导致分支预测失败。在我们的交易系统中，热路径用 CRTP 静态多态替代虚函数，延迟降低了约 200ns/call。

## 总结

理解对象模型不是面试八股，而是写出高性能 C++ 代码的基础。当你知道 vptr 在对象头部、多继承有 thunk 开销、虚继承会膨胀对象大小，很多设计决策就有了量化依据。建议大家多用 `-fdump-lang-class` 和 `pahole` 工具检查自己写的类，可能会有意想不到的发现。
