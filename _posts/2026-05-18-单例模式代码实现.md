### 引言

单例模式可能是面试中被问到最多的设计模式，也是实际工程中最容易写错的模式。看似简单的"确保一个类只有一个实例"，背后涉及线程安全、内存序、静态变量生命周期等深层C++知识。

工作中我见过太多"线程安全"的单例实现其实是有Bug的——特别是那些"双重检查锁"的实现，在没有正确处理内存序的情况下，在ARM平台上是不安全的。今天从底层原理角度复盘各种单例实现。

---

### 1. 为什么需要单例？

单例的核心需求：
- **全局唯一**：数据库连接池、日志系统、配置管理器
- **延迟初始化**：资源昂贵，首次使用时才创建
- **线程安全**：多线程环境下不能创建多个实例

---

### 2. 各版本实现及分析

#### 2.1 最朴素版本：双重检查锁（DCL）— 有Bug！

```cpp
// ⚠️ 经典但有Bug的实现！
template <class T>
class Singleton {
public:
    static T* instance() {
        if (s_instance == nullptr) {        // 第一次检查（无锁快速路径）
            std::lock_guard<std::mutex> lock(s_mutex);
            if (s_instance == nullptr) {    // 第二次检查（获锁后确认）
                s_instance = new T;         // ← Bug在这里！
            }
        }
        return s_instance;
    }

private:
    static T* s_instance;
    static std::mutex s_mutex;
};
```

**这个经典实现的Bug在哪？**

`s_instance = new T` 在编译器看来是三步：
1. 分配内存：`void* mem = operator new(sizeof(T))`
2. 构造对象：`new(mem) T()`
3. 赋值指针：`s_instance = (T*)mem`

编译器/CPU可能将步骤2和3**重排序**为：1→3→2

```
线程A：                        线程B：
  分配内存                      
  s_instance = mem  (步骤3)    
                                if (s_instance != nullptr) ← 不为空！
                                return s_instance;  ← 返回未构造的对象！
  构造对象 (步骤2)             
```

线程B拿到了一个**内存已分配但构造函数还没执行完**的对象！

#### 2.2 修复DCL：使用std::atomic + acquire/release

```cpp
template <class T>
class Singleton {
public:
    static T* instance() {
        T* tmp = s_instance.load(std::memory_order_acquire); // acquire读
        if (tmp == nullptr) {
            std::lock_guard<std::mutex> lock(s_mutex);
            tmp = s_instance.load(std::memory_order_relaxed); // 锁内可以relaxed
            if (tmp == nullptr) {
                tmp = new T;
                s_instance.store(tmp, std::memory_order_release); // release写
            }
        }
        return tmp;
    }

private:
    static std::atomic<T*> s_instance;
    static std::mutex s_mutex;
};

template <class T>
std::atomic<T*> Singleton<T>::s_instance{nullptr};

template <class T>
std::mutex Singleton<T>::s_mutex;
```

**为什么这样就安全了？**
- `release store`保证：new T的构造完全完成后，指针才对其他线程可见
- `acquire load`保证：看到非空指针后，一定能看到完整构造的对象
- 形成happens-before关系：构造 → release store → acquire load → 使用对象

#### 2.3 std::call_once — 标准库方案

```cpp
class Singleton {
public:
    static Singleton& getInstance() {
        std::call_once(s_flag, []() {
            s_instance.reset(new Singleton());
        });
        return *s_instance;
    }

private:
    Singleton() = default;
    Singleton(const Singleton&) = delete;
    Singleton& operator=(const Singleton&) = delete;

    static std::unique_ptr<Singleton> s_instance;
    static std::once_flag s_flag;
};

std::unique_ptr<Singleton> Singleton::s_instance;
std::once_flag Singleton::s_flag;
```

**优点**：标准库保证线程安全，不需要自己处理内存序
**缺点**：`std::once_flag`不能重置，一旦初始化就无法"重建"单例

#### 2.4 Meyers' Singleton — 最优雅的现代C++方案

```cpp
class Singleton {
public:
    static Singleton& getInstance() {
        static Singleton instance;  // C++11保证线程安全
        return instance;
    }

    void doSomething() { /* ... */ }

private:
    Singleton() { printf("Singleton created\n"); }
    ~Singleton() { printf("Singleton destroyed\n"); }

    Singleton(const Singleton&) = delete;
    Singleton& operator=(const Singleton&) = delete;
};
```

**为什么这是最优方案？**

C++11标准（§6.7）明确规定：

> If control enters the declaration concurrently while the variable is being initialized, the concurrent execution shall wait for completion of the initialization.

即：局部静态变量的初始化是**线程安全**的，编译器会自动插入同步代码。

**编译器实际生成的代码（GCC）**：

```cpp
// 编译器为 static Singleton instance 生成的伪代码
static Singleton instance;
static std::atomic<int> guard = 0;  // 编译器隐式生成

Singleton& getInstance() {
    if (guard.load(std::memory_order_acquire) != INITIALIZED) {
        // 慢速路径：用互斥量保证只初始化一次
        __cxa_guard_acquire(&guard);  // 类似mutex lock
        if (guard != INITIALIZED) {
            new (&instance) Singleton();
            guard.store(INITIALIZED, std::memory_order_release);
        }
        __cxa_guard_release(&guard);  // 类似mutex unlock
    }
    return instance;
}
```

本质上编译器帮你做了DCL + 正确的内存序，免费且正确。

### 4. 饿汉式：简单但有隐患

```cpp
class Singleton {
public:
    static Singleton& getInstance() {
        return s_instance;  // 直接返回，无需检查
    }

private:
    Singleton() = default;
    static Singleton s_instance;  // 程序启动时就初始化
};

Singleton Singleton::s_instance;  // 在main()之前构造
```

**问题：静态初始化顺序惨案（Static Initialization Order Fiasco）**

```cpp
// file_a.cpp
Singleton Singleton::s_instance;  // 全局静态对象A

// file_b.cpp
class Logger {
    Logger() {
        // 构造时使用Singleton — 但它可能还没初始化！
        Singleton::getInstance().doSomething();  // 💥 UB!
    }
};
Logger g_logger;  // 全局静态对象B
```

不同编译单元的全局静态对象初始化顺序是**未定义的**，如果B在A之前初始化，就会访问未构造的对象。

**Meyers' Singleton完美解决这个问题**——首次调用时才初始化，不依赖全局构造顺序。

### 5. 模板化单例（工程实用版）

```cpp
template<typename T>
class Singleton {
public:
    // 禁止拷贝和移动
    Singleton(const Singleton&) = delete;
    Singleton& operator=(const Singleton&) = delete;
    Singleton(Singleton&&) = delete;
    Singleton& operator=(Singleton&&) = delete;

    // 获取实例
    static T& getInstance() {
        static T instance;
        return instance;
    }

protected:
    Singleton() = default;
    virtual ~Singleton() = default;
};

// 使用方式
class ConfigManager : public Singleton<ConfigManager> {
    friend class Singleton<ConfigManager>;  // 允许基类访问私有构造
private:
    ConfigManager() { loadConfig(); }
    void loadConfig() { /* ... */ }

public:
    std::string get(const std::string& key) { /* ... */ }
};

// 调用
auto& config = ConfigManager::getInstance();
```

### 6. 单例的销毁顺序问题

Meyers' Singleton在程序退出时会以**构造的逆序**销毁。如果两个单例有依赖关系，可能出问题：

```cpp
// Logger在NetworkManager之后构造
// 所以Logger在NetworkManager之前销毁
// 如果NetworkManager的析构函数里要打日志——Logger已经死了！

class NetworkManager : public Singleton<NetworkManager> {
    ~NetworkManager() {
        Logger::getInstance().log("NetworkManager shutting down");
        // ← 如果Logger已销毁，这里是UB!
    }
};
```

**解决方案：Phoenix Singleton（凤凰单例）**

```cpp
template<typename T>
class PhoenixSingleton {
    static T* s_instance;
    static bool s_destroyed;

public:
    static T& getInstance() {
        if (!s_instance) {
            if (s_destroyed) {
                // 已销毁过一次，重新创建（凤凰涅槃）
                new(s_instance) T();
                atexit(destroy);
                s_destroyed = false;
            } else {
                create();
            }
        }
        return *s_instance;
    }

private:
    static void create() {
        static T instance;
        s_instance = &instance;
    }

    static void destroy() {
        s_instance->~T();
        s_destroyed = true;
    }
};
```

**工程建议**：在实际项目中，我更倾向于用**显式的初始化/销毁顺序**来管理全局对象的生命周期，而不是依赖单例的自动销毁。比如在main函数开头按顺序init，结尾按逆序shutdown。

### 7. 什么时候不该用单例？

单例被广泛滥用。以下情况应该避免：

| 场景 | 为什么不该用单例 | 替代方案 |
|------|------------------|----------|
| 单元测试 | 单例状态在测试间泄漏 | 依赖注入 |
| 多实例需求 | 未来可能需要多实例 | 工厂模式 |
| 隐式全局状态 | 函数的依赖关系不透明 | 显式传参 |
| 跨模块依赖 | 导致模块间强耦合 | 接口抽象 |

**我的经验**：在大型项目中，单例用在以下场景最合适：
- 日志系统（全局唯一，无状态依赖）
- 线程池（资源管理，不需要多实例）
- 配置中心（只读居多，初始化一次）

其他场景，优先考虑依赖注入。

### 总结

| 推荐度 | 实现方式 | 适用场景 |
|--------|----------|----------|
| ⭐⭐⭐⭐⭐ | Meyers' Singleton | 绝大多数场景（C++11+） |
| ⭐⭐⭐⭐ | std::call_once | 需要动态分配或重置的场景 |
| ⭐⭐⭐ | DCL + atomic | 学习原理用，生产不推荐手写 |
| ⭐⭐ | 饿汉式 | 无跨单例依赖、初始化开销小 |
| ⭐ | 朴素DCL | 不要用！有Bug！ |

**一句话总结**：现代C++（11及以上），直接用Meyers' Singleton（局部static），编译器保证线程安全，代码最简洁，没有任何理由再手写DCL。
