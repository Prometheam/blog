IM（即时通讯）系统是后端架构中最有挑战性的场景之一。我参与过一个千万级用户的 IM 项目，从 0 到 1 踩过无数坑。今天系统性地分享高并发 IM 的架构设计。

## 需求分析

**功能性需求**：
- 单聊（1v1）、群聊（上限 500 人 / 万人大群）
- 在线状态（presence）
- 消息类型：文本、图片、语音、视频、文件
- 已读回执、消息撤回
- 离线消息同步、多端同步

**非功能性需求**：
- DAU 1亿，峰值同时在线 3000 万
- 消息投递延迟 < 200ms（P99）
- 峰值消息吞吐 100K msg/s
- 消息可靠投递（不丢、不重、有序）

## 长连接管理

单机百万连接是基本要求。关键设计：

```cpp
// 连接路由表（分布式）：user_id -> gateway 节点
// 存储在 Redis Cluster 中
// Key: route:{user_id}
// Value: {gateway_ip}:{port}:{conn_id}:{login_time}

struct ConnEntry {
    uint64_t user_id;
    int fd;
    time_t last_heartbeat;
    uint8_t platform;  // iOS=1, Android=2, Web=3
};

// 每个gateway节点维护本地连接表
class ConnectionManager {
    std::unordered_map<uint64_t, std::vector<ConnEntry>> user_conns_;
    std::unordered_map<int, uint64_t> fd_to_user_;  // fd反查
    // 心跳超时检测用时间轮
    TimingWheel heartbeat_wheel_;
};
```

心跳机制：客户端每 30s 发送心跳，服务端 90s 无心跳判定断线。使用时间轮（Timing Wheel）高效检测超时。

## 消息流转

一条消息从发送到接收的完整链路：

```
发送方                Gateway          Logic           Storage       接收方Gateway    接收方
  |--- SendMsg ------->|                |                |               |             |
  |                    |--- RPC ------->|                |               |             |
  |                    |                |-- 生成msg_id -->|               |             |
  |                    |                |-- 写入存储 ---->|               |             |
  |                    |                |-- 写入时间线 -->|               |             |
  |                    |                |                |               |             |
  |                    |                |--- 查路由表 ------------------>|             |
  |                    |                |                |               |--- Push --->|
  |                    |<-- SendAck ----|                |               |             |
  |<--- ServerAck -----|                |               |             |
  |                    |                |               |<--- MsgAck --|
```

关键保证：
- **不丢消息**：Logic 写入存储成功后才返回 Ack，推送失败走离线
- **不重复**：客户端维护本地最大 seq_id，去重幂等
- **有序**：每个会话独立的递增 sequence

## 消息存储模型

这是 IM 架构中最核心的设计决策——**写扩散 vs 读扩散**：

```
写扩散 (Write Diffusion / Inbox模型):
+--------+     +----------+  +----------+  +----------+
| 消息体  | --> | A 的收件箱| + | B 的收件箱| + | C 的收件箱|
+--------+     +----------+  +----------+  +----------+
每人一份时间线副本

读扩散 (Read Diffusion / Timeline模型):
+--------+     +---------------+
| 消息体  | --> | 会话消息队列   |  所有人从同一队列读
+--------+     +---------------+
```

我的实践策略——**混合模型**：

```
消息类型        | 存储策略      | 原因
----------------+--------------+---------------------------------
单聊            | 写扩散        | 只写2份，离线同步方便
小群(≤200人)    | 写扩散        | 写入量可控，拉取快
大群(>200人)    | 读扩散        | 避免写放大，用户按需拉取
超大群(>5000人) | 读扩散+缓存   | 热消息缓存在Redis
```

## 消息序号生成

每个会话需要严格递增的 sequence ID：

```cpp
// 方案：Redis INCRBY (每个会话独立key)
// Key: seq:{conv_id}
// 批量获取减少网络往返
class SeqAllocator {
public:
    uint64_t allocBatch(const std::string& conv_id, int count) {
        // INCRBY seq:{conv_id} {count}
        // 返回值为分配的最大序号
        uint64_t max_seq = redis_.incrby("seq:" + conv_id, count);
        return max_seq - count + 1;  // 返回起始序号
    }
};
```

单聊用 `min(uid_a, uid_b):max(uid_a, uid_b)` 作为 conv_id，保证双方看到相同序列。

## 离线消息同步

采用 **推拉结合** 的方案：

```
登录时:
1. 客户端上报 last_seq (每个会话)
2. 服务端计算 diff = server_seq - last_seq
3. diff ≤ 100: 服务端主动推送（推模式）
4. diff > 100: 告知客户端按会话拉取（拉模式）

时间线拉取:
GET /sync?conv_id=xxx&start_seq=100&limit=50
返回: [{seq:101, msg_id:..., ...}, {seq:102, ...}, ...]
```

## 已读回执与在线状态

```cpp
// 已读回执：标记会话已读到的序号
// 单聊直接推送给对方
// 群聊做聚合：每5秒批量上报，服务端合并后推送
struct ReadReceipt {
    uint64_t conv_id;
    uint64_t user_id;
    uint64_t read_seq;  // 已读到的最大seq
    time_t timestamp;
};

// 在线状态（Presence）
// 不做精确实时推送（代价太大），而是：
// 1. 好友数 < 200：上下线时推送
// 2. 好友数 ≥ 200：被动查询（打开聊天窗口时拉取）
// 3. 大群：不推送成员状态
```

## 水平扩展

```
                    +--- Gateway集群 (按连接数扩展) ---+
                    |   node1  node2  node3  ...       |
                    +----------------------------------+
                                  |
                    +--- Logic集群 (无状态，按QPS扩展) --+
                    |   pod1  pod2  pod3  ...           |
                    +----------------------------------+
                                  |
          +-------------------+---+---+------------------+
          |                   |       |                  |
    Redis Cluster      MySQL集群     Kafka          对象存储
    (路由/时间线)     (消息持久化)   (异步处理)     (文件/图片)
                    (按conv_id分片)
```

**消息路由**：Logic 根据接收方的路由信息（Redis 中查询）确定推送到哪个 Gateway 节点。

**跨机房部署**：
- 就近接入：用户连接最近的 Gateway
- 消息跨机房同步：通过 Kafka 跨 DC 复制
- 每条消息带 `origin_dc` 标记防止回环

## 总结

IM 系统的核心挑战在于：海量长连接管理、消息可靠有序投递、存储模型选择。我的经验是不要一开始就追求完美——先用写扩散跑通全流程，大群场景后续再优化为读扩散。架构是演进出来的，不是设计出来的。
