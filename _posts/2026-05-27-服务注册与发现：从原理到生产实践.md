在微服务架构中，服务实例的地址是动态变化的——扩缩容、故障重启、滚动发布都会改变实例的 IP 和端口。如果还像单体时代一样把地址写死在配置文件里，运维成本会随着服务数量指数级增长。这就是服务注册与发现要解决的核心问题。

## 静态配置 vs 动态发现

最原始的做法是 Nginx 配置文件里写一组 upstream：

```nginx
upstream order_service {
    server 10.0.1.10:8080;
    server 10.0.1.11:8080;
    server 10.0.1.12:8080;
}
```

每次扩容都要改配置、reload，在几百个服务的场景下完全不可维护。动态发现的本质是把这个"地址簿"从静态文件搬到一个集中式（或分布式）的注册中心，让服务自己注册、自己注销。

## 两种发现模式

```
┌─────────────────────────────────────────────────────┐
│          Client-side Discovery                       │
│                                                     │
│  Consumer ──→ Registry ──→ 获取实例列表              │
│     │                                               │
│     └──→ 直接调用 Provider (自己做负载均衡)           │
└─────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────┐
│          Server-side Discovery                       │
│                                                     │
│  Consumer ──→ Load Balancer ──→ Provider            │
│                    │                                │
│                    └──→ Registry (LB 查询)           │
└─────────────────────────────────────────────────────┘
```

Client-side 模式（如 gRPC + etcd）让客户端直连，减少了一跳延迟，但客户端需要内置服务发现逻辑。Server-side 模式（如 K8s Service + kube-proxy）对客户端透明，但 LB 本身可能成为瓶颈。我在实际项目中两种都用过，内部 RPC 用 client-side，对外 HTTP 网关用 server-side。

## CP vs AP：注册中心选型

| 注册中心 | 一致性模型 | 适用场景 |
|---------|-----------|---------|
| ZooKeeper | CP (ZAB协议) | 强一致需求，节点数少 |
| etcd | CP (Raft) | K8s 生态，轻量级 |
| Consul | CP (Raft) + Gossip | 多数据中心，内置健康检查 |
| Eureka | AP | Spring Cloud 生态，高可用优先 |
| Nacos | CP/AP 可切换 | 阿里生态，同时支持配置管理 |

我的经验是：对于服务发现场景，**AP 往往比 CP 更合适**。理由很简单——注册中心短暂不一致（返回了一个刚下线的节点），客户端重试一次就好了；但如果注册中心因为选举而不可用（CP 在网络分区时的行为），所有服务都无法发现对方，这才是灾难。

## 服务生命周期与健康检查

```
┌──────┐    Register     ┌──────────┐
│Service├───────────────→│ Registry │
│      │    Heartbeat    │          │
│      ├───────────────→│  (TTL)   │
│      │   (every 5s)   │          │
│      │                 │          │
│      │   Deregister    │          │
│      ├───────────────→│          │
└──────┘   (graceful)   └──────────┘
                              │
                         TTL expired?
                              │
                         ┌────▼────┐
                         │ Remove  │
                         │Instance │
                         └─────────┘
```

三种健康检查方式：

1. **心跳续约 (TTL)**：服务定期发送心跳，注册中心在超时后摘除实例。简单但有延迟窗口。
2. **主动探测**：注册中心主动检查服务端口（TCP/HTTP），如 Consul 的 health check。
3. **应用层上报**：服务主动报告自身状态（如数据库连接池耗尽时标记为 unhealthy）。

生产中我推荐组合使用：心跳保证基本存活检测，应用层上报处理"进程活着但服务不可用"的场景。

## gRPC Name Resolution 集成

gRPC 原生支持可插拔的 name resolver。我在 C++ 项目中实现过基于 etcd 的 resolver：

```cpp
class EtcdResolver : public grpc::naming::ResolverInterface {
public:
    EtcdResolver(const std::string& etcd_addr, const std::string& service_name)
        : watcher_(etcd_addr, "/services/" + service_name) {}

    void Start(std::shared_ptr<grpc::naming::ResolverCallbackInterface> cb) override {
        callback_ = cb;
        watcher_.Watch([this](const std::vector<std::string>& endpoints) {
            std::vector<grpc::naming::Update> updates;
            for (const auto& ep : endpoints) {
                updates.push_back({grpc::naming::UPDATE_ADD, ep});
            }
            callback_->OnUpdate(updates);
        });
    }

private:
    EtcdWatcher watcher_;
    std::shared_ptr<grpc::naming::ResolverCallbackInterface> callback_;
};
```

配合 gRPC 内置的 round_robin 或 pick_first 策略，客户端无需关心具体实例地址。

## DNS-based Discovery（K8s CoreDNS）

在 K8s 环境中，每个 Service 自动获得 DNS 记录：`<service>.<namespace>.svc.cluster.local`。Headless Service（`clusterIP: None`）会返回所有 Pod 的 A 记录，天然适合 gRPC 客户端做客户端负载均衡。

但 DNS 有缓存问题——客户端 DNS 缓存、glibc 的 nscd 都可能导致实例下线后流量仍然打过去。我踩过的坑：Java 默认 DNS 缓存 30 秒，Go 默认不缓存，C++ 取决于 getaddrinfo 实现。解决办法是设置合理的 TTL 或者直接用 watch 机制绕过 DNS。

## 优雅关闭与反注册

```cpp
// 生产级优雅关闭流程
void GracefulShutdown(EtcdClient& registry, GrpcServer& server) {
    // 1. 先从注册中心摘除，不再接收新请求
    registry.Deregister(instance_id_);
    
    // 2. 等待一个心跳周期，确保消费者感知到变化
    std::this_thread::sleep_for(std::chrono::seconds(5));
    
    // 3. 等待正在处理的请求完成（设置截止时间）
    server.Shutdown(std::chrono::seconds(30));
    
    // 4. 强制关闭剩余连接
    server.ForceShutdown();
}
```

关键点：**先摘流量，再停服务**。如果顺序反了，在 deregister 和消费者感知之间的窗口期，请求会打到已关闭的端口上。

## 生产踩坑：脑裂与惊群

**脑裂**：CP 注册中心在网络分区时，minority 分区的节点无法提供服务。我遇到过一次 ZooKeeper 三节点集群，两个节点所在的机房网络故障，导致整个集群不可用——因为剩余一个节点无法形成多数派。解决方案：5 节点部署，跨三个可用区。

**惊群效应**：注册中心重启后，所有客户端同时重新拉取服务列表，形成请求风暴。缓解方案：

```cpp
// 带随机抖动的重试
int retry_delay_ms = base_delay * (1 << retry_count);
retry_delay_ms += random() % (retry_delay_ms / 2);  // 加入 50% 的随机抖动
```

## 总结

服务发现看似简单（不就是存个地址嘛），但在生产环境中涉及一致性、可用性、网络分区的权衡。我的建议是：K8s 环境优先用原生 Service + CoreDNS；非 K8s 环境根据技术栈选择（Go 生态选 etcd/Consul，Java 选 Nacos）；不管选什么，都要做好注册中心本身不可用时的降级方案——本地缓存最后一次拉取的实例列表，保证即使注册中心挂了，存量连接仍然可用。
