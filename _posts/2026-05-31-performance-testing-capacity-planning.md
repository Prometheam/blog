### 引言

"系统能抗住双11流量吗？"——这个问题不能靠猜，只能靠压测。性能压测不是"跑个wrk看QPS"那么简单：你需要模拟真实流量模型、全链路联动、定位瓶颈、推算容量需求。

我们在一次大促前做了全链路压测，发现瓶颈不在应用层而在Redis集群——某个热key的QPS已接近单分片上限。如果没有压测，大促当天这个点就会成为全链路雪崩的起点。

本文讲解从单接口压测到全链路压测的完整方法论，以及如何根据压测结果做容量规划。

### 1. 压测类型

```
  ┌──────────────────┬──────────────────────────────────────────────┐
  │ 类型             │ 目的                                         │
  ├──────────────────┼──────────────────────────────────────────────┤
  │ 基准测试         │ 单接口在理想条件下的极限性能                  │
  │ (Benchmark)      │ 确定单组件的能力上限                          │
  ├──────────────────┼──────────────────────────────────────────────┤
  │ 负载测试         │ 逐步增加压力，找到系统的拐点(拐点=瓶颈)      │
  │ (Load Test)      │ 找到"最大安全承载量"                         │
  ├──────────────────┼──────────────────────────────────────────────┤
  │ 压力测试         │ 超过系统承载能力，观察降级和恢复行为          │
  │ (Stress Test)    │ 验证过载保护机制是否生效                      │
  ├──────────────────┼──────────────────────────────────────────────┤
  │ 全链路压测       │ 模拟真实业务流量，端到端验证                  │
  │ (E2E Load Test)  │ 找到整条链路的最短板                          │
  ├──────────────────┼──────────────────────────────────────────────┤
  │ 稳定性测试       │ 长时间(24h+)持续中等压力                     │
  │ (Soak Test)      │ 发现内存泄漏、连接泄漏、GC问题              │
  └──────────────────┴──────────────────────────────────────────────┘
```

### 3. 压测执行方法

#### 3.1 逐步加压法（找拐点）

```
  QPS vs 延迟曲线（寻找拐点）：

  延迟(P99)
   │
   │                          ╱ ← 系统过载，延迟急剧上升
   │                        ╱
   │                      ╱
   │              ┄┄┄┄┄╱  ← 拐点（最大安全承载）
   │  ─────────────────
   │  ← 正常区间（延迟稳定）
   │
   └──────────────────────────────────→ QPS
          1K    2K    3K    4K    5K

  方法：
  1. 从低QPS开始（如1000 QPS）
  2. 每轮增加20-30%
  3. 每轮持续3-5分钟（等系统稳定）
  4. 记录每轮的P50/P99/P999延迟、错误率、资源使用
  5. 当P99延迟急剧上升或错误率>1%时 → 找到了拐点
  6. 拐点 × 0.7 = 建议最大生产负载（留30%余量）
```

```bash
# wrk2恒定速率压测（找拐点）
for rate in 1000 2000 3000 4000 5000 6000 8000 10000; do
    echo "=== Testing at ${rate} RPS ==="
    wrk2 -t4 -c100 -d60s -R${rate} --latency http://service:8080/api/orders
    sleep 10  # 间隔让系统恢复
done

# vegeta恒定速率 + 延迟报告
echo "GET http://service:8080/api/orders" | \
    vegeta attack -rate=5000/s -duration=60s | \
    vegeta report -type=text

# 输出:
# Requests      [total, rate]   300000, 5000.02
# Duration      [total]         60.000s
# Latencies     [mean, 50, 95, 99, max]  2.1ms, 1.8ms, 4.2ms, 12.1ms, 89ms
# Success       [ratio]         99.97%
```

#### 3.2 全链路压测

```
  全链路压测架构：

  ┌─────────────────────────────────────────────────────────────────┐
  │  压测流量（带染色标记）                                          │
  │                                                                 │
  │  压测引擎 ──→ [网关] ──→ [订单服务] ──→ [库存服务]              │
  │  (k6/locust)   │           │              │                    │
  │                 │           │              │                    │
  │                 │           ▼              ▼                    │
  │                 │      [影子DB]       [影子Redis]               │
  │                 │    (隔离的测试库)  (隔离的测试缓存)            │
  │                 │                                              │
  │  关键：压测流量不能影响真实数据！                               │
  │  方案：流量染色 + 影子库/影子表                                 │
  └─────────────────────────────────────────────────────────────────┘

  流量染色：
  - 压测请求Header: X-Traffic-Type: shadow
  - 中间件识别该标记 → 路由到影子DB/影子缓存
  - 真实数据完全不受影响
```

### 4. 瓶颈定位方法

```
  压测中发现瓶颈的诊断流程：

  P99延迟飙升或QPS打不上去
    │
    ├── 查CPU使用率
    │   ├── > 80%: CPU瓶颈 → perf火焰图定位热点函数
    │   └── < 50%: 不是CPU问题，往下看
    │
    ├── 查内存
    │   ├── RSS持续增长: 内存泄漏 → jemalloc prof
    │   └── 稳定: 不是内存问题
    │
    ├── 查网络
    │   ├── 带宽打满: 网络瓶颈 → 优化payload大小
    │   ├── 大量TIME_WAIT: 短连接过多 → 连接池
    │   └── 正常
    │
    ├── 查磁盘IO
    │   ├── iowait > 20%: IO瓶颈 → 加缓存/SSD/异步IO
    │   └── 正常
    │
    ├── 查下游依赖
    │   ├── DB延迟升高: DB瓶颈 → 索引/连接池/读写分离
    │   ├── Redis延迟升高: 热key/大value → 分片/拆分
    │   └── 正常
    │
    └── 查线程/连接池
        ├── 线程池满: 线程池太小 → 扩大或用异步
        └── 连接池满: 连接不够 → 扩大或检查泄漏
```

### 5. 容量规划

```
  容量规划公式：

  目标QPS = 日均QPS × 峰值倍数 × 安全系数
         = (日总请求数 / 86400) × 峰值比 × 1.5

  需要实例数 = 目标QPS / 单实例安全QPS

  示例：
  - 日均请求量: 1亿次
  - 平均QPS: 1亿 / 86400 ≈ 1157 QPS
  - 峰值倍数: 5倍 (高峰期)
  - 峰值QPS: 1157 × 5 = 5785 QPS
  - 安全系数: 1.5 (预留余量)
  - 目标QPS: 5785 × 1.5 ≈ 8700 QPS

  压测得单实例安全QPS: 2000 QPS (P99 < 50ms的拐点 × 0.7)
  需要实例数: 8700 / 2000 = 4.35 → 5个实例

  最终：部署5个实例，配合HPA在峰值时扩到8个
```

### 7. 压测检查清单

| 阶段 | 检查项 |
|------|--------|
| 准备 | 压测环境与生产配置一致（实例数/配置/数据量）|
| 准备 | 测试数据量级与生产相当（不能空库压测）|
| 准备 | 流量模型贴近真实（读写比、热点分布）|
| 执行 | 逐步加压（不要一次打满）|
| 执行 | 每轮至少3分钟（等系统稳定）|
| 执行 | 同时监控所有组件的资源指标 |
| 分析 | 关注P99而非平均值 |
| 分析 | 找拐点而非极限值 |
| 分析 | 确认瓶颈组件（CPU/IO/网络/依赖）|
| 规划 | 安全容量 = 拐点 × 0.7 |
| 规划 | 考虑峰值 × 安全系数 |

### 总结

性能压测与容量规划的核心：

1. **压测不是跑个wrk**：需要模拟真实流量模型、逐步加压、找拐点
2. **全链路压测找最短板**：单接口压测不够，瓶颈可能在下游依赖
3. **P99比平均值重要**：关注尾延迟，它决定用户体验
4. **容量 = 峰值 × 安全系数**：不能按平均值规划，必须考虑峰值
5. **性能回归要自动化**：CI中集成基准测试，退化自动告警
6. **流量染色保护生产**：全链路压测必须隔离测试数据，不污染真实数据

性能是"测出来"的，不是"猜出来"的。每次大促前都做一轮全链路压测，把瓶颈在压测中暴露，远比在生产中暴露好一万倍。
