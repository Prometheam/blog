### 引言

在调优IM系统跨区域同步性能时，我遇到过一个诡异问题：北京到新加坡的专线带宽1Gbps，但TCP传输只跑到50Mbps。经过抓包分析发现，拥塞控制算法（当时默认CUBIC）在高延迟链路上表现极差——RTT 80ms意味着cwnd增长极其缓慢。后来切换到BBR，吞吐立刻飙升到800Mbps。

这篇文章从拥塞控制的基本原理讲起，深入分析Reno、CUBIC、BBR三代算法的设计哲学和数学模型，最后给出Linux下的实战调优方法。

---

### 1. 拥塞控制的本质问题

#### 1.1 为什么需要拥塞控制

TCP是端到端协议，发送方不知道网络中间有多少带宽可用。如果所有连接都拼命发数据：

```
发送方A ──┐
发送方B ──┼──→ [路由器队列: ████████████████ 满了!] ──→ 接收方
发送方C ──┘         │
                    ▼ 丢包！
                  
没有拥塞控制 → 所有人拼命发 → 路由器缓冲区溢出 → 大面积丢包
→ 大面积重传 → 更多拥塞 → 网络崩溃（拥塞崩塌 Congestion Collapse）
```

**拥塞控制的目标**：让每个TCP连接"探测"出自己可用的网络容量，在不造成拥塞的前提下尽可能快地发送数据。

#### 1.2 核心概念

```
┌────────────────────────────────────────────────────────────────┐
│                   TCP拥塞控制核心变量                            │
├──────────────┬─────────────────────────────────────────────────┤
│ cwnd         │ 拥塞窗口：发送方允许在途（未确认）的最大数据量   │
│              │ 由拥塞控制算法动态调整                           │
├──────────────┼─────────────────────────────────────────────────┤
│ rwnd         │ 接收窗口：接收方通告的可用缓冲区大小             │
│              │ 由接收方控制（流量控制）                         │
├──────────────┼─────────────────────────────────────────────────┤
│ ssthresh     │ 慢启动阈值：cwnd超过此值后从慢启动切换为拥塞避免 │
├──────────────┼─────────────────────────────────────────────────┤
│ RTT          │ 往返时延：数据包来回一趟的时间                   │
├──────────────┼─────────────────────────────────────────────────┤
│ BDP          │ 带宽延迟积 = Bandwidth × RTT                    │
│              │ 理想的cwnd应该等于BDP                            │
├──────────────┼─────────────────────────────────────────────────┤
│ 发送速率     │ = cwnd / RTT（在途数据量除以往返时间）          │
└──────────────┴─────────────────────────────────────────────────┘

实际发送窗口 = min(cwnd, rwnd)
```

### 2. Tahoe/Reno：基于丢包的第一代算法

#### 2.1 三个阶段

```
cwnd
 ▲
 │           ssthresh
 │              │
 │              │      ┌─── 拥塞避免（线性增长）
 │              │     ╱
 │              │    ╱
 │              │   ╱  ← 每个RTT: cwnd += 1 MSS
 │              │  ╱
 │          ────┼─╱
 │         ╱    │╱
 │        ╱     │    ← 慢启动（指数增长）
 │       ╱      │      每个ACK: cwnd += 1 MSS
 │      ╱       │      即每个RTT: cwnd翻倍
 │     ╱        │
 │    ╱         │
 │───╱──────────┴───────────────────────────→ 时间
 │  1MSS
 │
 └──────────────────────────────────────────→

丢包发生时(Reno):
  ssthresh = cwnd / 2
  cwnd = ssthresh（快速恢复，不回到1）
```

#### 2.2 快速重传与快速恢复（Reno改进）

```
Tahoe（原始）：丢包 → cwnd回到1MSS → 重新慢启动（太保守）

Reno（改进）：
  收到3个重复ACK → 快速重传（不等超时）
                  → ssthresh = cwnd/2
                  → cwnd = ssthresh + 3MSS（快速恢复）
                  → 进入拥塞避免阶段

为什么+3？因为收到3个dupACK说明有3个包已经离开网络（被接收方收到了）

超时丢包（更严重）：
  → cwnd = 1MSS
  → 重新慢启动
```

#### 2.3 Reno的局限

```
问题1: AIMD不适合高BDP网络
  
  假设：1Gbps链路, RTT=100ms
  BDP = 1Gbps × 100ms = 12500 packets (按MSS=1460B)
  
  一次丢包后: cwnd从12500降到6250
  恢复到12500需要: 6250个RTT = 6250×100ms = 625秒！
  
  → 高带宽+高延迟网络下，Reno几乎永远跑不满

问题2: 丢包 ≠ 拥塞
  无线网络的随机丢包会被误判为拥塞 → 错误降速
```

### 3. CUBIC：Linux的默认选择

#### 3.1 设计思想

CUBIC的核心创新：**cwnd增长不再依赖RTT，而是依赖丢包后经过的时间。**

```
CUBIC增长曲线（三次函数）：

cwnd
 ▲        W_max
 │          │    ╭─────────────── 继续探测
 │          │   ╱
 │          │  ╱
 │          ├─╱  ← 接近上次丢包点时放慢速度
 │         ╱│
 │        ╱ │
 │       ╱  │
 │      ╱   │
 │     ╱    │   ← 远离丢包点时快速增长
 │    ╱     │
 │───╱──────┴────────────────────→ 时间(t)
 │
 │  公式: W(t) = C × (t - K)³ + W_max
 │  
 │  K = ∛(W_max × β / C)  ← 到达W_max的时间
 │  β = 0.7（乘性减少因子）
 │  C = 0.4（缩放常数）
```

#### 3.2 CUBIC的优势

```
┌────────────────────────────────────────────────────────────────┐
│              CUBIC vs Reno 对比                                 │
├──────────────────┬──────────────────┬──────────────────────────┤
│ 特性             │ Reno             │ CUBIC                    │
├──────────────────┼──────────────────┼──────────────────────────┤
│ cwnd增长依赖     │ RTT（每个RTT+1） │ 时间（与RTT无关）        │
│ 高RTT链路       │ 增长极慢          │ 增长速度不变             │
│ RTT公平性       │ 短RTT连接占优     │ 所有RTT连接公平          │
│ 丢包后恢复      │ 线性，慢          │ 三次曲线，先快后慢再快   │
│ 丢包点附近      │ 不减速            │ 主动减速（避免再次丢包） │
└──────────────────┴──────────────────┴──────────────────────────┘
```

#### 3.3 CUBIC的问题

```
CUBIC仍然是"基于丢包"的算法：

1. 必须把路由器队列填满才能检测到拥塞
   → 造成 Bufferbloat（缓冲膨胀）
   → 延迟从正常的20ms飙升到200ms+

2. 与其他CUBIC流竞争时表现良好
   但与Reno流共存时可能不公平

3. 在随机丢包环境（如无线网络）仍会误判
```

### 4. BBR：基于模型的革命

#### 4.1 设计哲学

BBR（Bottleneck Bandwidth and Round-trip propagation time）由Google于2016年提出，完全抛弃"丢包=拥塞"的假设。

**核心理念**：显式估计网络的两个物理属性——瓶颈带宽(BtlBw)和最小RTT(RTprop)，然后精确控制发送速率。

```
          ┌─────────────────────────────────────────────────┐
          │            网络管道模型                           │
          │                                                 │
          │    发送方 ═══════════════╗                       │
          │                         ║ 瓶颈链路              │
          │                         ║ BtlBw = 100Mbps      │
          │                         ╠═══════ 接收方         │
          │                         ║                       │
          │     ←──── RTprop ────→  ║                       │
          │        (传播延迟)        ║                       │
          │                                                 │
          │  最优操作点：                                    │
          │    inflight = BtlBw × RTprop (= BDP)           │
          │    发送速率 = BtlBw                              │
          │                                                 │
          │  inflight < BDP → 带宽没跑满                    │
          │  inflight > BDP → 数据堆积在路由器队列 → 延迟↑  │
          └─────────────────────────────────────────────────┘
```

#### 4.2 BBR的状态机

```
┌──────────────────────────────────────────────────────────────┐
│                    BBR 状态机                                  │
│                                                              │
│  ┌───────────┐   BtlBw稳定   ┌───────────┐                 │
│  │ STARTUP   │──────────────→│ DRAIN      │                 │
│  │(类似慢启动)│               │(排空队列)  │                 │
│  │ 2/ln2增长 │               │ 速率降低   │                 │
│  └───────────┘               └─────┬──────┘                 │
│                                     │ 队列排空               │
│                                     ▼                        │
│                              ┌───────────┐                   │
│                              │ PROBE_BW  │ ← 稳态（98%时间）│
│                              │           │                   │
│                              │ 8个阶段循环：                 │
│                              │ [1.25,0.75,1,1,1,1,1,1]      │
│                              │ × BtlBw                       │
│                              └──────┬────┘                   │
│                                     │ 每10s                  │
│                                     ▼                        │
│                              ┌───────────┐                   │
│                              │ PROBE_RTT │                   │
│                              │(探测最小RTT)│                  │
│                              │ cwnd=4    │                   │
│                              │ 持续200ms │                   │
│                              └───────────┘                   │
└──────────────────────────────────────────────────────────────┘
```

#### 4.3 BBR如何估计BtlBw和RTprop

```cpp
// BBR核心逻辑（简化版伪代码）

struct BBRState {
    double btl_bw;        // 瓶颈带宽估计值（取最近10个RTT的最大交付速率）
    double rt_prop;       // 最小RTT估计值（取最近10秒的最小RTT）
    double pacing_rate;   // 发送速率
    double cwnd;          // 拥塞窗口
    int    state;         // 当前状态
};

void on_ack(BBRState& bbr, AckInfo ack) {
    // 1. 更新BtlBw（滑动窗口最大值）
    double delivery_rate = ack.delivered_bytes / ack.rtt;
    bbr.btl_bw = max_filter(delivery_rate, 10_RTT);  // 最近10个RTT的最大值

    // 2. 更新RTprop（滑动窗口最小值）
    bbr.rt_prop = min_filter(ack.rtt, 10_seconds);  // 最近10秒的最小值

    // 3. 根据状态设置pacing_gain
    double pacing_gain = get_pacing_gain(bbr.state);

    // 4. 计算发送速率和cwnd
    bbr.pacing_rate = pacing_gain * bbr.btl_bw;
    bbr.cwnd = 2 * bbr.btl_bw * bbr.rt_prop;  // 2×BDP
}
```

#### 4.4 BBR vs CUBIC性能对比

```
场景: 1Gbps链路, RTT=100ms, 缓冲区200ms

┌────────────────────┬──────────────┬──────────────┐
│ 指标               │ CUBIC        │ BBR          │
├────────────────────┼──────────────┼──────────────┤
│ 吞吐量            │ ~300Mbps     │ ~950Mbps     │
│ 队列延迟          │ 150-200ms    │ <5ms         │
│ 丢包后恢复时间    │ 数十秒       │ 1-2个RTT     │
│ 带宽利用率        │ 30%          │ 95%          │
│ 链路稳定后延迟    │ RTT+150ms    │ RTT+<1ms    │
└────────────────────┴──────────────┴──────────────┘

关键差异：
- CUBIC填满路由器队列才知道带宽 → 高延迟
- BBR通过测量交付速率估计带宽 → 低延迟
```

#### 4.5 BBR的已知问题

```
1. BBR与基于丢包的算法（CUBIC/Reno）竞争时不公平
   → BBR可能抢占过多带宽（因为它不把丢包当拥塞信号）
   
2. 多条BBR流之间的公平性
   → BBRv1在某些场景下流间不公平
   
3. 浅缓冲网络
   → BBR的PROBE_BW阶段(1.25倍)可能超出浅缓冲容量
   
4. RTT测量噪声
   → 延迟ACK、CPU调度抖动会干扰RTprop估计
   
BBRv2改进：
  - 考虑丢包和ECN信号作为补充
  - 改进了带宽探测策略
  - 提高了与CUBIC的公平性
```

### 5. Linux下的实战配置

#### 5.1 查看和切换拥塞控制算法

```bash
# 查看当前使用的算法
sysctl net.ipv4.tcp_congestion_control
# 输出: net.ipv4.tcp_congestion_control = cubic

# 查看可用算法
sysctl net.ipv4.tcp_available_congestion_control
# 输出: cubic reno bbr

# 启用BBR（需要内核4.9+）
# 1. 加载BBR模块
modprobe tcp_bbr

# 2. 设置为默认算法
sysctl -w net.ipv4.tcp_congestion_control=bbr

# 3. 持久化配置（写入/etc/sysctl.conf）
echo "net.ipv4.tcp_congestion_control=bbr" >> /etc/sysctl.conf
echo "net.core.default_qdisc=fq" >> /etc/sysctl.conf
sysctl -p
```

**注意**：BBR需要配合`fq`（Fair Queueing）队列调度器使用，因为BBR依赖精确的pacing（匀速发送），而`fq`提供了per-flow的pacing支持。

#### 5.2 关键TCP内核参数调优

```bash
# 发送/接收缓冲区（高带宽场景需要增大）
# 格式：min default max（字节）
sysctl -w net.ipv4.tcp_rmem="4096 131072 67108864"   # 接收：4K-128K-64M
sysctl -w net.ipv4.tcp_wmem="4096 65536 67108864"    # 发送：4K-64K-64M

# 开启窗口缩放（支持>64KB窗口）
sysctl -w net.ipv4.tcp_window_scaling=1

# 开启SACK（选择性确认，减少不必要重传）
sysctl -w net.ipv4.tcp_sack=1

# 开启时间戳（精确RTT测量，BBR需要）
sysctl -w net.ipv4.tcp_timestamps=1

# 最大连接数相关
sysctl -w net.core.somaxconn=65535
sysctl -w net.ipv4.tcp_max_syn_backlog=65535
```

#### 5.3 用ss/tcpdump观察拥塞状态

```bash
# ss查看连接的拥塞信息
ss -ti dst 10.0.0.1
# 输出示例：
# cubic wscale:7,7 rto:204 rtt:80/5 ato:40 mss:1448 pmtu:1500
# cwnd:42 ssthresh:30 bytes_sent:1234567
# delivery_rate 150Mbps

# BBR专有信息
ss -ti | grep bbr
# bbr:(bw:950Mbps,mrtt:80,pacing_rate:1050Mbps,delivery_rate:940Mbps)
#     cwnd:149 ssthresh:149

# tcpdump + wireshark分析cwnd变化
tcpdump -i eth0 -w capture.pcap host 10.0.0.1
# 在Wireshark中: Statistics → TCP Stream Graphs → Window Scaling
```

### 6. 实战：跨区域链路优化

#### 6.1 问题诊断

```bash
# 场景：北京→新加坡，1Gbps专线，TCP传输只有50Mbps

# Step 1: 测量基本指标
ping singapore-server  # RTT ≈ 80ms
iperf3 -c singapore-server  # 吞吐：~50Mbps

# Step 2: 分析ss输出
ss -ti dst singapore-server
# cubic cwnd:15 ssthresh:15 rtt:80ms
# → cwnd太小！理论BDP = 1Gbps × 80ms = 10MB ≈ 6900个MSS
# → 实际cwnd只有15，严重受限

# Step 3: 检查缓冲区
sysctl net.ipv4.tcp_rmem
# 4096 87380 4194304 ← max只有4MB，不够！

# 诊断结论：
# 1. CUBIC在高RTT下cwnd增长太慢（每80ms才+1MSS）
# 2. 接收缓冲区上限4MB < BDP(10MB)，限制了rwnd
```

#### 6.2 优化方案

```bash
# Fix 1: 切换BBR
sysctl -w net.ipv4.tcp_congestion_control=bbr
sysctl -w net.core.default_qdisc=fq

# Fix 2: 增大缓冲区（>=2×BDP）
sysctl -w net.ipv4.tcp_rmem="4096 131072 26214400"  # max=25MB
sysctl -w net.ipv4.tcp_wmem="4096 65536 26214400"   # max=25MB

# Fix 3: 确保窗口缩放和时间戳开启
sysctl -w net.ipv4.tcp_window_scaling=1
sysctl -w net.ipv4.tcp_timestamps=1

# 验证
iperf3 -c singapore-server
# 优化后吞吐：~820Mbps（从50Mbps提升16倍）
```

### 7. 总结

```
┌─────────────────────────────────────────────────────────────────────┐
│                    拥塞控制算法选型指南                                │
├────────────────┬────────────────┬────────────────────────────────────┤
│ 场景           │ 推荐算法       │ 原因                               │
├────────────────┼────────────────┼────────────────────────────────────┤
│ 数据中心内部   │ DCTCP/CUBIC    │ 低RTT，需要精确ECN控制             │
│ (RTT<1ms)      │                │                                    │
├────────────────┼────────────────┼────────────────────────────────────┤
│ 公网/跨区域    │ BBR            │ 高RTT下CUBIC太慢，BBR快速收敛      │
│ (RTT>20ms)     │                │                                    │
├────────────────┼────────────────┼────────────────────────────────────┤
│ 视频流/实时    │ BBR            │ 低延迟优先，不填满队列             │
│ 通信           │                │                                    │
├────────────────┼────────────────┼────────────────────────────────────┤
│ 共享网络       │ CUBIC          │ 与其他CUBIC流公平竞争              │
│ (多租户)       │                │                                    │
├────────────────┼────────────────┼────────────────────────────────────┤
│ 无线/卫星      │ BBR            │ 随机丢包不被误判为拥塞             │
│ (高丢包率)     │                │                                    │
└────────────────┴────────────────┴────────────────────────────────────┘
```

核心认知：
1. **Reno/CUBIC是被动的**——填满缓冲区后通过丢包感知拥塞，代价是高延迟
2. **BBR是主动的**——通过测量建模，精确控制发送速率，保持低延迟
3. 高BDP链路（高带宽×高延迟）是BBR的主战场
4. 永远记得同时调整TCP缓冲区大小（>= 2×BDP），否则cwnd上限受限于rwnd
