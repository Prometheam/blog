### 引言

一次线上故障让我记忆犹新：用户中心服务响应变慢（P99从20ms飙升到5s），而依赖它的订单服务、消息服务、推荐服务全部跟着超时——线程池打满，级联雪崩，整个系统瘫痪了15分钟。

事后复盘发现，如果当时有熔断机制，在用户中心变慢的第3秒就切断调用，返回降级数据（缓存的用户信息），其他服务不会受到任何影响。这就是**熔断降级**的价值——用局部牺牲换取全局稳定。

---

### 1. 熔断器模式（Circuit Breaker）

#### 1.1 为什么重试比不重试更危险

```
没有熔断时的灾难循环：

下游服务变慢(5s响应)
    │
    ▼
上游等待超时 → 上游线程被占满
    │
    ▼
上游也变慢 → 上游的上游也超时
    │
    ▼
整条调用链全部雪崩

更糟糕：如果配置了重试
    │
    ▼
下游已过载 → 上游重试3次 → 下游负载×3 → 彻底崩溃
                                          ↑
                              这叫"重试风暴"(Retry Storm)
```

#### 1.2 熔断器状态机

熔断器灵感来自电路保险丝——电流过大时自动断开，保护整个电路：

```
┌──────────────────────────────────────────────────────────────────┐
│                   熔断器三状态                                     │
│                                                                  │
│  ┌──────────┐    失败率>阈值     ┌──────────┐                   │
│  │  CLOSED  │──────────────────→│  OPEN    │                   │
│  │ (正常)   │                    │ (熔断)   │                   │
│  │          │                    │          │                   │
│  │ 请求正常 │                    │ 快速失败 │                   │
│  │ 通过     │                    │ 不调用   │                   │
│  │          │    成功率回升       │ 下游     │                   │
│  │          │←─────────────────┐ │          │                   │
│  └──────────┘                  │ └─────┬────┘                   │
│       ▲                        │       │                        │
│       │                        │       │ 等待超时               │
│       │   探测成功             │       ▼                        │
│       │   (连续N次成功)        │ ┌──────────┐                   │
│       └────────────────────────┤ │HALF-OPEN │                   │
│                                │ │ (半开)   │                   │
│              探测失败           │ │          │                   │
│              (任何一次失败)      └─│ 放行少量 │                   │
│                                  │ 探测请求 │                   │
│                                  └──────────┘                   │
│                                                                  │
│  关键参数：                                                      │
│  - failureThreshold: 触发熔断的失败率阈值（如50%）              │
│  - windowSize: 统计窗口大小（如10秒内的请求）                   │
│  - openTimeout: 熔断后等待多久尝试恢复（如30秒）                │
│  - halfOpenRequests: 半开状态放行的探测请求数（如5个）           │
│  - successThreshold: 恢复到CLOSED需要的连续成功次数（如3次）    │
└──────────────────────────────────────────────────────────────────┘
```

#### 1.3 C++实现

```cpp
#include <atomic>
#include <chrono>
#include <mutex>
#include <functional>

enum class CircuitState { CLOSED, OPEN, HALF_OPEN };

class CircuitBreaker {
public:
    struct Config {
        double failure_threshold = 0.5;     // 失败率阈值（50%）
        int min_requests = 10;              // 最少请求数（不足时不触发）
        int window_seconds = 10;            // 统计窗口
        int open_timeout_ms = 30000;        // 熔断持续时间
        int half_open_requests = 5;         // 半开放行数
        int success_threshold = 3;          // 恢复阈值
    };

    CircuitBreaker(Config config = {}) : config_(config) {}

    // 执行受保护的调用
    template<typename Func, typename Fallback>
    auto execute(Func&& func, Fallback&& fallback)
        -> decltype(func()) {
        if (!allowRequest()) {
            return fallback();  // 熔断状态，直接走降级逻辑
        }

        try {
            auto result = func();
            onSuccess();
            return result;
        } catch (...) {
            onFailure();
            return fallback();
        }
    }

    CircuitState state() const { return state_.load(); }

private:
    Config config_;
    std::atomic<CircuitState> state_{CircuitState::CLOSED};
    std::mutex mutex_;

    // 统计窗口
    std::atomic<int> success_count_{0};
    std::atomic<int> failure_count_{0};
    std::atomic<int> total_count_{0};

    // 时间记录
    std::chrono::steady_clock::time_point open_time_;
    std::atomic<int> half_open_success_{0};
    std::atomic<int> half_open_attempts_{0};

    bool allowRequest() {
        auto current = state_.load();

        switch (current) {
        case CircuitState::CLOSED:
            return true;

        case CircuitState::OPEN: {
            // 检查是否到了尝试恢复的时间
            auto elapsed = std::chrono::steady_clock::now() - open_time_;
            if (elapsed >= std::chrono::milliseconds(config_.open_timeout_ms)) {
                // 转为半开状态
                if (state_.compare_exchange_strong(current, CircuitState::HALF_OPEN)) {
                    half_open_success_.store(0);
                    half_open_attempts_.store(0);
                }
                return true;  // 放行探测请求
            }
            return false;  // 仍在熔断中
        }

        case CircuitState::HALF_OPEN:
            // 限制半开状态的并发请求数
            return half_open_attempts_.fetch_add(1) < config_.half_open_requests;
        }
        return false;
    }

    void onSuccess() {
        auto current = state_.load();
        if (current == CircuitState::HALF_OPEN) {
            if (half_open_success_.fetch_add(1) + 1 >= config_.success_threshold) {
                // 连续成功达标，恢复CLOSED
                state_.store(CircuitState::CLOSED);
                resetCounters();
            }
        } else {
            success_count_.fetch_add(1);
            total_count_.fetch_add(1);
        }
    }

    void onFailure() {
        auto current = state_.load();
        if (current == CircuitState::HALF_OPEN) {
            // 半开状态任何失败都回到OPEN
            state_.store(CircuitState::OPEN);
            open_time_ = std::chrono::steady_clock::now();
        } else {
            failure_count_.fetch_add(1);
            total_count_.fetch_add(1);
            checkThreshold();
        }
    }

    void checkThreshold() {
        int total = total_count_.load();
        if (total < config_.min_requests) return;  // 样本不足

        double failure_rate = (double)failure_count_.load() / total;
        if (failure_rate >= config_.failure_threshold) {
            // 触发熔断
            auto expected = CircuitState::CLOSED;
            if (state_.compare_exchange_strong(expected, CircuitState::OPEN)) {
                open_time_ = std::chrono::steady_clock::now();
            }
        }
    }

    void resetCounters() {
        success_count_.store(0);
        failure_count_.store(0);
        total_count_.store(0);
    }
};
```

### 2. 降级策略

#### 2.1 降级方案分类

```
┌────────────────────────────────────────────────────────────────────┐
│                    降级策略矩阵                                      │
├───────────────────┬────────────────────┬───────────────────────────┤
│ 策略              │ 实现方式           │ 适用场景                   │
├───────────────────┼────────────────────┼───────────────────────────┤
│ 缓存降级          │ 返回上次缓存的结果 │ 用户信息、配置信息        │
│ 默认值降级        │ 返回预设的默认值   │ 推荐列表、排行榜          │

│ 人工预案          │ 运维手动切换       │ 活动页面、预设文案        │
│ 排队降级          │ 请求进入排队系统   │ 秒杀、抢购               │
│ 错误码降级        │ 返回友好错误提示   │ 非关键接口失败时          │
└───────────────────┴────────────────────┴───────────────────────────┘
```

#### 2.2 降级实现示例

```cpp
// 多层降级策略
class UserService {
public:
    UserInfo getUserInfo(int64_t user_id) {
        return breaker_.execute(
            // 正常逻辑
            [&]() { return rpcGetUserInfo(user_id); },
            // 降级逻辑（多层兜底）
            [&]() { return fallbackGetUserInfo(user_id); }
        );
    }

private:
    CircuitBreaker breaker_;
    LocalCache<int64_t, UserInfo> local_cache_;  // 本地缓存

    UserInfo fallbackGetUserInfo(int64_t user_id) {
        // 降级层级1: 本地缓存
        auto cached = local_cache_.get(user_id);
        if (cached) return *cached;

        // 降级层级2: Redis缓存
        auto redis_cached = redis_.get("user:" + std::to_string(user_id));
        if (redis_cached) return deserialize(*redis_cached);

        // 降级层级3: 返回默认值
        return UserInfo{
            .user_id = user_id,
            .nickname = "用户" + std::to_string(user_id),
            .avatar = DEFAULT_AVATAR_URL,
            .is_degraded = true  // 标记为降级数据
        };
    }
};

### 3. 熔断 + 限流 + 降级的协同

```
┌──────────────────────────────────────────────────────────────────────┐
│                  完整的韧性防护体系                                    │
│                                                                      │
│  请求入口                                                            │
│    │                                                                 │
│    ▼                                                                 │
│  ┌────────────────┐                                                  │
│  │  限流器        │  → 超过阈值: 返回429 / 排队                     │
│  │  (Rate Limiter)│     保护自身不被过载                              │
│  └───────┬────────┘                                                  │
│          │ 通过                                                       │
│          ▼                                                           │
│  ┌────────────────┐                                                  │
│  │  熔断器        │  → 已熔断: 快速失败 → 降级逻辑                  │
│  │(Circuit Breaker)│     保护下游不被打爆                             │
│  └───────┬────────┘                                                  │
│          │ 允许                                                       │
│          ▼                                                           │
│  ┌────────────────┐                                                  │
│  │  超时控制      │  → 超时: 取消请求 → 降级逻辑                    │
│  │  (Timeout)     │     防止线程被长时间占用                          │
│  └───────┬────────┘                                                  │
│          │ 成功                                                       │
│          ▼                                                           │
│  ┌────────────────┐                                                  │
│  │  重试策略      │  → 失败: 指数退避重试                            │
│  │  (Retry)       │     最多3次，避免重试风暴                        │
│  └───────┬────────┘                                                  │
│          │                                                           │
│          ▼                                                           │
│     下游服务调用                                                      │
└──────────────────────────────────────────────────────────────────────┘

组合顺序很重要：
  限流 → 熔断 → 超时 → 重试

错误的顺序会导致问题：
  ❌ 重试放在熔断外面：熔断后重试也是快速失败，浪费重试次数
  ❌ 限流放在熔断后面：已经熔断的请求不该占用限流配额
```

### 4. 超时控制设计

#### 4.1 超时策略

```cpp
// 分层超时设计
struct TimeoutConfig {
    int connect_timeout_ms = 100;    // 连接超时（网络不通就快速失败）
    int read_timeout_ms = 500;       // 读超时（下游处理太慢）
    int total_timeout_ms = 1000;     // 总超时（包含重试在内的最大时间）
};

// 超时传递（Deadline Propagation）
// 每个请求携带绝对截止时间，逐级传递
class RequestContext {
public:
    void setDeadline(std::chrono::steady_clock::time_point deadline) {
        deadline_ = deadline;
    }

    int remainingMs() const {
        auto remaining = deadline_ - std::chrono::steady_clock::now();
        return std::chrono::duration_cast<std::chrono::milliseconds>(remaining).count();
    }

    bool isExpired() const {
        return std::chrono::steady_clock::now() >= deadline_;
    }

private:
    std::chrono::steady_clock::time_point deadline_;
};

// 使用方式：
void handleRequest(RequestContext& ctx) {
    if (ctx.isExpired()) {
        throw TimeoutException("request already expired");
    }

    // 调用下游时，传递剩余时间
    int remaining = ctx.remainingMs();
    int downstream_timeout = std::min(remaining, 500);  // 不超过下游的默认超时

    auto result = callDownstream(downstream_timeout);
}
```

// 基于P99延迟动态调整超时时间
class AdaptiveTimeout {
public:
    AdaptiveTimeout(int base_timeout_ms = 200, double multiplier = 2.0)
        : base_timeout_(base_timeout_ms), multiplier_(multiplier) {}

    int getTimeout() const {
        // 超时 = P99延迟 × multiplier
        double p99 = latency_stats_.percentile(99);
        int adaptive = static_cast<int>(p99 * multiplier_);
        // 限制在合理范围内
        return std::clamp(adaptive, base_timeout_, max_timeout_);
    }

    void recordLatency(int latency_ms) {
        latency_stats_.add(latency_ms);
    }

private:
    int base_timeout_;
    int max_timeout_ = 5000;
    double multiplier_;
    SlidingWindowPercentile latency_stats_;  // 滑动窗口百分位统计
};

### 5. 重试策略

#### 5.1 指数退避 + 抖动

```cpp
class RetryPolicy {
public:
    struct Config {
        int max_retries = 3;
        int base_delay_ms = 100;
        int max_delay_ms = 5000;
        double multiplier = 2.0;
        bool add_jitter = true;  // 加随机抖动避免重试风暴
    };

    template<typename Func>
    auto executeWithRetry(Func&& func, Config config = {})
        -> decltype(func()) {
        int attempt = 0;
        while (true) {
            try {
                return func();
            } catch (const RetryableException& e) {
                attempt++;
                if (attempt > config.max_retries) throw;

                int delay = calculateDelay(attempt, config);
                std::this_thread::sleep_for(std::chrono::milliseconds(delay));
            } catch (...) {
                throw;  // 非重试异常直接抛出
            }
        }
    }

private:
    int calculateDelay(int attempt, const Config& config) {
        // 指数退避：100ms, 200ms, 400ms, ...
        double delay = config.base_delay_ms * std::pow(config.multiplier, attempt - 1);
        delay = std::min(delay, (double)config.max_delay_ms);

        if (config.add_jitter) {
            // Full Jitter: [0, delay] 随机
            // 比Equal Jitter效果更好（AWS最佳实践）
            std::uniform_real_distribution<double> dist(0, delay);
            delay = dist(rng_);
        }

        return static_cast<int>(delay);
    }

    std::mt19937 rng_{std::random_device{}()};
};
```

#### 5.2 哪些情况可以重试

```
✅ 可重试的故障（Retryable）：
  - 网络超时（对方可能没收到请求）
  - 连接被拒绝（TCP RST，可能是暂时过载）
  - 503 Service Unavailable
  - 429 Too Many Requests（但要退避）
  - DNS解析失败（DNS server暂时故障）

❌ 不可重试的故障（Non-Retryable）：
  - 400 Bad Request（参数错误，重试也不会对）
  - 401/403 认证/授权失败
  - 404 Not Found
  - 业务逻辑错误（余额不足等）
  - 幂等性无法保证的写操作（除非有请求唯一ID去重）

⚠️ 需要注意的：
  - POST请求重试前确认是否幂等
  - 写操作重试必须有去重机制（唯一请求ID）
  - 超时不代表失败——请求可能已经成功，只是响应丢了
```

### 6. 生产级熔断框架设计

```cpp
// 完整的韧性调用包装器
class ResilientCaller {
public:
    struct Config {
        CircuitBreaker::Config breaker_config;
        RetryPolicy::Config retry_config;
        int timeout_ms = 500;
    };

    ResilientCaller(Config config) : config_(config), breaker_(config.breaker_config) {}

    template<typename Func, typename Fallback>
    auto call(Func&& func, Fallback&& fallback) -> decltype(func()) {
        // 1. 检查熔断器
        if (breaker_.state() == CircuitState::OPEN) {
            metrics_.record("circuit_open");
            return fallback();
        }

        // 2. 带重试的调用
        int attempts = 0;
        while (attempts <= config_.retry_config.max_retries) {
            try {
                // 3. 超时控制
                auto result = callWithTimeout(std::forward<Func>(func),
                                              config_.timeout_ms);
                breaker_.onSuccess();
                metrics_.record("success");
                return result;
            } catch (const TimeoutException&) {
                breaker_.onFailure();
                attempts++;
                metrics_.record("timeout");
            } catch (const RetryableException&) {
                breaker_.onFailure();
                attempts++;
                metrics_.record("retryable_error");
            } catch (...) {
                breaker_.onFailure();
                metrics_.record("non_retryable_error");
                break;  // 不可重试的错误直接走降级
            }

            if (attempts <= config_.retry_config.max_retries) {
                int delay = calculateBackoff(attempts);
                std::this_thread::sleep_for(std::chrono::milliseconds(delay));
            }
        }

        // 所有重试失败，走降级
        metrics_.record("fallback");
        return fallback();
    }

private:
    Config config_;
    CircuitBreaker breaker_;
    MetricsCollector metrics_;
};

// 使用示例
ResilientCaller user_service_caller({
    .breaker_config = {.failure_threshold = 0.5, .open_timeout_ms = 30000},
    .retry_config = {.max_retries = 2, .base_delay_ms = 50},
    .timeout_ms = 200
});

auto user = user_service_caller.call(
    [&]() { return rpc_client.getUserInfo(user_id); },
    [&]() { return getCachedUserInfo(user_id); }
);
```

### 7. 监控与告警

```
熔断器必须配合监控，否则你不知道系统正在降级运行：

关键指标：
┌────────────────────────────┬─────────────────────────────────────┐
│ 指标                       │ 告警规则                             │
├────────────────────────────┼─────────────────────────────────────┤
│ circuit_breaker_state      │ 任何实例进入OPEN → P1告警           │
│ failure_rate               │ > 30% 持续1分钟 → P2告警            │
│ fallback_rate              │ > 10% → 服务在降级运行              │
│ retry_rate                 │ > 20% → 下游可能有问题              │
│ timeout_rate               │ > 5% → 延迟异常                    │
│ p99_latency                │ 超过基线3倍 → 性能恶化              │
└────────────────────────────┴─────────────────────────────────────┘

Grafana Dashboard建议：
  - 熔断器状态变化时间线（什么时候开/关）
  - 各服务的失败率趋势图
  - 降级请求比例
  - 重试放大系数（实际调用次数/请求次数）
```

### 8. 总结

```
┌──────────────────────────────────────────────────────────────────┐
│              韧性设计核心原则                                       │
├──────────────────────────────────────────────────────────────────┤
│ 1. 快速失败优于慢成功                                             │
│    → 超时时间要短，宁可快速降级也不要让线程等待                   │
│                                                                  │
│ 2. 隔离故障域                                                    │
│    → 每个下游服务独立熔断器，A的故障不影响对B的调用               │
│                                                                  │
│ 3. 降级是有准备的                                                │
│    → 降级逻辑要提前设计好，不能在故障时临时想                     │
│    → 定期测试降级路径（Chaos Engineering）                        │
│                                                                  │
│ 4. 保护性重试，不是盲目重试                                      │
│    → 指数退避+抖动，避免重试风暴                                  │
│    → 只重试可重试的错误                                          │
│    → 有总超时兜底                                                │
│                                                                  │
│ 5. 可观测性是基础                                                │
│    → 没有监控的熔断器等于摆设                                     │
│    → 必须知道系统当前是正常还是降级运行                           │
└──────────────────────────────────────────────────────────────────┘
```

选型建议：对于C++后端服务，建议自研轻量级熔断框架（如本文实现），而不是引入重量级的Java系Hystrix/Sentinel——C++项目需要的是零开销的抽象，而不是一个复杂的运行时。
