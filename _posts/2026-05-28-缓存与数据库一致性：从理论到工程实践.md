### 引言

"缓存一致性"大概是后端面试出现频率最高的话题之一，但真正在生产环境中做对的人并不多。我在做IM消息系统时，用户反馈"已读状态显示不对"——排查后发现是缓存与数据库不一致导致的：一个请求更新了DB但缓存还是旧值，另一个请求读到了过期缓存。

这篇文章系统梳理缓存一致性的各种方案，从最简单的Cache Aside到最终一致的Binlog同步，每种方案的适用场景、坑点和C++实现。

### 1. 缓存模式全景

```
┌──────────────────────────────────────────────────────────────────────────┐
│                     缓存读写模式对比                                       │
├──────────────────┬───────────────────────┬───────────────────────────────┤
│ 模式             │ 读逻辑                │ 写逻辑                         │
├──────────────────┼───────────────────────┼───────────────────────────────┤
│ Cache Aside      │ 先读缓存→miss则读DB   │ 先写DB→再删缓存               │
│ (旁路缓存)      │ 读DB后回填缓存        │                               │
├──────────────────┼───────────────────────┼───────────────────────────────┤
│ Read Through     │ 先读缓存→miss则       │ 同Cache Aside                 │
│                  │ 缓存层自动加载DB      │ （缓存层封装了加载逻辑）       │
├──────────────────┼───────────────────────┼───────────────────────────────┤
│ Write Through    │ 同Read Through        │ 先写缓存→缓存同步写DB         │
│                  │                       │ （写操作由缓存层代理）         │
├──────────────────┼───────────────────────┼───────────────────────────────┤
│ Write Behind     │ 同Read Through        │ 先写缓存→异步批量写DB         │
│ (Write Back)     │                       │ （高性能但有数据丢失风险）     │
└──────────────────┴───────────────────────┴───────────────────────────────┘
```

### 2. Cache Aside（最常用）

#### 2.1 标准流程

```
读操作：
  ┌──────┐    1.读缓存     ┌──────┐
  │ 应用 │ ──────────────→ │ Redis│
  │      │ ←────────────── │      │
  │      │    (命中返回)    └──────┘
  │      │
  │      │    2.未命中→读DB  ┌──────┐
  │      │ ──────────────→  │ MySQL│
  │      │ ←──────────────  │      │
  │      │                  └──────┘
  │      │    3.回填缓存    ┌──────┐
  │      │ ──────────────→ │ Redis│
  └──────┘                  └──────┘

写操作：
  ┌──────┐    1.写DB        ┌──────┐
  │ 应用 │ ──────────────→ │ MySQL│
  │      │                  └──────┘
  │      │    2.删缓存      ┌──────┐
  │      │ ──────────────→ │ Redis│  ← 注意：是删除不是更新！
  └──────┘                  └──────┘
```

#### 2.2 为什么是"删除"而不是"更新"缓存

```
方案A: 先写DB，再更新缓存 → ❌ 有并发问题

  Thread1: 写DB(x=1) ────→ 更新缓存(x=1)
  Thread2: 写DB(x=2) ─→ 更新缓存(x=2) ──→

  可能的时序：
  Thread1写DB(x=1) → Thread2写DB(x=2) → Thread2更新缓存(x=2) → Thread1更新缓存(x=1)
  结果：DB中x=2，缓存中x=1 → 不一致！

方案B: 先写DB，再删除缓存 → ✅ 下次读时重新加载最新值

  Thread1: 写DB(x=1) → 删缓存
  Thread2: 写DB(x=2) → 删缓存
  
  无论谁先删谁后删，缓存最终都是空的
  下次读请求会从DB重新加载最新值 → 一致
```

#### 2.3 Cache Aside的经典Race Condition

```
极端场景（概率很低但理论上存在）：

  1. 缓存过期，Thread A读缓存miss
  2. Thread A读DB得到旧值 x=old
  3. Thread B写DB更新 x=new
  4. Thread B删除缓存（此时缓存本来就是空的）
  5. Thread A将旧值回填缓存 x=old  ← 问题！缓存中是旧值

  为什么说概率极低？
  需要"Step 2读DB" 发生在 "Step 3写DB" 之前
  且 "Step 5回填" 发生在 "Step 4删除" 之后
  → 即读DB比写DB慢（通常不会，读<<写）

  解决方案：
  - 给缓存设置较短的TTL（兜底，即使不一致也很快过期）
  - 延迟双删（见下文）
```

### 3. 延迟双删策略

#### 3.1 原理

```
写操作改进：先删缓存 → 写DB → 延迟N毫秒 → 再删一次缓存

为什么要删两次？
  第一次删除：确保写DB期间不会有人读到旧缓存
  第二次删除：清理在"写DB期间"被其他读请求回填的旧值

延迟多久？
  > 一次读请求的耗时（读DB + 回填缓存的时间）
  通常设置为 500ms ~ 1s
```

#### 3.2 C++实现

```cpp
class CacheAsideService {
public:
    // 读操作
    std::optional<std::string> get(const std::string& key) {
        // 1. 读缓存
        auto cached = redis_.get(key);
        if (cached) return cached;

        // 2. 缓存miss，读DB
        auto db_value = db_.query(key);
        if (!db_value) return std::nullopt;

        // 3. 回填缓存（带TTL兜底）
        redis_.setex(key, *db_value, cache_ttl_seconds_);
        return db_value;
    }

    // 写操作（延迟双删）
    bool update(const std::string& key, const std::string& value) {
        // 1. 第一次删除缓存
        redis_.del(key);

        // 2. 写DB
        bool success = db_.update(key, value);
        if (!success) return false;

        // 3. 延迟双删（异步执行，不阻塞主流程）
        scheduleDelayedDelete(key, delay_ms_);
        return true;
    }

private:
    RedisClient redis_;
    DBClient db_;
    int cache_ttl_seconds_ = 300;  // 缓存5分钟过期（兜底）
    int delay_ms_ = 500;           // 延迟双删间隔

    void scheduleDelayedDelete(const std::string& key, int delay_ms) {
        // 方案1: 丢到延迟队列（推荐）
        delay_queue_.push(key, delay_ms);

        // 方案2: 简单场景用线程（不推荐大量使用）
        // std::thread([this, key, delay_ms]() {
        //     std::this_thread::sleep_for(std::chrono::milliseconds(delay_ms));
        //     redis_.del(key);
        // }).detach();
    }
};
```

#### 3.3 延迟双删的局限

```
问题1: 删除失败怎么办？
  Redis网络抖动 → 第二次删除失败 → 脏数据残留
  解决: 重试机制 + 消息队列保证最终删除

问题2: 延迟时间不好确定
  太短: 读请求还没回填完就删了，等于没删
  太长: 不一致窗口变大
  解决: 监控读请求P99延迟，延迟 = P99 × 1.5

问题3: 高并发下仍有短暂不一致窗口
  从写DB到第二次删除完成的这段时间内（延迟N ms），读到旧值
  对于大多数业务可接受（非金融场景）
```

### 4. 基于Binlog的最终一致方案

#### 4.1 架构

```
┌──────────────────────────────────────────────────────────────────────┐
│            Binlog同步方案（最强一致性保证）                             │
│                                                                      │
│  ┌──────┐     写DB      ┌───────┐                                   │
│  │ 应用 │──────────────→│ MySQL │                                   │
│  └──────┘               └───┬───┘                                   │
│      │                      │ Binlog                                │
│      │ 读缓存               ▼                                       │
│      │              ┌──────────────┐                                 │
│      │              │ Canal/Debezium│  ← 伪装为MySQL Slave            │
│      │              │ (Binlog监听) │                                 │
│      │              └──────┬───────┘                                 │
│      │                     │ 解析Binlog事件                          │
│      ▼                     ▼                                         │
│  ┌──────┐         ┌──────────────┐                                   │
│  │ Redis│ ←───────│ 缓存更新服务 │  ← 收到变更事件后更新/删除缓存    │
│  └──────┘         └──────────────┘                                   │
│                                                                      │
│  优势：                                                              │
│  - 应用层无需关心缓存一致性（只管写DB）                              │
│  - 保证最终一致性（Binlog不丢失就不会遗漏）                         │
│  - 解耦：缓存更新逻辑独立部署                                       │
│                                                                      │
│  代价：                                                              │
│  - 引入中间件（Canal/Debezium），运维复杂度增加                      │
│  - 有延迟（通常100ms~1s）                                           │
│  - 需要处理Binlog解析异常                                            │
└──────────────────────────────────────────────────────────────────────┘
```

#### 4.2 实现要点

```cpp
// Binlog消费者：接收变更事件，更新缓存
class BinlogCacheUpdater {
public:
    void onBinlogEvent(const BinlogEvent& event) {
        switch (event.type) {
        case EventType::INSERT:
        case EventType::UPDATE:
            // 方案1: 删除缓存（让下次读重新加载）
            redis_.del(buildCacheKey(event.table, event.primary_key));
            break;

        case EventType::DELETE:
            redis_.del(buildCacheKey(event.table, event.primary_key));
            break;
        }

        // 方案2: 直接更新缓存（减少一次DB查询，但要处理数据格式转换）
        // redis_.set(key, serialize(event.after_values), ttl);
    }

private:
    std::string buildCacheKey(const std::string& table, const std::string& pk) {
        return table + ":" + pk;
    }
};
```

├──────────────┬────────────┬────────────┬──────────────┬────────────────────┤
│ 方案         │ 一致性     │ 复杂度     │ 延迟         │ 适用场景           │
├──────────────┼────────────┼────────────┼──────────────┼────────────────────┤
│ Cache Aside  │ 最终一致   │ 低         │ TTL到期      │ 大多数读多写少场景 │

├──────────────┼────────────┼────────────┼──────────────┼────────────────────┤

├──────────────┼────────────┼────────────┼──────────────┼────────────────────┤
│ 不用缓存     │ 强一致     │ 最低       │ 无           │ 写多读少，或数据量 │

└──────────────┴────────────┴────────────┴──────────────┴────────────────────┘

选型建议：
  80%的场景 → Cache Aside + TTL兜底（简单够用）
  写频繁+一致性敏感 → 延迟双删
  大规模+最终一致 → Binlog同步
  金融交易 → Write Through 或 不用缓存
```

### 6. 缓存击穿/穿透/雪崩防护

```
┌──────────────────────────────────────────────────────────────────┐
│              三大缓存异常及解决方案                                 │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│ 缓存穿透（查询不存在的数据）：                                   │
│   问题: 大量查询一个不存在的key → 全部打到DB                    │
│   方案: ① 布隆过滤器前置拦截                                    │
│         ② 缓存空值(null) + 短TTL(30s)                           │
│                                                                  │
│ 缓存击穿（热点key过期瞬间）：                                   │
│   问题: 热点key过期 → 大量并发同时读DB → DB瞬间压力暴增         │
│   方案: ① 互斥锁(singleflight)：只让一个请求回源                │
│         ② 逻辑过期：缓存不设TTL，value中携带过期时间             │
│            过期时异步更新，读请求返回旧值                         │
│                                                                  │
│ 缓存雪崩（大量key同时过期）：                                   │
│   问题: 大批key同时失效 → 大量请求同时打到DB                    │
│   方案: ① TTL加随机偏移：TTL = base + random(0, 300)           │
│         ② 多级缓存：L1(进程内) + L2(Redis)                      │
│         ③ 限流降级：DB层面限制并发查询数                         │
└──────────────────────────────────────────────────────────────────┘
```

```cpp
// Singleflight实现：防止缓存击穿
class SingleFlight {
public:
    using LoadFunc = std::function<std::string(const std::string&)>;

    std::string getOrLoad(const std::string& key, LoadFunc loader) {
        // 1. 读缓存
        auto cached = redis_.get(key);
        if (cached) return *cached;

        // 2. 获取/创建该key的flight
        std::shared_ptr<Flight> flight;
        {
            std::lock_guard<std::mutex> lock(mu_);
            auto it = flights_.find(key);
            if (it != flights_.end()) {
                flight = it->second;  // 已有人在加载
            } else {
                flight = std::make_shared<Flight>();
                flights_[key] = flight;
            }
        }

        // 3. 等待或执行加载
        std::unique_lock<std::mutex> flock(flight->mu);
        if (flight->done) {
            return flight->value;  // 其他线程已加载完毕
        }

        if (!flight->loading) {
            flight->loading = true;
            flock.unlock();

            // 当前线程负责加载
            std::string value = loader(key);
            redis_.setex(key, value, 300);  // 回填缓存

            flock.lock();
            flight->value = value;
            flight->done = true;
            flight->cv.notify_all();

            // 清理flight
            std::lock_guard<std::mutex> lock(mu_);
            flights_.erase(key);
        } else {
            // 等待加载完成
            flight->cv.wait(flock, [&]() { return flight->done; });
        }

        return flight->value;
    }

private:
    struct Flight {
        std::mutex mu;
        std::condition_variable cv;
        bool loading = false;
        bool done = false;
        std::string value;
    };

    std::mutex mu_;
    std::unordered_map<std::string, std::shared_ptr<Flight>> flights_;
    RedisClient redis_;
};
```

### 7. 总结

```
核心原则：

1. 缓存是DB的"影子"，不是"真相"
   → 任何时候DB都是权威数据源
   → 缓存不一致时以DB为准

2. 删除优于更新
   → 删除缓存让下次读取重新加载（简单、不易出错）
   → 更新缓存有并发写覆盖的风险

3. TTL是最后的安全网
   → 即使所有一致性逻辑都失败了，TTL到期后自动恢复
   → 没有TTL的缓存 = 定时炸弹

4. 没有完美方案，只有适合的方案
   → 强一致性代价是性能和复杂度
   → 大多数业务能容忍秒级不一致（用户无感知）
   → 真正需要强一致的场景考虑不用缓存
```
