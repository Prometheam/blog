最近半年一直在做基于昇腾 NPU 的 RAG 系统落地，从零搭建了一套面向企业知识库的检索增强生成平台。这篇文章梳理整个系统的架构设计，包括踩过的坑和工程优化经验。

## 为什么需要 RAG

大语言模型有两个固有问题：

1. **幻觉**：模型会一本正经地编造不存在的 API、论文、事件
2. **知识过时**：训练数据有截止日期，无法回答最新问题

RAG 的核心思路：先检索相关文档，再将检索结果作为上下文喂给 LLM 生成答案。模型从"凭记忆回答"变为"开卷考试"。

## 整体架构

```
┌─────────────────────── RAG Pipeline ───────────────────────┐
│                                                             │
│  ┌──────────┐   ┌──────────┐   ┌──────────┐              │
│  │ 文档解析  │──→│ 文本分块  │──→│ Embedding │──→ 向量DB   │
│  │ PDF/Word │   │ Chunking │   │  Model   │   (Milvus)  │
│  └──────────┘   └──────────┘   └──────────┘              │
│                                                             │
│  ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌────────┐│
│  │  Query   │──→│ 向量检索  │──→│ Reranker │──→│  LLM   ││
│  │ Embedding│   │ Top-K=20 │   │ Top-K=5  │   │生成答案 ││
│  └──────────┘   └──────────┘   └──────────┘   └────────┘│
└─────────────────────────────────────────────────────────────┘
```

## 文档分块策略

分块质量直接决定检索效果，这是我试过的几种方案：

```
方案一：固定大小（512 tokens, overlap 64）
  ├── 优点：实现简单，chunk 大小统一
  └── 缺点：可能从句子中间切断，破坏语义

方案二：递归分割（按段落→句子→字符逐级切分）
  ├── 优点：尽量保持语义完整
  └── 缺点：chunk 大小不均匀

方案三：语义分块（用 embedding 相似度判断边界）
  ├── 优点：语义最完整
  └── 缺点：计算开销大，离线处理可接受
```

生产中我用的是方案二（LangChain 的 RecursiveCharacterTextSplitter），chunk_size=800，overlap=200。加上标题和来源的 metadata，检索时可以用来过滤。

## Embedding 模型与向量数据库

### Embedding 选型

| 模型 | 维度 | 中文效果 | 部署方式 |
|------|------|----------|----------|
| bge-large-zh | 1024 | 优秀 | 昇腾 NPU |
| m3e-base | 768 | 良好 | CPU 也能跑 |
| text-embedding-3-large | 3072 | 优秀 | API 调用 |

我们选择 bge-large-zh 部署在昇腾 310B 上，单卡吞吐约 200 sentences/s（batch=32）。

### 向量数据库

Milvus 集群部署，HNSW 索引（ef_construction=200, M=32）。50 万文档约 200 万 chunks，P99 检索延迟 < 15ms。FAISS 适合小规模或单机场景，大规模生产还是 Milvus 更稳。

## 检索策略：混合检索

单纯向量检索对精确关键词匹配较弱（如错误码、API 名称），我们采用混合方案：

```
┌─────────────┐
│  User Query │
└──────┬──────┘
       │
  ┌────┴────┐
  ↓         ↓
Dense     Sparse
(向量)    (BM25)
  │         │
  ↓         ↓
Top-50    Top-50
  │         │
  └────┬────┘
       ↓
  RRF Fusion（倒数排名融合）
       ↓
    Top-20
       ↓
   Cross-Encoder Rerank
       ↓
    Top-5 → LLM
```

RRF（Reciprocal Rank Fusion）公式：`score = Σ 1/(k + rank_i)`，k=60 效果较好。

## Reranking：精排提升准确率

初检用双塔模型（query 和 doc 分别编码），召回量大但精度一般。Reranker 用 Cross-Encoder 对 query-doc pair 联合编码，精度高但慢——所以只对 Top-20 做精排：

```python
# bge-reranker-large 部署在昇腾 NPU 上
from transformers import AutoModelForSequenceClassification

model = AutoModelForSequenceClassification.from_pretrained(
    "BAAI/bge-reranker-large"
)
# 输入: [[query, doc1], [query, doc2], ...]
# 输出: relevance scores
```

加入 Reranker 后，我们的 Hit@5 从 72% 提升到 89%。

## Prompt Engineering for RAG

```python
RAG_PROMPT = """基于以下参考资料回答用户问题。
如果参考资料中没有相关信息，请明确说明"根据现有资料无法回答"。

参考资料：
{context}

用户问题：{query}

要求：
1. 答案必须基于参考资料，不要编造
2. 引用来源时标注 [来源X]
3. 如果多个资料有矛盾，指出差异
"""
```

关键设计：明确告诉模型"不知道就说不知道"，大幅减少幻觉。

## 工程优化

### 异步流水线

```cpp
// 生产端代码骨架（C++ 协程 + gRPC streaming）
asio::awaitable<void> HandleRAGQuery(Request req) {
    // 1. Query embedding（2ms）
    auto query_vec = co_await embedding_service_.Encode(req.query());
    
    // 2. 并行检索
    auto [dense_results, sparse_results] = co_await when_all(
        milvus_client_.Search(query_vec, /*top_k=*/50),
        bm25_client_.Search(req.query(), /*top_k=*/50)
    );
    
    // 3. 融合 + Rerank（~30ms）
    auto fused = RRFFusion(dense_results, sparse_results, /*k=*/60);
    auto reranked = co_await reranker_.Rerank(req.query(), fused, /*top_k=*/5);
    
    // 4. LLM streaming 生成
    auto prompt = BuildRAGPrompt(req.query(), reranked);
    co_await llm_client_.StreamGenerate(prompt, [&](std::string_view chunk) {
        response_writer_.Write(chunk);  // gRPC server streaming
    });
}
```

### 缓存策略

```
┌─────────────────────────────────────────┐
│  L1: Query 完全匹配缓存（Redis, TTL=1h）│
│  L2: Embedding 缓存（避免重复编码）      │
│  L3: 语义相似 Query 缓存（余弦>0.95）   │
└─────────────────────────────────────────┘
```

L3 语义缓存命中率约 15%，对高频相似问题效果显著。

## 昇腾 NPU 部署架构

我们的硬件拓扑：

```
┌─────── 昇腾 910B 服务器 ─────────┐
│  NPU 0-3: LLM 推理 (Qwen-72B)   │
│  NPU 4-5: Embedding (bge-large)  │
│  NPU 6-7: Reranker (bge-reranker)│
└───────────────────────────────────┘
         │
    MindIE 推理框架
         │
   ┌─────┴─────┐
   gRPC API    Triton Inference Server
```

用 MindIE 部署 LLM，支持 Continuous Batching 和 PagedAttention，Qwen-72B 在 4 卡 910B 上首 token 延迟约 180ms，生成速度 ~35 tokens/s。Embedding 和 Reranker 模型通过 ONNX 转 OM 格式部署，性能比 GPU A10 上的 TensorRT 略优。

## 效果与反思

上线三个月后的数据：
- 答案准确率：92%（人工评估 500 条）
- 端到端延迟 P50：1.2s，P99：3.8s（含 LLM 生成）
- 日均 QPS：约 2000

最大的教训：**数据质量 > 模型能力 > 工程技巧**。早期花大量时间调 retrieval 参数，不如花同样时间清洗数据、完善文档结构。垃圾进垃圾出，这个道理在 RAG 系统里体现得淋漓尽致。

第二个教训：评估体系要先行。没有 ground truth 数据集做 benchmark，所有优化都是盲调。我们后来标注了 500 条 QA 对作为评测集，每次改动都跑一遍，才真正进入了科学优化的正循环。
