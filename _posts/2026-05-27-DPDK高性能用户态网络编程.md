当网络带宽达到 10Gbps 甚至 100Gbps 时，传统的内核协议栈已经成为瓶颈。我在做网关项目时深入研究了 DPDK，今天分享这套用户态网络框架的核心设计思想。

## 内核协议栈的瓶颈

一个数据包在内核中的旅程：

```
NIC → 硬件中断 → softirq → sk_buff分配 → 协议栈解析
    → socket缓冲区 → 系统调用 → 用户态拷贝 → 应用处理

每个环节的开销：
- 中断处理:     ~2μs (含上下文切换)
- sk_buff分配:  ~0.5μs (slab allocator)
- 协议栈遍历:   ~2μs
- 系统调用:     ~0.2μs (syscall/vDSO)
- 内存拷贝:     ~0.3μs (1500B包)
总计: ~5μs/packet → 理论上限 ~200Kpps/core
```

而 10Gbps 线速小包（64B）需要处理 14.88Mpps。内核每核 200Kpps 的能力，需要 74 个核才能线速——这显然不可接受。

## DPDK 的架构设计

DPDK 的核心思路：绕过内核，在用户态直接操作网卡。

```
+----------------------------------------------------------+
|                    User Space                              |
|  +--------+  +--------+  +--------+  +--------+          |
|  | Worker |  | Worker |  | Worker |  | Worker |          |
|  | Core 1 |  | Core 2 |  | Core 3 |  | Core 4 |          |
|  +---+----+  +---+----+  +---+----+  +---+----+          |
|      |           |           |           |                |
|  +---v-----------v-----------v-----------v----+           |
|  |              DPDK Libraries                 |           |
|  |  EAL | Mempool | Ring | Timer | Hash       |           |
|  +---+-------------------------------------------+        |
|      |                                                    |
|  +---v------------------------------------------------+   |
|  |          PMD (Poll Mode Driver)                     |   |
|  |   直接通过 MMIO/DMA 操作网卡收发队列               |   |
|  +---+------------------------------------------------+   |
+------+----------------------------------------------------+
       |  (UIO/VFIO: 将网卡寄存器映射到用户态)
+------v----------------------------------------------------+
|  NIC Hardware (RSS多队列, 硬件卸载)                        |
+----------------------------------------------------------+
```

## 核心组件

**EAL（Environment Abstraction Layer）**：初始化大页内存、CPU 绑核、PCI 设备探测。是 DPDK 的启动引擎。

**Mempool**：预分配的 mbuf 对象池，基于每核缓存避免跨核竞争：

```cpp
// 创建 mempool：8192个mbuf，每核缓存256个
struct rte_mempool *mbuf_pool = rte_pktmbuf_pool_create(
    "MBUF_POOL", 8191,  // n - 1 (需要为2^n-1)
    256,                 // per-core cache size
    0,                   // priv_size
    RTE_MBUF_DEFAULT_BUF_SIZE,
    rte_socket_id()      // NUMA node
);
```

**Ring**：无锁环形队列，用于核间通信：

```
+---+---+---+---+---+---+---+---+
| 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |  (slot)
+---+---+---+---+---+---+---+---+
          ^               ^
          |               |
       cons_head       prod_head
```

生产者/消费者通过 CAS 操作移动 head/tail 指针，支持单生产者/多生产者模式。

## 包处理模型

**Run-to-Completion 模型**（我在项目中主要使用）：

```
Core N:
  while (true) {
      nb_rx = rte_eth_rx_burst(port, queue, pkts, BURST_SIZE);
      for (i = 0; i < nb_rx; i++) {
          parse(pkts[i]);
          process(pkts[i]);      // 查表、修改、转发决策
          prepare_tx(pkts[i]);
      }
      rte_eth_tx_burst(port, queue, pkts, nb_rx);
  }
```

**Pipeline 模型**：

```
Core 1 (RX)         Core 2 (Process)      Core 3 (TX)
+-----------+        +-----------+         +-----------+
| rx_burst  |--ring->| 解析+处理 |--ring-->| tx_burst  |
+-----------+        +-----------+         +-----------+
```

Run-to-Completion 延迟更低（无核间通信），Pipeline 吞吐更高（流水线并行）。

## 简单的 L2 转发器示例

```cpp
#include <rte_eal.h>
#include <rte_ethdev.h>
#include <rte_mbuf.h>

#define BURST_SIZE 32

static void l2_forward(uint16_t port) {
    struct rte_mbuf *bufs[BURST_SIZE];
    // 轮询收包
    uint16_t nb_rx = rte_eth_rx_burst(port, 0, bufs, BURST_SIZE);
    if (nb_rx == 0) return;

    for (uint16_t i = 0; i < nb_rx; i++) {
        struct rte_ether_hdr *eth = rte_pktmbuf_mtod(bufs[i],
                                        struct rte_ether_hdr *);
        // 交换源目MAC
        struct rte_ether_addr tmp = eth->dst_addr;
        eth->dst_addr = eth->src_addr;
        eth->src_addr = tmp;
    }
    // 批量发包
    uint16_t nb_tx = rte_eth_tx_burst(port ^ 1, 0, bufs, nb_rx);
    // 释放未发送成功的mbuf
    for (uint16_t i = nb_tx; i < nb_rx; i++)
        rte_pktmbuf_free(bufs[i]);
}

int main(int argc, char *argv[]) {
    rte_eal_init(argc, argv);
    // ... 端口初始化省略 ...
    while (!force_quit) {
        l2_forward(0);
        l2_forward(1);
    }
    return 0;
}
```

## 性能对比

实测数据（64B 小包，单核，Xeon E5-2680v4）：

```
方案             |  PPS (单核)  |  延迟(avg)  |  CPU占用
-----------------+--------------+-------------+---------
Kernel Stack     |   ~200K      |   ~50μs     |  中等
AF_PACKET        |   ~1M        |   ~20μs     |  中等
XDP (native)     |   ~6M        |   ~5μs      |  高
DPDK PMD         |   ~14.8M     |   ~2μs      |  100%
```

DPDK 能达到线速的关键：
1. **零系统调用**：PMD 轮询，无中断、无上下文切换
2. **零拷贝**：DMA 直接写入用户态 hugepage 内存
3. **批量处理**：`rx_burst`/`tx_burst` 摊平每包开销
4. **CPU 亲和性**：绑核避免缓存颠簸
5. **NUMA 感知**：内存分配在本地 NUMA 节点

## 适用场景

DPDK 的代价是独占 CPU 核（100% 轮询）和开发复杂度。适合：

- **软件负载均衡器**：如 GitHub 的 GLB、阿里云 SLB
- **防火墙/DPI**：包级别的深度检测
- **NFV 网元**：vRouter、vSwitch（OVS-DPDK）
- **网关/代理**：需要线速转发的场景

不适合的场景：连接数少但逻辑复杂的业务服务（此时内核协议栈的开销可忽略）。

## 实践心得

在网关项目中使用 DPDK 一年多，几个关键教训：
1. Hugepage 一定要预留够，运行时分配失败很难排查
2. 多队列 RSS 要确保哈希对称（保证同一流的双向包落在同一核）
3. 生产环境务必用 VFIO 而非 UIO（IOMMU 保护，防止 DMA 越界）
4. 调试困难——没有 tcpdump，需要自己实现 pcap dump 逻辑

DPDK 不是银弹，但在需要极致网络性能的场景下，它是 C++ 后端工程师武器库中不可或缺的利器。
