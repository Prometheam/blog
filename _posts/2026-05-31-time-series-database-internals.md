### 引言

监控指标、IoT传感器、金融行情——这些数据有一个共同特征：按时间有序写入、很少修改、查询总是带时间范围。传统关系型数据库对这类workload效率很低（索引膨胀、写放大大）。时序数据库（TSDB）针对这种"写多读少、按时间有序"的特征做了专门优化。

我们的监控系统每秒写入50万数据点（500个服务×1000个指标），用MySQL存储时写入延迟不断增长，最终切换到VictoriaMetrics后写入延迟稳定在2ms，存储空间减少了10倍。

---

### 1. 时序数据特征

```
  时序数据模型：

  metric_name{label1="value1", label2="value2"} value timestamp

  示例：
  cpu_usage{host="prod-01", core="0"}  0.75  1716980400
  cpu_usage{host="prod-01", core="1"}  0.62  1716980400
  http_requests{service="order", method="POST", status="200"}  1523  1716980400

  特征：
  1. 写入密集：每秒写入百万级数据点
  2. 按时间有序：新数据追加，几乎不修改历史
  3. 时间范围查询：查最近1小时/1天/1周的数据
  4. 聚合查询：avg/sum/max/min/percentile over time
  5. 高基数标签：host × service × method × status 组合爆炸
  6. 冷热分明：最近数据访问频繁，历史数据很少查
```

### 2. 时序数据库 vs 通用数据库

```
  ┌──────────────────┬──────────────────────┬──────────────────────┐
  │ 维度             │ MySQL/PostgreSQL     │ 时序数据库(TSDB)     │
  ├──────────────────┼──────────────────────┼──────────────────────┤
  │ 写入模式         │ 随机(B-Tree插入)     │ 顺序追加(时间有序)   │
  ├──────────────────┼──────────────────────┼──────────────────────┤
  │ 压缩率           │ ~2x (通用压缩)       │ ~10-20x (列式+特化) │
  ├──────────────────┼──────────────────────┼──────────────────────┤
  │ 写入性能         │ ~5万点/秒            │ ~500万点/秒          │
  ├──────────────────┼──────────────────────┼──────────────────────┤
  │ 时间范围查询     │ 索引扫描(慢)         │ 时间分区直接定位     │
  ├──────────────────┼──────────────────────┼──────────────────────┤
  │ 自动过期         │ 需手动DELETE         │ 整块删除(秒级)       │
  ├──────────────────┼──────────────────────┼──────────────────────┤
  │ 降采样           │ 需应用层实现         │ 内建支持             │
  └──────────────────┴──────────────────────┴──────────────────────┘

  为什么通用DB不适合？
  - B-Tree索引随数据量增长写入变慢（页分裂）
  - 过期数据DELETE产生大量碎片和IO
  - 无法利用时序数据的"相邻值相似"特性做高效压缩
```

### 3. 存储引擎：TSM（Time-Structured Merge Tree）

```
  TSM引擎（InfluxDB使用）：

  写入路径：
  ┌──────────────┐     ┌──────────────────────┐
  │   WAL        │────→│   In-Memory Cache    │
  │ (写前日志)    │     │ (按series+time排序)  │
  └──────────────┘     └──────────┬───────────┘
                                   │ flush (定期或达到阈值)
                                   ▼
  磁盘：
  ┌─────────────────────────────────────────────────────────┐
  │  TSM File (不可变)                                       │
  │  ┌──────────────┬──────────────┬──────────────┬───────┐│
  │  │ Series Block │ Series Block │ ...          │ Index ││
  │  │ (压缩数据)   │ (压缩数据)   │              │       ││
  │  └──────────────┴──────────────┴──────────────┴───────┘│
  └─────────────────────────────────────────────────────────┘

  TSM文件内部：
  - 按series(metric+labels)分组
  - 每个series内按时间排序
  - 时间戳：Delta-of-Delta编码（连续等间隔时只存1个差值）
  - 数值：Gorilla压缩（XOR编码，相邻相似值压缩到几bit）
```

### 4. 时间分区策略

```
  按时间分片（Shard）：

  时间轴：
  ├── Shard 1 ──┤── Shard 2 ──┤── Shard 3 ──┤── Shard 4(当前) ──┤
  │ 5/1 - 5/7   │ 5/8 - 5/14  │ 5/15 - 5/21 │ 5/22 - 5/28      │
  │ (冷数据)    │ (冷数据)    │ (温数据)    │ (热数据)          │

  优势：
  1. 写入只在当前shard（追加写，不修改历史）
  2. 查询时间范围 → 只扫描对应shard（跳过无关分片）
  3. 过期数据 → 整个shard直接删除（文件级，瞬间完成，无碎片）
  4. 冷数据可以压缩/降采样后归档到廉价存储

  分片策略选择：
  ┌──────────────────────┬──────────┬──────────────────────┐
  │ 数据量/天            │ 分片粒度 │ 原因                  │
  ├──────────────────────┼──────────┼──────────────────────┤
  │ < 10GB              │ 7天      │ 减少分片数            │
  ├──────────────────────┼──────────┼──────────────────────┤
  │ 10-100GB            │ 1天      │ 平衡粒度和数量        │
  ├──────────────────────┼──────────┼──────────────────────┤
  │ > 100GB             │ 6小时    │ 控制单分片大小        │
  └──────────────────────┴──────────┴──────────────────────┘
```

### 5. 时序数据压缩

```
  时间戳压缩（Delta-of-Delta）：

  原始时间戳：  [1000, 1010, 1020, 1030, 1040]
  Delta:       [-, 10, 10, 10, 10]
  Delta-of-Delta: [-, -, 0, 0, 0]

  等间隔数据→Delta-of-Delta全是0→用几个bit表示整个序列！
  压缩率: 8字节/点 → 0.5-1 bit/点（压缩64-128倍）

  数值压缩（Gorilla/XOR编码）：

  原始浮点值：  [12.5, 12.6, 12.4, 12.7, 12.5]
  XOR with prev: [-, 0x3F...很多, 少数bit变化, ...]

  相邻相似的浮点数XOR后大部分bit为0
  只需存储非零bit的位置和值
  压缩率: 8字节/点 → 1-2字节/点（压缩4-8倍）

  总压缩效果：
  原始: 16字节/点(8B时间戳+8B值)
  压缩后: 1-2字节/点
  压缩比: 8-16倍（实际常见10倍以上）
```

### 6. 降采样（Downsampling）

```
  降采样策略：

  原始数据（10秒间隔）：保留7天
  ├── 1分钟聚合: avg/min/max/count → 保留30天
  ├── 5分钟聚合 → 保留90天
  └── 1小时聚合 → 保留1年

  ┌────────────────────────────────────────────────────────────┐
  │ 最近7天: 每10秒一个点 → 精确到10秒                         │
  │ 7-30天:  每1分钟一个聚合点 → 精确到分钟                    │
  │ 30-90天: 每5分钟一个聚合点 → 精确到5分钟                   │
  │ 90天-1年: 每小时一个聚合点 → 精确到小时                    │
  └────────────────────────────────────────────────────────────┘

  存储节省计算（假设1000个指标）：
  原始7天:  1000 × 6点/分 × 60分 × 24时 × 7天 = 6048万点
  降采样30天: 1000 × 1点/分 × 60 × 24 × 30 = 4320万点
  降采样90天: 1000 × 12点/时 × 24 × 90 = 2592万点
  降采样1年: 1000 × 1点/时 × 24 × 365 = 876万点

  总存储 vs 全量保留1年:
  全量: 1000 × 6 × 60 × 24 × 365 = 31.5亿点 × 2B/点 = 5.9GB
  分层: (6048万+4320万+2592万+876万) × 2B/点 = 277MB
  节省: 95%！
```

### 7. 主流TSDB对比

```
  ┌──────────────────┬──────────────┬──────────────┬────────────────┐
  │ TSDB             │ 引擎         │ 查询语言     │ 适用场景        │
  ├──────────────────┼──────────────┼──────────────┼────────────────┤
  │ Prometheus       │ 本地TSDB     │ PromQL       │ 监控(单机/拉)  │
  ├──────────────────┼──────────────┼──────────────┼────────────────┤
  │ VictoriaMetrics  │ 自研(类TSM)  │ MetricsQL    │ 大规模监控     │
  ├──────────────────┼──────────────┼──────────────┼────────────────┤
  │ InfluxDB         │ TSM          │ InfluxQL/Flux│ IoT/通用时序   │
  ├──────────────────┼──────────────┼──────────────┼────────────────┤
  │ TimescaleDB      │ PostgreSQL扩展│ SQL          │ 需要SQL生态    │
  ├──────────────────┼──────────────┼──────────────┼────────────────┤
  │ ClickHouse       │ MergeTree    │ SQL          │ 分析型时序     │
  └──────────────────┴──────────────┴──────────────┴────────────────┘

  选型建议：
  - K8s监控 → Prometheus + VictoriaMetrics(长期存储)
  - IoT/工业 → InfluxDB (丰富的数据模型)
  - 需要SQL → TimescaleDB (PostgreSQL兼容)
  - 日志+指标+分析 → ClickHouse (万金油)
```

### 总结

时序数据库的核心设计：

1. **追加写+时间分区**：写入只追加到当前分片，历史不修改
2. **列式存储+特化压缩**：Delta-of-Delta+Gorilla可达10-20倍压缩
3. **分片级过期**：过期数据整文件删除，瞬间完成无碎片
4. **降采样控制成本**：精度随时间递减，存储节省95%+
5. **高基数是最大挑战**：标签组合爆炸导致series数暴增，需要限制
6. **冷热分离**：热数据在内存/SSD，冷数据压缩到对象存储

时序数据库不是"通用数据库的特化版本"，而是完全不同的设计哲学：为"大量写入、时间范围查询、自动过期"这三个特征量身定制的存储引擎。
