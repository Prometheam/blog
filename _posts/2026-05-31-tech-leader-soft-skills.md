### 引言

写了9年代码，技术能力早已不是瓶颈。真正的挑战变成了：如何做出好的技术决策、如何让团队的代码质量持续提升、如何让知识不随人员流动而丢失。

作为技术Leader，你的影响力不再来自"自己写多少代码"，而是"团队整体交付质量"。一个好的Code Review流程比你亲自写代码的价值大10倍；一个好的技术决策框架能避免团队走弯路半年。

本文分享技术Leader的三个核心软技能：技术决策、代码审查、知识管理。

### 1. 技术决策框架

```
  技术决策的常见陷阱：

  ❌ "这个框架很火" → 跟风决策（没评估适用性）
  ❌ "我之前用过X" → 经验锤子（拿着锤子看什么都像钉子）
  ❌ "先用着，以后再改" → 技术债借条（永远不会"以后"）
  ❌ "这是最好的方案" → 缺少trade-off分析
  ❌ 一个人拍板 → 缺少多视角输入
```

#### ADR（Architecture Decision Record）模板

```markdown
# ADR-001: 选择消息队列方案

## 状态: 已决定 (2026-05-31)

## 背景
订单系统需要异步处理支付回调，当前同步调用在高峰期超时率>5%。
每日消息量约500万条，峰值QPS 2000，需要至少一次投递保证。

## 决策
采用 Kafka 作为消息队列。

## 考虑的方案

| 方案 | 优点 | 缺点 | 否决原因 |
|------|------|------|---------|
| Kafka | 高吞吐、持久化、回溯 | 运维复杂 | - |
| RabbitMQ | 简单、功能丰富 | 吞吐较低 | 吞吐不满足需求 |
| Redis Stream | 轻量、现有基础设施 | 持久化有限 | 可靠性不够 |
| 自研队列 | 完全可控 | 开发成本高 | ROI不合理 |

## 影响
- 需要引入Kafka集群（3节点）
- 团队需要学习Kafka运维
- 未来其他异步场景可复用

## 参与者
- 决策者: 张三(Tech Lead)
- 评审: 李四(架构师), 王五(SRE)
```

#### 决策原则

```
  技术决策的5个原则：

  1. 可逆性优先
     ─────────────
     可逆的决策快速做，不可逆的决策慎重做。
     选Redis还是Memcached？可逆（切换成本低）→ 快速决定。
     数据库从MySQL迁到MongoDB？不可逆 → 深度评估。

  2. 满足当前需求 + 预留扩展点
     ──────────────────────────
     不为"可能的未来需求"过度设计。
     但在关键接缝处用接口/抽象预留扩展性。

  3. 约束条件比理想方案重要
     ──────────────────────────
     团队没人懂Rust → 即使Rust更好，选C++也是对的。
     上线deadline 2周 → 选最熟悉的方案，不冒险。

  4. 写下来
     ────────
     口头决策=没决策。ADR文档让未来的人知道为什么这么选。
     半年后有人问"为什么用Kafka" → ADR给出完整上下文。

  5. 设定评估点
     ──────────
     "3个月后review这个决策的效果"
     技术选型不是一锤子买卖，如果发现不合适要敢于改。
```

### 2. 代码审查方法论

#### 2.1 Review 的目标层次

```
  代码审查的四层关注（从上到下逐层检查）：

  ┌─────────────────────────────────────────────────────────┐
  │ Layer 1: 正确性                                          │
  │ "这段代码做了它声称做的事吗？有没有bug？"                │
  │ - 边界条件、空指针、并发安全、资源泄漏                    │
  └─────────────────────────────────────────────────────────┘
  ┌─────────────────────────────────────────────────────────┐
  │ Layer 2: 设计                                            │
  │ "这个抽象合理吗？职责划分清晰吗？"                       │
  │ - 类/函数职责单一、依赖方向合理、接口设计清晰             │
  └─────────────────────────────────────────────────────────┘
  ┌─────────────────────────────────────────────────────────┐
  │ Layer 3: 可维护性                                        │
  │ "6个月后其他人能理解这段代码吗？"                        │
  │ - 命名清晰、注释有价值、复杂度可控、测试覆盖             │
  └─────────────────────────────────────────────────────────┘
  ┌─────────────────────────────────────────────────────────┐
  │ Layer 4: 规范                                            │
  │ "代码风格、格式、lint是否通过？"                         │
  │ - 自动化工具处理，不浪费人工review时间                    │
  └─────────────────────────────────────────────────────────┘

  原则：把Layer 4交给CI自动化，人工Review聚焦Layer 1-3
```

#### 2.2 Review 评论的表达方式

```
  ❌ 差的Review评论：
  "这里有问题" ← 没说什么问题
  "这样写不好" ← 没说为什么不好
  "改成X" ← 没解释为什么X更好
  "为什么不用Y？" ← 质问语气，没有建设性

  ✅ 好的Review评论：
  "这里在并发场景下可能有竞争条件：线程A读取count后，
   线程B可能已经修改了count。建议用atomic或加锁保护。"

  评论分类前缀（让作者知道严重程度）：
  [blocker]   必须修复才能合并（bug/安全问题）
  [suggestion] 建议改进，不阻塞合并
  [question]  我不理解这里的意图，能解释一下吗？
  [nit]       非常小的风格问题，可以忽略
  [praise]    写得好！（正面反馈很重要）
```

#### 2.3 Review 效率

| 实践 | 原因 |
|------|------|
| PR不超过400行 | 超过400行review质量急剧下降 |
| 描述清楚"为什么" | reviewer不需要猜PR的目的 |
| 自动化检查先过 | CI通过后再请人review |
| 24小时内完成 | 拖太久阻塞开发者 |
| 每次最多review 1小时 | 超过1小时注意力下降 |

### 3. 团队知识管理

```
  知识流失的典型场景：

  - 核心开发者离职 → 模块无人能维护
  - 线上故障 → 排查经验只在当事人脑中
  - 架构决策 → 没人记得为什么这么设计
  - 技术栈升级 → 新人不知道历史坑

  知识管理的目标：让关键知识从"个人脑中"变为"团队资产"
```

#### 知识文档体系

```
  文档金字塔（从具体到抽象）：

  ┌────────────────────────────────┐
  │     架构决策记录 (ADR)         │ ← 为什么这么设计
  ├────────────────────────────────┤
  │     系统设计文档               │ ← 整体架构和数据流
  ├────────────────────────────────┤
  │     Runbook (运维手册)         │ ← 故障怎么处理
  ├────────────────────────────────┤
  │     开发指南                   │ ← 如何开发/调试/部署
  ├────────────────────────────────┤
  │     API文档 (OpenAPI)          │ ← 接口契约
  ├────────────────────────────────┤
  │     代码注释 + README          │ ← 代码级说明
  └────────────────────────────────┘

  各文档维护策略：
  - ADR: 决策时写，之后不改（历史记录）
  - 设计文档: 大变更前写，重构后更新
  - Runbook: 每次故障后补充/更新
  - 开发指南: 新人入职时验证/更新
  - API文档: 代码生成（OpenAPI/Protobuf自动生成）
```

#### Runbook 模板

```markdown
# Runbook: 订单服务数据库连接池耗尽

## 告警
- 告警名: OrderService_DB_Pool_Exhausted
- 指标: db_pool_active / db_pool_max > 0.9
- 严重度: P1

## 快速恢复（5分钟内）
1. 确认是否有慢查询: `SHOW PROCESSLIST` 看是否有>5s的查询
2. 如果有: `KILL <thread_id>` 杀死慢查询
3. 如果连接池真的满了: 重启服务实例（K8s会自动rolling restart）

## 根因排查
1. 查看慢查询日志: `slow_query.log` 最近5分钟
2. 检查是否有锁等待: `SELECT * FROM innodb_lock_waits`
3. 检查连接泄漏: 服务日志搜索 "connection not returned"

## 历史案例
- 2026-03-15: 新上线的统计查询缺索引，全表扫描3s → 加索引解决
- 2026-04-22: 异常路径未释放连接 → 代码修复 + RAII封装

## 预防措施
- 连接获取超时: 500ms（超时快速失败而非排队等待）
- 慢查询告警: >100ms 记录日志，>1s 触发告警
- 定期索引审查: 每月检查 sys.schema_unused_indexes
```

### 总结

技术Leader软技能的核心：

1. **决策要写下来(ADR)**：让未来的人知道为什么这么选
2. **Code Review聚焦正确性和设计**：规范交给自动化
3. **知识系统化**：文档金字塔 + Runbook + 分享制度化
4. **技术债可视化**：不能只欠债不还，每Sprint留20%
5. **影响力>产出**：你的价值是让团队10个人都更好，不是自己多写代码
6. **数据驱动沟通**：与非技术stakeholder用数字说话

技术Leader的终极目标是"让自己不可被需要"——建立流程、文档、自动化，让团队即使没有你也能高效运转。这比写出最牛的代码更难，也更有价值。
