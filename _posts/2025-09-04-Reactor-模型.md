<p style=""></p><p style="">这是一个在高性能网络编程中至关重要的设计模式，它用于高效地处理大量的并发连接，而无需为每个连接创建昂贵的线程。像 Node.js、Nginx、Netty、Redis 等众多知名软件的核心都基于 Reactor 模型。</p><hr><h3 style="" id="1.-%E6%A0%B8%E5%BF%83%E6%80%9D%E6%83%B3%EF%BC%9A%E4%B8%8D%E8%A6%81%E7%AD%89%EF%BC%8C%E6%9C%89%E4%BA%8B%E6%88%91%E5%96%8A%E4%BD%A0">1. 核心思想：不要等，有事我喊你</h3><p style="">Reactor 模式的核心思想是 <strong>“非阻塞同步”</strong> 和 <strong>“事件驱动”</strong>。</p><ul><li><p style=""><strong>传统多线程模型</strong>：为每个客户端连接创建一个线程。线程在等待数据（例如调用 <code>read</code>）时会被阻塞（休眠），直到数据到达。当连接数非常多时（C10K 问题），线程上下文切换的开销会变得巨大，耗尽系统资源。</p></li><li><p style=""><strong>Reactor 模型</strong>：由一个或多个线程（Reactor）来<strong>循环监听</strong>各种事件（如连接建立、数据到达、数据可写）。当某个事件发生时，Reactor 就会<strong>分发（Dispatch）</strong> 这个事件给对应的处理程序（Handler）进行快速处理。处理程序自身是非阻塞的，它会立即返回，不会等待操作完成。</p></li></ul><p style="">用一个生动的比喻来理解：</p><ul><li><p style=""><strong>传统模型</strong>：就像一家餐厅，每个顾客（连接）都有一个专属服务员（线程）。服务员点完餐后，就站在厨房门口等菜做好，这期间他不能服务其他顾客。</p></li><li><p style=""><strong>Reactor 模型</strong>：只有一个或少数几个服务员（Reactor 线程）。他们不停地在餐厅里巡逻（事件循环），接收新顾客（连接事件）、记录点餐（读事件）。他们把点菜单交给厨房（工作线程池），然后就去忙别的了。厨房做好菜后，会把菜放在出餐口（事件就绪），服务员巡逻到出餐口时（写事件就绪），就会把菜端给顾客。</p></li></ul><hr><h3 style="" id="2.-reactor-%E6%A8%A1%E5%9E%8B%E7%9A%84%E6%A0%B8%E5%BF%83%E7%BB%84%E6%88%90%E9%83%A8%E5%88%86">2. Reactor 模型的核心组成部分</h3><ol><li><p style=""><strong>Reactor（反应器）</strong>：</p><ul><li><p style="">整个模式的大脑。运行在一个独立的线程中。</p></li><li><p style="">其核心是一个<strong>事件循环（Event Loop）</strong>，它会监听和分发事件。</p></li><li><p style="">它使用一个 <strong>I/O 多路复用器（如 select, poll, epoll, kqueue）</strong> 来同时监听多个文件描述符（Socket）上的事件。</p></li></ul></li><li><p style=""><strong>Handlers（事件处理器）</strong>：</p><ul><li><p style="">每个 Handler 负责处理一种特定类型的事件（如连接事件、读事件、写事件）。</p></li><li><p style="">它们实现了具体的业务逻辑。当 Reactor 将事件分发给它们时，它们会执行相应的操作（如读取数据、处理数据、发送响应）。</p></li></ul></li><li><p style=""><strong>Demultiplexer（事件分离器 / I/O 多路复用器）</strong>：</p><ul><li><p style="">这是操作系统提供的机制（如 Linux 的 <code>epoll</code>），是 Reactor 能够高效工作的基石。</p></li><li><p style="">它允许一个线程同时监视多个网络连接，并在任何一个连接有数据可读或可写时<strong>通知</strong> Reactor。</p></li></ul></li></ol><hr><h3 style="" id="3.-reactor-%E7%9A%84%E5%B7%A5%E4%BD%9C%E6%B5%81%E7%A8%8B">3. Reactor 的工作流程</h3><p style="">一个典型的 Reactor 处理 TCP 请求的流程如下：</p><ol><li><p style=""><strong>注册监听</strong>：Reactor 通过 Demultiplexer 注册对 <strong>Acceptor</strong>（接受连接的处理器）的“可读”事件感兴趣，即监听是否有新的连接到来。</p></li><li><p style=""><strong>事件循环（Event Loop）</strong>：Reactor 启动循环，调用 Demultiplexer 的 <code>select</code> 方法。该方法会阻塞，直到一个或多个被监视的事件发生。</p></li><li><p style=""><strong>事件通知</strong>：当有新连接到来时，Demultiplexer 返回，通知 Reactor “Acceptor 对应的 Socket 可读了”。</p></li><li><p style=""><strong>事件分发</strong>：Reactor 根据事件类型，将事件分发给预先注册好的 Acceptor Handler。</p></li><li><p style=""><strong>处理事件</strong>：</p><ul><li><p style=""><strong>Acceptor</strong>：接受新连接，创建一个新的 Socket Channel。并为这个新 Channel 创建一个对应的 Handler（如 Read Handler），并将其“可读”事件注册到 Demultiplexer 中，由 Reactor 继续监听。</p></li><li><p style=""><strong>Read Handler</strong>：当某个客户端发送数据，导致 Socket 可读时，Reactor 会分发该事件给对应的 Read Handler。Handler 会非阻塞地读取数据，并进行业务处理。</p></li><li><p style=""><strong>Write Handler</strong>：业务处理完成后，可能需要返回数据。Handler 会将响应数据写入输出缓冲区，并注册“可写”事件。当网络可写时，Reactor 会分发“可写”事件给 Write Handler，由它负责将数据发送出去。</p></li></ul></li><li><p style="">回到步骤 2，继续事件循环。</p></li></ol><hr><h3 style="" id="4.-reactor-%E7%9A%84%E4%B8%89%E7%A7%8D%E5%B8%B8%E8%A7%81%E5%8F%98%E4%BD%93">4. Reactor 的三种常见变体</h3><p style="">根据 Reactor 线程和业务处理线程的数量和分工，可以分为三类：</p><ol><li><p style=""><strong>单 Reactor 单线程</strong></p><ul><li><p style="">所有工作（事件监听、连接建立、数据读写、业务处理）都在一个线程内完成。</p></li><li><p style=""><strong>优点</strong>：模型简单，没有线程切换和同步的开销。</p></li><li><p style=""><strong>缺点</strong>：无法充分利用多核CPU；一个Handler处理慢会阻塞整个系统。</p></li><li><p style=""><strong>适用场景</strong>：业务处理非常快速的场景，如 Redis。</p></li></ul></li><li><p style=""><strong>单 Reactor 多线程</strong></p><ul><li><p style="">Reactor 线程只负责事件监听和分发（包括接受新连接和I/O读写）。</p></li><li><p style="">当有数据可读时，Reactor 读取数据后，将其封装成一个任务对象，交给<strong>线程池</strong>去进行业务处理。</p></li><li><p style="">处理完成后，线程池将结果返回给 Reactor 线程，由 Reactor 将响应结果发送给客户端。</p></li><li><p style=""><strong>优点</strong>：充分利用多核CPU，业务处理不会阻塞主循环。</p></li><li><p style=""><strong>缺点</strong>：Reactor 仍然是单点，处理所有客户端的I/O操作，高并发时可能成为瓶颈；多线程间数据同步复杂。</p></li></ul></li><li><p style=""><strong>主从 Reactor 多线程</strong></p><ul><li><p style=""><strong>主 Reactor</strong>：只负责监听和接受新连接。一旦接受，将新连接的 Socket Channel 分配给<strong>子 Reactor</strong>。</p></li><li><p style=""><strong>子 Reactor</strong>：有多个，每个都在自己的线程中运行。主 Reactor 将新连接注册到某个子 Reactor 上，由该子 Reactor 负责这个连接后续的所有 I/O 事件（读、写）的监听和分发。业务处理依然交给线程池。</p></li><li><p style=""><strong>优点</strong>：职责明确，性能更高。主 Reactor 专注接受连接，子 Reactor 分担了I/O压力，进一步提升了系统吞吐量。这是 Netty、Nginx 等框架采用的模式。</p></li></ul></li></ol><hr><h3 style="" id="5.-reactor-vs.-proactor">5. Reactor vs. Proactor</h3><ul><li><p style=""><strong>Reactor</strong>：基于 <strong>同步I/O</strong>。它监听的是“I/O操作<strong>是否就绪</strong>”（例如“socket是否有数据可读了”）。就绪后，<strong>需要应用程序自己执行</strong>实际的I/O操作（调用 <code>read</code> 去读取数据）。</p></li><li><p style=""><strong>Proactor</strong>：基于 <strong>异步I/O</strong>。它监听的是“I/O操作<strong>是否完成</strong>”（例如“数据已经读完了”）。操作系统会帮你完成实际的I/O操作，完成后再通知你，你直接处理结果即可。</p></li></ul><p style="">简单说：</p><ul><li><p style=""><strong>Reactor</strong>：<code>epoll_wait</code> -&gt; <strong>通知可读</strong> -&gt; 应用程序调用 <code>read</code></p></li><li><p style=""><strong>Proactor</strong>：<code>aio_read</code> -&gt; 操作系统读 -&gt; <strong>通知已读完</strong> -&gt; 应用程序处理数据</p></li></ul><p style=""></p>
