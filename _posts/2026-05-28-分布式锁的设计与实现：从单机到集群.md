### 引言

去年在做IM系统群组消息时遇到一个bug：两个用户"同时"被设为群管理员。排查发现，两台服务器同时读取了群成员列表，各自判断管理员数量未超限后都执行了写入。本质原因是：**分布式环境下没有全局互斥机制**。

分布式锁是解决这类问题的标准方案。但网上大多数教程只讲"Redis SETNX加锁"，忽略了锁续约、节点崩溃、脑裂等生产级问题。这篇文章从需求出发，对比Redis/ZooKeeper/etcd三种主流方案，并深入分析各自的坑和最佳实践。

---

### 1. 为什么需要分布式锁

#### 1.1 单机锁 vs 分布式锁

```
单机环境：
  Thread A ──┐
  Thread B ──┼──→ [std::mutex] ──→ 共享资源
  Thread C ──┘
  
  std::mutex在同一进程内有效，操作系统保证互斥

分布式环境：
  Server 1 ──┐                    
  Server 2 ──┼──→ [??? ] ──→ 共享资源（DB/文件/第三方API）
  Server 3 ──┘
  
  不同进程、不同机器，没有共享内存
  需要一个外部系统来协调互斥
```

#### 1.2 分布式锁的基本要求

| 要求 | 说明 | 重要度 |
|------|------|--------|
| 互斥性 | 同一时刻只有一个客户端持锁 | **必须** |
| 无死锁 | 持锁客户端崩溃后锁能被释放 | **必须** |
| 容错性 | 锁服务部分节点故障仍可用 | 高 |
| 可重入 | 同一客户端可重复获取同一把锁 | 中 |
| 公平性 | 按请求顺序获取锁 | 低（看场景） |

### 2. 基于Redis的分布式锁

#### 2.1 基本实现：SETNX + 过期时间

```cpp
#include <hiredis/hiredis.h>
#include <string>
#include <chrono>

class RedisDistLock {
public:
    RedisDistLock(redisContext* ctx, const std::string& key,
                  int ttl_ms = 10000)
        : ctx_(ctx), key_(key), ttl_ms_(ttl_ms) {
        // 生成唯一标识（防止误删别人的锁）
        value_ = generateUniqueId();
    }

    bool tryLock() {
        // SET key value NX PX ttl_ms
        // NX: 仅当key不存在时设置（互斥）
        // PX: 设置毫秒级过期时间（防死锁）
        redisReply* reply = (redisReply*)redisCommand(ctx_,
            "SET %s %s NX PX %d",
            key_.c_str(), value_.c_str(), ttl_ms_);

        bool acquired = (reply && reply->type == REDIS_REPLY_STATUS
                        && strcmp(reply->str, "OK") == 0);
        freeReplyObject(reply);
        return acquired;
    }

    bool unlock() {
        // 必须用Lua脚本保证原子性：先检查value再删除
        // 防止删除了别人的锁！
        const char* lua_script = R"(
            if redis.call('get', KEYS[1]) == ARGV[1] then
                return redis.call('del', KEYS[1])
            else
                return 0
            end
        )";

        redisReply* reply = (redisReply*)redisCommand(ctx_,
            "EVAL %s 1 %s %s",
            lua_script, key_.c_str(), value_.c_str());

        bool released = (reply && reply->integer == 1);
        freeReplyObject(reply);
        return released;
    }

private:
    redisContext* ctx_;
    std::string key_;
    std::string value_;  // 唯一标识，用于安全释放
    int ttl_ms_;

    std::string generateUniqueId() {
        // UUID或 hostname:pid:threadid:timestamp
        // 保证全局唯一
    }
};
```

#### 2.2 锁续约（Watchdog机制）

问题：如果业务逻辑执行时间超过了锁的TTL，锁会自动过期，导致互斥性失效。

```cpp
// Watchdog：后台线程定期续约
class WatchdogLock {
public:
    bool lock() {
        if (!tryLock()) return false;

        // 启动watchdog线程
        watchdog_running_ = true;
        watchdog_thread_ = std::thread([this]() {
            while (watchdog_running_) {
                std::this_thread::sleep_for(
                    std::chrono::milliseconds(ttl_ms_ / 3));  // TTL的1/3时续约

                if (!watchdog_running_) break;

                // 续约：重新设置过期时间
                const char* lua = R"(
                    if redis.call('get', KEYS[1]) == ARGV[1] then
                        return redis.call('pexpire', KEYS[1], ARGV[2])
                    else
                        return 0
                    end
                )";
                redisReply* reply = (redisReply*)redisCommand(ctx_,
                    "EVAL %s 1 %s %s %d",
                    lua, key_.c_str(), value_.c_str(), ttl_ms_);

                if (!reply || reply->integer == 0) {
                    // 锁已被他人获取，停止续约
                    watchdog_running_ = false;
                }
                freeReplyObject(reply);
            }
        });

        return true;
    }

    void unlock() {
        watchdog_running_ = false;
        if (watchdog_thread_.joinable()) {
            watchdog_thread_.join();
        }
        releaseLock();
    }

private:
    std::atomic<bool> watchdog_running_{false};
    std::thread watchdog_thread_;
};
```

#### 2.3 Redis单点问题与RedLock

```
单Redis节点的问题：
  Client A 获取锁 → Redis master崩溃 → 锁数据丢失
  → Sentinel切换新master → Client B也获取到锁
  → 互斥性被打破！

RedLock算法（Redis作者提出）：
  使用N个独立的Redis节点（建议N=5），获取多数派锁

┌────────────────────────────────────────────────────────────┐
│                  RedLock 流程                                │
│                                                            │
│  Client 依次向5个Redis节点尝试加锁：                        │
│                                                            │
│  Redis1: SET key val NX PX 10000  → OK ✓                  │
│  Redis2: SET key val NX PX 10000  → OK ✓                  │
│  Redis3: SET key val NX PX 10000  → FAIL ✗ (已被占)       │
│  Redis4: SET key val NX PX 10000  → OK ✓                  │
│  Redis5: SET key val NX PX 10000  → TIMEOUT ✗             │
│                                                            │
│  成功数: 3/5 ≥ 多数派(3) → 加锁成功                       │
│                                                            │
│  有效TTL = TTL - 获取锁总耗时                              │
│  如果有效TTL < 0 → 锁已过期 → 加锁失败                    │
│                                                            │
│  释放时：向所有5个节点发送DEL（无论是否加锁成功）           │
└────────────────────────────────────────────────────────────┘
```

**RedLock的争议**（Martin Kleppmann vs Salvatore Sanfilippo）：

```
反对方观点（Kleppmann）：
  1. 依赖时钟同步——如果某节点时钟跳跃，TTL判断会出错
  2. GC停顿问题——Client获取锁后GC暂停，锁过期，另一Client获取锁
     → 两个Client同时认为自己持锁
  3. 这些问题不是RedLock特有的，但RedLock声称解决了单点问题实际没有完全解决

支持方观点（Antirez）：
  1. 实际工程中时钟漂移很小
  2. GC问题可以通过fencing token解决
  3. 在大多数场景下足够安全
```

### 3. 基于ZooKeeper的分布式锁

#### 3.1 利用临时顺序节点

ZooKeeper提供了更强的一致性保证，实现分布式锁更加自然：

```
加锁流程：
  1. 在 /locks/my_resource 下创建临时顺序节点
     → 创建 /locks/my_resource/lock-000000001
  
  2. 获取 /locks/my_resource 下所有子节点
     → [lock-000000001, lock-000000002, lock-000000003]
  
  3. 判断自己是否是序号最小的节点
     ├── 是 → 获取锁成功！
     └── 否 → Watch前一个节点（而不是所有节点，避免惊群效应）
              等待前一个节点删除时收到通知 → 回到Step 2

释放锁：
  1. 删除自己创建的临时节点
  2. 或者客户端断连后，ZK自动删除临时节点（防死锁）

┌─────────────────────────────────────────────────────────────┐
│  ZooKeeper路径:  /locks/my_resource/                         │
│                                                             │
│  lock-000000001  (Client A, 当前持锁)                       │
│  lock-000000002  (Client B, Watch 001)                      │
│  lock-000000003  (Client C, Watch 002)                      │
│                                                             │
│  Client A释放锁 → 删除001 → Client B收到通知              │
│  → Client B发现自己是最小的 → 获取锁                        │
└─────────────────────────────────────────────────────────────┘
```

#### 3.2 优势与代价

```
✅ 优势：
  1. 强一致性（ZAB协议，类似Raft）
  2. 临时节点 → 客户端崩溃自动释放锁（无需TTL）
  3. 顺序节点 → 天然公平锁（FIFO）
  4. Watch机制 → 不需要轮询

❌ 代价：
  1. 性能较低（每次加锁需要ZK集群共识 → 延迟较高）
  2. 运维复杂（ZK集群本身需要维护）
  3. 会话超时问题：网络抖动导致session断开 → 临时节点删除 → 锁丢失
     客户端可能不知道自己已经失去锁！
```

### 4. 基于etcd的分布式锁

#### 4.1 Lease + Revision机制

etcd使用Lease（租约）实现锁的自动过期，用Revision（全局递增版本号）实现排序：

```
加锁流程：
  1. 创建Lease（设置TTL，例如10秒）
  2. 用事务写入key（带Lease）
     → PUT /locks/my_resource value=client_id lease=lease_id
     → 条件: key不存在（CreateRevision == 0）
  3. 获取该key的Revision
  4. 如果是最小Revision → 持锁成功
  5. 否则Watch比自己Revision小的key删除事件
  6. 后台KeepAlive续约Lease

释放锁：
  1. 撤销Lease → key自动删除
  2. 或客户端崩溃 → Lease到期 → key自动删除
```

#### 4.2 etcd官方客户端使用

```cpp
// 使用etcd C++客户端(etcd-cpp-apiv3)
#include <etcd/Client.hpp>
#include <etcd/Watcher.hpp>

class EtcdDistLock {
public:
    EtcdDistLock(const std::string& endpoints, const std::string& lock_name,
                 int ttl_seconds = 10)
        : client_(endpoints), lock_name_("/locks/" + lock_name),
          ttl_(ttl_seconds) {}

    bool lock() {
        // 1. 创建Lease
        auto lease_resp = client_.leasegrant(ttl_).get();
        lease_id_ = lease_resp.value().lease();

        // 2. 启动KeepAlive（续约）
        keep_alive_ = client_.leaseKeepAlive(lease_id_);

        // 3. 用事务尝试写入
        std::string key = lock_name_ + "/" + std::to_string(lease_id_);
        auto txn_resp = client_.put(key, client_id_, lease_id_).get();
        my_revision_ = txn_resp.value().index();

        // 4. 检查是否是最小Revision持有者
        auto range_resp = client_.ls(lock_name_).get();
        int64_t min_revision = INT64_MAX;
        for (auto& kv : range_resp.keys()) {
            min_revision = std::min(min_revision, kv.created_index());
        }

        if (my_revision_ == min_revision) {
            return true;  // 获取锁成功
        }

        // 5. 等待前面的key被删除
        waitForLock(min_revision);
        return true;
    }

    void unlock() {
        // 撤销Lease → 关联的key自动删除
        client_.leaserevoke(lease_id_).get();
    }

private:
    etcd::Client client_;
    std::string lock_name_;
    std::string client_id_;
    int ttl_;
    int64_t lease_id_{0};
    int64_t my_revision_{0};

### 6. 踩坑实录

#### 6.1 锁过期但业务未完成

```
最危险的场景：

t=0s:   Client A 获取锁 (TTL=10s)
t=0s:   Client A 开始执行业务逻辑
t=5s:   Client A 发生Full GC (暂停8秒)
t=10s:  锁过期，被自动释放
t=11s:  Client B 获取锁，开始执行
t=13s:  Client A GC结束，继续执行业务（但已无锁！）
t=13s:  → Client A 和 B 同时操作共享资源 → 数据不一致！

即使有Watchdog续约，GC期间续约线程也会被暂停。
```

#### 6.2 Fencing Token：终极解决方案

```
原理：每次获取锁时获得一个全局递增的token，共享资源拒绝旧token的操作

┌──────────────────────────────────────────────────────────────────┐
│                                                                  │
│  Client A: 获取锁, fencing_token = 33                            │
│  Client A: GC暂停...                                             │
│  锁过期...                                                       │
│  Client B: 获取锁, fencing_token = 34                            │
│  Client B: 写数据库 (token=34) → 成功（34 > 最大token 0）       │
│  Client A: GC恢复, 写数据库 (token=33) → 拒绝！（33 < 当前34）  │
│                                                                  │
│  数据库/存储层需要支持：                                          │
│    记录最新token，拒绝任何小于当前token的写入                     │
└──────────────────────────────────────────────────────────────────┘
```

```cpp
// Fencing Token实现
class FencedLock {
public:
    struct LockResult {
        bool acquired;
        int64_t fencing_token;  // 全局递增的token
    };

    LockResult lock() {
        // Redis实现：用INCR生成递增token
        redisReply* reply = (redisReply*)redisCommand(ctx_,
            "EVAL %s 1 %s %s %d",
            LOCK_WITH_TOKEN_SCRIPT, key_.c_str(), value_.c_str(), ttl_ms_);

        if (reply && reply->type == REDIS_REPLY_ARRAY) {
            bool acquired = reply->element[0]->integer == 1;
            int64_t token = reply->element[1]->integer;
            return {acquired, token};
        }
        return {false, 0};
    }

private:
    // Lua脚本：原子地获取锁并递增fencing token
    static constexpr const char* LOCK_WITH_TOKEN_SCRIPT = R"(
        local acquired = redis.call('SET', KEYS[1], ARGV[1], 'NX', 'PX', ARGV[2])
        if acquired then
            local token = redis.call('INCR', KEYS[1] .. ':token')
            return {1, token}
        end
        return {0, 0}
    )";
};

// 使用方
auto [acquired, token] = lock.lock();
if (acquired) {
    // 所有后续操作都带上token
    db.updateWithFencing(data, token);  // DB层校验token
}
```

#### 6.3 幂等设计

```
即使有fencing token，也要做幂等设计：

场景：Client A发送写请求 → 网络超时 → Client A重试
  → 如果操作不幂等，数据被写了两次

幂等策略：
  1. 唯一请求ID（每个操作生成UUID，服务端去重）
  2. 状态机（只允许合法的状态转移：PENDING→PROCESSING→DONE）
  3. 条件更新（UPDATE ... WHERE version = expected_version）
```

### 7. 最佳实践

```
┌──────────────────────────────────────────────────────────────────┐
│              分布式锁最佳实践清单                                   │
├──────────────────────────────────────────────────────────────────┤
│ 1. 锁的粒度尽量小                                                │
│    ❌ lock("user_service")        → 整个服务串行化              │
│    ✅ lock("user:" + user_id)     → 只锁定单个用户              │
│                                                                  │
│ 2. 持锁时间尽量短                                                │
│    ❌ 在持锁期间做RPC调用、IO操作                                │
│    ✅ 只在更新共享状态时持锁                                     │
│                                                                  │
│ 3. 必须有超时释放机制                                            │
│    → Redis: TTL + Watchdog                                       │
│    → ZK: 临时节点 + session超时                                  │
│    → etcd: Lease + KeepAlive                                     │
│                                                                  │
│ 4. 释放锁时验证身份                                              │
│    → 只释放自己加的锁（比对唯一标识）                            │
│    → 用Lua脚本保证检查+删除的原子性                              │
│                                                                  │
│ 5. 核心业务加Fencing Token                                       │
│    → 分布式锁不能100%保证互斥（网络分区、GC等）                  │
│    → Fencing Token是最后一道防线                                  │
│                                                                  │
│ 6. 考虑是否真的需要分布式锁                                      │
│    → 能用数据库乐观锁（version字段）解决的，不需要分布式锁       │
│    → 能用幂等设计避免的，不需要分布式锁                          │
│    → 分布式锁应该是最后手段，不是第一选择                        │
└──────────────────────────────────────────────────────────────────┘
```

### 8. 总结

选型建议：

1. **大多数场景用Redis**：简单、高性能、够用。锁偶尔失效可以通过幂等+fencing token兜底
2. **金融/支付等强一致场景用ZooKeeper/etcd**：宁可牺牲性能也要保证互斥
3. **已有K8s/etcd基础设施时优先etcd**：少引入依赖
4. **无论选哪种，都要做好锁失效后的兜底**：幂等设计 + fencing token

最后记住：分布式锁是分布式系统中**最难做对**的组件之一。如果你的场景能用数据库行锁或乐观锁解决，不要引入分布式锁——复杂度是有代价的。
